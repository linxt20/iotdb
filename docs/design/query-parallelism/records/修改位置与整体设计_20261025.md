# 修改位置与整体设计

目的：说明 IoTDB 表模型查询内并行的生产责任、主要修改位置和验收边界。

摘要：实现分为属性判断、资源构建、运行统计和静态计划。各层使用真实计划及执行身份关联。多源交换需要所有消费者就绪后再启动共享生产者。动态反馈通过 E 的独立方案实施。

结论：A–D 的生产实现及补修已进入最终冻结源码，核心、RPC、严格三十二桶、一般资源与真实非法数据块已有同版运行证据。完整退出按最终源码分别核对构建、模块及服务回执，状态统一由 [A–D 完整核查](A-D_完整实现补全核查_20261102.md) 维护。E 的普通查询历史与动态策略处于设计阶段。

## 查询正确性

相同键必须送到同一个最终分组，扫描行必须恰好读取一次，整体有序输出必须经过可证明的有序流合并。代码存在、单元通过和真实服务查询分别取证。

例如，两个来源各有键 a 的两行与三行，最终聚合必须返回计数五。有序查询还须比较全部行的顺序。

数据来源：sc01 `/root/iotdb`，分支 `feat/next-p0`，发布基线 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`。工作区 manifest、完整发行包及实际加载来源见 [A–D 核查](A-D_完整实现补全核查_20261102.md)。

## 属性与计划节点

提供者读取实际输出，强制器补齐分布和顺序。生成器保留专用聚合哈希准入与所有权检查，并记录冻结决策。未知节点使用保守属性。

例如，只有一个未知输入时，整体排序要求仍需补排序。多个输入时，强制器必须保留全部分支。

数据来源：`plan/relational/planner/distribute/` 下的 `PlanPropertyProvider`、`PropertyEnforcer`、`PropertyEnforcementDecision`、`PlanProperties` 和 `DistributionProperty`，生产接入为 `TableDistributedPlanGenerator` 与 `TableDistributedPlanner`。

## 扫描计划与流水线

纯规划器确定模式、工作单元和桶。设备、时间分区和有序扫描通过公共构建器建立上下文、交换和 factory。接管路径采用纯规划器选择的并行度。表模型无序收集读取就绪子流，受检内存估计包含同时存活的保留量与自身对象。

例如，四条扫描流水线加一条合并流水线，计划扫描并行度为四，实际流水线数为五。两个量分别保存。

数据来源：`plan/planner/` 下的 `ScanParallelPlan`、`ScanParallelPlanner`、`LocalScanPipelineBuilder`、`DataNodeTableOperatorGenerator` 和 `LocalExecutionPlanner`。算法和文件处理见 [D 实现规划](D_静态数据并行实现规划_20261101.md)。

## 资源与生命周期

实际对象登记后一次冻结，执行沿用兼容额度。独立算子根在创建时登记，父根接管关闭责任。工厂成功创建后由驱动负责关闭，部分失败和取消分别结算未移交资源。规划开始前的取消在同一身份表中保留轻量终态，并与队列创建共用互斥边界。真实查询终止清除共享上下文的映射，活动片段继续持有自己的对象引用。

例如，第二个扫描尚未挂入父根就失败时，两个独立扫描均有清理责任。它们挂入同一父根后，由父根统一关闭。

数据来源：`LocalExecutionResourceRegistry`、`LocalExecutionPlanContext`、`PipelineDriverFactory`、`FragmentInstanceManager`、`FragmentInstanceContext`、`SharedTsBlockQueue` 和 `MemoryPool`。完整合同见 [B 设计](B_静态数据并行统一设计_20261031_实施版_复审修订.md)。

## 多源交换

哈希源按桶显式路由，只有本批待发送通道参与背压。片段派发读取实际交换依赖，消费者全部确认后启动生产者。父 sink 的结束通知独立于子通道是否已被关闭。

例如，两个源和三十二桶形成六十四条唯一边。共享源必须等待三十二个消费者全部确认，空桶也须收到结束通知。

数据来源：`TableGroupByHashRepartitionTopology`、`TableHashPartitioningShuffleSinkNode`、`HashPartitioningSinkOperator`、`ShuffleSinkHandle`、`FragmentDispatchDependencyGraph` 和 `FragmentInstanceDispatcherImpl`。共享键规范化位于 calc-commons 的 `HashKeyCanonicalizer`。

## 统计与解释

运行快照复用已有计时、计数和 RPC。驱动计数取根输出，失败通知与终态写锁冻结前幂等记录完成信息，墙钟由同次捕获的端点计算。实时和终态抓取分别保留，解释输出按交换字节上限分批。

例如，扫描十行、过滤输出四行时，驱动输出为四。CPU 缺失时保留字段级原因，墙钟只表示驱动的经过时间。

数据来源：`Driver`、`QueryStatistics`、`FragmentInstanceExecution`、`QueryStatisticsFetcher`、`statistics/snapshot/`、两个统计 Drawer 和 `ExplainAnalyzeOperator`。字段来源见 [运行字段映射](A-D_运行字段来源_20261102.json)。

## 后续反馈与验证

E 在下一片段资源创建前读取独立冻结历史。配对由实际源及驱动身份建立，策略生成一个计划后只执行一次真实准入。运行中的驱动与队列保持原计划。

验证同时检查局部断言、完整模块和真实查询。运行响应分别自校验，候选与对照按业务多重集比较。有序查询额外比较完整序列。

数据来源：[E 设计](E_动态数据并行设计_20261102_第二轮修订.md)、[E 实现规划](E_动态数据并行实现规划_20261102_第二轮修订.md) 和 [A–D 完整核查](A-D_完整实现补全核查_20261102.md)。
