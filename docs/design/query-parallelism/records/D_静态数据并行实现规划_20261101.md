# D 静态数据并行实现规划

目的：将 D 的静态扫描计划落实到生产文件、测试和机器验收。

摘要：实施按 D0 至 D6 组织。先固定源码与执行身份，再接设备、时间分区和有序扫描。计划身份通过 C 的生产适配器进入不可变快照。最终使用完整发行包核对业务、拓扑和全量回归。

结论：纯计划先于资源构造，选定计划只执行一次内存准入。原因分类修补及正式测试已经验证。完整退出继续要求最终源码的核心服务、完整模块与构建回执，状态统一由 [A–D 完整核查](A-D_完整实现补全核查_20261102.md) 维护。

## 未决问题

- 性能数字口径待 sxing 决定。
- hash join 生产路径待 sxing 决定。第一版不实现。
- CPN 论文范围待 sxing 决定。

## 生产调用链和时序

`LocalExecutionPlanner.plan()` 的两个重载先创建 `LocalExecutionPlanContext`。
随后 `generateOperator()` 进入 `DataNodeTableOperatorGenerator`。
D 接管点在这里生成 `ScanParallelPlan`。
原额度计算先记录请求。
接着 `freezeResourceQuota()` 在完整树上合并发布执行约束并冻结资源记录。
之后构造内存估计并执行 `checkMemory()`。
检查通过后才添加 pipeline driver factory。
最后写入 source paths、device paths、query data source type 和 time partitions。

DOP 决策发生在资源冻结之前。DOP 公式只能使用 planner 输入。
`checkMemory()` 抛出 `MemoryNotEnoughException` 时，计划已经生成但执行准入失败。该情况在 D6 记录为 admission failure。它不改写成 planner determinism 失败。
`setTimePartitions()` 只写入已经选定的时间分区，不重新决定 DOP。

### 退回原因的实现与验证

D1 必须完整实现 [D 原因分类表](D_静态数据并行设计_20261101.md#退回原因)，并保留旧原始值的回放能力。全部原因枚举必须有明确分支，正常资格限制禁止通过默认分支进入计划异常类别。字段含义与四类资格映射统一使用该设计表。

例如，输入上界为一、三十二个设备的扫描仍保留全部设备工作。规范类别表示没有选择并行，原始值继续表示配置限制。测试必须同时检查两个值。

生产修改位于计划值对象的原因归一化函数。四类资格原因显式使用未选择并行类别，顺序证明失败继续使用原顺序类别，真实生成异常才使用计划异常类别。已有空输入、溢写、估计缺失、无效成本和时间范围的明确语义必须保持。

正式单元测试使用独立期望表逐项覆盖全部原因枚举。四类资格限制还必须通过实际串行计划核对原始值、规范值和完整工作集合。生产身份测试必须核对两项原因从记录入口写入片段身份，纯函数断言和生产写入核对分别取证。

正式原因测试已完成正反验证，实际回执与统一源码的输入对应关系见 [D 原因分类](A-D_完整实现补全核查_20261102.md#d-退回原因分类)。完整模块和核心服务继续绑定自己的终态回执。

## D5 C 指标复用和快照只读输入

### 状态和生产接线

生产端在片段快照构造中调用统一响应适配器，生成 Java 不可变快照。计划身份保存于片段级，快照视图从该身份读取扫描并行度、实际驱动数和覆盖信息。

运行快照的读取与静态策略分别处理。历史成本筛选提供只读帮助方法，D 默认规划仍使用静态文件成本。规划期读取冻结反馈并调整下一片段属于 E 的新增生产路径。

没有扫描任务的交换根片段保留真实拓扑，扫描并行度为零。串行扫描保留真实工作单元。多个扫描源按稳定源键组合，禁止相互覆盖。

### 代码改动

`RuntimeSnapshotDelta.java` 不修改。它只属于 E。

### 校验和与复用规则

运行快照和计划身份各自在本侧自校验。终态重复读取必须保持代次及校验和。采样时间、查询 ID 与并行度进入身份，因此跨侧值可以不同。

例如，候选四条扫描驱动各输出八行，对照一条输出三十二行，业务覆盖相同。禁止要求两侧逐驱动行数或运行校验和相等。

强制计数按本侧实际来源、非负值和身份核对。墙钟有来源时核对其范围，无来源时保留字段级原因。CPU、输出字节、逐驱动就绪与阻塞没有来源时同样保持不支持。

历史帮助接口只接受同形态、同端点且资格完整的记录。D 生产计划继续使用静态元数据。E 的规划服务负责读取独立历史。

数据来源：运行自校验为 `RuntimeSnapshotChecksum.forFragment()`，计划校验为 `StaticParallelPlanChecksum`。驱动输出采用根边界计数，响应由 `RuntimeSnapshotAdapters.fromResponse()` 统一构造。

4. source、bucket、work unit、driver 和 exchange edge 身份唯一且可回放。扫描计划并行度、实际流水线及实际驱动数分开记录。
5. C 终态按本侧驱动核对行数、块数、代次、身份及字段资格。运行与计划校验和各自自校验。跨侧比较完整业务覆盖与有序结果，禁止比较不同驱动结构的逐条计数。
6. candidate 和 control 至少三次通过 `checkMemory()` 且准入状态一致后才比较 EXPLAIN ANALYZE 的业务结果多重集、SHA 和快照身份，任何一侧拒绝或三次结果仍不一致都算失败。
7. 全量 DataNode 必须完成全部规则，回归结论和失败证据分别归档。
