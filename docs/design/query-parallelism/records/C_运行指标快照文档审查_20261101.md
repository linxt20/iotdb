# C 运行指标快照文档审查

**目的**：核对 C 的两份 2026-11-01 文档能否进入代码实施。审查逐项比对新设计的四级快照模型、冻结与并发协议、跨节点合并协议、输出兼容要求与实现规划的 C0 至 C6 文件级步骤同真实源码是否一致，重点回答两个问题：实现后的测试设计够不够支撑退出判据，以及实现内容本身是否合理高效。审查只读源码与文档，不运行测试，不改动仓库。

**摘要**：C 要把 IoTDB 已有的片段、算子与查询统计采集点收敛为一个可冻结、可校验、可跨 DataNode 合并的运行快照，供 D 的静态调度实验与 E 的动态控制使用。两份文档给出的架构方向成立：不另造一套平行计数器，用不可变值对象承载四级快照，用稳定字段序的校验和保证可审计，新增键与旧键并存而不替换。本文按固定源码基线逐条核查，发现四条 P0、十四条 P1 与十五条 P2。四条 P0 分别关于跨节点传输载体上没有文档声称的扩展位、driver 墙钟只有一条默认关闭的路径且是毫秒字符串、计划并行度在全链路没有来源、以及退出判据要求的三条派生规则在整套测试计划里没有任何一条测试能证明。十四条 P1 分别关于终态快照的触发前提、冻结协议与文档自己的禁令互相矛盾、附加信息合并器在异常路径上永久泄漏终态写锁、完整片段的判定不可达、CPU 没有采集点、两个 Drawer 的主回归护栏被漏出测试清单、规划把基线已实现的步骤写成待做工作、查询统计的序列化没有屏障、有序并行子扫描进不了逐驱动快照、驱动级时间与就绪阻塞没有来源、三个驱动计数没有来源、基线冻结清单漏文件、折叠逻辑覆盖父算子、以及验收命令缺两个参数。这些条目修改完成前，C2 至 C6 不进入实施。C0 与 C1 中不依赖这些条目的部分可以开始。

**结论**：两份文档可以分段放行，不能整体放行。C0 的源码身份固化与 C1 的值对象、校验和、JSON 编解码、NaN 与 Infinity 拒绝这几项没有依赖本文的 P0 与 P1，可以立即开始。C2 至 C6 依赖全部十八条，其中四条会在实施后直接造成运行期故障或让退出判据无法验收。第一条是把 driver 级字段经 specifiedInfo 传输，同类算子数达到十个时抛异常，异常路径不释放终态写锁，该片段的驱动、临时文件与内存配额全部不再释放。第二条是按文档第七步协议在显式抓取的读锁内调用驱动记录助手，两个并发抓取会同时改写同一个映射。第三条是完整的片段判定，预期集合里必然包含一个永远不返回数据区域的虚拟片段，完整永远不可达。第四条是 C4 的合并器建立在一个不存在的 generation 字段与一个不存在的 driver 身份上，写不出可执行代码。测试设计只覆盖值对象与渲染层，缺对账、派生规则、故障注入、真并发与集成五类用例，退出判据第三条在整套计划里没有对应测试。实现内容的效率问题集中在传输选型。规划自己列出的四条修改 thrift 的触发条件其实已经全部满足，第一版直接加 thrift 字段比先走 specifiedInfo 再迁移省一整轮返工。

**未决问题**：性能倍数口径、生产哈希连接是否进入规划、CPN 是否进入论文正文三项等 sxing 决定。C 是否需要把终态冻结从仅 EXPLAIN ANALYZE 查询扩展到全部查询，等 sxing 在设计第 100 行的终态要求与现有门控之间做选择。B 的未提交工作区内容是否在 C 实施前提交，等 sxing 决定，它影响 C0 冻结的源码身份是否稳定。

## 审查任务与判定标准

一次查询在多个 DataNode 上分成多个片段执行，每个片段再分成多条驱动。要比较两种静态调度策略哪个更省，需要拿到每一条驱动各自处理了多少数据、花了多少时间。拿不到驱动级的量，就只能看到片段总数，两条策略在片段数上可能完全相同。C 要解决的就是这件事：把已经散落在查询统计、片段执行、驱动与算子四处的计时与计数收成一个对象，冻结时不被人改写，跨节点合并时不把缺失当成零。

做得好有两条判据。第一条是可冻结：同一片段重复抓取必须返回同一代际与同一校验和，驱动记录与统计冻结之间不能有竞态。例如四个驱动里第三个在监听器加锁后才写入墙钟，冻结读到的必须是写入后的值，不能是零。第二条是可合并：两个 DataNode 各返回若干片段，少返回一个要标成部分，多返回一个要标成意外，两者都不能标成完整。丢一个节点的响应不能让它名下的片段计成零行。例如一条查询预期两个片段，只有一个节点应答，输出必须写明缺哪个来源，不能只报幸存片段的四百行。

本文核查支撑这两条判据的文档陈述与源码是否一致。受审文档是 `C_运行指标快照设计_20261101.md` 与 `C_运行指标快照实现规划_20261101.md`。审查方法是读源码，比对文档写出的方法名、字段名、算术式与文件名。

分级按四条定义。P0 表示正确性或方向存在阻断，实施前必须解决。P1 表示关键行为或验证存在缺口。P2 表示文字与位置存在问题。每条意见写出文档位置、源码依据、具体反例、影响与可验证的修改要求。

本文的判定分两类。已证实问题有源码依据，本文直接给出结论。待执行验证只有测试运行才能裁定，本文列进待执行验证清单，不预先判定。

本文的发现经过两轮独立检索。第二轮另起一批检索代理，对每条发现做反向驳斥。因并发上限，多数驳斥代理被限流拒绝，实际完成并给出结论的只有一条，其结论已并入本轮 P1 第一条。其余发现只经过发现者与本文作者的直接源码核实，没有经过独立驳斥。

## 基线上已经存在的部分

C 的文档把一部分机制描述成待建设工作，其中三项在基线里已经完成。这一节先固定这三项的状态，后面的意见才能区分要新建与要修改。

基线提交本身就是 B 阶段的提交，提交信息是完成受守卫的属性驱动并行规划。因此 metric-tree 的传输注入、按驱动展开的流水线快照键、morsel 完成墙钟的写入、以及 605 行的指标树渲染测试都在基线里，已经提交，不是工作区改动。工作区另有 B 的未提交改动，内容是内存池记账、资源登记表与扫描并行规划器，与 C 要改的统计链路基本不重叠。

第一项已存在的是终态冻结的主体。片段执行的状态监听器在片段进入终态后先取统计写锁，再对每一条驱动调用 morsel 完成记录，然后构建统计并写入上下文缓存，最后才释放驱动与接收端。设计第七步冻结协议的七个步骤里，第一、二、四、六、七步已经在源码里，位置与顺序和文档写的一致。

第二项已存在的是 per-driver 快照的逃生通道。构建统计时，计划节点号含 parallel 或 morsel 后缀的算子会被单独复制一份，存到一个不带连字符的键下面。这样做的原因写在源码注释里：合并统计的函数会把所有含连字符的键折叠进父键，而扫描算子的合并器直接返回空映射，不先取快照的话每驱动的明细会被抹平。

第三项是终态缓存的门控。上下文缓存的写入被一个条件包着，只有 EXPLAIN ANALYZE 查询会写，对应的读取方法注释写明仅用于 EXPLAIN ANALYZE。D 与验收脚本要拿终态快照，一律走 EXPLAIN ANALYZE 查询，这一条经核实不影响并行规划。前提没有写进两份文档，是 P1-1 的问题本身。

## 本轮确认的 P0

四条 P0 分别关于传输载体、driver 墙钟、计划并行度与派生规则的测试覆盖。四条都不改变架构方向，修改完成后 C2 至 C6 进入实施。

### 传输载体上没有文档声称的扩展位

设计第 53 行写第一版可以在既有 response 的 specifiedInfo 或扩展 map 中传递版本化字段。规划第 119 行写先尝试复用 response 与算子统计的 specifiedInfo。两处都假设 response 上有一个能放片段级字段的位置。

源码里这个位置不存在。response 结构体共 17 个字段，依次是状态、片段实例号、数据区域、起止毫秒、查询统计、算子统计映射、数据源初始化成本、四个序列开关计数、就绪排队、阻塞排队、自报 IP、状态串、数据源重试次数。整份 thrift 文件里 specifiedInfo 只出现一次，位于算子统计结构体内部，是算子级的，不是 response 级的。response 上没有 generation、schemaVersion、来源节点、校验和，也没有任何扩展 map。

后果分三层。第一层是 C3 的先不改 thrift 分支没有落脚点，评审会据此给出无需改 thrift 的错误结论。第二层是 C4 的合并协议第一步校验 response 里的 generation 无字段可读，第二三步按片段实例号加代际去重无键可用。第三层更严重：第四步按片段号、驱动号、计划节点号建层级索引，其中驱动号在算子统计结构体上不存在，唯一逐驱动线索是片段执行用计划节点号替换连字符拼出的字符串键。这个键正是设计第 80 行自己禁止当去重主键的由字符串解析得到的 ID。C4 的三个新类建立在一个不存在的字段与一个被自己禁用的键上。

修改要求分两处。设计第 53 行删去 response 的 specifiedInfo 与扩展 map 的表述，改为 thrift 变更为必做项。规划第 119 行到第 125 行的三条前置条件重写为针对真实字段集，并列出要加的字段：response 一侧加快照代际、schema 版本、来源数据节点号、来源端点、有效性集合、校验和、采集纳秒。算子统计一侧加流水线号、驱动任务号、驱动角色、驱动首末处理纳秒、驱动就绪阻塞纳秒、采样代际。C0 的 manifest 把现在无处安放的六个片段级字段标为需 thrift 变更，不得标为可复用。

### driver 墙钟只有一条默认关闭的路径

设计第 72 行把 driver wall 列为驱动级必填原始量，第 84 行要求所有内部时长使用纳秒，第 145 行让 D 读驱动墙钟纳秒，第 147 行让 E 读累计阻塞。

源码里这条量的处境是三重的。第一重是路径唯一。全仓只有一处调用给算子上下文打 morsel 标记，位于表模型算子生成器构造设备加时间分区扫描的方法内。设备并行与有序并行两条扫描路径都不调用它。第二重是默认关闭。配置类里时间分区 morsel 开关的初值是 false。于是一个 20 设备的设备并行查询在默认配置下，所有驱动都没有墙钟值，写入门控直接返回。第三重是单位与类型都不对。写入实现是先把纳秒差值转成毫秒，再转成字符串。这同时违反第 84 行的纳秒规则和第 137 行的对象而不是拼接字符串要求，而且下游要解析成长整数才能用。

三重合起来的后果是 D 的核心比较量在默认配置下恒为空，打开开关后拿到的是毫秒精度的字符串。设计第 89 行的吞吐要用输出行除以有效墙钟区间，分母为空时吞吐不可计算，而第 88 行的分母为零输出 missing 规则覆盖不到这一种。

修改要求分三处。设计第 72 行把 driver wall 的来源标注为仅 morsel 路径且默认关闭，并写明设备并行与有序并行两条路径没有该量。第 84 行补一条：morsel 写入的是毫秒字符串，C 必须新增纳秒级 long 字段而不是解析该字符串。manifest 把驱动墙钟标为需新增采集点，拟在驱动完成时直接写纳秒 long 进快照侧字段，不经过 specifiedInfo。

### 计划并行度在全链路没有来源

设计第 145 行把计划并行度列为 D 的最少读取，第 147 行让 E 读计划驱动数，规划第 189 行把计划并行度列为视图输出。

全仓检索这两个名字零命中。B 确实写了扫描并行规划器与扫描并行计划两个类，前者暴露输入并行度、目标并行度与流水线数三个读取方法。但这两个类在主代码里只被自身引用，本地执行规划器与表模型算子生成器都不调用它们。真正决定并行度的是表模型算子生成器里的一行，取配置并行度与设备数两者的较小值，开开关时还会被数据量估算再压低。配置并行度这个值放在本地执行计划上下文里，该上下文在规划结束即丢弃，片段上下文没有对应的读取入口。

构造一个并行度为 8、设备数为 20 的设备表扫描。实际驱动数由上述那行决定，快照里既没有 8 也没有实际值。D 无法判断实际驱动数是否达到计划值，退出判据第六条因此不可达。

修改要求分两处。manifest 把计划并行度标为无来源待实现，并二选一落地。第一条路是在规划时把扫描并行计划或等价的输入并行度、目标并行度、模式、降级原因、设备组与时间分区组规模写进片段上下文或每个驱动上下文。第二条路是明确计划并行度只能取配置值的查询时快照，并在 manifest 注明这是配置值不是计划值，与实际值可能不等。同时把扫描并行规划器接入生产路径或明确记为实验件。

### 派生规则在整套测试计划里没有对应测试

设计第 167 行退出判据第三条要求 CPU、墙钟、就绪阻塞、行、块、内存的单位与求和取最大值规则有单元断言。第 86 行到第 91 行定义了六条派生规则：可加量求和、驱动墙钟取有效最大值与最小值而不求和、就绪与阻塞分别求和并算占比且分母为零输出 missing、吞吐由总分子总分母派生、查询 elapsed 用明确起止算、内存区分三类不相加。

规划的测试清单逐条对完后，没有一条测试断言这六条。C1 的值对象测试第 63 行到第 69 行只覆盖空值、负值、边界、不可变性、校验和与 JSON 编解码。C4 的合并测试第 176 行列的是正常、重复、乱序代际、缺失来源、意外片段五项，没有一条涉及派生规则。规划第 170 行写了实现要求，但测试清单漏了它。

唯一看起来覆盖聚合的既有测试是指标树渲染测试里的并行驱动聚合行数方法。它是自证的：测试在夹具里手写了合并条目的输出行为 250，再断言渲染结果含 250 行。这证明的是抽屉回显夹具值，不证明构建统计真把四个驱动加起来了。四个驱动的行数 50、75、60、65 与合计 250 都是测试自己写进夹具的字面量。

后果是退出判据第三条按现计划无法满足。而这六条规则正是 D 比较静态策略时唯一的负载口径。没有断言意味着一次把墙钟当求和、把三类内存相加的改动可以静默穿过全部绿灯。

修改要求分三处。C1 或 C4 补一组派生规则断言，被测对象必须是快照构建器或合并器而不是抽屉。预期值全部用字面量：可加量写 50 加 75 加 60 加 65 等于 250，墙钟写取最小值与最大值两个数，占比写 50 除以 250 等于百分之二十，分母为零时输出 missing 且不带数值，内存三类各给一个值并断言不相加。把指标树渲染测试那条自证用例改写为驱动真实构建统计，或在文档里注明它只覆盖渲染。退出判据第三条在测试矩阵里落到具体类名。

## 本轮确认的 P1

十四条 P1 分别关于终态前提、协议矛盾、合并器异常、完整判定、CPU 采集点、测试护栏、规划步骤、序列化屏障、后缀识别、驱动级来源、驱动计数、冻结清单、折叠逻辑与验收命令。十四条都不改变实施方向，与四条 P0 一并修改。

### 终态快照的触发前提没有写明

设计第 100 行要求取消、失败、超时与正常完成都必须带终态与原因，第 103 行要求最终快照必须含终态标志、状态、采集时刻、代际与来源节点。第 41 行说统一冻结入口在片段管理器，终态读上下文缓存。三处合起来读，结论是任何查询终态后都有快照可读。

源码里这个前提不成立。终态监听器确实在写锁内构建统计，但构建与写缓存整段被一个条件包着，只有 EXPLAIN ANALYZE 查询会写。一个不带 EXPLAIN ANALYZE 的查询跑完后，监听器只让每条驱动补写墙钟，然后把统计已移除标志置真，上下文缓存从未写入。

这条限制有可用的绕行通道，且不改变并行规划。已核实四个决策点。分布并行规划器只把该标志原样传进片段实例构造函数。分发实现的两处分支只决定清哪些字段便于回收，两个动作都发生在派发之后。表模型逻辑规划器的一处分支只把输出列的列头换成说明列。CTE 物化器的一处分支只在物化结果里加一行说明文字。四处都不改变并行度、扫描拆分与调度次序。因此 D 用 EXPLAIN ANALYZE 查询可以在不改代码的情况下读到终态快照，拿到的并行规划与普通查询一致。这一条经核实成立，应写成明文前提，不留给实施者自行推断。

仍有三处缺口。第一处是两份文档都没有写这个前提。设计第 41 行写终态读上下文缓存，读起来像任何查询都成立。C6 的双节点验收第二步到第五步要的是终态快照与完整、部分、恢复三态，没有说查询必须带 EXPLAIN ANALYZE。实施者用普通查询跑验收，第一步就会失败，而失败原因不在任何一条退出判据的预期里。

第二处是读取侧把缺失报成成功。片段管理器在实例已移除且缓存为空时返回一个新建的空响应，两个分支都是这个行为。这个空响应经内部 RPC 出去时被盖上成功状态码，正是设计第 15 行与第 153 行禁止的全零成功。规划第 98 行只约束新入口，旧入口的两处空响应构造没有改。C4 的合并器读到这个响应会把它当成一次成功返回，缺失不归零这条协议在这一形态下失效。

第三处是时效限制。终态缓存放在上下文里，受片段管理器的信息缓存时间约束，该值在构造时硬编码为五分钟。manifest 没有这个数。C6 第五步恢复节点后验证完整的重取必须控制在这个窗口内，否则会偶发失败。

还有一处使用限制要写进文档。EXPLAIN ANALYZE 会把查询的可见输出列换成说明列，CTE 物化时还会往结果里加一行说明文字。D 若拿查询输出的行数作判据，两个模式下的行数不同。片段执行侧的驱动、算子与计时量不受影响。

修改要求分三处。设计第 41 行补上门控前提，写明终态缓存当前只对 EXPLAIN ANALYZE 查询写入，D 与验收脚本一律经 EXPLAIN ANALYZE 取终态，并把不改变并行规划的四个决策点写成可逐条核查的条目。设计第 100 行之前增加一段选择：保留门控则按前述执行，移除门控则列入 C2 的修改清单并评估普通查询终态多一次全量统计构建的开销。设计第 153 行与第 154 行把空响应加成功状态码这一现有行为列为必须改掉的项，规划第 98 行把旧入口的两处空响应构造一并纳入，改为返回明确的未找到状态。manifest 记录五分钟硬编码窗口，C6 验收脚本写明重取必须落在窗口内。

### 冻结协议第二步与第 119 行禁令互相矛盾

设计第 119 行禁止在冻结过程中修改算子的用户可见附加信息，并点名现有代码为兼容传输注入 TsBlock 输出计数这一处。第 110 行冻结协议第二步要求对仍存在的驱动调用 morsel 完成记录。第 117 行要求终态监听器与显式抓取走同一个助手。

三步连起来看，矛盾出在第二步调用的方法写的就是附加信息。morsel 完成记录的实现是从驱动上下文里取算子上下文，往它的附加信息映射里写一个墙钟毫秒值。这个映射是运行时可变的共享映射。第 119 行只点了 TsBlock 输出计数的名，没有意识到 morsel 写入用的是同一个机制，同一个映射。

这个键还不在隐藏之列。两个抽屉跳过的前缀只有一个内部前缀，morsel 墙钟键不带该前缀，于是它被当成普通附加信息渲染成一级行进文本，也进 JSON。指标树渲染测试就断言 JSON 里能读到它。所以第 110 行第二步执行后，冻结过程必然修改一个用户可见附加信息，而且快照里该键的可见性取决于第二步是否执行，同一个驱动在抓取触发的冻结与终态触发的冻结下可能一个有值一个无值。

矛盾在执行时还有第二层。第 117 行要求同一个助手，而助手包含第二步。终态监听器走的是写锁，显式抓取走的是读锁，读锁是共享的。两个并发抓取会同时进入助手，同时执行同一个守卫判断：映射里没有这个键才写。这个判断与写入不是一步完成，后落地者胜出。今天不可并发，只因为两个写入点在调用图上不重叠。按第 117 行统一入口后，重叠成为必然。E 的采样正好是并发抓取这个形态。

还有一层地基问题。第 109 行只写取得统计读写锁，没有说取哪一侧。源码里同一把锁的两侧被两个入口分别使用：显式抓取取读锁，终态监听器取写锁。实现者按字面把同一助手建在读锁入口上，终态冻结只持有读锁，两个线程可同时进入冻结体，得到的不是一个快照而是两个交叉的快照。反之若助手统一取写锁，第 117 行说的较早的运行中快照可以返回部分就需要补一条抓取侧重查步骤才成立。

修改要求分三处。第 110 行改为对仍存在的驱动调用快照侧记录助手，该助手只写快照对象或已复制的映射，不触碰运行映射。第 117 行明确同一个助手指身份、代际与缓存逻辑相同，不是同一把锁，并新增一条：显式抓取与驱动写入并发时返回的部分快照允许校验和变化，终态快照必须静止。第 109 行改为分路径陈述，终态路径取写锁，显式抓取路径取读锁，并新增一条抓取侧在构造快照前必须在读锁内重查已发布标志，已发布则直接返回缓存对象。规划 C2 增加一条要求：morsel 写入的目标改为快照侧字段，且并发下只写一次要有原子保证，用先比较再放入代替判断后放入。

### 附加信息合并器会抛异常，异常路径不释放终态写锁

规划第 83 行给出两个传输选项，其中一个是由算子统计适配器添加传输字段。第 133 行要求对空值、非数值与无穷做显式检查。两处都把经附加信息传输写成无代价选项。

源码里有两条已经存在的数据丢失与异常路径，文档都没有分析。第一条在合并器。合并器按算子类型分派：过滤投影算子、交换算子与四个排序算子走长整数合并，实现是把两侧的值都解析成长整数后相加。其余算子走默认合并，实现是直接返回空映射。于是把 C 打头的非数值键写进过滤投影算子的附加信息后，只要触发合并就会抛数值格式异常。另一侧的键不存在时同样抛，因为空值解析成长整数也抛。第二条是折叠。合并统计的函数会把所有含连字符的键折叠进父键，per-driver 的明细正是靠换成不带连字符的键才活下来的。

触发条件在配置里，默认值是十。一个片段内同一类型的算子数达到十个就触发全量合并。B 的 morsel 并行度由设备数与时间分区组数决定，达到十条驱动是常见形态，每条驱动都有一个过滤投影根算子，正好命中长整数合并这一路。

异常的后果比丢数据严重。构建统计在终态写锁内调用，加锁与解锁之间没有 finally 保护。异常从构建统计冒出后，解锁被跳过，写锁永久持有，统计已移除标志不置位。监听器后续的清理接收端句柄、关闭驱动、等待全部驱动关闭、删除临时文件、从内存池注销片段整段都不执行。之后任何抓取都会在片段管理器的读锁上永久阻塞，因为读锁要等写锁释放。

另有一条叠加风险。查询统计转 thrift 的实现是一次构造传入三十余个独立的原子计数器读取值，每次读取之间没有屏障也没有锁。两个并发抓取会读到不对应同一时刻的计数组合，相同校验和这一退出判据因此不成立。

修改要求分三处。规划 C3 增加一节传输键约束：列出合并器的分派表，规定新增 C 键在长整数合并算子上必须能被解析成长整数，在默认合并算子上必须承认合并即丢失，或者不进入附加信息。构建统计要捕获合并异常并保证锁释放，把现有没有 finally 的加锁段改成有 finally。manifest 把查询统计转 thrift 标为无屏障读取，C 的快照构建必须在单一锁内一次取完全部计数后立即冻结成不可变对象。

### 完整片段的判定在现有语义下不可达

设计第 133 行要求比较查询计划预期的片段集合与实际返回集合，少一个是部分，多一个是意外，两者都不能标为完整。第 169 行退出判据第五条要求双 DataNode 查询能得到完整与部分两种可审计结果。

源码里这两句碰在一起，完整永远拿不到。预期集合来自查询执行分发的计划里的实例清单，这个清单包含承载 EXPLAIN ANALYZE 算子的那个片段实例。而这个实例在填充片段统计时会被一个判断拦掉：只要任一驱动含该算子，填充直接返回假，构建统计随之提前返回，响应里不设数据区域。JSON 抽屉又以数据区域非空过滤片段列表，片段计数取过滤后的个数。于是预期集合永远比返回集合多至少一个，按第 133 行的判据，每次查询至少是部分。同一套过滤也让多一个是意外这一支在现有结构里根本不可达。

还有一个反向问题。预期集合里除虚拟片段外，还有 CTE 物化扫掠的虚拟区域，文档没有给划分规则。新旧两份片段集合也会同时出现在一个 JSON 里且互相矛盾，文档没说以哪份为准，也没要求把差集写进有效性或校验和。规划第 145 行的序列化测试清单因此缺了唯一要紧的对账断言，实现时可以两边各写各的而测试全绿。已有的两个测试把数据区域为空的过滤钉成了既定行为，所以把片段计数改义为计划片段数这类改法会直接打破第 145 行要求的旧字段兼容。

修改要求分三处。设计第 133 行增加第三态与划分规则：预期集合必须分成可返回统计的片段与故意忽略的片段，后者是承载该算子的虚拟片段与 CTE 扫掠的虚拟区域。只有可返回集合的缺失判部分，意外多出判意外。第 139 行把保留旧键改成显式结构描述，并新增一条：新键的片段集合与旧键的片段集合按片段实例号求差集，差集逐条进入有效性与缺失来源，旧键的片段计数不得作为完整判据。序列化测试增加注入一个数据区域为空的响应的用例，断言旧数组为空、新键有一条带来源缺失、校验和覆盖该差异。C6 第四步与第五步之外补一个正常双节点查询得到完整的基线用例。

### CPU 这一项在全链路没有采集点

设计第 21 行把 CPU 与墙钟并列为 C 负责提供的原始量，第 71、72、73 行在片段、驱动、算子三级都列了 CPU，第 145 行让 D 读驱动 CPU 纳秒，第 147 行让 E 读累计 CPU。

源码里没有任何 CPU 计时。算子每次执行记录的是墙上时钟差值，累加进算子上下文的总执行纳秒字段。全链路只有工具类目录下一个 CPU 计时器碰线程 CPU，且不接入查询统计。两个抽屉还用同一个字段算每秒行数，分子是输出行数，分母就是这个被文档称作 CPU 的量。

按规划第 34 行的 manifest 逐字段对应源码的要求做 C0，三项 CPU 会全部落入源码中不存在。最省事的交差办法是把总执行纳秒改名成 CPU，数值上是墙钟。D 用它比较静态策略时，会把等待、被抢占与锁竞争全部算进 CPU，跨臂比较失去意义。每秒行数继续拿墙钟当分母，字段名与语义的偏差被固化进新 schema。

这是 C 唯一需要从零新增采集点的大项，成本与风险都写在明处却没有被评估。按驱动归属 CPU 需要围绕处理切片包一层线程 CPU 差值，还要处理驱动线程是共享池、一个线程跑多个任务的归属问题。文档既没说这项成本，也没说交付不了时的降级路径。

修改要求分三处。设计第 72 行与第 73 行把 CPU 标注为需新增采集点，给出归属规则与开销上限。manifest 里这三个字段的来源方法一栏写 C 新增，禁止复用总执行纳秒。明确吞吐分母的权威口径是有效墙钟区间，与第 89 行一致，并说明现有每秒行数与它的偏差如何处理。第一期不交付 CPU 就在退出判据里显式降级并写进有效性，不要留一个同名的墙钟字段。

### 测试清单漏掉两个 Drawer 的主回归护栏

规划第 30 行与第 221 行各列一份既有测试清单，两份清单合起来也没有指标树渲染测试。这个测试有 605 行、十个测试方法，已经提交在基线里，内容是 C3 要改的两个 Drawer 的直接回归：按驱动展开的流水线渲染、TsBlock 输出计数的注入与隐藏、JSON 与文本字段对齐、阻塞比例、合并后的 TsBlock 计数求和、以及畸形值被忽略。

C3 要修改的两个 Drawer 正是这个测试的被测对象。文档要求新增 C 前缀字段、改变空值与无穷的处理、按三个身份稳定排序驱动数组、继续隐藏内部字段。每一项都会动到这个测试覆盖的代码路径。不把它列进 C0 的清单与 C6 的回归矩阵，实施者改完 Drawer 会看到这个测试失败，而文档里没有任何一处说明它是预期要同步修改的。

漏列还有一处连带后果，比失败本身更值得写进文档。规划第 83 行给了两个分支：复制映射后再添加传输字段，或者由算子统计适配器添加。若走第二个分支，TsBlock 输出计数不再出现在附加信息里，两个抽屉都取不到值，该测试的四个方法同时变红。两种结局都坏：要么全量回归在一个没人排期的测试上失败，直接阻塞收口。要么为了让它绿，有人把注入改回写算子上下文，恰好违反设计第 119 行自己定下的边界。

修改要求分两处。规划第 30 行与第 221 行的清单加入指标树渲染测试，并注明它是 C3 修改两个 Drawer 的主回归护栏，修改 Drawer 时必须同步修改它。C2 落地前先定死 TsBlock 输出计数的归属，写在 manifest 里，并同步更新该测试。另补一条断言：新的 driver 级字段必须能穿过折叠合并与默认合并器，默认合并器对表扫描算子返回空映射，会吞掉附加信息。

### 规划把基线已实现的冻结第一步写成待做工作

规划 C2 第一条修改位置写的是：在现有统计锁保护下，先让所有驱动调用 morsel 完成记录。源码里这一步已经在终态监听器内完成，连注释都写了原因：驱动在调度期间完成的已经自己写了值，写入是幂等的，这里只补监听器关闭的那些驱动。

规划的表述会让实施者做两件事之一。要么在同一个位置再写一遍循环，形成重复代码。要么以为现有顺序不对，把已有的循环挪位，破坏监听器先补写再构建统计的时序。设计第七步协议同样没有区分已有与待改，七步里有五步已经在源码里。

修改要求分两处。规划 C2 的第一节改成先列基线现状：终态监听器已在写锁内完成驱动补写、统计构建与缓存写入，顺序与文档一致。C 要改的是把构建统计拆成快照构建适配层、补上 EXPLAIN ANALYZE 门控的处理、以及把传输注入改成复制后注入。设计第七步协议给每一步加一个状态标注，写明已在基线、待修改或待新增。

### 查询统计的序列化没有屏障

设计第 165 行退出判据第一条要求同一终态片段重复冻结返回相同校验和与代际。第 115 行要求生成不可变内部快照和校验摘要。

查询统计转 thrift 的实现是一次构造调用传入三十余个独立的原子计数器读取值。每次读取是一个独立的易失读，读取之间没有锁也没有屏障。同一个对象连续两次转换可以得到不对应同一时刻的计数组合，差值大小取决于并发写入的密度。

这不只是理论问题。构建统计在终态写锁内调用，读锁只挡住另一个构建统计，挡不住查询执行侧对计数器的写入。于是一个片段终态时的两次抓取，查询统计部分的校验和可以不同。退出判据第一条在查询统计这一项上无法满足，而它是四级里最大的一项。

修改要求分两处。manifest 把查询统计转 thrift 标为无屏障读取。C 的快照构建要么在单一锁内一次取完全部计数后立即冻结成不可变对象，要么给查询统计加一个快照方法，一次返回全部计数的数组。退出判据第一条补一条针对查询统计部分的断言。

### 有序并行子扫描进不了逐驱动快照

设计第 47 行要求保留一份按实际驱动与流水线身份的原始快照，第 145 行让 D 按驱动比较负载。判定是否为并行子扫描的实现是检查计划节点号是否含两种后缀之一。

有序并行子扫描用的是另一种后缀。它含不到这两种后缀，于是不会被识别为并行子扫描，不会走复制一份存到不带连字符键的通道。它的逐驱动明细会在后续的折叠合并里被抹平，或者因为扫描算子的合并器返回空映射而整条消失。

后果是 B 交付的三条并行扫描路径里，只有两条能产出逐驱动快照。D 比较静态策略时，有序并行这一臂的负载读数与另外两臂不可比，而这一点两份文档都没有提。

修改要求分两处。设计第 47 行补一句：识别条件当前只覆盖两种后缀，有序并行子扫描需要新增一种后缀或改为按驱动上下文枚举。manifest 把三条并行扫描路径分别标注能否进入逐驱动快照。序列化测试对三条路径各断言一次逐驱动条目存在。

### 驱动级时间与就绪阻塞没有来源

设计第 72 行驱动行的原始量列了首次处理、末次处理、就绪、阻塞。规划 C1 第 53 行把驱动就绪阻塞列为驱动快照字段。

源码里首次处理是驱动类里的一个私有 long 字段，初值是负一，没有公开读取入口。末次处理在全仓不存在，驱动类与驱动上下文里都没有这个名字。就绪与阻塞只有片段级来源：驱动调度器用单调时钟差值累加片段上下文上的两个字段，没有按驱动分开记。

后果是驱动行有四个字段没有来源。规划 C1 要求实现的驱动快照对象有三个字段只能填零或标缺失，而填零正是设计第 15 行禁止的行为。第 88 行的就绪阻塞分别求和规则因此只能在片段级算，驱动级的占比无从得出。

修改要求分两处。设计第 72 行把首次处理标注为需新增访问器，末次处理标注为需新增字段，驱动级就绪阻塞标注为需在驱动调度器按驱动分开记。manifest 把这四个字段标为待实现并写拟议采集点。C1 的驱动快照对象对无来源字段必须输出缺失加原因，不得填零。

### 三个驱动计数没有来源

设计第 147 行让 E 读活跃驱动数、排队驱动数、阻塞驱动数，规划 C5 第 192 行把这三个列为视图输出，第 145 行让 D 读已完成驱动数。

### 基线冻结清单漏掉实际会读的文件

规划 C0 第 27 行列了九个待冻结源码身份的文件。C1 到 C5 真正会读或会改的文件不在这九个里。

漏的有四类。第一类是计划并行度与内存预留峰值的来源：本地执行计划上下文、扫描并行计划、本地执行资源登记表、内存池，这四个是 B 的未提交改动，其中两个还是新增文件。第二类是现有第二套聚合逻辑：驱动调度器、统计合并工具、附加信息合并器工厂。第三类是 C3 要改的 RPC 两侧：内部 RPC 服务实现与 EXPLAIN ANALYZE 算子。第四类是查询上下文的计划成本读取方法与查询计划统计。

### 折叠逻辑覆盖父算子且结果取决于迭代顺序

设计第 133 行要求按片段号、驱动号、计划节点号建层级索引。第 79 行说计划节点号可以重复出现在不同驱动，对象键必须含片段号与驱动身份。

折叠合并的实现是把所有含连字符的键取第一段作为目标键，多个含连字符的键会合并进同一个目标。子扫描键形如节点号加平行加序号，两个子扫描键都折到节点号上，覆盖的正是父算子的条目。多个子扫描合并时，先遇到的那个成为累加目标，后遇到的并进去，而遇到顺序取决于哈希映射的迭代顺序。

后果有两条。第一条是同一份输入在不同运行下可以给出不同的算子条目组合，而这正是设计第 165 行退出判据第一条要排除的。第二条是折叠会把扫描算子的附加信息一起折，而扫描算子走默认合并器返回空映射，逐驱动明细在这里被吞。

修改要求分两处。manifest 把折叠合并标为按字符串切分与迭代顺序相关。设计第 133 行的层级索引改为用片段号加驱动任务号加计划节点号三元组建键，不用折叠后的字符串键。序列化测试注入两个同基号的子扫描键，断言父算子条目不被覆盖，并断言多次运行的条目组合一致。

### 验收命令缺两个参数

规划 C6 第 207 行的 Maven 命令用模块路径指定数据节点模块，没有带同时构建依赖模块的参数。数据节点依赖计算公共模块，该模块的改动不会被这次命令构建，链接到的是本地仓库里的旧快照。B 的改动里有计算公共模块的内容，这条命令会静默用过期的计算库跑测试。

命令还缺一个 JVM 参数。数据节点测试里有使用 PowerMock 形态的用例，需要额外的模块开放参数才能在新版 JDK 上跑。不加会在全量回归阶段出现与 C 无关的失败。另外命令跨行没有续行符，直接复制执行会断。

修改要求分三处。命令补同时构建依赖模块的参数，并写明它构建计算公共模块。补 JVM 模块开放参数。命令写成一行或加续行符。C6 的定向测试矩阵对每一类测试保存实际加载的计算公共模块类 SHA，与 manifest 记录的上一次比对。

## 本轮确认的位置与文字问题

十五条 P2 分别关于文件名、字段来源、数值卫、键可见性、丢弃的量、来源身份、落点、归因、文件组织、字符串解析、抓取路径、内存峰值与词汇冲突。十五条都不改变实施方向，与四条 P0 和十四条 P1 一并修改。

### thrift 文件名写错

规划第 28 行要求冻结 mpp.thrift 中三个结构体的生成来源与校验和。仓库的 thrift 目录只有 client.thrift 与 datanode.thrift 两个文件，三个结构体都在 datanode.thrift 里，行号分别是 786、798 与 868。全仓找不到 mpp.thrift。

### Query 级计划成本的来源不在采集点清单里

设计第 70 行把分析、分发与计划成本列为 Query 级原始量，第 39 行的采集点清单只列了查询统计。查询统计这个类全是布隆过滤器、时间序列元数据、chunk 读取、页解码与过滤行数类计数，没有计划成本字段。

计划成本在查询计划统计类里，经查询上下文转发，字段有分析、取分区、取模式、逻辑计划、逻辑优化、分发计划与分发七项。两个抽屉已经用一个渲染方法把它们输出成 planStatistics 旧键。这一项的实际情况比缺来源好：来源存在且已在传输，但 C 的清单没点名它。

还有一层限制要写进 manifest。这个渲染方法的入参是查询上下文，不是片段上下文。计划成本是查询级量，由抽屉在查询侧一次性渲染，不进入片段统计响应。C 的跨节点合并走的是片段统计响应，因此计划成本按现在的载体无法跨节点携带，只能在协调者本地读。设计第 70 行把它列为快照的 Query 级原始量时没有说明这一层。修改要求是 manifest 的来源一栏写查询计划统计类与查询上下文，并标注不可跨节点，需 thrift 变更或本地读取二选一。

### 计划成本的读取方法多数没有空值卫

查询上下文的七个计划成本读取方法里，分析、分发计划、逻辑计划、逻辑优化与分发五个没有空值卫，查询计划统计为空时直接抛空指针。取分区与取模式两个有卫，返回零。已有的 JSON 抽屉测试在第 496 行专门写了一句注释说明要先初始化才避免空指针，并调了一次设置分析成本置零。

这一条对 C 的直接影响是：C 的快照构建要读这些量，而构建在终态写锁内。结合 P1-3 的发现，任何未初始化的查询上下文都会让空指针异常冒到没有 finally 的加锁段里，后果与该条相同。修改要求是 manifest 记录这五个无卫读取方法，C 的快照构建对它们包空值卫并把缺失标成不支持字段，不得让异常进入冻结锁内。

### 聚合成本的三项不在传输载体里

设计第 39 行说查询统计保存文件、元数据、解码、过滤与聚合相关计数与耗时。查询统计里没有聚合字段，聚合零命中。

三项聚合成本在片段上下文里，分别是从原始数据聚合、从统计聚合与聚合算子三类。它们有三个对应的方法把值取出并清零，清零动作发生在释放资源时，只写查询执行指标集。构建统计不读它们，thrift 的结构体也没有对应字段。跑一个带聚合的表扫描，这三个量在本地累加过，但既不进响应也会被清零，跨节点永远拿不到，事后本地也读不到。

修改要求分两处。第 39 行改成查询统计保存文件、元数据、解码与过滤类计数，聚合成本在片段上下文且当前不出片段。manifest 把这三项标为仅本地可用待实现，写明清零这一竞态，把 CPU 总量标为按算子求和派生，把资源终态标为待实现并说明拟议采集点。

### 毫秒格式化把非数值改成有限值

设计第 141 行要求任何 JSON 数值拒绝非数值与无穷。JSON 抽屉的毫秒格式化实现是四舍五入到三位小数。按语言规范，非数值取整为零，正无穷取整为长整数上限，于是非数值输出 0.0，正无穷输出 9.22e12。

十六个调用点都有大于零的守卫，所以这一形态今天不可达。这是巧合不是保证。将来任何新增的比率字段漏掉守卫，非数值会以 0.0 出现在 JSON 里，不是被拒绝，而是被伪装成合法值。修改要求是第 141 行补一句现有毫秒格式化会把非数值与无穷变形为有限值而非拒绝，C 必须在取值点显式检查并输出空值加有效性原因，不得依赖该格式化。值对象测试补一条针对该格式化的断言。

### 传输键的可见性规则只写了一族

规划第 143 行的继续隐藏内部字段是全文唯一的可见性规则。源码里实际有三族键，三种待遇。

第一族以一个内部前缀开头，两个抽屉都跳过它，不渲染。第二族以流水线前缀开头，是算子统计映射的键，由抽屉提升成并行流水线段，对用户可见。第三族是 morsel 键，写进算子附加信息后直接进用户可见输出，渲染测试明确断言 JSON 里能读到它，规划器的注释也说明这是刻意设计，目的是让调度决策与观测到的长尾从同一份导出的计划里可比较。

C 若新增内部键但漏加内部前缀，会泄漏进用户可见输出且无法回头。反之给本应可见的键加内部前缀又会被隐藏。修改要求是第 143 行改成完整枚举加规则：列出全部传输键及各自可见性，规定新增内部键一律内部前缀即隐藏，需要用户可见的指标一律 C 前缀并带单位后缀。序列化测试对每个前缀断言一次可见或隐藏。

### 交换算子的字节数被丢弃

设计第 145 行让 D 读输出字节，第 147 行让 E 读交换队列字节。交换算子把自己收到的字节数写进自己的附加信息，键名是 size_in_bytes，两个写入点都在累加路径上。

填充算子统计的循环里有一个提前跳过：计划节点号为空的算子直接跳过，注释写明有些交换算子没有计划节点号。于是这个量被采集、被跳过、永远不上屏。它是这两个字段唯一的现成来源。修改要求是 manifest 把该项标为已采集但被计划节点号为空的分支丢弃，C 需决定是补计划节点号还是在构建器里单独收集。序列化测试加一条断言交换字节数出现在快照里。

### 跨节点来源身份用节点自报配置值

设计第 133 行说跨节点时用 DataNode 端点作为来源身份，同时保留实际返回的 fragment owner。填充片段统计时设的 IP 是配置里的内部地址加内部端口，是节点自报值。跨节点抓取用的端点是实例上的宿主数据节点内部端点，是协调器实际连接值。

多网卡、网络地址转换或容器端口映射下，两者可能不同。抓取校验若用自报值做身份校验会误判，D 按端点分组比较节点负载时会串。请求侧也不带调用方端点，两侧无法互校。修改要求是第 133 行明确端点以协调器实际使用的端点为准，响应内自报值仅作诊断，两者不一致时记入有效性而非拒绝。校验用片段实例号加查询号做主键。

### 文本侧驱动级字段没有落点

设计第 137 行要求文本输出新增驱动 CPU 纳秒、驱动墙钟、驱动输出行与驱动块数组等字段。文本抽屉只有一个按驱动渲染的段落，渲染的是并行子扫描。根驱动与收集驱动在文本里没有任何行。

排序原语也不能直接当稳定排序用。驱动任务号的比较实现是两个全串的大小写无关比较，字典序意味着流水线 10 排在流水线 2 前面。规划第 134 行要求驱动数组按三个身份稳定排序，实现者图省事直接用这个比较方法，顺序既不是数字序也不稳定可预期。修改要求是文本抽屉清单补一条驱动级字段渲染在哪个段落、非子扫描驱动如何呈现。第 134 行改为显式比较器，先片段号、再流水线号数值、再驱动任务号全串，并要求测试断言顺序。

### Gson 失败的证据链指错了路径

设计第 141 行说 B6 已发现 SHOW REGIONS 的非数值资源字段会使 Gson 序列化失败，C 的序列化测试必须覆盖这个边界。B6 的失败日志确实存在，栈顶是非数值不是合法双精度值，调用方是 Gson 的写方法。

但栈最外层是验收探针自己的 main 方法第 60 行，那一行是把 JDBC 结果集转成映射后用 Gson 写成文件。失败发生在探针自己的转储里，不在 IoTDB 的生产统计渲染路径上。非数值这个数据事实是真的，SHOW REGIONS 的结果集里确实有。把失败归到生产序列化路径是归因错误。

这一条不影响第 141 行要求的正确性，拒绝非数值与无穷本来就是该做的事，而且成本极低。影响的是证据链与测试设计：C 不能据此认为生产路径已经出现过这个失败，测试必须直接构造非数值用例，不能假设它天然可达。修改要求是第 141 行把 B6 的证据改成事实陈述，写明失败点在验收探针的结果集转储，生产渲染路径尚无该失败的观测记录。序列化测试直接构造非数值与无穷字段。

### 一个文件装两个公共顶层类型

规划第 55 行把 RuntimeSnapshotValidity.java 描述为枚举和不可变集合。一个 Java 源文件只能有一个公共顶层类型，否则编译不过。这句话要么让实施者把集合写成嵌套类型，要么直接编译失败。

连带一处是第 55 行列的有效性枚举值以等结尾，读起来像穷举，实际第 101 行还有 partial、stale、clockInvalid、overflow、missingDriver、duplicateSuppressed 六个值要进同一个集合。两处口径不一致。修改要求是把第 55 行拆成两个文件或明确集合为枚举内的嵌套类，并让第 55 行与第 101 行的值清单一致。

### 工作单元与分区号只能从字符串解析

设计第 145 行让 D 读工作单元、分区与来源三类 ID，第 147 行让 E 读分区 ID。这三个量在源码里没有结构化字段，只能从计划节点号字符串里切出来。

这与设计第 80 行自己的规则冲突：任何由字符串解析得到的 ID 只作为显示字段，不能作为去重主键。而 RuntimeSnapshotDelta 的对象键正是按同一对象键算增量，用字符串解析结果当键，键的稳定性取决于计划节点号的生成格式。B 若改后缀格式，增量对象键静默改变，E 的增量全部错配。修改要求是 manifest 把这三个 ID 标为仅显示可用，D 与 E 的读取位置改用结构化身份。若短期内必须用字符串，在 manifest 写明格式依赖与失效条件。

### 抓取路径没有超时且首个失败即抛

设计第 130 行要求节点缺失、超时、RPC 错误或版本不兼容进入缺失来源，不把缺失当成零。规划 C4 第 158 行要求严格区分 RPC 错误、状态非成功、响应缺失等七种情况。

抓取实现是串行循环，逐个节点调用，没有超时设置，也没有把异常收进集合。一个节点抛异常会中断整个循环，后面的节点不会被抓取，已抓到的结果随调用栈一起丢。这与第 130 行的协议直接矛盾。修改要求是规划 C4 增加一节抓取路径改造：每个节点的抓取包超时与异常捕获，失败进缺失来源并保留下一步继续，全部完成后再合并。

### 内存峰值没有来源

设计第 147 行让 E 读内存预留与峰值，第 91 行要求内存区分估算、预留、观测峰值三类。预留有来源，B 的未提交改动里有片段预留快照与注销回执两个类。峰值没有：全仓唯一带最大值语义的字段只覆盖序列扫描的一条路径，表模型恒为零。注销回执是一个无上限且没有生产读取方的旁路。

修改要求是 manifest 把内存峰值标为待实现并写拟议采集点，把注销回执标为无生产读取方。第 91 行的三类规则在峰值无来源时显式降级，不得用预留冒充峰值。

### 冻结词汇与 B 的未提交代码冲突

规划 C2 第 93 行与第 94 行要求快照元数据不得与资源注销回执混淆。B 的未提交代码里已经有 freeze 与 frozen snapshot 两个同名概念，指的是内存预留的冻结，不是运行指标快照。

C 若沿用这两个词，读代码的人无法从名字区分是哪一套。而第 93 行的消歧要求只覆盖元数据与回执，没有覆盖词汇本身。修改要求是 C 的类与方法名加运行指标前缀，并在 manifest 的名词表里固定中英文对应。

## 实现内容的合理性与效率

用户关注的第二个问题是实现内容是否合理高效。结论是架构合理，有四处会付出返工或长期开销，需要在一开始就改判。

### 合理的部分

不另造平行计数器这一条核过源码，站得住：片段、算子、查询三级的主要量都已有采集点，C 用不可变值对象承载而不新增计数。不可变值对象加稳定字段序的 SHA-256 校验和这个设计没有重复建设。四级模型与 D、E 的消费面精确匹配：D 要按来源、工作单元、流水线、驱动比较负载，正好是四级里的后三级。E 要按代际读增量，正好是采样代际这一节。旧键兼容走新增根键而不动旧渲染路径，这一条也成立，规划点名的既有测试文件都真实存在，说明作者对现有测试面有了解。

### 传输选型

把驱动级快照塞进算子统计的附加信息，意味着每个驱动的每个字段都要转成字符串再解析回长整数，键空间还受折叠约束，并且要踩合并器的两条地雷。规划第 121 行到第 123 行自己列出的四条修改 thrift 触发条件是：现有映射无法表达代际或 schema 版本或大整数、严格 schema 校验无法在适配器完成、混合版本节点可以忽略未知字段且有版本协商。这三组条件其实已经全部满足，代际与 schema 版本是新概念、大整数指纳秒与字节、严格校验是 C 的核心诉求。第一版直接加 thrift 字段，比先走附加信息过渡再迁移省一整轮返工，运行时开销也更低。

叠加 P0-1 的事实，这个选择已经不是省不省返工的问题，而是第一版走附加信息根本走不通：response 上没有扩展位，片段级字段无处安放。

### 冻结路径的锁内工作量

构建统计现在已经在终态写锁内对每个驱动的每个算子做一次全量深拷，附加信息的转换是每个算子新建一个映射。C 若在同一把锁内再构造四级不可变快照并算 SHA-256，锁持有时间会显著变长，而同一把锁被 on-demand 抓取的读锁争抢，E 采样越频繁争抢越狠。

校验和可以移出锁外。它只依赖不可变对象，锁内只需要完成对象构造。按驱动展开的量要有条数与内存上限加截断策略，文档没有写，并行度高的片段会放大。以一个八驱动、每驱动六个算子的片段计，单次抓取要拷贝四十八个算子映射、构造八个驱动快照，再对全部字段做一次 SHA-256。这个量级本身不构成问题，问题在于它发生在写锁内且没有上限。

查询统计那三十余次无屏障读取也在同一把锁内，是锁内工作量的第二大项，且它让相同校验和这一判据落空。见 P1-8。

### 采集点的总成本

C 需要从零新增的采集点有六处：线程 CPU、纳秒驱动墙钟、驱动首次与末次处理、驱动级就绪阻塞、三个驱动计数、内存峰值。这六处都没有现成来源，每一项都要新写字段、新写访问器、新写测试。文档对总成本没有评估，也没有交付不了时的降级路径，这是 C 最可能超支的一块。

时间窗口是一条硬约束。终态缓存有五分钟硬编码上限，C6 第五步的恢复后重取必须落在窗口内，否则验收会偶发失败。
