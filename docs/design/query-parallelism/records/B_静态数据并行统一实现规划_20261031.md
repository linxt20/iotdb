# B 静态数据并行统一实现规划

目的：为实施者规定 B 的文件级修改、依赖顺序与测试退出条件，供 sxing 在实施前审核范围和工期。

摘要：B 需要把已有三条扫描构建路径的公共步骤集中到统一入口。资源治理还涉及本地队列、远端通道、完整内存估计和驱动创建失败后的清理。本文将工作分为冻结基线、纯拆分计算、公共构建、资源准入和真实执行验收。每一步都列出代码落点与可验证产物。

结论：B 按 B0 至 B6 顺序实施，每一步关闭退出条件后再进入下一步，预计单人六至九个工作日。首版沿用已有扫描资格、DOP 输入和静态分组配置，并补齐资源身份计数、兼容额度、轮询门限与异常释放。本文为待审规划，B 生产代码、单元测试和真实运行均尚未实施。

未决问题：性能倍数、生产哈希连接和 CPN 正文范围均等待 sxing 决定。兼容额度与本地验收观测接口作为本稿方案等待 sxing 复审，B 按[设计范围](B_静态数据并行统一设计_20261031.md#术语与范围)实施。

## 查询拆分的实施背景

扫描分支增加后，系统必须继续读取同一批数据，并在需要时保持整体排序。实施者还必须证明资源不足或创建中断时，已经建立的执行对象都能释放。只移动代码或只比较最终行数，都不足以完成这项工作。

例如，三条分支中第二条创建失败时，第一条已经成功的驱动也必须关闭。若只关闭失败分支自身，查询虽报告失败，第一条驱动的队列仍可能保留内存。B 必须把这些责任写入同一构建流程并验证。

数据来源：代码基线为 sc01 `/root/iotdb` 的 `feat/next-p0`，提交 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`，行为约束由[B 统一设计](B_静态数据并行统一设计_20261031.md)定义。

## 文件归属与接口清单

新增类集中在已有本地 planner 包，算子执行和交换协议继续使用原实现。本文以下源码名均相对于 DataNode 模块，符号名和测试类名属于待实现接口，已有同名方法则明确标注为接入点。

四个新类分别保存不可变描述、执行纯拆分计算、管理公共构建和管理资源登记。文件名统一在本节末尾列出，具体接入方法在各步骤末尾定位。

新增入库文件必须带 Apache License 2.0 头，JSON 按仓库规则豁免。每次修改 Java 后必须执行模块格式化，最终验证再核查差异范围。新增生产异常和日志必须使用同名中英文消息常量。

四个类分别服务四类断言。例如，纯描述可以用六个设备序号测试，无需启动数据区域。公共构建必须检查真实算子和工厂，资源登记必须检查真实队列与故障关闭。测试不得用描述自带的覆盖判断作为唯一预期。

数据来源与路径：模块为 `/root/iotdb/iotdb-core/datanode/`，主包前缀为 `src/main/java/org/apache/iotdb/db/queryengine/`，测试包前缀为 `src/test/java/org/apache/iotdb/db/queryengine/`，四个新文件均位于主包的 `plan/planner/`，文件名为 `ScanParallelPlan.java`、`ScanParallelPlanner.java`、`LocalScanPipelineBuilder.java` 和 `LocalExecutionResourceRegistry.java`。

## B0 基线与执行身份

B0 必须建立隔离的源码与运行身份记录，并保存后续比较使用的构造快照。实施者首先核对分支、提交、工作区差异、六个已有测试类和 A 的最终回归证据。保留存量未跟踪安全资源目录，禁止将其混入 B 改动。

执行前记录必须包含真实入口与 driver 的绝对路径及 SHA256、源码与 POM 哈希、测试清单、配置快照、JDK 与 Maven、classpath、实际 JAR 和本地库身份。启动后继续记录实际类来源与本地库路径。与 B 无关的权重项记录为不适用。

例如，同一个 Java 类在冻结发行包与工作区 target 中各有一份时，只有加载记录才能说明执行了哪一份。任何入口与清单不匹配都必须先修复绑定，再执行测试。

B0 的基线快照必须覆盖设备拆分、时间分区、字节加权、等数量对照、有序两层合并、过滤融合及各个退回条件。已有六类测试先单独运行，完整模块在 B6 验收。源码核查只能作为定位依据，运行证据单独保存。

退出条件：六类定向测试全部成功，形态与资源对象清单可重放，配置在每个测试退出时恢复。例如，开关初值全开与全关各执行一轮后，退出快照必须逐字段等于进入快照。

数据来源与修改位置：基线证据为 `/root/property-b-artifacts/B-docs-20261028-01/source-audit.json`，拟新建仓库工具目录 `research/query-intra-parallelism-e2e-acceptance/static-scan/`，入口拟为 `run-baseline.py` 与 `baseline-manifest.json`，已有测试为 `DeviceTableScanParallelPipelineTest`、`DeviceTimePartitionMorselTest`、`LocalExecutionPlannerOperatorsMemoryTest`、`DriverMorselCompletionStatisticsTest`、`PipelineBuilderTest` 与 `MetricTreeRenderTest`，六类分别属于 planner、driver 与 statistics 对应测试包。

## B1 纯拆分计算

B1 必须先完成不可变描述与独立计算测试，再连接真实算子。输入使用设备快照序号、有序分区列表、可选权重和配置快照。输出包含模式、实际组、输入与目标并行度、排序证明、过滤融合标记和原因。

### 新增描述与计算类

描述构造函数必须复制列表与映射，拒绝重复分区和非法组，禁止保存可变上下文。输入类型必须显式携带无序并行许可位、是否溢写和输入 DOP，取值时刻为扫描入口创建子上下文之前。有序模式采用共同基础条件与排序证明，无序和直接过滤融合额外检查许可位。串行退回必须在建立任何子上下文前决定。

例如，设备数为一、分区数为三、DOP 为四，输出仍为串行。设备数为六、分区数为三、DOP 为四，输出的分组按设计的时间优先公式产生三条工作单元，覆盖预期十八个组合。

区域文件列表与分区大小的元数据采集保留在生成器与 TsFileManager 一侧，纯计算接收文件大小快照及独立的完整性状态。区域文件估计中的负大小、累加、整数向上取整，以及目标分支的设备数乘分区数均归 B1。缺失数据改用等数量分组，完整权重按确定顺序分配。计数乘法、累加和向上取整必须按[配置与估计边界](B_静态数据并行统一设计_20261031.md#配置与估计边界)处理。

退出条件：纯测试覆盖空输入、单设备、DOP 为一、溢写、许可位按模式区分、上限夹取、重复分区、稳定同值、无元数据与描述不可变。负大小必须输出元数据无效原因，禁止把负大小解释成小区域。接近 long 上限的累计保持饱和，整数向上取整必须经过目标上限夹取后才转 int。

例如，100,000 台设备与 30,000 个分区的中间乘积为 3,000,000,000，输入 DOP 为八时，最终目标为八。测试仅传入计数与少量代表数据，禁止构造三十亿个组合。每个算术反例必须关联提取前方法和提取后被测函数。

修改位置与测试：新增 `plan/planner/ScanParallelPlan.java` 和 `ScanParallelPlanner.java`，新增 `plan/planner/ScanParallelPlannerTest.java`，从 `DataNodeTableOperatorGenerator.java` 提取 `partitionIntoGroups`、权重分配、`estimatePipelineNumByDataSize`、`decideParallelScanPipelineNum` 的纯部分，以及 `constructParallelDeviceTpMorselScan` 的目标乘法。区域元数据读取仍在原侧，已有加权路径的饱和与负值检查保持合同，入口暂以适配器保留。

### 时间范围与语义复制

时间范围必须按运行时真实分区间隔与时间精度计算，源查询条件始终保留。实现者必须核查全局时间工具与目标数据库分区配置的绑定，绑定无法证明时在建资源前退回原扫描。边界预期必须独立于被测助手计算。

例如，输入时间区间包含负一、零和分区边界，测试必须逐点比较是否落入相应子扫描。针对 long 最大值，测试必须证明可读数据域内没有遗漏，无法表示的半开范围走已定义的边界退回原因。

退出条件：范围测试覆盖负分区、时间别名、原条件相交、多分区逻辑或、极值和不支持的配置，克隆前后原节点字段逐项一致。例如，子扫描缩小为两台设备后，原扫描仍包含六台设备，TopK 关联 ID 保持原值。

修改位置与测试：`DataNodeTableOperatorGenerator.java` 的 `requireTimeColumnName`、`buildTimePartitionRangePredicate`、`cloneSubScanNode` 及参数构造入口，扩展 `plan/planner/DeviceTimePartitionMorselTest.java`，独立纯范围测试可以加入 `ScanParallelPlannerTest.java`。

## B2 设备与时间分区公共构建

B2 必须把两条无序路径接入公共构建器，保持父 Collect、参数构造和源登记语义。B2 同时建立资源登记表的规划清理部分，B4 再补齐额度冻结。生成器负责采集输入与构造具体算子，构建器负责接线与所有权。每创建一个资源立即登记，禁止先批量构建再补登记。

公共构建器接收不可变描述和构造回调，逐组生成子上下文、克隆扫描、参数、扫描算子及可选过滤根。扫描构造返回即登记关闭根，sink 工厂内部先登记队列，再登记 sink，source 返回即登记端点。随后才建立 ExchangeOperator、估计与工厂，并分别登记额度身份、估计父关系和未消费责任。工厂加入共享列表必须晚于它的责任登记。物理 ID 使用源节点与组序号，整数流水线 ID 继续由上下文共享分配。

例如，六个工作单元必须对应六个不同工厂、六个队列和六个交换源。每个估计必须关联正确父节点，根工厂仍由本地规划器最后追加。两源同组序号的物理扫描 ID 必须保持不同。

规划登记表必须提供独立关闭根登记与父子挂接接口。父子挂接完成后，子树关闭责任转移到父根，独立关闭集合只保留父根。端点中止项保持独立且幂等。

例如，两个扫描挂入组内合并后，清理只调用合并根的递归关闭。测试应当记录各算子的关闭次数，禁止以所有算子都至少关闭一次代替恰当的所有权验证。

过滤融合继续调用原执行构造，单独保留直接子扫描、无 diff 等限制。普通投影仍使用既有访问入口。所有构建回调必须传递原克隆语义字段，禁止以手写最小构造替代完整 clone。

退出条件：已有设备与工作单元测试通过，构建断言覆盖工厂、sink/source、源登记、父估计、唯一 ID 和原节点字段。故障分别注入队列创建前、队列已建而 sink 构造失败、sink 已建而 source 失败三个位置。

例如，第三组在 source 建立处失败时，前三组已经存在的对象必须全部出现在登记记录中。独立扫描根各递归关闭一次，sink 与队列各只有一次有效终态转换，所有回调通知按对象身份核对。结构记录移除数量单独核对，禁止把工厂项与队列通知混成同一个总数。

修改位置与测试：新增 `plan/planner/LocalScanPipelineBuilder.java` 与 `LocalScanPipelineBuilderTest.java`，建立 `LocalExecutionResourceRegistry.java` 的清理与子上下文共享接口，修改 `DataNodeTableOperatorGenerator.java` 的 `constructParallelDeviceScan`、`constructParallelDeviceTpMorselScan`、`visitFilter`，保留 `constructTransparentMorselFilter` 的执行表达式入口，扩展 `DeviceTableScanParallelPipelineTest.java` 与 `DeviceTimePartitionMorselTest.java`，修改 `execution/exchange/MPPDataExchangeManager.createLocalSinkChannelForPipeline` 增加接受登记回调的生产重载，原签名委托新实现以保留既有调用方。

## B3 有序构建与属性交接

B3 必须在同一构建器中保留每设备扫描、组内合并与组间合并三层对象关系。共用的是流水线接线，单设备扫描和比较器继续由有序模式的回调构造。有序入口继续使用忽略无序许可位的共同基础资格，并额外证明完整自然顺序。

例如，四台设备被分为两组时，每组包含两台独立扫描，并通过组内合并输出有序流，根再合并两条流。相同时间戳按完整排序条件比较，null 顺序与升降序必须继承原排序定义。

许可位为假但排序证明成立的样例必须继续形成有序并行。相同许可位为假时，无序扫描和直接过滤融合必须使用原入口。两条断言共同检查资格适配，避免共用助手扩大或缩小已有能力。

退出条件：两层合并结构、完整输出序列、反向扫描、标签加时间、相同键与 null、字段排序退回、时间位于非末位退回、列映射缺失退回均有断言，A 的属性合同与快照回归通过。

修改位置与测试：`DataNodeTableOperatorGenerator.java` 的 `visitSort`、`visitStreamSort`、自然顺序守卫和有序构建方法接入 `LocalScanPipelineBuilder.java`，新增 `plan/planner/OrderedScanPipelineContractTest.java`，沿用 `DeviceTableScanParallelPipelineTest.java` 的已有有序样例，分布式属性组件保持 A 的合同。

## B4 真实资源计数与内存准入

B4 必须把真实对象计数、基线兼容额度与既有全池记账连接起来。上下文的 data、schema 构造初始化登记表，子上下文共享同一实例。原局部计数的 add、set、保存和恢复继续作为原算法输入。

### 登记与基线额度快照

登记表按真实队列、远端 source 与远端 channel 去重，并保存实际 planNodeId 记账键。各个原 setter 调用点必须把作用对象和原额度交给登记表，普通本地 source 的空 setter 也必须显式记录为无生效写入。最终 ExchangeOperator 遍历产生的基线收紧仍需计入独立快照。

B0 先冻结 A 基线的完整额度轨迹，B4 用同形态记录比较真实计数与兼容下限。纯 sink、纯 source、两源合并、多桶输出、本地跨片段、树模型与 schema 都必须有记录。字段缺失或类型未适配时，规划必须明确失败。

例如，同一队列被两个 ExchangeOperator 包装，真实数量为一。32 桶输出具有 32 个不同 channel，但可能只有一个记账键。测试必须同时给出对象数、记账键数与基线额度，不能用其中一个代替其他两个。

修改位置与测试：完善 `plan/planner/LocalExecutionResourceRegistry.java`，新增 `LocalExecutionResourceRegistryTest.java`，修改 `LocalExecutionPlanContext` 的三个构造、`addExchangeOperator`、原额度计算及最终遍历。通用侧接入 `OperatorTreeGenerator.visitExchange`、`visitIdentitySink`、`visitShuffleSink` 和创建子流水线的交换路径，表模型侧接入 `DataNodeTableOperatorGenerator.visitTableExchange`、`visitIdentitySink`、`visitShuffleSink`，sink 由 `MPPDataExchangeManager.createShuffleSinkHandle` 创建。

### 冻结与兼容退出条件

冻结按设计的分配目标和兼容下限生成每对象额度，发布前校验对象初始上限和全部基线调用轨迹。原额度应用改为记录加冻结，禁止先用较小目标收紧对象再尝试提升下限。已经存在的跨片段额度继续按实际队列的单调收紧规则生效。

例如，32 个通道的目标为 125,703 字节，下限为 4,022,509 字节，最终申请必须保持后一个值。通过真实 SinkChannel 或 LocalSinkChannel 发送一个大小介于两值之间的数据块，必须通过单块校验，并在消费后释放。测试必须保存实际 TsBlock.getSizeInBytes 的返回值，纯 MemoryPool 参数测试另外使用 163,840 字节反例。

退出条件：B0 六类测试覆盖的各基线形态中，每个对象申请额度均不低于该形态基线最终值，差异报告包含形态、通道数、基线值、目标值及实际值。32 桶纯 sink 样例必须执行真实预留，查询成功且结果完整。零对象、非正预算、零目标经下限提升、最高优先级和跨片段不同冻结顺序均有测试。

例如，四个对象和三字节预算产生零目标，但三字节兼容下限仍允许一字节数据块。一个真实记账键若已有两字节，再申请两字节，应当进入累计额度不足的等待，并在释放后完成。单块超过三字节则属于异常路径。

修改位置与测试：`LocalExecutionResourceRegistry.freezeAndApplyLimits`，`LocalExecutionPlanContext.setMaxBytesOneHandleCanReserve`，扩展 `plan/planner/PipelineBuilderTest.java` 核对局部计数保持原值及真实登记独立计数，扩展 `execution/memory/MemoryPoolTest.java` 与 `execution/exchange/SinkChannelTest.java`，必要断言也纳入 `LocalSinkChannelTest.java`。

### 原子收紧与读可见性

共享队列额度字段必须采用同一个原子数读写，setter 执行原子的最小值更新，getter 和预留调用均读取该原子数。流水线 source 和本地 sink 的 setter 必须直接委托，移除自身读后判断。远端 source 与 sink 在本片段驱动启动前发布额度，其同步读写与 in-flight 行为必须另行核对。

例如，队列、流水线 source、本地 sink 三类入口各执行一轮双线程 8 MiB 与 4 MiB 的收紧测试，每轮最终值为 4 MiB。测试用屏障保证读线程在更新后读取，不能只反复运行后检查偶然结果。

退出条件：每类入口的收紧与读可见性断言均通过，真实共享队列两侧顺序互换后最终额度与基线比较仍兼容，阻塞后可以继续读取。故意让包装层写回原始值的副本必须被测试拒绝。

### 驱动与工厂的释放责任

工厂必须提供生产可用的未消费资源关闭入口，成功创建驱动后把责任移交给驱动。片段管理器必须使用显式创建循环，保留已建驱动列表，并在任意失败时逐个关闭。最后一个根工厂的顺序继续保留。

工厂必须区分未消费、创建中、已移交和已关闭四种状态，并保护创建与关闭的状态转换。创建循环开始前按工厂数量初始化关闭槽，成功驱动销毁与未消费工厂关闭各自通过幂等状态完成一个槽。当前失败工厂与剩余工厂都必须结算，避免提前关闭触发空 latch 或永久等待。创建循环必须在移交前检查片段终态，取消发生在构造返回之后时，创建循环负责关闭尚未移交的驱动。工厂状态、登记表与创建列表只能有一个有效关闭责任方。

例如，用屏障把第二个工厂暂停在驱动构造返回与移交之间，再发送取消。解除屏障后，第二个驱动必须关闭，第三个工厂必须保持未消费并释放资源，禁止继续提交调度。

例如，第二个工厂失败时，第一个驱动和第三个未消费工厂都必须释放。第一次关闭抛异常后，清理循环仍必须处理剩余对象，并保留原异常及 suppressed 异常。工厂和登记表只释放自己仍拥有的对象。

退出条件：生成根失败、建立 source 失败、内存准入失败、首个与中间工厂失败、创建时取消、提交调度器失败、运行中取消均恢复进入时的预留值，所有 future 必须已完成或已取消。三个工厂的第二个失败时，三个关闭槽最终必须归零，已建驱动有效销毁一次。
