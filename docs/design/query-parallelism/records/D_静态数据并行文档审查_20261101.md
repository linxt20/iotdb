# D 静态数据并行文档审查报告

## 目的

核对 D 两份文档与 `/root/iotdb` 工作区实际代码的对应关系，判定 D0–D6 各阶段门能否按文档执行，并核对其退出判据所依赖的 C 快照字段是否已有来源。

## 摘要

本轮审查对象为 sc01 `/root/w5-docs/` 下的 D 设计与 D 实现规划，MD5 与请求给出值一致。审查方式为逐条比对文档陈述与工作区源码、thrift 结构、配置项和已有测试类。核对范围包括 D 声称负责的三种扫描切分的生产现状、两个 DOP 决策路径的关系、`ScanParallelPlanner` 的调用链、退出判据对 C 快照字段的依赖、结果比较规则和 DOP 公式的输入来源。

## 结论

两份文档表述规范，范围和正确性约束写得完整。当前有七项阻塞。

第一，D 范围内的三种扫描切分已在生产实现并由配置开关控制，文档按待实现描述。第二，生产已有 `decideParallelScanPipelineNum` 这条 DOP 决策路径，与 D 的 planner 形成两条并存路径，文档未规定优先级。第三，`ScanParallelPlanner` 和 `ScanParallelPlan` 没有任何生产调用方。第四，退出判据第 5 项依赖 C 的四个未建值字段。第五，exchange edge、work unit、bucket 和实际 driver 数四项身份在 thrift 和 `FragmentInstanceContext` 里都没有位置。第六，D 的结果比较没有继承 C 的 EXPLAIN ANALYZE 说明列剥离规则。第七，DOP 公式里的 `cpuBudget` 没有来源。

修复这七项之后 D1 可按文档推进。

## 未决问题

- 性能倍率口径、hash join 生产路径、CPN 论文范围三项，两份文档已标注待 sxing 决定，本报告不重复展开。
- `decideParallelScanPipelineNum` 与 D 的 planner 二者谁主谁从，待 sxing 决定。
- D 的 fallbackReason 词表与生产已写入的取值如何合并，待 sxing 决定。

## 判定标准

分三级。P1 指阶段门无法按文档执行或退出判据可被不满足。P2 指文档与代码存在可指名的差异但不阻塞阶段门。P3 指表述和一致性问题。每项给出文档位置、代码位置和数值算例。

## 文档规范符合性

两份文档的写作规范核查通过：没有分号连接从句，没有破折号，没有会过期的相对时间词，没有第四种规范动词，设计的输入表是 7 行 3 列且单元格均为短值，粗体没有超限，每个判据都配了具体分支。设计 L92 一句列三个全局监控类名，属枚举而非推理链，可接受。

两份文档都没有数据来源节。C 的两份文档各有一节，路径和行号集中在节末。D 的路径分散在设计的「关键文件」节和规划的 D0–D6 修改文件列表里，位置同样集中，缺的只是统一的节名和行号。

## 范围内的三种切分已在生产实现

设计 L25 把设备、时间分区和有序扫描切分列为 D 负责的范围，规划 D2、D3、D4 各作为一个阶段实现其中一种。工作区实际情况是三种切分都已在 `DataNodeTableOperatorGenerator` 中实现，并由配置开关控制：

| 模式 | 生产入口 | 开关 |
| --- | --- | --- |
| TIME_PARTITION | 1402 行记录点 | isEnableTimePartitionMorsel |
| DEVICE | 1462 行记录点 | 无专用开关 |
| ORDERED | 1510 与 1527 行 | isEnableOrderedParallelScan |

`recordScanParallelMetadata` 在 1402、1462、1480、1510、1527 五处被调用。它把四个标量写进 `FragmentInstanceContext`。这四条链路已经打通。

D 真正新增的是 LPT 分桶、work unit 和 bucket 结构化身份、source ID 生成规则，以及把这些接进 planner 的接线。文档把已经存在的部分和真正要做的部分放在同一层次描述，读者无法据文档判断 D2 到 D4 各要写多少代码。

**修订方向**：在范围节区分「已在生产、由开关控制」和「本版新增」两类，D2–D4 的阶段目标改为只描述新增部分和要改的接线点。

## 两个 DOP 决策路径

生产的并行度决策在 `DataNodeTableOperatorGenerator.decideParallelScanPipelineNum`（1728 行起）。基础逻辑是取并行度配置与设备数的较小值。开关 `isEnableDopEstimation` 打开时，再与 `estimatePipelineNumByDataSize` 的结果取较小值。该方法在 1642、1851、2252 三处被调用。

设计 L73 给出 D 的公式 `target = min(configuredDop, workUnitCount, cpuBudget, memoryBudget)`。设计 L81 写 `LocalScanPipelineBuilder` 按 bucket ID 顺序创建 pipeline。`LocalScanPipelineBuilder.build` 现有 6 处生产调用，都不接受 `ScanParallelPlan` 参数。两条路径产出同一个数字，文档没有规定谁覆盖谁。

一个算例：configuredDop 为 8，设备数为 5，`isEnableDopEstimation` 打开且数据量估计为 3 时，生产路径给出 3。若 planner 的 workUnitCount 为 5、memoryBudget 为 4，D 路径给出 4。同一个 fragment 得到两个不同的 pipeline 数，`actualPipelineCount` 写哪一个没有定义。

**修订方向**：在计划算法节明确 planner 的 target 覆盖 `decideParallelScanPipelineNum`，或明确两者各管一段并在 `LocalExecutionPlanContext` 里规定合并规则。退出判据第 1 项写相同输入产生字节级相同的计划。这条不明确规定，该判据不可判。

## ScanParallelPlanner 的调用链

规划 L13 写「D 的代码入口固定为 `ScanParallelPlanner.plan(Input)` 和 `LocalScanPipelineBuilder.build(...)`」。前者在生产代码里没有任何引用，全仓只有 `ScanParallelPlannerTest` 一个使用方。后者有 6 处生产调用。

`ScanParallelPlanner.plan(Input)` 这个 API 确实存在，它的入参内部类和估算内部类也都在。所以规划 L13 的签名描述准确，缺的只是调用方。

C 的设计 L78 已经为这种情况写过规则：`ScanParallelPlan`/`ScanParallelPlanner` 必须接入实际表模型规划入口，只有测试对象没有生产调用链时 plannedDop 标为 UNSUPPORTED。D 的文档没有引用这条已有约定，也没有说明自己处在哪一种情形。

**修订方向**：在 D1 或 D2 写明 `ScanParallelPlanner` 当前无生产调用方，接线是 D2 的交付物之一，并在 D0 记录该事实。

## 对 C 快照的依赖缺口

设计 L87 到 L90 列出 D 直接复用的 C 字段。逐个核对 `buildDriverSnapshots` 后，其中四个字段有 thrift 传输位但没有建值，也没有 unsupported 标记：

| 字段 | thrift 位置 | C 侧建值 |
| --- | --- | --- |
| driverCpuNanos | 808 | 无 |
| driverReadyNanos | 811 | 无 |
| driverBlockedNanos | 812 | 无 |
| driverOutputBytes | 813 | 无 |
| driverWallNanos | 809 | 有条件 |
| driverOutputRows | 812 之后 | 有 |

`driverWallNanos` 有正确的降级分支可参照：值小于零时写入 `UNSUPPORTED_FIELD:driverWallNanos`。

设计 L131 和规划 L133 的退出判据第 5 项写「C final snapshot 能按 driver 比较 wall、CPU、rows、bytes、blocked 和 validity」。六项里 CPU、bytes、blocked 三项没有值，按现状该判据不可能通过。

另有三项身份在 thrift 和 `FragmentInstanceContext` 里都没有位置：

| 身份 | thrift | FragmentInstanceContext |
| --- | --- | --- |
| work unit | 无 | 无 |
| bucket | 无 | 无 |
| exchange edge | 无 | 无 |
| actual driver count | 无 | 无 |

设计 L96 写 source、bucket、exchange edge 和 driver ID 必须唯一。设计 L130 和规划 L132 的判据第 4 项写 planned DOP、actual pipeline/driver、work unit、bucket、exchange edge 均有结构化身份。四项里只有 planned DOP 和 actual pipeline 有位置。`FragmentInstanceContext` L184-187 有 plannedDop、actualPipelineCount、splitMode、splitReason 四个字段，没有 driver 计数，没有 work unit，没有 bucket。

规划 D5 L95 写 `RuntimeSnapshotView` 提供 driver、work unit、validity 的只读视图。`RuntimeSnapshotView` 现有三个公开方法。其中 `getDrivers` 返回 driver 列表，`isFieldSupported` 判断某个 validity 是否出现。work unit 视图没有对应字段可读。

**修订方向**：判据第 5 项改为分两级，C 侧已建值的 wall 和 rows 作为第一版必过，CPU、bytes、blocked 标注为依赖 C 的降级交付。判据第 4 项的 exchange edge、work unit、bucket、driver count 四项先在 thrift 和 `FragmentInstanceContext` 定位，再决定保留还是移出第一版判据。

## 结果比较未继承 EXPLAIN ANALYZE 规则

设计 L13 写「静态策略的质量用 C6 的候选/对照完整结果和快照对账验证」。设计 L132 和规划 L134 的判据第 6 项写「双 DataNode candidate/control 闭环通过，结果 SHA 和完整多重集一致」。

C 的设计 L49 到 L53 规定 C 的 final snapshot 只由 EXPLAIN ANALYZE 查询生成，且 D 和 C6 的结果比较必须使用 EXPLAIN ANALYZE，同时把说明列和 CTE 说明行从结果正确性比较中剥离。D 的两份文档没有出现 EXPLAIN ANALYZE，也没有出现剥离规则。

D 的快照对账依赖 C 的 final snapshot，而 final snapshot 只在 EXPLAIN ANALYZE 查询上存在。D 若用普通查询做 candidate/control，拿不到 final snapshot，判据第 5 项无从执行。D 若用 EXPLAIN ANALYZE，结果集里带说明行，判据第 6 项的完整多重集比较需要先剥离。

**修订方向**：在结果比较相关章节写明查询形态取 EXPLAIN ANALYZE，并写明说明列和 CTE 说明行的剥离规则，与 C 的设计 L53 对齐。

## DOP 公式的输入来源

设计 L41 到 L49 的输入表有 7 行：configured DOP、device IDs、time partitions、ordering property、file/row estimate、historical cost、memory budget。设计 L73 的公式用了四个项：configuredDop、workUnitCount、cpuBudget、memoryBudget。

`cpuBudget` 不在输入表里，全文没有定义它的来源。公式带一个无定义运算数时无法实现，也无法按判据第 1 项做字节级一致性测试。

一个算例：configuredDop 为 8、workUnitCount 为 5、memoryBudget 为 4 时，若 cpuBudget 为 2 则 target 为 2，若 cpuBudget 为 6 则 target 为 4。同一个输入的两种合理实现给出不同计划。

命名也有四种：输入表用 configuredDop，设计 L56 的输出用 inputDop，设计 L73 的公式用 target，设计 L56 的输出同时有 targetParallelism。同一量的四个名字分布在同一份文档里。

**修订方向**：输入表补 cpuBudget 一行并写明来源，或从公式中删除该项。四个名字统一为一个，其余作为别名在字段 manifest 登记。

## 文件归因与词表

自然有序证明的位置与文档不一致。设计 L65 写「有序扫描只有在 `TableDistributedPlanGenerator` 已证明自然顺序可合并时进入 ORDERED」，规划 D4 L82 把 `TableDistributedPlanGenerator.java` 列为修改文件。实际的证明方法是 `DataNodeTableOperatorGenerator.isNaturallyMergeableDeviceScanOrder`。它在 1508 和 1525 两处被调用，调用方是排序节点的两个 visit 方法。`TableDistributedPlanGenerator` 位于 `plan/relational/planner/distribute/` 包下。`DataNodeTableOperatorGenerator` 在另一个包。按 D4 的修改文件清单动手会找错类。

fallbackReason 词表与生产已写入的取值不重合。生产五处记录点写出两个取值：`NONE`（1402、1462、1510、1527）和 `PARALLEL_SCAN_NOT_SELECTED`（1480）。设计 L107 到 L110 定义四个取值：`ORDERING_NOT_PROVEN`、`EMPTY_INPUT`、`SPILLED_DEVICE_ENTRIES`、`ESTIMATE_UNAVAILABLE`。两组没有交集，也没有映射关系。thrift 的 `splitReason` 是 optional string，两套词表可以同时存在，但对账时无法判断一个 `NONE` 属于哪一种情形。

`ScanParallelPlan` 已有规划 D1 列为待增加的字段。该类 L29 有 `Mode` 枚举，L36 有 `FallbackReason` 枚举，L49 到 L54 有 mode、fallbackReason、inputDop、targetParallelism、deviceGroups、timePartitionGroups 六个字段。规划 D1 L36 写「增加结构化 WorkUnit、Bucket、成本、source ID 和 fallback reason」，其中 fallbackReason 已存在，inputDop 和 targetParallelism 也已存在。真正缺的是 WorkUnit、Bucket、成本和 source ID。

**修订方向**：D4 的修改文件改为 `DataNodeTableOperatorGenerator`，并保留 `TableDistributedPlanGenerator` 仅在确有改动时列入。fallbackReason 词表与生产的两个取值做合并或映射，映射表写入 D0 manifest。规划 D1 的待增清单删去已存在的三项。

## 排序与视图语义

`RuntimeSnapshotView.getDrivers()` 按 `RuntimeSnapshotDerivation.stableDriverOrder()` 排序，该比较器对 driverPipelineId 用字符串自然序。C 的设计 L118 写 driverPipelineId 按数值比较。

一个算例：两个 driver 的 pipeline ID 为 9 和 10 时，字符串序返回 10 在前，数值序返回 9 在前。D 的判据第 1 项写相同输入产生字节级相同的计划，判据第 5 项写按 driver 比较。两条都经过这个排序，而 D 的文档没有规定 driver 顺序。

`RuntimeSnapshotView.isFieldSupported(RuntimeSnapshotValidity)` 的语义是「快照的 validity 集合不含该枚举值即视为支持」。C 实际写入的理由是 `UNSUPPORTED_FIELD:driverWallNanos` 这种带字段名的字符串，枚举本身不带字段名。规划 D5 L102 写按字段门控，这个方法回答不了「driverCpuNanos 是否支持」。

`RuntimeSnapshotView` 现在只有一个测试使用方，没有生产使用方。D5 是它的第一个生产消费者。

**修订方向**：在指标复用规则一节写明 driver 迭代顺序及其比较方式，并说明与 C 的设计 L118 是否一致。D5 的按字段门控改用解析理由字符串，或在 C 侧增加按字段的查询方法。

## 命令与测试覆盖

D6 的两条命令没有提 argLine 和 `--add-opens`。C 的规划 L212 到 L218 写所有命令使用根 POM 自动激活的 profile 提供六条 `--add-opens`，命令行不覆盖 argLine，并保存实际生效的 opens 作为证据。D 的命令只列了 skip 系列参数，既没有对应规定，也没有保存证据的条目。Java 17 环境下缺 `java.base/java.net=ALL-UNNAMED` 会直接失败。

D6 的定向测试命令列了 5 个测试类：`StaticParallelPlannerTest`、`StaticDeviceBucketMappingTest`、`StaticTimePartitionBucketTest`、`StaticOrderedBucketTest`、`StaticCostCalibratorTest`。D 的判据第 2 项写 determinism、accounting、overflow 和 fallback 测试通过。其中 `StaticParallelPlanDeterminismTest` 与 `StaticParallelPlanAccountingTest` 在 D1 定义但不在命令里，overflow 和 fallback 没有独立测试类。判据点名的测试与命令覆盖的测试不一致。

D1 到 D5 定义的测试类共 11 个，D6 命令覆盖 5 个。

**修订方向**：命令补 argLine 和 opens 证据规定，与 C 的口径对齐。定向测试命令按判据第 2 项点名的测试类补全，或在判据里改用「D1 到 D5 定义的全部测试类」表述。

## 其他一致性问题

- 设计 L88 用 `driverTsBlocks`，C 的 thrift L814 是 `driverTsBlockCount`。同一个量的两个拼写。
- 规划 L85 写「`FragmentInstanceStatisticsDrawer` 两个输出边界」，未指名是哪两个。C 的文档点名 `FragmentInstanceStatisticsDrawer` 和 `FragmentInstanceStatisticsJsonDrawer`。
- 设计 L69 的 source ID 是斜杠拼接字符串 `queryId/fragmentId/planNodeId/mode/partitionId/deviceGroupId`。同一节写「禁止从 planNodeId 字符串后缀解析增量主键」，C 的设计 L79 写工作单元用结构化字段。一个需要反向解析的拼接字符串与这两条冲突。
- 两份文档的未决问题都提 CPN，全文没有定义。
- 两份文档都没有数据来源节，路径和行号分散在关键文件节和各阶段修改文件列表里。
