# B 静态数据并行统一设计

目的：供 sxing 和独立审查者核查 B 的实现边界、扫描拆分规则及资源释放责任，作为文件级实现规划的依据。

摘要：IoTDB 已有按设备拆分、按时间分区拆分和有序扫描的本地执行路径。三条路径分别构造驱动、交换队列和内存估计，资源计数还参与父子计划的局部计算。本文依据 A 的已推送提交核查这些入口，并提出统一的构建与准入方案。全部新增组件和接口均为待审设计。

结论：B 采用纯拆分计算、公共流水线构建和片段内资源登记三个部分。真实资源计数及其分配目标在首版用于可核查记录，生效额度保持基线，轮询策略也保持基线。扫描构建与生命周期清理统一实施，额度收紧收益交给独立后续方案。构建、准入、移交和关闭分别具有明确责任与验收出口。B 的代码实施等待本文与[实现规划](B_静态数据并行统一实现规划_20261031_第二轮.md)审核，C 至 E 分别负责运行快照、策略评估和动态控制。

未决问题：性能倍数、生产哈希连接和 CPN 正文范围等待 sxing 决定。基线额度保持、真实计数只记录及本地验收接口按本文方案提交 sxing 复审，B 代码实施等待文档审核。

## 查询拆分的背景

一条查询可以让多个执行分支读取不同设备或时间范围，但每行必须恰好读取一次。需要整体有序的查询还必须按完整排序条件合并结果。资源申请失败、查询取消或驱动创建失败后，系统必须释放已经建立的队列和算子。

例如，六台设备各有三个时间分区，扫描范围包含十八个设备与分区组合。并行分支的读取范围合起来必须覆盖这十八个组合，每个组合只能出现一次。仅检查输出行数无法识别一处漏读与另一处重复读取相互抵消的错误。

数据来源：代码位于 sc01 `/root/iotdb`，分支为 `feat/next-p0`，基线提交为 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`，下文简称 A 发布基线，A 的通过证据见[A 验收结果](A_属性框架验收结果_20261028.md)。

## 术语与范围

扫描源是一个物理扫描节点承担的读取工作。流水线是同一驱动连续执行的一组算子。驱动是参与执行调度的运行对象。片段实例是分布式查询在一个节点上的一次片段执行，下文统一称片段实例。

工作单元是规划时分配给某条扫描流水线的设备子集与时间分区子集。并行度是拆分计算使用的分支数量目标，代码沿用 Degree of Parallelism 的缩写 DOP。B 首版保持执行上下文传入的每扫描源 DOP 语义，父级流水线拆分可能调整该输入。

例如，一个扫描源的输入 DOP 为四时，它最多生成四条扫描子流水线，根合并流水线另外存在。一个片段实例若含两个扫描源，实际驱动数量还取决于父级拆分、流水线依赖和根驱动。验收必须分别报告扫描子流水线数和实际驱动总数。

B 首版统一已有三条路径及直接过滤融合入口，并保留串行路径。资源登记同时接入表模型、树模型与 schema 模型查询使用的通用交换构建，影响全部这些路径的限额计算、登记和失败清理。无扫描拆分的查询同样受兼容性测试约束。单设备多分区扩展、任意投影融合、全片段硬 DOP 限制和执行中重新分配留待独立方案。B 使用 A 输出的扫描资格，A 负责分布式属性判定，B 负责本地执行构造。

数据来源：执行上下文的 `getDegreeOfParallelism` 与 `setDegreeOfParallelism`、通用生成器的 `dealWithConsumeAllChildrenPipelineBreaker`、本地规划器的 `plan` 共同决定驱动结构，三者位于 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/`。

## A 发布基线的执行路径

已有实现覆盖三种扫描构建形态，B 要统一它们的公共步骤。源码事实与拟新增行为分别标注，源码核查本身只证明入口与条件。

### 无序设备扫描

已有入口先检查规划器允许并行、上下文 DOP、设备列表、设备溢写状态和下推限制，再把设备分成连续的近等量组。每组使用独立子上下文、扫描算子和本地队列，父流水线使用 Collect 收集输出。全局下推 limit 或 offset 会使该入口退回既有扫描，按设备下推 limit 沿用既有判断。

例如，八台设备、DOP 为四时，分组各含两台设备。两台设备、DOP 为八时，最多产生两条扫描子流水线。单台设备沿用串行入口，即使它具有多个时间分区。

数据来源：`DataNodeTableOperatorGenerator.java` 的 `visitDeviceTableScan`、`canSplitDeviceTableScanIntoParallelPipelines`、`canSplitDeviceTableScanIntoParallelPipelinesIgnoringOrder`、`constructParallelDeviceScan`，符号定位与源码 SHA 固定于本文末节的核查清单。

### 时间分区工作单元

已有时间分区入口在设备拆分资格成立后，要求真实数据区域、功能开关开启且分区数大于一。它先决定目标分支数，再把分区和设备分别分组，使用两组列表的笛卡尔积建立流水线。目标分支数仍受设备数限制。

例如，六台设备、三个分区、DOP 为四，目标数为四。现有公式产生三个分区组和一个设备组，因此实际产生三条子流水线。六台设备、两个分区、DOP 为六时，两个分区组与三个设备组产生六条子流水线。

已有字节权重策略在规划前读取 TsFile 元数据，按大小降序分配到累计字节最少的分区组，同值使用确定的顺序。元数据缺失时使用连续的等数量分组。B 保留这两种静态策略，元数据字节数只作为估计值。

例如，三个不可拆分区的估计大小为 100、10、10 MiB，两组分配得到 100 MiB 与 20 MiB。因为最大的分区保持完整，这个策略仍可能保留负载差异，性能效果由 D 的矩阵验收。

数据来源：`DataNodeTableOperatorGenerator.java` 的 `constructParallelDeviceTableScan`、`constructParallelDeviceTpMorselScan`、`partitionIntoGroups`、`partitionTimePartitionsBySize` 和 `annotateTimePartitionMorsel`，区域文件对 DOP 的大小估计覆盖全部区域文件，未按查询时间条件裁剪。

### 有序扫描与过滤融合

已有有序入口只处理紧邻设备扫描的排序节点，并检查自然顺序是否满足完整排序条件。每台设备建立独立扫描，组内先合并排序，组间再合并排序。B 必须保留这两层结构。

无序路径在共同基础条件上额外要求扫描许可位为真。有序路径使用共同基础条件和完整排序证明，许可位可以为假。直接过滤融合使用无序路径的完整资格。

例如，排序保留在扫描上方时，扫描许可位可以为假，但有效自然顺序仍允许有序两层合并。若把无序许可位直接加到该入口，已有有序优化可能被错误退回，B 的测试必须识别这一差异。

例如，两台设备分别返回时间 1、3 和时间 2、4。按设备拼接会产生 1、3、2、4，无法满足时间升序。两层合并排序必须产生 1、2、3、4，并按完整比较器处理相同时间的其他排序键。

已有直接过滤融合入口要求过滤节点的直接子节点为设备扫描，并复用无序拆分资格。它还检查时间分区开关、真实数据区域、多个分区及谓词内没有 diff 函数。B 首版保持这些实际条件，过滤算子构造继续复用原表达式执行逻辑。

例如，过滤条件保留十八个设备与分区组合中值大于十的行，分组覆盖仍针对原十八个组合检查，输出再按过滤后的独立预期检查。带 diff 的谓词使用原执行入口，避免跨分支状态改变结果。

数据来源：`DataNodeTableOperatorGenerator.java` 的 `visitSort`、`visitStreamSort`、`constructParallelOrderedDeviceTableScan`、`isNaturallyMergeableDeviceScanOrder`、`canPushTransparentFilterIntoParallelMorsels` 与 `constructTransparentMorselFilter`。

## 拆分计算与不可变描述

B 拟新增不分配执行资源的拆分计算组件，由它一次性产出不可变描述。描述包含扫描模式、输入 DOP、目标分支数、实际分组、排序要求、过滤融合模式和确定的退回原因。描述只保存计划所需的数据快照，禁止持有可变执行上下文。

输入在单次扫描入口、创建任何子上下文前由调用方采集一次。快照必须包含允许无序并行标记、设备溢写句柄是否存在、上下文 DOP 和入口模式。其余输入包含设备顺序、分区 ID、数据区域类型、原 limit 与 offset、按设备限制标记、过滤形态、分区间隔和时间精度。可选区域文件大小、分区权重、开关值和完整排序证明也在此时冻结。设备列表复制为不可修改的列表，分区 ID 排序并检查重复。描述使用快照内的稳定设备序号，执行器在克隆扫描节点时解析设备对象。

例如，规划描述含设备序号 0 至 5 时，之后修改调用者的列表不能改变六个序号的分组结果。空设备列表沿用串行路径构造 TableScanOperator。发现重复分区 ID 时，规划器必须在资源构造前拒绝该描述并记录原因。

原因枚举区分串行条件、元数据不完整和构造错误。元数据不完整允许使用等数量分组。资格不足允许使用原串行入口。资源建立后的异常使整个片段实例失败，并由统一清理负责释放资源。

数据来源与拟新增接口：在 planner 包下新增 `ScanParallelPlan.java` 与 `ScanParallelPlanner.java`，主接口为 `plan(input)`，输出模式为 `SERIAL`、`DEVICE`、`TIME_PARTITION`、`ORDERED`，退回原因作为该描述的嵌套枚举，避免与 A 的 `FallbackReason` 混用。

## 覆盖、谓词与排序约束

拆分描述必须同时满足完整覆盖和分组互斥，执行构造必须保留源扫描的语义字段。设备组拼接必须等于输入设备序列，分区组的并集必须等于输入分区集合。任意两个不同分组的同轴交集必须为空。

例如，设备组为三台加三台、分区组为两个加一个时，四个矩形共覆盖十八个组合。若一个分区同时出现在两个分区组，则至少六个组合被重复读取，纯描述测试必须拒绝。

每条子扫描必须从原节点克隆，只改物理 ID、设备子集与新增时间条件。新增条件与原时间条件取逻辑与，同一工作单元内多个分区的范围取逻辑或。TopK 运行过滤关联、类型、列映射和方向继续来自原克隆节点及既有参数构造。

例如，分区覆盖时间从零到一百，原查询要求时间从二十到八十，实际子扫描只能读取二十到八十。B 必须针对端点、负时间、时间别名和 long 边界验证范围，保留时间精度与分区间隔的真实绑定。

基线范围助手使用半开区间，最终上界采用饱和相加。B 必须用独立范围预期检查最大时间戳是否属于可读域。遇到无法无损表达的边界时，拆分计算必须在建资源前退回原扫描，并记录边界原因。

有序模式必须证明每个输入流按完整比较器有序。原扫描资格、方向、空值顺序和所有排序键共同决定证明。缺少证明时，入口使用原 Sort 或 StreamSort 路径。

例如，需要先按设备标签再按时间升序时，比较器必须同时包含两列。时间放在中间、字段参与自然顺序推断或列映射缺失时，使用基线的保守路径。

数据来源：现有 `cloneSubScanNode`、`requireTimeColumnName`、`buildTimePartitionRangePredicate` 和自然顺序守卫位于 `DataNodeTableOperatorGenerator.java`，B 拟将纯分组和范围计算移入 `ScanParallelPlanner.java`，节点克隆及表达式绑定保留在生成器侧。

## 公共流水线构建

B 拟新增公共构建器，集中管理子上下文、扫描根算子、本地交换、内存估计和工厂登记。三种模式只提供各自的扫描根构造与父合并方式。无序模式使用 Collect，有序模式使用完整比较器的两层合并排序。

构建器必须把创建与登记交错执行，每次创建返回后、下一次可能抛异常的动作之前完成登记。创建子上下文后登记上下文归属，克隆节点后保留字段快照，创建扫描算子后立即登记独立关闭根。组装过滤或合并父算子后，立即完成子根向父根的责任移交。

交换工厂必须在队列构造后、初始化动作前登记队列，并在 sink 构造后、返回调用方前登记端点。source 构造返回后立即登记端点和额度身份，随后才能建立 ExchangeOperator。内存估计构造后立即登记父关系，工厂构造后立即登记未消费状态，再追加到共享列表。

队列与 sink 在基线工厂内部一起创建，调用方只能看见返回的 sink。B 必须增加接受登记回调的生产重载，把登记放到工厂内部的对应创建点。上下文、克隆节点和估计属于结构记录，清理只移除其关系，禁止为普通数据对象伪造 close 操作。

例如，第三条子流水线建立交换源时抛异常，前两条与第三条已建的队列、sink 和扫描根必须全部进入清理。独立关闭根、端点与队列分别核对一次有效关闭转换，包装层对同一队列的重复 abort 调用由幂等状态处理。此时片段实例报告失败，禁止在半成品上再构造串行计划。

流水线与算子 ID 继续使用上下文共享的计数器，物理扫描 ID 由源节点 ID、模式和组序号确定。内存估计仍关联父计划节点，依赖索引继续沿用通用生成器规则。根工厂必须保留在工厂列表最后，供片段管理器取得最终 sink。

首版必须保留三条路径已有的物理 ID 后缀形式，保证已有解释解析器可以定位工作单元。新增静态字段补充原始源节点关联，禁止仅依赖字符串拆分推断运行对象身份。

例如，四条扫描子流水线与一条根流水线具有五个不同流水线 ID。两个源节点即使组序号相同，物理扫描 ID 也必须不同。测试应当同时检查对象身份、父关系和工厂顺序。

数据来源与拟新增接口：新增 `LocalScanPipelineBuilder.java`，提供 `build(plan, context, operatorFactory)`，接入点为 `DataNodeTableOperatorGenerator.java` 的三种构建方法，公共状态位于 `LocalExecutionPlanContext.java`。

## 交换资源与限额

B 使用共享登记表记录真实资源身份，并按真实数量计算诊断分配目标。每个对象的有效申请额度沿用 A 发布基线在同形态、同配置下的最终值。额度发布保持本片段基线最终值，跨片段共享队列按双方基线收紧值生效。局部规划计数继续服务原父子流水线算法。

### 对象身份与内存记账

登记表按本地共享队列、远端 SourceHandle 和远端 SinkChannel 的对象身份去重。多桶 sink 必须展开各个 channel，同队列的 source 与 sink 在片段内只计一次。跨片段队列在两侧登记资源关联，物理队列在节点观测中只计一次。

例如，四条本地流水线、一条远端输入和两个各含一条远端 channel 的输出共登记七个对象。若两个输出各含三条 channel，则真实对象数为十一。两层包装指向同一队列时，该队列在本片段的真实对象数仍为一。

共享队列的内存记账键固定为生产方的查询 ID、片段实例 ID 和源计划节点 ID。同节点跨片段路径中，这些值属于上游生产片段。实际执行 new Queue 的一方可以是下游接收方，分配对象的调用方与记账归属必须分别记录。

例如，上游片段 A 的 sink 节点 S 向下游片段 B 发送数据，即使 B 先创建共享队列，键仍为该查询、A、S。两端分别登记 A 的 sink 与 B 的 source，预留只记到 A 的账户。B 首版保留这种归属，只补读取、观测和清理顺序验证。

本地扫描的 source 与 sink 包装层可以没有片段标识。记账键必须由共享队列的新增生产 getter 返回，禁止从这些包装层的 nullable 字段推断。getter 返回不可变字符串记录，创建时快照三个真实记账参数，不暴露可变 Thrift 对象。

例如，四条本地扫描流水线的包装层片段字段均为空，四个队列仍必须返回四条非空、与实际 reserve 调用一致的键。测试必须同时证明 getter 值与真实内存池映射对应。

内存池在 query 和片段之内按 planNodeId 累计对象预留，并对整个交换内存池执行总量约束。一个多通道 sink 的通道共用它的本地 planNodeId。通道对象数量、唯一记账键数量与实际预留字节必须分别核对。

例如，全池余量充足时，两个远端 channel 共用一个记账键，额度为 1 MiB，各申请 600 KiB。第二笔因累计 1200 KiB 超过键额度而等待。真实对象数为二、键数为一，实际预留只能按唯一键累加一次。

数据来源与拟新增入口：`MPPDataExchangeManager.createLocalSinkChannel`、`createLocalSourceHandleForFragment`，`SharedTsBlockQueue` 的三个私有记账字段及 `add`。拟新增 `SharedTsBlockQueue.MemoryReservationKey` 嵌套不可变记录及 `getMemoryReservationKey`，字段为 `queryId`、`fragmentInstanceId`、`planNodeId`，其中片段字符串来自 `fullFragmentInstanceId`。

数据来源：预留由 `MemoryPool.reserveWithPriority`、`tryReserve` 执行。对象枚举由 `ISinkHandle.getChannel`、`IChannelRoutingSinkHandle.getChannelCount` 与 `LocalSourceHandle.getSharedTsBlockQueue` 提供。

### 分配目标与兼容下限

首版保留每个对象的基线最终额度，真实对象计数只计算并记录诊断分配目标。兼容下限仍表示基线生效额度，实际发布就取这个值。发布沿用单调收紧，禁止根据诊断目标扩大或缩小已有合法申请域。

分配目标按片段配置预算除以真实对象数向下取整。单扫描三种拆分路径的真实队列数等于相应局部增量，多桶 sink 展开后数量大于或等于原 sink 计数，因此这些形态的目标不高于兼容下限。通用生成器还会复制、恢复和取局部计数最大值，其组合形态继续逐项冻结，首版对任何比较结果都保持基线额度。

例如，堆上限为 2 GiB、查询线程数为 32，默认配置公式得到片段预算 4,022,509 字节。一个 32 通道的纯 sink 形态，其基线局部计数为一，真实对象数为 32、记账键数为一。诊断分配目标必须为 125,703 字节，生效申请额度仍为 4,022,509 字节。

这个数值例子只在上述配置下成立，服务验收必须记录实际加载的预算。把 32 个通道误计为一仍可能得到正确的生效额度，所以额度相等断言只能证明兼容。对象身份集合、对象数、键数与诊断目标必须有独立断言。

对象数为零时，分配目标记录为不适用，禁止除零。预算为非正数时，规划必须明确失败。正预算产生零字节诊断目标时，实际额度仍用基线值，禁止把零目标发布给对象。

例如，预算为三字节、纯 sink 有四个通道时，目标为零，基线额度仍为三字节。一字节单块继续通过原参数校验，是否合法累计预留由原记账键额度决定。

首版真实计数的收益是准确对应对象、记账键与诊断目标，并为后续资源分配提供可验证输入。B 的验收结论覆盖构建与正确性，配额收紧收益保持待设计。配置预算继续作为既有分配输入和单次申请上限，严格片段总量预留需要独立方案。

数据来源与拟新增记录：`LocalExecutionResourceRegistry` 保存 `nominalShareBytes`、`legacyCapBytes`、`effectiveRequestBytes`、`memoryAccountKey` 与 `quotaPolicy`，首版策略为 `LEGACY_COMPATIBILITY`。预算公式位于 `DataNodeMemoryConfig.maxBytesPerFragmentInstance`，B0 保存原计数、全部限额调用和最终对象值。

### 限额应用与并发

B 必须在原 setter 调用点记录原额度及作用对象，把本片段的基线额度应用集中到最终冻结。原局部计数及其保存恢复保持原语义，不能直接改成共享原子整数。基线原调用清单必须覆盖早期 sink、远端 source、最终 ExchangeOperator 遍历及普通本地 source 的空 setter。

冻结发生在完整算子树建成后、本片段驱动开始前，额度只能发布一次，冻结后登记新对象必须明确失败。共享队列在另一片段已经使用时，冻结遵守单调收紧，保留在途缓冲与已有 future 的原申请条件。B 禁止在此处回收在途数据，验收必须覆盖两片段不同冻结顺序和最终进展。

例如，两侧基线额度分别为 8 MiB 和 4 MiB，B 两侧分别发布相同的基线值。实际队列最终为 4 MiB。原子收紧只固定并发写入的最小结果，禁止把它解释成新增配额策略。

队列使用同一个原子数保存额度，更新执行原子的取最小操作，读取使用该原子数。流水线 source 与本地 sink 直接委托这一操作，自身移除读后判断。登记表对普通本地 source 必须取得实际队列，禁止依赖它的空 setter。

例如，原额度为 16 MiB，两个线程分别通过流水线 source 和本地 sink 申请 8 MiB 与 4 MiB。最终必须为 4 MiB，读线程必须看到该值。双线程测试还必须分别直接通过队列、source 和 sink 执行相同检查。

数据来源与拟新增接口：`registerSource`、`registerSink`、`recordLegacyLimit`、`freezeAndApplyLimits`。修改 `SharedTsBlockQueue` 的额度字段、getter 和 setter，`PipelineSourceHandle.setMaxBytesCanReserve` 与 `LocalSinkChannel.setMaxBytesCanReserve` 直接委托，`SourceHandle` 与 `SinkChannel` 的发布与读路径按各自同步规则验证。

### 多通道轮询门限

B 首版冻结并记录轮询策略的基线门限，保持原通道选择结果。硬预留由 channel 与内存池约束，轮询门限只决定 SIMPLE_ROUND_ROBIN 尝试切换到哪条通道。PLAIN 与哈希显式选桶继续使用各自入口。

基线门限在 sink 构造时计算，使用构造时完整片段预算，先整数除以通道数再乘三。后续规划发布的句柄额度不改变这个门限。B 必须分别保存构造门限与最终申请额度，禁止从最终句柄额度反推构造值。

例如，堆为 2 GiB、查询线程数为 32 时，预算为 4,022,509 字节。四个通道的基线轮询门限为 3,016,881 字节，同片段另有四条扫描流水线时，原局部计数为五，最终句柄额度为 804,501 字节。两个数分别控制选路与预留，B 保持这两个原值。

同一预算下，32 个通道的基线轮询门限为 377,109 字节。该门限可能高于或低于某条通道的最终额度，首版验收按各自基线值分别比较，禁止增加两者必须相等或门限必须更小的约束。

轮询按原循环顺序寻找满足缓冲字节门限、缓冲块数小于三且有效的其他通道。没有其他通道满足条件时，策略必须保留原下标。B 必须用相同受控缓冲状态序列对比冻结基线与候选的每次选路、发送序列和每通道发送计数。

例如，四个通道的下一候选均不满足条件时，两侧都保持通道零。依次释放通道一和通道二后，两侧应当产生相同的切换序列。计数一致与消费后有进展共同验证策略保持，机器吞吐倍数由 D 单独测量。

数据来源与拟新增接口：`ShuffleSinkHandle` 的额度初值、构造函数、`SimpleRoundRobinStrategy.channelMemoryThreshold`、`shuffle` 与 `satisfy`。冻结接口拟为 `freezeLegacyChannelLimits`，只核查并记录构造门限和基线额度，保留 `sendToChannel` 与 `isAllChannelsNotFull` 的合同。

### 申请异常与等待

单块申请大于对象额度或大于片段单次申请上限时，内存池抛 IllegalArgumentException，查询失败。单块合法但累计键额度或全池余量不足时，普通查询进入异步等待。最高优先级的零预留豁免只作用于后一个分支，单块校验继续执行。

例如，采用本节前述堆为 2 GiB、查询线程数为 32 的预算配置，故障额度 125,703 字节无法接受 163,840 字节的单块，会在预留前抛异常。基线额度 4,022,509 字节允许该块通过单块校验，后续是否等待由累计使用量决定。B 必须保持基线额度以避免新增第一种回归，并用故障副本验证异常清理。

数据来源：`MemoryPool.reserveWithPriority` 的参数校验、`tryReserve`、`rollbackReserve`。全局算子内存由 `LocalExecutionPlanner.checkMemory` 单独管理。

## 内存准入与失败清理

B 保留完整算子树的单次全局内存准入，并补齐准入前后的清理责任。构建完成后先冻结真实交换对象，再构造完整内存估计，随后沿用本地规划器的全局申请。读取剩余内存只提供诊断，申请返回值决定准入结果。

例如，完整估计为 96 MiB，全局只剩 64 MiB，普通查询必须申请失败并释放全部规划资源。最高优先级查询按已有规则可能返回零预留，此时记录零预留和豁免原因。两类路径分别验收。

data 与 schema 两条执行入口都按同一协议管理关闭槽。规划阶段由资源登记表拥有新建算子和本地交换，驱动创建阶段逐个移交所有权，运行阶段由现有驱动生命周期关闭算子。登记表必须区分用于限额的对象与用于清理的对象，跨片段队列不能因去重而丢失端点的失败通知。

新建算子暂时作为独立关闭根登记，挂到父算子后由父根承担子树关闭责任，登记表同时撤销子根的独立关闭项。交换端点单独保留中止责任，并使用幂等状态保护回调。这样既覆盖构造中途失败，也避免对同一子树重复递归关闭。

例如，两个扫描挂入同一个组内合并算子后，规划清理只关闭这个合并根，由它关闭两个扫描。若第二个扫描尚未挂入就抛异常，登记表分别关闭已经存在的独立根。

驱动创建、工厂消费和所有权移交必须处于同一受保护的阶段。创建循环开始前必须初始化关闭计数，每个工厂占一个关闭槽。未创建槽由幂等工厂关闭入口完成，已建驱动槽只由驱动实际销毁完成，禁止在失败工厂数上永久等待。取消先标记片段终态，创建循环每次移交前检查终态，已创建但尚未移交的驱动由创建循环负责关闭。B 必须用可控并发测试覆盖取消发生在构造返回与移交之间的情况。

第二个驱动工厂失败时，片段管理器必须关闭第一个已成功创建的驱动，并释放尚未移交的工厂资源。当前工厂的失败关闭继续保留，所有关闭操作必须幂等，附加关闭异常必须保留为原始异常的 suppressed 信息。原全局预留继续由片段终态监听释放，监听必须以一次性状态保护实际 release，禁止额外重复释放。关闭、取消与登记表移交之间必须建立同一状态转换协议。

例如，三个工厂中第二个构造失败，系统必须关闭第一个驱动、第二个已建算子以及第三个未消费工厂。重复取消后，交换预留和算子预留均必须回到基线值，原构造异常仍是主异常。

调度启动前遇到取消时，所有权移交必须拒绝继续创建驱动。调度提交抛异常时，片段管理器沿同一清理入口处理。已经运行的驱动继续按现有取消和关闭协议释放资源。

数据来源与拟新增接口：`FragmentInstanceContext.allDriversClosed`、`initializeNumOfDrivers`、`decrementNumOfUnClosedDriver` 与 `releaseResourceWhenAllDriversAreClosed` 是关闭计数和等待点。`DataDriver.releaseResource` 与 `SchemaDriver.releaseResource` 递减计数，`LocalExecutionPlanner.plan` 与 `checkMemory`、`PipelineDriverFactory.createDriver`、`FragmentInstanceManager.execDataQueryFragmentInstance`、`execSchemaQueryFragmentInstance` 与 `clearFIRelatedResources`、`MPPDataExchangeManager.forceDeregisterFragmentInstance`，新增登记表的 `abortUntransferred` 与 `transferToDriver` 管理移交，现有全局交换注销只覆盖其登记对象，本地流水线资源由新登记表补齐。

## 配置与估计边界

B 首版沿用 A 发布基线的配置项及默认值，并在一次扫描拆分开始时读取快照。区域文件大小对 DOP 的估计仅能缩小扫描分支目标。估计缺失时使用已有设备数量上限。

源码默认值为 DOP 取可用处理器数的一半且最小为一，由区域文件大小估算扫描分支数的功能关闭，时间分区拆分关闭，有序并行扫描关闭，按分区大小加权分组开启。按分区大小加权分组只有在分区拆分入口启用且元数据完整时生效。

例如，区域估计为 256 MiB，既有每驱动目标为 128 MiB，区域文件大小对 DOP 的估计提出两条分支。若设备数为八、输入 DOP 为四，最终目标收紧为二。若元数据缺失，则目标保持四。

区域文件大小对 DOP 的估计必须检查负大小、使用饱和加法，并用整数商与余数完成向上取整，随后按 DOP 和设备上限收紧。空文件列表、缺失元数据和负文件大小输出元数据无效原因，并保持原设备上限。合法零字节文件仍按原规则产生至少一个目标分支。

设备数与分区数的乘积必须先用 long 计算，再按正数 DOP 上限收紧。已有分区字节加权路径的饱和累加与负值退回继续保留，只提取它的纯分配部分。区域文件估计与目标分支乘法的纯部分由 B1 一并提取。

例如，两份大小接近 long 最大值的文件相加后必须饱和，禁止变为负数。纯计算测试可以构造十万设备与十万分区的数量输入，结果仍受 DOP 限制，计算过程不能分配百亿个工作单元。

数据来源：`IoTDBConfig.java` 与 `IoTDBDescriptor.java`，配置键为 `degree_of_query_parallelism`、`enable_dop_estimation`、`enable_timepartition_morsel`、`enable_timepartition_morsel_size_weighting`、`enable_ordered_parallel_scan`，两项大小相关开关依次控制区域文件对 DOP 的估计和分区大小加权分组，估计常量为 `TARGET_BYTES_PER_SCAN_DRIVER`。修改承载点为 `estimatePipelineNumByDataSize`、`decideParallelScanPipelineNum` 与 `constructParallelDeviceTpMorselScan` 的纯算术部分，B 首版不新增配置键。

B 复用算子统计的记录和导出通道，仅补充静态构建信息。CPU 时间、输出行数、TsBlock 数和已存在的工作单元信息继续由原采集点提供。驱动墙钟时间沿用 A 验证过的完成记录入口及幂等写入规则。

## 正确性验收与发布边界

B 的通过条件同时覆盖纯计算、真实构造、资源故障、完整模块和双节点查询。纯计算断言检查独立预期覆盖，真实构造断言检查扫描字段、工厂次序、估计父关系和比较器。资源故障必须证明关闭通知、计数和预留全部恢复。

例如，故意让两个分组重复一个分区，覆盖断言必须失败。故意遗漏一个本地队列登记，最终资源计数断言必须失败。故意跳过首个已建驱动的关闭，故障注入的资源归零断言必须失败。

双节点验收分别运行候选配置、DOP 为一的对照和确定性预期。无序查询比较保留类型与 null 的完整结果多重集及规范化 SHA，有序查询额外比较完整行序列。候选必须证明实际产生多个扫描驱动，防止串行退回形成假通过。

例如，两个来源各有重复键时，完整多重集可识别重复数差异。相同多重集对应两种行序列时，有序查询必须拒绝其中乱序的一种。所有原始观测、失败输出和实际加载身份必须保留。
