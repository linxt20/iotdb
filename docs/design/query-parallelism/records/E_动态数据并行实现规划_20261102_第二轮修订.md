# E 动态数据并行实现规划

目的：将 E 设计拆成 E0 至 E5 实施步骤，并固定生产调用位置、文件改动、单元测试和机器验收证据。

摘要：E 需要把已完成扫描的反馈送到下一片段规划之前。实施先增加身份和规划期读取入口，再接历史成本与纯策略。协议传输、单次准入和决策回执随后接入。最后用单节点、双节点和完整 DataNode 套件验证。

结论：E0 至 E5 为待实施任务，每步必须具备生产调用、正反测试和版本身份。实施边界和完成判据以本规划为准。A–D 的前置验收与冻结生产版本统一见 [A–D 完整核查](A-D_完整实现补全核查_20261102.md)，运行工具按独立覆盖文件清单核对。

## 未决问题

- hash join 是否进入生产规划路径，等 sxing 决定。
- CPN 是否进入论文正文，等 sxing 决定。
- 性能口径采用 3.33 倍还是 2.95 倍，等 sxing 决定。

## 实施范围

本规划只实现下一片段的扫描计划调整。E 使用冻结运行反馈，禁止迁移运行中的驱动。没有扫描任务的根片段保持其拓扑身份，禁止把其零扫描并行度当作串行扫描。验收必须区分设计对象、编译通过和真实运行结果。

例如，下一片段尚未建立交换端点时，可以把十二个工作单元改分为三个桶。前一片段已有队列数据时，其归属保持原值。

数据来源：对应 [E 设计](E_动态数据并行设计_20261102_第二轮修订.md)。工程根为 sc01 `/root/iotdb`，分支为 `feat/next-p0`。固定基线为 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`。

E 的前置版本使用最终冻结源码及其发行包。核心、RPC、单源三十二桶、一般资源与真实数据非法块已有同版运行证据。无序收集与受检内存估计已接入表模型，候选大输入通过仅覆盖活性。原八项反证已完成组件身份与变动生成器的适用性审核。完整模块与补充边界均已完成同版独立终态审核。前置状态统一见 [A–D 原合同与证据](A-D_完整实现补全核查_20261102.md#原合同与证据)，原因语义沿用 [D 原因分类](D_静态数据并行设计_20261101.md#退回原因)。本文的反馈历史、生产配对、策略和回执属于 E 待实施范围。

数据来源：[A–D 原合同与证据](A-D_完整实现补全核查_20261102.md#原合同与证据) 保存前置范围与权威回执。研究验收工具 r14 单独绑定版本，其源码身份与生产构建 manifest 分别记录。

## E0 输入、身份与生产入口

E0 建立规划服务和不可变身份，先用无反馈分支接入生产路径。服务在算子构造前返回只读输入。历史为空时必须返回 D 的静态选择。

### 新增文件

- `plan/planner/DynamicQueryShape.java` 保存扫描语义并计算规范校验和。
- `plan/planner/DynamicWorkUnitKey.java` 保存区域、设备值和分区身份。
- `plan/planner/DynamicDriverBucketAssignment.java` 保存实际驱动与扫描桶配对。
- `plan/planner/DynamicParallelScheduleInput.java` 复制配置、身份和反馈。
- `plan/planner/DynamicParallelScheduleDecision.java` 保存动作、目标及原因。
- `plan/planner/DynamicParallelPlanningService.java` 提供规划期 prepare 入口。
- `statistics/snapshot/DynamicSnapshotHistoryStore.java` 提供冻结响应存取接口。
- `statistics/snapshot/DynamicSnapshotRecord.java` 保存独立响应副本与发布范围。

以上相对路径都位于 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/`。

### 修改文件与处理

本地规划器必须在生成算子前调用规划服务。调用先提取扫描语义，再读取历史响应。服务按来源查询分组，逐组适配并合并，最后构造只读视图。E0 使用可注入的空存储实现生产接线。准备结果按源扫描 ID 分别保存到本地规划上下文。后续扫描入口只读取自己的决策，禁止最后一个源覆盖其他源。

接收适配器必须验证驱动的完整查询归属。旧响应缺少配对时，样本保持不支持。重复桶只在同一源内拒绝，两个源可以分别有桶零。同一驱动可以传输两个源归属，其计数与墙钟只能读取一次。

数据来源：修改 `plan/planner/LocalExecutionPlanner.java` 的 data `plan()`。视图构造写在 `DynamicParallelPlanningService.prepare()`。响应集合使用 `RuntimeSnapshotFetchResult`。合并使用其 `merge()`，视图构造使用 `new RuntimeSnapshotView(...)`。修改 `statistics/snapshot/RuntimeSnapshotAdapters.java` 和 `RuntimeSnapshotView.java`。`LocalExecutionPlanContext` 新增一次写入的不可变决策映射。关闭开关时使用空映射，并跳过历史读取。

### 单元测试与退出

E0 测试必须实际调用本地规划器，并确认服务发生在算子生成前。空历史与动态开关关闭都必须得到原静态计划。

例如，两条不同源各有桶零时输入有效。同一源两条驱动持有同一个工作单元时输入无效。

数据来源：规划入口测试为 `DynamicParallelPlanningServiceTest`。输入与身份测试为 `DynamicParallelScheduleInputValidityTest` 和 `DynamicParallelScheduleIdentityTest`。测试包含同驱动多源、串行源登记、扫描与合并根隔离、同表别名区分及跨查询语义键稳定。反向验证删除 prepare 调用，生产接线测试必须失败。

## E1 历史、差分与成本

E1 实现有界存储和历史估计。运行快照差分与跨查询成本匹配分别处理。

### 文件改动

- 实现 `statistics/snapshot/DynamicSnapshotHistoryStore.java` 的容量、过期和去重。
- 新增 `plan/planner/DynamicCostHistoryStore.java` 作为同一存储的成本视图。
- 新增 `plan/planner/DynamicBucketRuntime.java` 保存桶级反馈。
- 新增 `plan/planner/DynamicSnapshotAggregator.java` 校验并汇总配对反馈。
- 修改 `statistics/snapshot/RuntimeSnapshotDelta.java` 使用结构化驱动键。

### 存储与差分处理

存储复制响应后才对读取方发布。写入按运行身份去重。容量与过期值由设计的反馈保存一节定义，测试注入时钟。

差分检查同一运行和同一计划。差分同时覆盖行数、TsBlock、墙钟和样本代次。驱动增删、计数回退和计划变化时返回无效。不同运行的终态反馈只能经过语义键匹配进入成本视图。

例如，同一驱动从二十行增加到三十五行时，增量为十五。换成另一查询后，差分类必须拒绝。

### 成本处理

成本视图先过滤过期、端点不符和资格不全的记录。聚合器保留测量来源。同一驱动多源时先分摊总时间，禁止对每个源复制整份时间。缺少逐工作单元计时时，再按桶内工作量分摊。缺少历史时沿用 D 的文件大小或等量成本。

数据来源：复用 `StaticCostCalibrator` 的键过滤思路。`DynamicCostHistoryStore` 与响应存储共用容量，禁止建立第二份无界缓存。差分类禁止比较运行快照校验和是否相等。

### 单元测试与退出

注入固定时钟，分别超过条数、键数、字节数和保留时间。每次写入后，四类上界都必须成立。相同响应再次发布时，样本数保持不变。

发布记录使用规划时登记的预期片段集合。单片段反馈只按单片段范围合并，禁止声明整个查询完整。测试必须覆盖缺失的预期响应，禁止把返回键集合当作预期集合。

例如，容量为二时写入三个不同样本，只能保留后两个。桶成本为一百、两个工作量分别为一和三时，分摊为二十五和七十五。

数据来源：存储测试为 `DynamicSnapshotHistoryStoreTest` 和 `DynamicCostHistoryStoreTest`。聚合测试为 `DynamicSnapshotAggregatorTest`。扩展 `RuntimeSnapshotDeltaTest` 的代次、身份、计数回退和缺墙钟用例。

## E2 纯策略与不可变计划输入

E2 只计算下一片段计划，不创建驱动或交换资源。策略输入使用唯一的配置上界名称。

### 文件改动

- 新增 `plan/planner/DynamicParallelScheduler.java` 实现纯决策。
- 新增 `plan/planner/DynamicParallelPolicy.java` 保存阈值与冷却状态。
- 新增 `plan/planner/DynamicParallelDecisionReason.java` 定义可核对原因。
- 修改 `plan/planner/ScanParallelPlanner.java` 增加不可变拷贝方法。

### 处理

计划输入增加带并行度的拷贝方法。该方法复制完整输入，三种构造入口仍汇合到完整构造器。读取 DOP 的三个位置继续读取同一 final 字段。策略根据历史成本生成设备或时间分区的稳定成本输入。

动态计划可以改变下一片段的桶归属。它必须经过 D 的属性守卫与覆盖检查。相同输入按成本降序、稳定语义键和桶编号打破平局。

数据来源：新增 `ScanParallelPlanner.Input.withDop(int)`，禁止增加 setter。配置取自 `LocalExecutionPlanContext.getDegreeOfParallelism()`，名称为 `inputDop`。目标公式、四个动作和数值算例统一由设计的并行度与动作一节定义。

### 单元测试与退出

策略测试必须覆盖阈值两侧、首次样本、同向第二次和三次冷却。并发请求必须得到不同检查序号。

例如，两次成本比均为六时，第二次可以重分组。比值为一点二时，策略必须保持静态计划。

数据来源：策略与滞回测试为 `DynamicParallelSchedulerTest` 和 `DynamicParallelHysteresisTest`。确定性与属性测试为 `DynamicParallelLptDeterminismTest` 和 `DynamicParallelPropertyGateTest`。所有测试使用固定快照，禁止依赖实时墙钟波动。

## E3 协议、发布与单次准入

E3 将配对写入真实驱动快照，并建立普通查询的冻结反馈发布。每个片段只为选定计划执行一次真实准入。

### 协议与生产写入

驱动协议新增可选配对列表，每项包含源扫描、扫描桶及工作单元。并行构建器登记实际扫描流水线，串行扫描入口登记当前驱动上下文。根 factory 加入后，规划器统一校验全部归属。冻结方法按真实流水线键查找列表，并补入实际任务身份。配对的桶编号读取各源原始扫描计划，D 的片段级全局展示编号继续独立保留。

旧节点缺少这些字段时，适配器保留运行统计，但拒绝动态成本使用。合并驱动缺少扫描归属时保持字段缺失。

数据来源：修改 `iotdb-protocol/thrift-datanode/src/main/thrift/datanode.thrift`。新增 `TDriverBucketAssignment`，源与桶字段为 sourcePlanNodeId 和 bucketId。工作集合字段为 workUnitIds。`TDriverRuntimeSnapshot` 新增 optional `list<TDriverBucketAssignment> scanAssignments`。修改 `DataNodeTableOperatorGenerator` 与 `LocalScanPipelineBuilder` 的扫描登记。修改 `LocalExecutionPlanner` 与 `FragmentInstanceContext` 的归属保存。冻结修改 `FragmentInstanceExecution.buildDriverSnapshots()`。外层实际驱动身份与条目源 ID 共同组成配对键。

### Java 值对象与版本校验

Java 驱动快照保存不可变配对列表，逐条复制工作集合后才发布。第二版快照校验和规范编码整个列表，缺失值使用明确标记。同一驱动的多个源禁止互相覆盖。第一版响应继续按 C 的算法校验，禁止重新解释桶零。

数据来源：值对象修改 `statistics/snapshot/DriverRuntimeSnapshot.java`。校验与接收修改 `RuntimeSnapshotChecksum.java` 和 `RuntimeSnapshotAdapters.java`。修改 `RuntimeSnapshotView.java` 暴露按源和驱动读取的配对。两个统计 Drawer 展示相同字段。

### 冻结发布

动态开关开启后，普通查询也在终态冻结统计。发布器保存响应副本，并记录冻结接收时间。发布发生在 C 的统计冻结完成后、驱动和上下文释放之前。发布器深拷贝响应后保存独立记录。发布失败只记录反馈错误，必须继续执行已有清理。查询清理删除 C 的上下文后，历史记录仍按 E 的容量和过期规则管理。

本地规划服务在下一次 prepare 调用里读取这些响应，构造只读视图。发布器和规划服务分别持有存储接口，禁止依赖 EXPLAIN ANALYZE 的渲染调用。

数据来源：新增 `statistics/snapshot/DynamicSnapshotPublisher.java`。修改 `FragmentInstanceExecution.initialize()` 的终态监听。配置新增默认关闭的 `enable_dynamic_scan_parallelism`。配置解析修改 `IoTDBConfig` 与 `IoTDBDescriptor`，并同步配置模板。

### 准入与回执

选定计划生成算子树后，沿用资源冻结和单次内存检查。成功后，回执定稿并进入驱动创建。失败后，管理器清理本次资源并保存拒绝回执。后续请求可以据此降低目标。

两个内存开关都关闭时，记录免检查原因。该路径的成功只表示允许执行。禁止把它当作内存上界测量。

例如，成功计划预留一百二十 MiB，生命周期结束释放一百二十 MiB。失败计划净预留为零。重复查看决策不得增加预留。

数据来源：`LocalExecutionPlanner.checkMemory()` 保持私有。修改 `FragmentInstanceManager` 的规划失败分支保存回执。新增 `DynamicDecisionReceipt`。多源回执按源扫描 ID 保存，准入状态属于整个片段。不存在候选 DOP 的多次预留试探。免检查原因使用 `CHECK_DISABLED`。最高优先级零预留原因使用 `HIGHEST_PRIORITY_ZERO_RESERVATION`。

### 单元测试与退出

真实生产快照测试必须检查协议往返、配对键和校验和。准入测试必须统计预留与释放次数，并验证失败后的下一请求降级。

数据来源：协议与准入测试为 `DynamicParallelTransportCompatibilityTest` 和 `DynamicParallelAdmissionTest`。生产快照测试为 `DynamicSnapshotProductionTest`。成功用例断言预留一次、释放一次，失败用例断言净预留为零。零预留例外分别核对两个明确原因。第一版往返必须保持原校验和，第二版更换任一配对字段必须改变校验和。同驱动两源往返必须保留两条配对，输入列表后续修改不能改变已冻结值。

## E4 片段边界与计划回执

E4 在新片段资源创建前使用已选决策，并冻结可重放的计划回执。运行中片段只读原计划。

### 修改文件

- `plan/planner/DynamicParallelPlanningService.java` 将决策交给 D 的纯 planner。
- `plan/planner/DataNodeTableOperatorGenerator.java` 在三类扫描入口使用选定计划。
- `execution/fragment/FragmentInstanceContext.java` 保存不可变决策回执。
- `statistics/FragmentInstanceStatisticsDrawer.java` 展示回执字段。
- `statistics/FragmentInstanceStatisticsJsonDrawer.java` 展示同一回执。

### 边界处理与测试

下一片段的工作单元全部参与纯分组。构建开始后，计划代次固定。取消、驱动关闭和交换注销继续按 B 的协议执行。真实查询终止经 `FragmentInstanceManager.cancelQuery()` 统一处理，本地终止器与 RPC 使用同一入口。尚未派发的生产者沿用真实取消上下文，查询终止同时移除共享查询映射，活动片段继续持有原对象。E 不得仅按已经创建的驱动枚举清理责任。B 的资源审计、原子队列额度及完整树发布继续复用，E4 只增加计划选择和回执。

例如，已提交片段保持四个桶，下一片段可以选择三个桶。重复读取前一个片段的回执仍必须得到四个桶。重复派发继续返回原有重复 RPC 错误，禁止重复预留。

数据来源：边界与回执测试为 `DynamicFragmentBoundaryTest` 和 `DynamicDecisionReceiptTest`。队列与生命周期测试为 `DynamicQueueOwnershipTest` 和 `DynamicPipelineLifecycleTest`。`PipelineDriverFactory` 和 `SharedTsBlockQueue` 作为回归对象，E4 对这两个文件没有生产改动。

## E5 机器验收

E5 绑定同一源码与发行依赖，分别验证策略动作、业务正确性和统计可用性。单元通过、文件校验和真实集群运行分别归档。

### 运行身份

启动前保存 HEAD、工作区源码 manifest 和查询形态。保存 launcher、fixture、查询及比较器的绝对路径和 SHA。server jar 与 Thrift jar 必须逐一对应构建产物。启动后保存实际 classpath、配置、进程和类来源。

例如，server 使用新字段而 Thrift jar 缺少该方法时，预检必须失败。禁止只替换 server jar 后执行验收。

数据来源：证据放在 sc01 `/root/property-e-artifacts/` 的独立运行目录。旧运行原件保留。执行入口必须通过 `sh /tmp/sc01exec.sh '远端命令'`。

### 单节点与双节点

单节点必须实际触发四个动作。每个动作都要保留输入反馈和独立预期。缺墙钟时，两侧都缺失才能采用行数与块数的降级比较。

双节点候选与对照使用相同 fixture 和查询。候选使用反馈策略，对照显式 DOP 为一。每侧必须核对实际 DataNode、fragment 和扫描驱动身份。

资源验收可以临时开启 B 的本地窗口，读取真实片段、对象、future 和注销回执。生产反馈由 C 的冻结响应发布，禁止把本地观察窗口当作历史服务。未开始规划的取消终结证据不构成驱动样本。`sharedQueryContextPresent` 只核查查询终止后的本地映射，不能代替 C 的冻结响应或 E 独立历史。

至少重复三轮完整查询。每轮先检查准入与快照资格，再比较完整结果多重集和规范 SHA。有序查询还必须比较完整行序列。任何一侧拒绝时，该轮业务等价验收失败。

例如，候选四条已配对扫描驱动各八行，对照一条三十二行时，应当比较扫描覆盖和业务行。合并根单独核对输出，禁止加进扫描覆盖。禁止逐驱动要求八等于三十二。两份运行快照校验和分别自校验，禁止跨侧要求相等。

数据来源：新增 E 专用验收 runner，复用 D 的隔离 launcher 和 JDBC 业务值编码。输出保存三轮回执、运行快照、计划身份、准入状态、canonical 结果和 SHA。

## 退出核对

E0 至 E5 各自产出要求对应测试日志、源码身份和生产运行证据。验收记录逐项链接证据，缺失项保持未完成。

- 输入和策略必须通过不可变、重复身份及确定性测试。
- 规划服务必须在算子创建前取得冻结反馈。
- 协议必须由真实生产写入方传输配对。
- 内存必须满足单次成功预留和一次释放。
- 四个动作必须在单节点和双节点证据中可回放。
- 三轮业务结果、计划覆盖和快照自校验必须通过。
- 完整 DataNode 套件必须完成并保留逐类报告。
- 架构测试必须从实际 classpath 读取所有生产包，禁止写死工程路径或缩小检查范围。

例如，六项有证据而一项缺失时，整体仍为未完成。文档中的设计决定不能替代运行回执。
