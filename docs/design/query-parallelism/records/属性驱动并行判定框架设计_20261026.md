# 属性驱动并行判定框架设计

> 编写日期：2026-10-26
> 适用代码基线：sc01 `/root/iotdb`，分支 `feat/next-p0`，HEAD `0ec0e02`
> 适用范围：大块任务 A，属性 enforcement 完整化

## 目的

本文定义 IoTDB 表模型查询中 required/provided 属性的统一语义、推导边界、enforcer 选择和 fallback 规则。本文先解决计划期契约，不实现静态 DOP、动态 DOP 或 hash join 生产路径。B 到 E 只读取 A 输出的契约，不重新推导“能不能并行”。

## 当前实现的准确边界

当前代码已经有一套可运行的窄框架，但它不是一个独立的通用 property engine：

- `PlanProperties` 包含 `DistributionProperty` 和可选 `OrderingScheme`，并提供 `satisfies()`。
- `DistributionProperty` 支持 `Single`、`Arbitrary`、`Partitioned(keys)`。
- `TableDistributedPlanGenerator.enforce()` 会根据 required/provided 选择 `CollectNode`、`SortNode` 或 `MergeSortNode`。
- `propertiesOf()` 目前主要根据子分支数量推导 `Single/Arbitrary`，ordering 从 `nodeOrderingMap` 读取。
- `allowParallelScanOn()` 通过 `DeviceTableScanNode.allowParallelScan` 向下标记 scan eligibility。
- `TableDistributedPlanner.appendRuleTrace()` 和 `recordRuleHit()` 提供诊断文本。
- `Partitioned(keys)` 的实际 consumer 主要是受限 GROUP BY 哈希路径；join 仍然是 merge-sort fallback。
- `AddExchangeNodes` 处理 fragment 层结构交换，不是一个通用的 property enforcer，不能与 `enforce()` 混为一层。

因此 A 的目标不是再加一个 flag，而是把这套已有逻辑拆成“属性计算、属性满足性、执行 enforcer、诊断记录”四个可测试部件。

## 设计原则

1. **提供属性只由子计划决定。** required 是父节点需求，不能反过来污染 provided。
2. **保守优先。** 无法证明属性满足时进入明确 fallback，不靠类名计数或隐式 visitor 顺序。
3. **诊断和执行分离。** rule trace 说明为什么选择某条路径，不能单独改变准入；真正的执行路径必须由 enforcer 结果和 plan node 形状决定。
4. **fragment 交换和 pipeline 并行分层。** fragment 层决定跨节点边和 ownership，pipeline 层决定一个 fragment 内的 driver/morsel 数量。
5. **属性契约可序列化、可快照、可反向验证。** 每个新增规则要有正例和把规则关闭后的负例。

## 属性模型

### Distribution

`DistributionProperty` 保留三个值：

| 值 | 语义 | 满足关系 |
| --- | --- | --- |
| `Single` | 所有行由一个分支产生 | 满足 `Arbitrary` 和任意 `Partitioned(keys)` |
| `Arbitrary` | 行分布无可用共定位保证 | 只满足 `Arbitrary` |
| `Partitioned(keys)` | 相同 key 的行在同一分支 | 满足 key 集合要求更宽的 partitioned requirement |

属性层的 key 集合使用集合语义；哈希路由层的 key 顺序、类型、null policy、bucket 数和 hash version 由 `HashPartitioningDescriptor` 负责。A 不把两层对象合并，避免属性等价和物理路由等价混为一谈。

### Ordering

ordering 继续复用现有 `OrderingScheme`：

- `null` 表示没有可依赖的 ordering。
- required ordering 只能由相同 ordering 满足。
- `MergeSortNode` 只能合并每个 child 已经具备的相同 ordering。
- 如果 child 没有 required ordering，先在每个 child 插入 `SortNode`，再决定是否需要 `MergeSortNode`。
- 禁止从 required ordering 反写到 provided ordering。

### PlanProperties

`PlanProperties` 继续作为两个轴的值对象，但 A 增加三项约束：

1. `satisfies()` 的 distribution 和 ordering 判定分别有独立测试。
2. `toString()` 是诊断格式，不作为 runner 的执行证据。
3. property 对象不保存运行期 DOP、DataNode 位置或 fragment ID；这些属于 B/C 的执行层状态。

## 目标组件

### `PlanPropertyProvider`

新增文件：

```text
iotdb-core/datanode/src/main/java/
org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/PlanPropertyProvider.java
```

职责是给一个已经完成 child rewrite 的 `PlanNode` 返回 provided properties。接口不负责插入节点：

```java
PlanProperties providedBy(
    PlanNode node,
    List<PlanProperties> childProperties,
    TableDistributedPlanGenerator.PlanContext context);
```

第一版只覆盖现有表模型 operator：scan、filter、project、collect、merge sort、sort、aggregation、window、top-k、row-number、join、union、output。未知 node 返回 `PlanProperties.any()` 并生成 `UNKNOWN_PROVIDER` 诊断，不能假装满足 `Single` 或 `Partitioned`。

### `PropertyEnforcer`

新增文件：

```text
iotdb-core/datanode/src/main/java/
org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/PropertyEnforcer.java
```

职责是接收 required、provided、children 和 context，返回一个不可变的 enforcement result：

```java
final class PropertyEnforcementResult {
  PlanNode node();
  PlanProperties provided();
  EnforcerKind enforcer();
  FallbackReason reason();
}
```

`EnforcerKind` 第一版包含 `NONE`、`COLLECT`、`SORT`、`MERGE_SORT`、`HASH_REPARTITION`、`FALLBACK`。`HASH_REPARTITION` 只有当 `TableGroupByHashRepartitionTopology` 的所有权、descriptor 和执行 consumer 都可用时才返回；否则返回 `FALLBACK`，不能返回一个只有诊断文本的“半启用”状态。

`FallbackReason` 使用稳定枚举或稳定代码，例如：

- `ORDERING_REQUIRED`
- `PARTITIONING_UNSUPPORTED`
- `DISTINCT_OR_MASKED_AGGREGATION`
- `MULTIPLE_GROUPING_SETS`
- `UNKNOWN_PROVIDER`
- `HASH_DESCRIPTOR_INCOMPATIBLE`
- `JOIN_HASH_PATH_NOT_ENABLED`

### `PropertyEnforcementDecision`

新增文件：

```text
iotdb-core/datanode/src/main/java/
org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/PropertyEnforcementDecision.java
```

该对象记录 `nodeId`、required、provided、enforcer、reason 和 child IDs。`TableDistributedPlanner.appendRuleTrace()` 只负责把 decision 渲染到 EXPLAIN；runner 不依赖自然语言 trace 判定执行是否成立。

## 现有文件的修改设计

### `PlanProperties.java`

修改内容：

1. 保持值对象不可变。
2. 增加 `requirementFor(DistributionProperty, OrderingScheme)` 的命名工厂，避免 visitor 直接拼装 nullable ordering。
3. 增加 `satisfiesDistribution()` 与 `satisfiesOrdering()`，让失败原因可以分别记录。
4. 增加 `withDistribution()` 和 `withOrdering()` 只用于 provider 返回新值，不允许原地修改。

不在此文件加入 DOP、morsel、fragment 或 DataNode 字段。

### `DistributionProperty.java`

修改内容：

1. 保留 `Single/Arbitrary/Partitioned` 三值。
2. 增加 `isPartitioned()`、`isArbitrary()` 和 `isCompatiblePartitioning()`，把调用点从 `getType()` 加集合比较收敛到一个地方。
3. 保留空 key 归并为 `Arbitrary`。
4. 明确 key 集合只表示逻辑共定位，不表示 hash key 的物理顺序和类型编码。
5. 为 `satisfies()` 增加反例：`Arbitrary -> Single`、`Partitioned -> Single`、不同 key 的 partitioned 不满足。

### `TableDistributedPlanGenerator.java`

这是 A 的主要迁移文件。修改顺序固定为：

1. 在构造函数中注入 `PlanPropertyProvider` 和 `PropertyEnforcer`。
2. 将当前 `propertiesOf()` 的逻辑迁移到 provider；原方法只保留兼容委托，完成迁移后删除重复逻辑。
3. 将 `enforce()` 改成调用 `PropertyEnforcer.enforce()`，不再在 visitor 内直接 new `CollectNode`、`SortNode`、`MergeSortNode`。
4. `recordRuleHit()` 改为接收 `PropertyEnforcementDecision`，记录稳定 reason code 和 node IDs。
5. `visitOutput()`、`visitFilter()`、`visitProject()`、`visitTopK()`、`visitWindowFunction()`、`visitTopKRanking()`、`visitAggregation()`、`visitJoin()`、`visitUnion()` 逐一确认走同一 provider/enforcer 入口。
6. `mergeChildrenViaCollectOrMergeSort()` 在迁移完成后只作为兼容 facade，最后删除或限制为 `PropertyEnforcer` 的内部 helper。
7. `canUseGroupByHashRepartition()` 保持为 hash path 的具体准入规则，但把失败 reason 返回给 `PropertyEnforcementResult`，不再只返回 boolean。
8. `allowParallelScanOn()` 只处理静态 scan eligibility，不承担 distribution/ordering 的推导。

### `TableDistributedPlanner.java`

修改内容：

1. 保存每个 `PropertyEnforcementDecision`，供 EXPLAIN 和测试读取。
2. `appendRuleTrace()` 只渲染已冻结的 decision。
3. grouped hash ownership gate 继续放在 fragment split 完成后；A 只把它注册为 `HASH_REPARTITION` 的后置执行检查，不把 fragment ownership 检查塞回普通 property provider。
4. 失败时使用稳定 reason 和 topology ID，保持当前 default-off 路径不变。

### `AddExchangeNodes.java`

该文件不改成通用 property enforcer。A 只补充注释和测试，明确：

- `AddExchangeNodes` 负责 fragment-level distribution tree 的结构化切分。
- `PropertyEnforcer` 负责 logical/physical plan 的 required/provided 满足关系。
- 已存在的 `TableHashPartitioningShuffleSinkNode` edge 不能被普通 Collect/Exchange rewrite 覆盖。

### `DataNodeTableOperatorGenerator.java`

修改内容：

1. `visitTableHashPartitioningShuffleSinkNode` 只消费已冻结的 `HashPartitioningDescriptor`，不自行推导 property。
2. `allowParallelScan` 只决定本 fragment 内是否允许拆 pipeline。
3. filter/project 的 transparent wrapper 规则由 A 的 provider 给出；执行侧只校验 node shape 和类型信息。
4. 对未知或不兼容 descriptor 保守抛出稳定错误，不静默退回 round-robin hash。

### `TableEquiJoinHashRepartitionGuard.java`

修改内容：

1. 保留 canonical type、key count、hash version、null routing、partition count 的检查。
2. 返回 `FallbackReason` 或可转换成 `PropertyEnforcementDecision` 的结构，而不是只返回字符串。
3. 明确当前 join path 仍然 fallback 到 merge-sort；A 不把 guard 变成生产 hash join admission。

### `DeviceTableScanNode.java`、序列化和 schema

A 不新增 scan 属性字段。现有 `allowParallelScan` 的 serde 兼容测试保留。若后续要序列化 property contract，必须先加 schema version 和旧 reader 默认值，不能直接追加字段。

## 测试设计

### 值对象测试

文件：

- `DistributionPropertyTest.java`
- `PropertyDrivenDistributionTest.java`

新增断言：

- 每种 distribution 满足关系的完整真值表。
- ordering 不会被 required 反向污染。
- unknown provider 只能得到 `Arbitrary`/fallback，不得得到 `Single`。
- key 集合语义和 physical descriptor 顺序语义分开。

### provider/enforcer 测试

新增文件：

```text
PlanPropertyProviderTest.java
PropertyEnforcerTest.java
PropertyEnforcementDecisionTest.java
```

覆盖：

- plain scan、filter、project 的 transparent wrapper。
- unordered multi-child 到 `Single` 的 Collect。
- unordered child 到 ordered requirement 的 per-child Sort + MergeSort。
- ordered child 已满足 ordering 时不重复插 Sort。
- partitioned requirement 未接入 hash consumer 时明确 fallback。
- distinct、mask、multiple grouping set、window、top-k、join 的 fallback reason。
- property flag 开启/关闭时 plan shape 与 rule trace 的一致性。

### 端到端矩阵

属性矩阵 `research/query-intra-parallelism-e2e-acceptance/manifests/property-enforcement-matrix.json` 继续作为机器可读合同，但每个 entry 增加：

- `required_property`
- `provided_property`
- `enforcer`
- `fallback_reason`
- `execution_marker`
- `plan_test`

离线 verifier 必须同时检查 JSON 合同和 JUnit method/assertion marker，防止文档先于代码漂移。

## A 的非目标

- 不实现 hash join 生产路径。
- 不实现动态 DOP。
- 不把 DataNode 全局 metric 直接变成 query controller 输入。
- 不改变 default-off 的 grouped hash path 行为。
- 不在 A 阶段重写 `DriverScheduler`。

## A 的完成定义

A 完成后，给定任意已支持的表模型 plan node，可以从一个统一入口得到：

```text
required properties
provided properties
enforcer or fallback
stable reason code
rewritten plan shape
diagnostic decision
```

并且 property flag 关闭时，legacy heuristic 与 property-driven plan 的快照差异只有已记录的实验性路径，不会出现“visitor 某处绕过 enforcement”的未审计分支。
