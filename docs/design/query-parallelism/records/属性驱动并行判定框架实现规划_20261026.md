# 属性驱动并行判定框架实现规划

> 编写日期：2026-10-26
> 代码基线：sc01 `/root/iotdb`，分支 `feat/next-p0`，HEAD `0ec0e02`
> 对应大块：A，属性 enforcement 完整化
> 前置要求：不改变 A→E 的总体顺序；A 完成前不进入动态调度实现

## 实现目标

把当前集中在 `TableDistributedPlanGenerator` 内的属性判断拆成可复用、可测试、可诊断的四个部件：

1. `PlanPropertyProvider`：从物理 child plan 读取 provided properties。
2. `PropertyEnforcer`：比较 required/provided，选择 enforcer 或 fallback。
3. `PropertyEnforcementDecision`：冻结稳定的 reason、node ID 和 enforcer 结果。
4. `TableDistributedPlanner`：把 decision 写入 EXPLAIN，并在需要时执行 post-split ownership gate。

第一版仍然支持 `Single`、`Arbitrary`、`Partitioned(keys)` 和 `OrderingScheme`；不在 A 阶段引入 Broadcast、runtime DOP 或 hash join consumer。

## 分阶段实施步骤

### A0：冻结当前行为与基线快照（0.5–1 天）

工作：

1. 以 `0ec0e02` 建立 A 工作分支或 tag。
2. 记录 property flag 开启/关闭时的 `EXPLAIN`、rule trace 和主要 plan shape。
3. 固化现有测试命令，不在 A 中混入 B–E 的实现。
4. 统计 visitor 中所有 `mergeChildrenViaCollectOrMergeSort()`、`propertiesOf()`、`allowParallelScanOn()` 调用点。

文件：

- `TableDistributedPlanGenerator.java`
- `TableDistributedPlanner.java`
- `PropertyDrivenDistributionTest.java`
- `DistributionPropertyTest.java`

退出条件：同一 SQL 在 flag 开/关两种模式下有可比较的 plan snapshot，所有 bypass 点都有清单。

### A1：补齐属性合同和值对象（1 天）

修改：

1. `PlanProperties.java`
   - 增加 `satisfiesDistribution()`、`satisfiesOrdering()`。
   - 增加 `requirementFor()`、`withDistribution()`、`withOrdering()`。
   - 保持类不可变，不加入 runtime state。
2. `DistributionProperty.java`
   - 增加 `isPartitioned()`、`isArbitrary()`、`isCompatiblePartitioning()`。
   - 明确 key 集合语义不等于 `HashPartitioningDescriptor` 的物理语义。
3. `DistributionPropertyTest.java`
   - 补全 Single/Arbitrary/Partitioned 真值表。
   - 保留 key order equality 测试，并添加注释说明它只属于逻辑 property 层。

退出条件：值对象测试通过；任何 property 比较不再需要调用点自行组合 `getType()` 和集合判断。

### A2：新增 provider/enforcer/decision（1.5–2 天）

新增：

```text
iotdb-core/datanode/src/main/java/
org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/PlanPropertyProvider.java
org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/PropertyEnforcer.java
org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/PropertyEnforcementDecision.java
```

实现：

1. Provider 对 scan、filter、project、collect、sort、merge sort、aggregation、window、top-k、row-number、join、union、output 给出明确结果。
2. 未知 node 返回保守 `Arbitrary`/fallback decision。
3. Enforcer 对 required/provided 分轴处理 distribution 和 ordering。
4. ordered requirement 的 child 未排序时生成 `SortNode`；多个已排序 child 才生成 `MergeSortNode`。
5. unordered `Single` requirement 生成 `CollectNode`，并在结果中记录 `COLLECT`。
6. `Partitioned(keys)` 没有已接入 consumer 时返回 `PARTITIONING_UNSUPPORTED`，不生成伪 hash path。

新增测试：

- `PlanPropertyProviderTest.java`
- `PropertyEnforcerTest.java`
- `PropertyEnforcementDecisionTest.java`

退出条件：每个 enforcer kind、fallback reason 和 ordering 分支都有正反例。

### A3：迁移 `TableDistributedPlanGenerator`（2 天）

修改方法：

1. `enforce()`：改为调用 `PropertyEnforcer`，保留兼容签名直到所有 visitor 迁移完成。
2. `propertiesOf()`：迁移到 provider，原方法改为委托或删除。
3. `recordRuleHit()`：从传入 required/provided/glue 改为传入 `PropertyEnforcementDecision`。
4. `visitOutput()`、`visitFilter()`、`visitProject()`、`visitTopK()`、`visitWindowFunction()`、`visitTopKRanking()`：逐个确认 required/provided 均经统一入口。
5. `visitAggregation()`：保留 `hasDistinctOrMaskedAggregation()`、grouping set、streamable、ordering 等准入条件，但把失败原因转成稳定枚举。
6. `visitJoin()`：保留现有 merge-sort fallback，并记录 `JOIN_HASH_PATH_NOT_ENABLED`。
7. `allowParallelScanOn()`：只设置 scan eligibility，不参与 property satisfies 判定。

迁移规则：每迁移一个 visitor，立即保留一条 legacy/property-driven plan snapshot 对照，不允许最后一次性改完再查回归。

退出条件：`TableDistributedPlanGenerator` 中只有一个 property enforcement 入口；grep 结果不再出现绕过入口的直接 Collect/Sort/MergeSort 生成，除非在白名单中。

### A4：接入 planner trace 与 fragment 边界（1 天）

修改：

1. `TableDistributedPlanner.java`
   - 保存当前 plan 的 decision 列表。
   - `appendRuleTrace()` 渲染稳定 reason、required/provided 和 enforcer。
   - grouped hash ownership gate 仍在 `setSinkForRootInstance()` 后执行。
2. `AddExchangeNodes.java`
   - 添加注释和测试，证明它不替代 `PropertyEnforcer`。

3. `TableDistributedPlanGenerator.recordHashRepartition()`
   - trace 可以包含 source/bucket/exchange ID，但 runner 不把自然语言 trace 当执行证明。

退出条件：EXPLAIN 能区分 `satisfied`、`Collect`、`Sort`、`MergeSort`、`fallback`；W5 runner 仍通过现有 ID gate。

### A5：执行侧契约收敛（1 天）

## 回滚与提交边界

A 实现应保持一个主题内的小提交序列：

1. `feat: add property provider and decision model`
2. `feat: route distributed planner through property enforcer`
3. `test: cover property contracts and fallback reasons`

不要把 B 的统一 pipeline、C 的实时快照、D 的静态调度或 E 的 controller 混入 A。这样出现计划回归时，可以只回滚 A 的 enforcer，而不影响已经验收的 W5 fragment ownership。

## A 完成后的交付物

- 设计合同：required/provided/enforcer/fallback reason。
- 代码：provider、enforcer、decision 和 planner 接入。
- 测试：值对象、计划形状、fallback、flag 对照、矩阵校验。
- 证据：legacy/property-driven plan snapshot、EXPLAIN trace、测试命令和结果。
- 下一块输入：B 只读取 A 的 `PlanProperties` 与 `PropertyEnforcementDecision`，不再在 scan/morsel builder 中复制准入逻辑。
