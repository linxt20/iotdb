# 汇报 PPT 结构与讲法

目的：为《IoTDB 查询执行并行化的设计与实现》组织中期汇报内容，并固定实现与数据的引用边界。

摘要：汇报先解释一条查询拆分后必须保持的结果和顺序要求。实现部分按属性、构建、指标和静态计划展开。验证部分展示完整业务结果、真实拓扑与全量测试。动态方案作为后续实施内容。

结论：正文采用十四页结构，实现部分按 A 至 D 说明。核心双节点、真实 RPC、严格计数、资源故障与候选大输入活性使用各自冻结证据，完整模块与其余验收状态统一由 [A–D 完整核查](A-D_完整实现补全核查_20261102.md) 维护。E 作为待实施方案介绍，性能倍率由独立实验确定。

## 未决问题

- 性能倍率采用 3.33 倍还是 2.95 倍，等 sxing 决定。
- hash join 是否进入生产规划路径，等 sxing 决定。
- CPN 是否进入论文正文，等 sxing 决定。

## 汇报背景

听众需要知道查询为何值得并行、并行后怎样保持正确，以及哪些结论已有证据。每个实现主题配一个具体例子，验证页使用同一次运行的数据。

例如，两个来源各有键 a 的两行与三行，最终必须得到计数五。扫描拆成四份后，输入十二行仍须恰好处理十二行。

数据来源：工程为 sc01 `/root/iotdb`，分支为 `feat/next-p0`。实现入口见 [整体设计](修改位置与整体设计_20261025.md)，最终数据和测试范围见 [A–D 核查](A-D_完整实现补全核查_20261102.md)。本文件提供讲法，实际 PPT 文件按其独立发布流程更新。

## 第一至四页 背景与研究内容

第一页展示题目、作者和导师，并用一句话说明目标：让同一条查询使用多个执行单元，保持完整结果。

第二页画扫描、局部聚合、交换和最终聚合。用重复键例子说明为什么需要汇合，标出可拆分的位置。

第三页区分计划、执行和策略三项职责。计划负责满足分布与顺序要求，执行负责消费数据，策略负责分配工作。

第四页介绍 A → B → C → D → E 的依赖顺序。每块只给一个问题和一个验收条件，具体实现放在后续页面。

## 第五至七页 属性与执行

第五页画提供者、强制器、生成器和片段切分。说明实际输出属性由子计划提供，父要求只触发必要处理。

第六页画设备、时间分区及有序扫描的公共构建路径。有序扫描先桶内合并，再根合并。用四条扫描加一条根流水线说明计划并行度与实际数量的区别。

第七页说明资源登记、一次冻结和关闭责任。展示第二个工厂失败的例子，指出已建驱动与未消费工厂分别关闭。

备用页补充真实内存准入失败：本地与远端生产者尚未规划时，消费方已能创建其归属队列。取消后必须关闭队列、取得真实注销回执，并移除查询共享映射。该证据说明故障清理正确，不能用作性能加速数据。

数据来源：[A 实施记录](属性驱动并行判定框架实施记录_20261028.md) 和 [B 实施记录](B_静态数据并行统一实施记录_20261031.md)。

## 第八页 多源交换

主图使用两源两桶，标出四条边及各桶的最终聚合。补充真实三十二桶验收的数量，完整 ID 放在备用页。

讲法先解释消费者全部确认后启动共享源，再说明发送器只检查待发送桶。最后解释空桶也需要结束通知。

例如，两源三十二桶形成六十四条唯一交换边。数量、节点和片段均从最终运行回执读取。

数据来源：最终双节点目录的 `nxp32-receipt.json` 和同次运行的计划、TEXT、JSON，目录由 [A–D 核查](A-D_完整实现补全核查_20261102.md) 索引。

## 第九页 运行指标复用

展示已有采集点、结构化响应和调度输入三个位置。已复用项包括算子计时、根输出行数、TsBlock 数和驱动墙钟。新增项主要是身份、代次、校验和和缺失原因。

用扫描十行、过滤输出四行说明根输出计数。用两次终态读取的相同代次说明冻结。CPU 缺来源时直接标明不支持。

数据来源：[C 设计](C_运行指标快照设计_20261101.md)、[C 实施记录](C_运行指标快照实施记录_20261101.md) 和 [字段来源](A-D_运行字段来源_20261102.json)。

## 第十页 静态分配

用工作成本九、六、三、二分到两个桶的构造例子说明稳定分配。每次把下一项放到累计成本较小的桶，成本相同时按编号选择。

说明配置上界只限制并行度，内存检查在构建后执行。静态算法的确定性由单元测试证明，实际结果由查询验收证明。

数据来源：[D 设计](D_静态数据并行设计_20261101.md) 和 [D 实现规划](D_静态数据并行实现规划_20261101.md)。例子是算法说明，禁止标成实测耗时。

## 第十一页 正确性与测试

将单元断言、实际拓扑、完整业务结果和完整模块回归分别展示。测试总数、跳过数和退出码直接从完整退出后的 XML 读取，运行中的报告数量只作为带时间的过程快照。

业务场景覆盖普通、空值、倾斜和空输入。扫描场景还覆盖过滤及完整排序。对照使用显式串行配置，结果同时比较独立预期。

数据来源：[A–D 核查](A-D_完整实现补全核查_20261102.md) 集中维护最终执行目录。反向验证可用丢输入或丢背压等待说明测试如何识别故障。

## 第十二页 性能材料

性能页必须列计时边界、DOP、数据规模、重复数、冷热状态和资源配置。三十二桶的小型 fixture 用于正确性，不能据此推导吞吐倍率。

3.33 倍与 2.95 倍保留为待统一的历史口径。正式图表必须从独立性能矩阵和原始计时生成。

## 第十三页 动态方案

E 使用已冻结历史，调整下一片段，运行中驱动保持原归属。介绍真实驱动与桶配对、有界历史和单次准入三项新增工作。

例如，前次四桶被准入拒绝，后续请求可以选择三桶。当前失败请求仍按原内存失败合同结束。

数据来源：[E 设计](E_动态数据并行设计_20261102_第二轮修订.md) 和 [E 实现规划](E_动态数据并行实现规划_20261102_第二轮修订.md)。页面必须明确 E 为待实施方案。

## 第十四页 交付与后续

展示 A–D 的最终状态及 E 的审核入口。后续安排包含 E 实施、独立性能矩阵和三项用户决策。代码提交状态从工程核查读取。

## 提问材料

节点问题使用实际 DataNode、片段及交换所有权回执。结果问题使用完整多重集、规范 SHA 和有序序列。监控复用问题使用字段来源映射，性能问题使用原始测量条件。

数据来源：[A–D 完整核查](A-D_完整实现补全核查_20261102.md) 和 [总体实现规划](实现规划_20261025.md)。
