## 物化预算补充

原公式只限制工作单元总数为 1024。十万设备和三万分区产生一个设备组与 1024 个时间组，每个工作单元又复制设备列表。设备引用约一亿，计划校验和还重复编码这些设备，首轮测试在此发生 Java 堆内存不足。

E 增加引用量上限 1,048,576。设备数为 D、分区数为 P、设备组数为 d、时间组数为 t 时，引用量为 `R = D × t + P × d`。计算使用 long，不展开设备与时间分区的全部组合。

时间分区模式枚举满足原模式前提的组数。先要求 `d × t ≤ 1024`，再要求 R 不超预算。选择工作单元最多者，并列时取引用量更小者，再并列时取时间组数较大者。设备和有序模式的 t 固定为一。找不到合法组合时，由计划器按预算错误串行退回。

例如，十万设备与三万分区选择 d=18、t=5。它产生 90 个工作单元，引用量为 1,040,000。全体设备和分区仍被完整覆盖。两个设备、512 个分区仍可产生 1024 个单元，单桶上界场景不受影响。

引用预算约束计划的重复引用数量。单条历史记录仍有独立的 4 MiB 计费上限，不能把二者互相替代。计划覆盖、历史载荷和运行期内存准入分别检查。

数据来源：`DynamicScanGrouping`、`DynamicScanGroupingBuilder` 与 `ScanParallelPlanner`。原始失败保留在 `foundation-tests.ansi.log` 及对应 Surefire XML。补充决定保存为 `/root/property-e-artifacts/implementation-20261103-r1/materialization-budget-decision.json`。

## 已完成的定向验证

首轮六类测试共 33 项，其中一项因 Java 堆内存不足失败。补充引用预算后，同样六类 33 项全部通过。随后加入动作与冷却测试，八类共 42 项通过，失败与错误均为零。

这批测试覆盖十二单元四桶、同 DOP 重分配、单桶 1024 单元、规模预算和实际输入上限。它也覆盖单单元退回、编码平局顺序、来源校验和、动作优先级、零成本与冷却。旧 D 计划的确定性、账目与原因合同同时通过。

加入身份和逐项守卫反证后，九类共 50 项通过，失败与错误均为零。守卫测试给出十四组独立输入，覆盖空输入、重复范围、成本错误、上限及属性守卫。外部分组超预算、负成本、成本溢出与零成本覆盖也已验证。

这些组件测试尚未形成生产准备入口的证据。完整 DataNode 套件、协议兼容与机器验收尚未执行。

数据来源：`foundation-r2/test-summary.json`、`policy-r1/test-summary.json` 与 `guard-r1/test-summary.json`。两者位于 `/root/property-e-artifacts/implementation-20261103-r1/`。每次运行分别保存源码 manifest、入口 SHA、标准 Maven 命令、ANSI 与去色日志及 Surefire XML。
