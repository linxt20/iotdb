# C 运行指标快照修订版文档审查

**目的**：核对 C 两份文档的审查修订版能否进入代码实施。审查逐条判定上一轮 33 条发现的关闭状态，核查修订总则新增技术断言的源码依据，比对保留正文与修订总则的冲突，并回答两个问题：修订后的测试设计够不够支撑退出判据，修订后的实现内容是否合理高效。审查只读源码与文档，不运行测试，不改动仓库。

**摘要**：受审文档是 C 的两份审查修订版，一份覆盖运行指标快照的设计，一份覆盖实现规划，修订前的原稿备份在证据目录。上一轮审查对这两份文档提了 33 条发现，本轮要判定这些发现在修订版里的关闭状态。修订版把新增内容放在文件头的审查修订总则与阶段门，原稿正文整段接在总则之后，本文逐条核对总则新增的技术断言在源码里是否成立，比对保留正文与总则的冲突，并回答修订后的测试设计是否够用、实现内容是否合理高效。核查基线是 sc01 上 next-p0 分支的固定提交，方法为读源码与读文档，不运行测试，不改动仓库。

**结论**：两份文档的总则部分可以放行，文件整体不能放行。C0 与 C1 只依赖总则，可以开始。C2 至 C6 依赖的四个 P0 在总则里已正确落地，但同一份文件里还保留着一份更可执行的旧程序，实施者照旧程序的编号步骤做会重新引入已定性的竞态、已定性的锁不释放、已定性的完整判定不可达三个缺陷。七条退出判据只写在保留正文里，总则没有重述，直接删掉保留正文会把判据一并删掉。必须先把七条判据迁入总则并把第三条与 CPU 降级对齐，再删去两份文件分隔线之后的保留正文，原稿已备份在证据目录，删去不损失内容。另须完成七项：补 thrift 驱动字段、统一三处字段命名、改 C6 的 Maven 命令、把驱动计数来源改成待新增、把逐节点超时机制写成可实施、给两个零绑定的退出测试类补上阶段归属、给两份文件各补三段式头部。这九项完成前 C2 至 C6 不进入实施。

**未决问题**：聚合成本三项是否纳入 C 的范围，等 sxing 决定，它影响设计第 165 行与 manifest 的口径。C 的 final snapshot 是否在后续版本扩展到普通查询，等 sxing 决定，修订总则已把保留门控写成第一版决定并给出评估要求。B 的未提交工作区是否在 C 实施前提交，等 sxing 决定，它影响 C0 冻结的源码身份是否稳定。

## 审查任务与判定标准

一次查询在多个 DataNode 上分成多个片段执行，每个片段再分成多条驱动。要比较两种静态调度策略哪个更省，需要拿到每一条驱动各自处理了多少数据、花了多少时间。拿不到驱动级的量，就只能看到片段总数，两条策略在片段数上可能完全相同。C 要解决的就是这件事：把已经散落在查询统计、片段执行、驱动与算子四处的计时与计数收成一个对象，冻结时不被人改写，跨节点合并时不把缺失当成零。

做得好有两条判据。第一条是可冻结：同一片段重复抓取必须返回同一代际与同一校验和，驱动记录与统计冻结之间不能有竞态。例如四个驱动里第三个在监听器加锁后才写入墙钟，冻结读到的必须是写入后的值，不能是零。第二条是可合并：两个 DataNode 各返回若干片段，少返回一个要标成部分，多返回一个要标成意外，两者都不能标成完整。丢一个节点的响应不能让它名下的片段计成零行。例如一条查询预期两个片段，只有一个节点应答，输出必须写明缺哪个来源，不能只报幸存片段的四百行。

本文核查支撑这两条判据的文档陈述与源码是否一致。受审文档是 sc01 上的 C 运行指标快照设计审查修订版与 C 运行指标快照实现规划审查修订版，修订前的原稿备份在证据目录。审查方法是读源码，比对文档写出的方法名、字段名、算术式、文件路径与行号。

分级按三条定义。P0 表示正确性或方向存在阻断，实施前必须解决。P1 表示关键行为或验证存在缺口。P2 表示文字与位置存在问题。每条意见给出文档位置、源码依据、具体反例、影响与修改动作。

本文的判定分两类。已证实问题有源码依据，本文直接给出结论。待执行验证只有测试运行才能裁定，本文列进待执行验证清单，不预先判定。

本文的发现来自一轮六维度并行检索加一轮反向驳斥。受并发上限影响，六个检索维度里三个在限流中失败，分别是关闭状态核对、实现效率、新增断言三个维度。三个驳斥代理里一个失败。失败的四个维度由本文作者自行补齐核查。返回的三个维度是保留正文矛盾 28 条、测试设计 8 条、文档规范 10 条。两个驳斥代理分别核查矛盾维度 28 条与文档规范维度 10 条，一条也没有驳倒。

## 修订的落地方式

两份修订版采用同一个结构：文件头新增审查修订总则，声明优先于后文同名概括，然后用一条分隔线把修订前的原稿正文几乎原样接在后面。设计文档的原稿正文只被改了一句，位置在跨节点和输出一节里讲传输载体那句。实现规划的原稿正文一句未改，与修订前的原稿备份逐字节相同，只差标题与引用块三行。

这个落地方式带来一个直接后果：修订前的每一处错误陈述都还在文件里，而且都在更靠后、更具体、更接近实施动作的位置。设计文档的原稿正文含一份七步编号的冻结协议，实现规划的原稿正文含六节 C0 至 C6 的文件级步骤与一条可直接复制的 Maven 命令。这些正是实施者会照着做的文本。

修订总则用一句话来处理这个冲突，说的是优先于后文同名概括。这句话的作用范围无法判定。保留正文里哪些句子属于同名概括因此被覆盖，哪些不属于因此仍然有效，没有清单，没有逐条标注。至少七处无法判定。设计第 267 行讲 B6 非数值失败的归因，总则里对应的一节标题是 B6 证据修正，正文所在的一节标题是输出和兼容性。设计第 165 行讲聚合成本，总则里对应的一节标题是字段来源与降级，正文所在的一节标题是查询和片段级。设计第 280 行讲终态缓存时效，总则里对应的一节标题是终态门控，正文所在的一节标题是采样代际和状态。规划第 299 行讲 morsel 补写，总则里对应的一节标题是冻结和锁，正文所在的一节标题是 C2 冻结协议。规划第 315 行讲终态快照保留，总则里对应的一节标题是终态门控，正文所在的一节标题是失败和降级语义。规划第 356 行讲驱动数组稳定排序，总则里对应的一条埋在身份计划和有效性与聚合和可见性两节里，没有同名标题。规划第 429 行的 Maven 命令位于标题为当前工程验证命令的一节，总则里对应的一节标题为命令。七处的两节标题都不同名，是否被覆盖读不出来。

还有一个结构后果。分隔线之后设计文档出现一个二级标题叫原设计正文，紧接着又是另一个二级标题叫目标与当前状态，包装层没有子级。规划文档更严重，新增头部与保留正文出现六个同级的重复 C0 至 C6 章节标题。把全文标题抄成目录读，新旧章节混排，看不出哪份是生效版本。

退出判据的位置是这份结构里最贵的一处。七条退出判据只写在保留正文的 C 的退出判据一节，位置在设计第 287 行至第 297 行，总则的 C 的审查后退出测试一节只列了十个必测类名，没有重述七条判据。按上文删掉保留正文，七条判据随之消失，C2 至 C6 的退出条件只剩一张测试类名清单。第三条判据要求断言 CPU、墙钟、就绪阻塞、行数、块数与内存的单位与求和最大值规则，而总则已把 CPU 降级为无来源即标不支持字段，并写明可以不交付 CPU 采样。这条判据原样迁入总则后，C1 或 C2 不交付 CPU 采样时第三条永远无法满足。

必须先做的一步是把七条判据逐条迁入总则，第三条改成 CPU 有采集点时断言单位与求和最大值规则、无采集点时断言降级为不支持字段，再删去两份文件分隔线及其后的全部保留正文，原稿已备份在证据目录，删除不损失内容，也能一次性消掉 26 处冲突与标题层级混乱。另一步是在总则里补一段生效声明，写明本文件只有总则生效，任何与总则不一致的表述以总则为准，不设同名限定。若 sxing 要求保留原稿备查，则改为逐条标注：保留正文的每一处与总则冲突的句子后面加一行作废标记，并写明作废依据对应总则哪一条。

## 保留正文与修订总则的冲突

### 驱动墙钟与输出字节的传输归宿

设计第 25 行列出 thrift 一侧的必加字段，response 一侧九项，算子统计或新驱动结构一侧十三项，十三项是片段实例号、流水线号、驱动任务号、驱动角色、驱动采样代际、驱动首次处理纳秒、驱动末次处理纳秒、驱动 CPU 纳秒、驱动就绪纳秒、驱动阻塞纳秒、驱动输出行、驱动块数与字段有效性。这份清单里没有驱动墙钟纳秒，也没有驱动输出字节。

### C6 命令的模块开放参数

规划第 192 行的 Maven 命令用命令行参数指定了五条模块开放参数，覆盖语言、工具、并发、非阻塞输入输出与输入输出五处。仓库根 POM 里有一个 Java 17 profile，在 JDK 17 及以上自动激活，它把开放参数属性设成六条，比命令多一条网络包。

命令行传的用户属性优先级高于 profile 里设的属性，所以这条命令执行时开放参数属性被命令行的五条替换掉，profile 的第六条被丢掉。修改这条命令的初衷是避免出现与 C 无关的失败，而丢掉一条开放参数恰好会造成同一类失败：任何触碰网络包内部结构的测试会以非法访问异常失败，失败原因与 C 的改动无关。

更稳的写法是不传这条参数，让自动激活的 profile 自己提供。传了就要传全六条，并且要在六条与 profile 不一致时能发现，而命令里没有任何一处引用 profile。

必须删去规划第 192 行命令行的开放参数，改为依赖根 POM 自动激活的 Java 17 profile，并在 C0 记录该 profile 的激活条件与实际生效的开放参数清单。若坚持命令行指定，则补全六条并在命令后注明它与 profile 的对应关系，C6 保存实际生效的开放参数作为证据。

### 驱动计数的来源

设计第 71 行把活跃、排队、阻塞、已完成四个驱动计数的第一版来源写成调度器快照接口、队列长度和驱动状态转移。源码里调度器接口只有三个方法：提交驱动、中止查询、中止片段实例。没有快照接口，也没有任何按驱动的活跃或阻塞计数。

排队数有近似来源，调度器持有一个就绪队列，长度可以当排队数。已完成驱动数可以从驱动状态推。活跃与阻塞两个计数没有任何字段或方法承载。上一轮 P1-11 已定性这三个计数无来源，修订总则在无来源一列正确地写了标不支持字段且不返回零，但来源一栏写成了一个不存在的接口，与上一轮 P0-3 里把死代码写成生产来源是同一类错误。

### 逐节点超时的承载层

设计第 98 行与规划第 151 行都要求抓取改成逐节点独立超时加异常捕获。抓取实现的循环里，每个节点从一个客户端管理器借一个同步内部服务客户端，调用抓取方法。借客户端的方法只接受端点一个参数，没有按调用传超时的入口，客户端的超时是客户端管理器级的全局值。

也就是说逐节点超时必须新增一个机制，要么给这个方法开一个带超时的重载，要么把同步调用包进一个有超时的future。文档要求了行为，没写机制，也没写超时值从哪个配置来。实施者要么忽略这条，要么自己造一个与全局客户端超时冲突的机制。

必须在规划 C4 增加一节抓取路径改造，写明超时的承载层是按调用重载还是异步包装，超时值的来源是新增配置项还是复用现有客户端超时，以及与全局客户端超时不一致时的优先级。

## 修订总则里核查通过的部分

下列新增断言本文逐条读源码后确认可行，可以直接作为实施依据。这一节同时是审查可信度的组成部分：本轮四条 P1 与六条 P2 是在这些确认项之外的发现。

plannedDop 的写入时序可达，这是本轮最要紧的一项核查。修订总则要求由表模型算子生成器在构造时把计划并行度、实际流水线数、拆分模式、降级原因与工作单元结构写进片段上下文。源码里本地执行规划器的计划方法以片段上下文为入参，先构造本地执行计划上下文，再调用算子生成，最后把来源路径、设备路径、查询数据源类型与时间分区写回片段上下文。也就是说片段上下文在规划期就存在，而且已经有四条规划期写入的先例。算子生成器内部通过本地执行计划上下文的驱动上下文可以取到片段上下文。这条指令可执行。

有一个精度缺口要一并改。并行度决策是一个私有方法，只返回一个整数，不产出拆分模式与降级原因。现有实现在开启数据量估算时用一个下限钳制，钳制动作发生了但没有理由串。要写降级原因必须把这个方法的返回值改成一个携带模式与理由的结构，或在决策点直接写入。修订总则列了五个字段，其中三个现在没有产出。

驱动 CPU 采样有现成落点。驱动的主处理方法在持有驱动锁的lambda里先取首次处理时间戳，再取一个起始纳秒值，然后进入初始化与一个受运行时长上限约束的处理循环。线程 CPU 的差分发在这两点之间是成立的，因为单个线程在一个时刻只跑一个驱动任务，跨调用迁移驱动不影响单次差分的正确性。有一个代价要写进文档：这段代码在驱动锁内，采样调用会加长临界段，而文档写了说明开销上限却没给数值。

-am 参数确实解决了它要解决的问题。数据节点模块依赖的计算公共模块是根 POM 的反应堆成员，-am 会把它并入本次构建，不会链接到本地仓库的旧快照。命令行的测试阶段目标会作用于反应堆内每个模块，配合按类名过滤与无测试不失败两个参数，上游模块空跑，行为正确。

第七处缺口是有序并行路径没有采集点。驱动覆盖测试要求有序并行路径有逐驱动条目，而源码里并行子扫描的识别只匹配两种计划节点后缀，分别是并行与分片，时间分区有序并行的节点号两种都不匹配，进不了逐驱动分支。必须把有序并行的识别补上，或在该测试里显式记录这个缺口并把它标为不支持字段。

## 修订后实现内容的合理性与效率

修订后的实现内容方向合理，新增采集点的成本写在了明处，剩下三处要改。

合理的部分。不另造平行计数器这一条经源码核查成立。四级模型与 D、E 的消费面精确匹配。旧键兼容走新增根键而不动旧渲染路径。校验和用稳定字段序，不依赖哈希映射迭代顺序。身份规则把字符串解析结果限定为显示字段，与折叠合并的缺陷一致。终态门控保留并给出移除时的评估要求，没有把成本略过。

第一处要改的是传输清单与消费清单不一致，见本轮 P1 第一条。这是效率问题也是正确性问题：字段没有传输归宿，实施到 C3 会发现要回头改 thrift，而 thrift 是要同时改生成代码、服务端实现、同步客户端、响应适配器与混合版本测试的一整套。

第二处要改的是采集点的成本仍然没有数值。修订总则写了 CPU 采样的开销上限、线程归属与关闭开关，但没给上限数值，也没给驱动级就绪阻塞改成按驱动累加后的每次调度事件额外开销。以一个八驱动片段计，每次调度事件多一次按驱动任务号的映射查找，八驱动就是八次，这个量级本身不构成问题，问题在于它发生在调度热路径上且文档没有要求测量。必须在总则里给两项各写一个可测的上限表达式，并把测量列进待执行验证清单。

第三处要改的是命令的实际开销。同时构建依赖模块会让每次定向测试都编译上游模块的测试源码。更省的写法是上游模块跳过测试编译，只构建主产物，再单独对数据节点模块跑测试。文档没有给这个替代。必须在规划 C6 给出两条命令，一条全量用于身份冻结，一条跳过上游测试用于日常定向测试。
