# C 运行指标快照实施记录

目的：记录 C 如何复用 IoTDB 的采集点，以及冻结、传输、缺失和真实 RPC 验收的实现证据。

摘要：C 把已有计时与计数组织成不可变运行快照。源端和接收端共用适配与校验规则。生产路径覆盖终态冻结、实时读取、解释输出和异常清理。双节点验收分别检查完整、部分缺失和恢复请求。

结论：C 的生产采集、协议、冻结和展示已经接入 IoTDB。最终包的正常与失败驱动时间、完整/部分/恢复 RPC 和双语言构建已有实际通过证据。可靠来源缺失的字段保留明确原因。完整模块及架构规则已完成独立终态审核，状态统一由 [A–D 完整核查](A-D_完整实现补全核查_20261102.md) 维护。E 的普通查询独立历史属于待实施范围。

## 运行统计背景

调度需要知道实际执行了哪些扫描，以及它们产生多少输出。统计必须保留来源，才能区分数据倾斜、过滤效果和采集缺失。完成标准包括实际生产写入、协议自校验和故障后清理。

例如，扫描读十行而过滤输出四行，驱动输出记录四行。扫描计数仍保存在扫描算子上，两个量分别解释。

数据来源：工程为 sc01 `/root/iotdb`，分支为 `feat/next-p0`。HEAD 为 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`。完整字段与缺失原因见 [运行字段来源](A-D_运行字段来源_20261102.json)。

## 抓取与合并边界

抓取方核对响应片段身份和实际连接端点。版本化响应缺失身份或端点时，抓取结果保存对应错误。另一个片段的成功响应不能代替所请求的片段。旧协议保留原始读取，结构化视图按缺失字段标记资格。

合并器保留协议第一版的校验和语义，并核对完整驱动身份与短片段键的所属查询。只有没有管理扫描且工作与桶均为空的根片段，可以使用零扫描并行度。重复驱动采用同一片段内的实际流水线和任务键判断。

例如，查询 q 的片段键为 1.0，驱动身份为 q.1.0 时，两者属于同一片段。返回 q.2.0 的响应不能放入 1.0 的读取结果。没有扫描工作的合并根可以保留实际交换边，其扫描并行度为零。

数据来源：抓取边界为 `QueryStatisticsFetcher` 和 `RuntimeSnapshotFetchResult`。合并边界为 `RuntimeSnapshotMerger` 和 `RuntimeSnapshotAdapters`。边界回归为 `RuntimeSnapshotProductionBoundaryTest` 与 `QueryStatisticsFetcherTerminalTest`。对应二十八项定向回归记录在 `/root/property-c-artifacts/C-boundary-complete-20261102/tests-reports/`。

## C1 值对象与派生

查询、片段、驱动和算子分别使用不可变值对象。合并按稳定身份去重，并显式区分预期、忽略、缺失和意外片段。墙钟保留逐驱动区间，比例按总分子与总分母计算。

例如，就绪二百、阻塞五十时，阻塞占比为百分之二十。两项都为零时，比率保持缺失。

数据来源：值对象位于 `statistics/snapshot/`。合并和派生为 `RuntimeSnapshotMerger` 与 `RuntimeSnapshotDerivation`。测试从这些实际入口验证。

## C2 生产冻结与清理

驱动输出读取根输出边界，墙钟直接读取驱动纳秒字段。终态监听先幂等记录完成统计，再在统计写锁下生成冻结响应。DONE 临时读取保留非终态，写锁冻结完成后才发布终态标志。

驱动在失败通知前记录实际执行端点，初始化失败使用同一路径。冻结先各读取一次末次和首次时间，再计算墙钟。正常 RPC 与真实数据扫描失败均已通过最终包运行审核，重复终态记录保持幂等。

快照异常仍释放统计锁、sink、驱动、交换内存、算子内存和 spill。测试从另一线程重新取得写锁，核对清理没有永久持锁。

例如，统计构造主动抛出异常后，已建驱动仍必须关闭，内存预留回到执行前值。

数据来源：采集对象为 `Driver` 与 `QueryStatistics`。冻结由 `FragmentInstanceExecution` 组织。时间捕获定向证据为 `/root/rivermind-data/iotdb-ad-acceptance-20261103/AD-C-wall-capture-fix-20261103-r1/independent-delivery-audit.json`。终态生命周期交付为 `/root/rivermind-data/iotdb-ad-acceptance-20261103/AD-C-driver-terminal-timing-fix-20261103-r1/delivery.json`，覆盖十九类五十四个方法及六项指定故障断言。实际正常与失败运行由运行字段来源的 `finalAcceptance.cTimingCaptureAndFailurePublication` 索引。生产与故障测试为 `FragmentRuntimeSnapshotProductionTest` 和 `FragmentSnapshotFailureCleanupTest`。父 shuffle sink 终态通知由 B 生命周期处理。

## C3 协议与解释

Thrift 传输实际驱动、计划身份、采样代次及校验和。响应显式写入成功状态。接收端核对完整查询归属、端点和重复身份，源端与接收端共用适配器。

TEXT 与 JSON 使用同一字段语义。扫描与有序合并根分别保存，类型化 TsBlock 数经过复制与合并仍须保留。非法、缺失和溢出字符串保持缺失。

大型说明按实际字节上限分批，统计只构造一次。最后一批发送后算子才完成。单行自身超限返回内存错误，close 即使子算子失败仍清除待输出引用。

例如，说明有十万字节、单批上限四千零九十六字节时，输出必须分批。拼接后的全部行与原说明逐行一致。

数据来源：协议为 `datanode.thrift`，适配入口为 `RuntimeSnapshotAdapters.fromResponse()`。合并实现为 `StatisticsMergeUtil` 与 `SpecifiedInfoMergerFactory`。两个统计 Drawer 展示相同语义，说明分批由 `ExplainAnalyzeOperatorTest` 验证。

## C4 抓取与部分失败

实时入口单次采样，终态入口在每个来源自己的超时内等待冻结。一个来源失败保留其他来源。重复片段在提交请求前拒绝，禁止覆盖 Future。

查询关闭可能提前清理片段上下文，五分钟保留值仅是上限。RPC 验收持有有效查询句柄，分别读取完整、部分缺失和恢复正确请求的终态。每场景读取两次以检查冻结稳定性。

例如，三个片段里两个位于被替换端点，部分场景预期两条错误与一条成功。恢复实际实例后，再取得三个冻结响应。

数据来源：抓取与测试为 `QueryStatisticsFetcher` 和 `QueryStatisticsFetcherTerminalTest`。响应生命周期由 `FragmentInstanceManager` 管理。真实探针为最终双节点目录中的 `HeldSnapshotSqlProbe.java` 和 `RuntimeSnapshotRpcProbe.java`，其源码及 class SHA 均在运行前记录。

## C5 只读视图与指标边界

只读视图展示片段计划和驱动信息。行数、TsBlock 及墙钟沿用 IoTDB 采集来源。全局调度器计数只描述 DataNode，CPU、逐驱动就绪与阻塞、输出字节及峰值内存缺少来源时保持不支持。

同运行差分接口保留 C 的已有能力。E 要求的完整计划身份、驱动集合及更多计数字段校验，列入 E 的文件级修改。

数据来源：[C 设计](C_运行指标快照设计_20261101.md)、[C 实现规划](C_运行指标快照实现规划_20261101.md) 和 [E 实现规划](E_动态数据并行实现规划_20261102_第二轮修订.md)。

## C6 退出证据

最终源码的设备、时间分区、有序及多源业务和真实 RPC 按 C6 原要求验收。完整、部分缺失和恢复请求必须重复读取，逐来源核对终态、代次、身份与输出计数。

最终包的上述真实 RPC 已通过独立审核。核心服务的完整范围、历史冻结记录及完整模块终态由中央核查分别维护。

例如，三个片段中一个请求身份无效时，两个成功响应继续保留。纠正请求后，三个响应恢复，并各自满足重复冻结读取。

数据来源：[C 统计与终态响应](A-D_完整实现补全核查_20261102.md#c-统计与终态响应) 与 [历史冻结证据](A-D_完整实现补全核查_20261102.md#历史冻结证据) 保存各自回执。
