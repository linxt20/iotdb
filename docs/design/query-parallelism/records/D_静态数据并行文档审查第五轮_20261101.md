# D 静态数据并行文档审查第五轮

## 目的

核对 D 两份第五轮修订稿与 `/root/iotdb` 固定基线、工作区源码的一致性，逐条确认第四轮十项意见的落地情况，指出修订引入的新问题，并给出 D 实现的放行门槛判断。

## 摘要

核对对象是 sc01 `/root/w5-docs/` 下的两份第五轮修订稿，两份 MD5 与请求给出的一致，第四轮的十项意见逐条核对后都有对应改动。修订暴露出三项新的阻塞项，其中一项落在 D0 的冻结范围，另外两项落在 D5。D0 至 D4 的文档达到放行门槛。D5 开工前需要先处理上面三项。

## 结论

D0 至 D4 阶段可以放行开工。D5 开工前必须先解决三项，三项都只需要改文档。D0 的两份清单要覆盖工作区全部未登记的 20 个路径。快照链要补上计划身份的载体，否则 view 的只读视图缺两组字段。判据 5 和复用规则要写明 checksum 指哪一个口径。

## 未决问题

- 性能倍率口径、hash join 是否进入生产规划路径、CPN 形式化是否进入论文正文，三项仍待 sxing 决定。
- work unit 和 bucket 的载体挂在 fragment 级还是 query 级，需要 sxing 定。
- checksum 按生产口径重算，还是排除墙钟后按 Java 口径重算，需要 sxing 定。
- 未登记的 20 个路径里哪些进 D0 冻结清单，哪些只记录不改动，需要 sxing 定。

## 核对范围与方法

核对对象是 sc01 `/root/w5-docs/` 下的两份第五轮修订稿，MD5 在远端复算，与本地副本一致。源码事实由本机直接读取 `/root/iotdb` 工作区得出，并与固定基线的 `git show HEAD:` 结果比对，用于区分固定基线与工作区。修订方的处理说明只作为待核对待办，未以其自述为准。全程只读，未修改仓库与文档。

## 阻塞项

### 1. D0 冻结范围

严重度：阻塞 D0。

D0 的两份清单共 28 个路径。工作区实际有 33 个改动路径，其中 20 个不在任何一份清单里。

未登记的 20 个路径里有 12 个是主源码文件，其中两个与本文档的论断直接相关。`Driver.java` 是 wall 机制的载体，工作区给三个计时字段加了 volatile，并新增三个取值方法。`DeviceTableScanParallelPipelineTest` 是规划第 152 行点名要扩展的测试，却没有进入冻结清单。

其余未登记主源码文件覆盖 exchange、RPC 和查询统计三条链路。规划第 165 行要求传输 exchange edge，规划第 296 行的 RPC stub 验收也经过这几条链路。它们的身份不在 D0 的证据里，D6 无法判断这些链路是否发生过改动。

测试侧还有 7 个未登记文件和一个未登记目录。其中一个文件对应规划第 295 行的单节点验收。另一个文件与规划第 127 行新增的 `StaticParallelPlannerTest` 测同一个 planner。这两个测试的行为没有被 D0 钉住，文件名见数据来源。

处置：D0 的两份清单按 `git status --porcelain` 的实际输出补齐，逐条标注是冻结 SHA 还是只记录不改动。这 20 个路径列在数据来源。

### 2. 快照链的计划身份载体

严重度：阻塞 D5。

规划第 240 行要求 `RuntimeSnapshotView` 提供计划身份的只读视图。该视图的构造入参只有一个 `QueryRuntimeSnapshot`。

`QueryRuntimeSnapshot` 与 `FragmentRuntimeSnapshot` 的字段清单见数据来源，两组都没有计划身份。整个 snapshot 包的 13 个文件对计划身份标识的匹配数都是 0。`RuntimeSnapshotBuilder.buildFragment()` 的入参也没有计划身份项。规划第 228 行至第 233 行的六步接线没有任何一步引入它。

协议侧的四个计划字段见数据来源。这四项覆盖并行度、实际 pipeline 数、切分模式和切分理由。协议没有 work unit 字段，也没有 bucket 和 exchange edge 字段。规划第 165 行要求传输这三项，设计第 221 行要求它们在快照值对象里可回放。两条都缺少落点。

处置：在规划 D5 改动清单里补一个计划身份的载体，写明它挂在 fragment 级还是 query 级、由谁写入、view 从哪个对象读。载体若挂在 `FragmentRuntimeSnapshot` 上，`RuntimeSnapshotBuilder` 需要新增入口。`RuntimeSnapshotChecksum` 要同步决定是否把计划身份纳入覆盖范围。

### 3. checksum 的两个口径

严重度：阻塞 D5 与 D6。

生产侧的口径在 `FragmentInstanceExecution` 第 388 行，字段见数据来源。Java 侧的口径在 `RuntimeSnapshotBuilder` 第 61 行，由 `RuntimeSnapshotChecksum.forFragment()` 生成。

两个口径的覆盖近乎不相交。生产口径不含墙钟时间戳，含 driver 内容。Java 口径含墙钟时间戳，不含任何 driver 内容。

举一个数。同一条查询采两次，墙钟读数分别是 1000 和 2500，两次的 driver 行数完全相同。按 Java 口径算出的两个 checksum 不同。按生产口径算出的两个 checksum 只差两项。这两项是 instanceId 和 generation，driver 内容完全相同。

后果一：该时间戳取自 `System.nanoTime()`，两次独立采集必然不同。判据 5 写比较 checksum，按 Java 口径做相等比较时 D6 恒失败。

后果二：Java 口径不含 driver 内容，判据 5 却把它和 rows、TsBlocks 并列成按 driver 比较的字段。driver 行数全部一致时，checksum 仍会不同。

后果三：规划第 259 行的复用规则写 checksum 正确，没有说按哪个口径重算。`RuntimeSnapshotChecksum` 只有两个公开静态方法，没有排除墙钟的变体。

后果四：`RuntimeSnapshotChecksum.java` 不在 D5 改动清单里，只在 D0 冻结清单和数据来源中出现。若要改 `forFragment()` 的覆盖范围，它必须成为改动目标。

处置：判据 5 和复用规则写明 checksum 指哪一个口径。保留 Java 口径时，写明该时间戳排除在跨侧比较之外，或明确它是完整性自校验而非跨侧相等比较。

## 次要问题

### 4. 设计输出节的字段分组

设计第 83 行和第 85 行各有一句含 3 个内部名，超过一句两个的上限。第四轮要求把 6 个名字拆成 4 句，实际拆出的前两句各仍有 3 个。

同时有一组字段在拆分中丢失。修订前的设计有一句写 `ScanParallelPlan` 保存计划身份和字段 validity，本轮四个句子都不含这组内容。规划第 124 行的 D1 改动也只补估计成本、reason 和 checksum。两份文档都没有 `ScanParallelPlan` 身份绑定字段的落点，原句的四个字段名见数据来源。

处置：设计输出节把身份绑定字段补回一句，内部名控制在两个以内。规划 D1 的改动项同步补上。

### 5. D5 适配器的两处来源

`RuntimeSnapshotBuilder.buildFragment()` 对两个列表的空值处理不同。drivers 可以为空，operators 不可以。生产侧的 per-operator 数据在一个 map 里，类型见数据来源，两者之间没有适配器。规划 D5 改动清单不含 `OperatorRuntimeSnapshot.java`，六步接线也没有 operator 来源。第一版传空列表可以接受，但要写出来。

第二处来源是四个无来源字段的理由。生产侧只为 wall 生成字段级理由，其余四个计时和字节字段在 `buildDriverSnapshots()` 里既不设值也不写理由。规划第 267 行要求这四项返回字段级标记，没有说由谁生成。

处置：规划 D5 补两句，一句定 operator 列表第一版的取值，一句定四个字段级理由由适配器生成。

### 6. 两份判据 5 的范围

设计第 222 行的判据 5 比规划第 308 行的窄两处。设计没有写按 driver 比较，也没有写其余字段无来源时保持字段级 unsupported。规划第 267 行有后一条，设计第 179 行至第 182 行有四条字段的逐条规则。两条判据应取同一范围。

处置：设计判据 5 补上窄掉的两处，或两份都指向同一份字段规则。

### 7. 规划改动清单的条目句式

规划的代码改动清单有 20 个条目采用文件名加描述的两句式，超出列表项一句的上限。第四轮只要求判据和验收顺序单项化，这一类漏掉了。设计第 18 行和规划第 21 行的未决问题各有一个两项条目。

处置：把条目里的第一句改成主语短语，用逗号接上描述。以规划第 125 行为例，把修改某文件后面的句号改成逗号，全清单同改。
