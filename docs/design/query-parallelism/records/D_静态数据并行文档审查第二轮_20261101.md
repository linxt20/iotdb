# D 静态数据并行文档审查第二轮

## 目的

核对 D 两份修订稿与 `/root/iotdb` 固定基线、工作区源码的一致性，指出仍然阻塞 D0-D6 实施或验收的问题，并说明初版七项阻塞意见的落地情况。

## 摘要

初版报告提出的七项阻塞意见全部进入修订稿，其中六项的改写与源码一致。第七项改错了方向：修订稿把三个扫描切分和五个记录点写成「已在生产」，而这些代码在固定基线 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520` 上并不存在，只存在于未提交的工作区。修订稿同时带回一处写作规范回归，两份文档分别出现 26 个和 27 个分号连接的从句。本轮新发现四项阻塞项：DOP 公式的第三个运算数不可计算，本地规划的实际编排者被调用链和 D0 冻结清单同时漏掉，一处行号归错形态，以及分号连接从句回归。

## 结论

五项阻塞项需要先处理，其中三项直接影响 D0 的身份冻结。最关键的一项与基线归属有关：文档把基线钉在 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`，又把只存在于工作区的代码写成生产事实，读者按基线取码会找不到文档描述的大部分对象。D1 的字节级一致性测试当前无法设计，因为 DOP 公式的第三个运算数没有可计算的来源。写作规范需要回到修订前的水平，修订前的备份副本中两份文档的分号数都是 0。

## 未决问题

- 性能倍率口径、hash join 是否进入生产规划路径、CPN 形式化是否进入论文正文，三项仍待 sxing 决定。
- memoryBudgetCap 取哪个字节字段、字节数如何换成 pipeline 数，需要 sxing 在 D0 之前定，否则 D1 的确定性测试没有输入。
- `LocalExecutionResourceRegistry.Snapshot` 属于未提交新增，D 是否以它为 memoryBudgetCap 的来源，需要 sxing 定。

## 核对范围与方法

核对对象是 sc01 `/root/w5-docs/` 下的两份修订稿，MD5 与请求给出的一致：

- 设计 `61b3953d93aec6b77dba5a165ba0d8c2`
- 规划 `d16dd7758e6537c28c0bfeb81af0e969`

源码事实由本机直接读取 `/root/iotdb` 工作区得出，并与 `git show HEAD:<path>` 的结果比对，没有委托其他会话代查。修订前的备份副本取自 `/root/property-d-artifacts/D-docs-before-review-20261101-r1/`，用于区分修订引入的问题与初版已有的问题。全程只读，未修改仓库与文档。

## 阻塞项

### 1. 「已在生产」在固定基线上不成立

严重度：阻塞 D0 与 D1。

修订稿设计第 30 至 38 行称 `DataNodeTableOperatorGenerator` 已有五个记录点和切分入口。同节还称这些路径已把四个计划字段写入 `FragmentInstanceContext`。实现规划第 9 行称当前生产代码已经覆盖三种切分。两份文档的数据来源节都把基线写成 HEAD `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`。

按该基线逐项核对，结果分两类：

| 对象 | 固定基线 | 工作区 |
| --- | --- | --- |
| `decideParallelScanPipelineNum` | 有 | 有 |
| `recordScanParallelMetadata` | 无 | 有 |
| `FragmentInstanceContext` 四个计划字段 | 无 | 有 |
| `ScanParallelPlan` 等三个类 | 无 | 有 |
| `LocalExecutionResourceRegistry` | 无 | 有 |
| `statistics/snapshot` 包 | 无 | 有 |
| 三个扫描并行配置开关 | 有 | 有 |
| `isNaturallyMergeableDeviceScanOrder` | 有 | 有 |

固定基线上确实存在的是 `decideParallelScanPipelineNum`、三个配置开关和 `isNaturallyMergeableDeviceScanOrder`。`decideParallelScanPipelineNum` 在基线上的定义位于第 1709 行，调用点在第 1612、1832、2256 行，它是基线唯一的并行度机制。

不在基线上的对象分两种。

第一种是已跟踪文件的未提交修改。`DataNodeTableOperatorGenerator` 在基线上 `recordScanParallelMetadata` 出现 0 次，工作区出现 6 次。`FragmentInstanceContext` 在基线上 `plannedDop` 出现 0 次。`setScanParallelMetadata()` 同样为 0 次。

另一种是未跟踪的新文件，`git status` 显示为 `??`，共五个：

- `ScanParallelPlan.java`
- `ScanParallelPlanner.java`
- `LocalScanPipelineBuilder.java`
- `LocalExecutionResourceRegistry.java`
- `statistics/snapshot/` 目录，含 `RuntimeSnapshotView.java`

这项工作影响实现规划的 D1。D1 第一条写保留已有 `inputDop` 与 `targetParallelism` 等四个字段，并写「已有字段不重复声明」。「已有」指向一个没有提交历史的文件，B 那一侧若改写或撤回，D1 的改动就失去可 Review 的基线。

处置：设计第 9 行与第 28 至 38 行应当区分「固定基线已有」和「工作区已有但未提交」两类，表格加一列或拆成两张表。数据来源节引用的行号应当注明取自工作区，因为基线上同名的调用点在 1612、1709、1832、2256 行，且 `recordScanParallelMetadata` 在基线上不存在。

### 2. 1480 行归错形态，SERIAL 行缺失

严重度：阻塞 D0。

设计第 34 行的表格把 1480 行归到 TIME_PARTITION 行下，写成「约 1402、1480 行」。1480 行的实际内容是 `recordScanParallelMetadata(context, "SERIAL", "PARALLEL_SCAN_NOT_SELECTED")`。TIME_PARTITION 的记录点只有 1402 行一处。

表格只有三行，没有 SERIAL 形态行。而 `SERIAL` 与 `PARALLEL_SCAN_NOT_SELECTED` 正是设计第 106 行写必须原样保留的生产值，也是规划 D1 必测行为里要验证映射可回放的两个旧值。现状表漏掉唯一产生这两个值的入口。

数据来源节把五个记录点平铺成一行，不带 mode 与 reason，读者无法从那里发现归错。五个点的实际归属是：1402 行 TIME_PARTITION，1462 行 DEVICE，1480 行 SERIAL，1510 行与 1527 行 ORDERED。

处置：设计第 34 行的表格应当补 SERIAL 行，1480 行从 TIME_PARTITION 行移出。数据来源节的记录点清单应当带上 mode 与 reason。

### 3. DOP 公式第三个运算数不可计算

严重度：阻塞 D1。

设计第 94 行给出公式 `targetParallelism = min(configuredDop, workUnitCount, memoryBudgetCap)`。同句把第三个运算数写成「query reservation 推导的正整数」，无 reservation 时取 `UNBOUNDED`。`UNBOUNDED` 不是正整数，`min` 的第三个运算数在这种情况下类型不成立。

输入表第 64 行把来源写成「query 的 MemoryPool/reservation 视图」。逐个核对可用访问器，没有一处能给出 reservation 推导的正整数上限：

- `MemoryPool.getMaxBytes()` 返回池总容量，不是 reservation。
- `MemoryPool.getRemainingBytes()` 返回空闲字节，随其他查询占用变化。
- `MemoryPool.getQueryMemoryReservationSize()` 与 `getMemoryReservationSize()` 返回 int 计数，不是字节。
- `MemoryReservationManager` 只有 reserve 与 release 两组方法，没有字节上限访问器。

文档没有写的来源反而已经存在。`LocalExecutionPlanContext.freezeResourceQuota()` 返回 `LocalExecutionResourceRegistry.Snapshot`。这是一个 record，字节字段有三个：

- `nominalShareBytes`
- `legacyCapBytes`
- `effectiveRequestBytes`

`LocalExecutionPlanner` 的两个 `plan` 重载各调用它一次。

这个来源有两个时序问题。第一，时序在 `LocalExecutionPlanner.plan()` 内部。`freezeResourceQuota()` 排在 `generateOperator()` 之后。扫描切分与并行度决策都发生在算子生成阶段，planner 决定 DOP 的时刻拿不到冻结值。第二，`Snapshot` 的 `quotaPolicy` 只有一个枚举值。该值是 `LEGACY_COMPATIBILITY`，没有非 legacy 策略可选。

退一步读配置常量可以绕过时序，但会引入另一类问题。`getMaxBytesOneHandleCanReserve()` 在 `exchangeSumNum` 非零时返回配置常量除以该值。`exchangeSumNum` 在算子生成过程中被累加。以它为上限，计划就依赖于算子生成的进度。`getRemainingBytes()` 与 `effectiveRequestBytes` 同理。这些候选都与设计第 126 行判据 1 的「相同输入产生字节级相同的计划」冲突。

这项工作阻塞规划 D1 的必测行为，其中列了「重复规划字节级一致」。运算数不可计算时该测试没有输入。

处置：设计第 64 行与第 94 行应当改成明确的单一来源，写明是 `freezeResourceQuota()` 的哪个字节字段，还是 `getMaxBytesOneHandleCanReserve()`，并给出字节数换成 pipeline 数的算式。若来源在 planner 决策时刻不可得，应当把冻结调用前移到扫描规划之前，或明确 memoryBudgetCap 只做执行前校验而不参与 DOP 计算。`UNBOUNDED` 与「正整数」的矛盾应当去掉一处。

### 4. 调用链与 D0 冻结清单漏掉 LocalExecutionPlanner

严重度：阻塞 D0 与 D2。

设计第 15 行和第 86 行的调用链、规划第 15 行的调用链，三处都不含 `LocalExecutionPlanner`。两份修订稿中该名字出现 0 次。规划 D0 第 32 行的 SHA-256 清单列了七个文件，同样没有它。

`LocalExecutionPlanner.plan()` 是本地规划的实际编排者，执行顺序如下：

1. 新建 `LocalExecutionPlanContext`
2. 调 `generateOperator()`
3. 调 `freezeResourceQuota()`
4. 调 `setMaxBytesOneHandleCanReserve()`
5. 构造内存估计
6. 调 `checkMemory()`
7. 调 `addPipelineDriverFactory()`
8. 写 `setSourcePaths()` 与 `setDevicePathsToContext()`
9. 写 `setQueryDataSourceType()` 与 `setTimePartitions()`

三类事实因此没有进入文档。第一，扫描切分与 `decideParallelScanPipelineNum` 都发生在 `generateOperator()` 内部，冻结排在其后。这是第 3 项的时序根源。第二，`checkMemory()` 可抛 `MemoryNotEnoughException`，是并行度选定之后的准入拒绝，文档没有说它与 DOP 决策的先后，也没有说被它拒绝的计划算不算 D 的失败。第三，`setTimePartitions()` 是 TIME_PARTITION 模式的既有上下文写入，设计第 86 行的优先级链只到 `recordScanParallelMetadata`，没有覆盖它。

D0 若不冻结 `LocalExecutionPlanner.java` 的 SHA-256，D2 与 D3 改动后无法证明编排层未被触动。

处置：设计第 15 行与第 86 行应当把 `LocalExecutionPlanner.plan()` 写进调用链。冻结与准入检查的相对位置也应当写明，二者是 `freezeResourceQuota()` 与 `checkMemory()`。规划 D0 第 32 行应当补 `LocalExecutionPlanner.java` 与 `LocalExecutionResourceRegistry.java` 的 SHA-256。

### 5. 修订引入分号连接从句

严重度：阻塞发布。

修订稿设计有 26 个分号，分布在 21 行。规划有 27 个，分布在 22 行。修订前的备份副本中两份文档的分号数都是 0，这一项是本次修订新增的。

典型位置：设计第 15 行用三个分号连接四个子句。规划第 51 行在一条必测行为里用了六个分号。设计第 106 行与第 110 行各在一句内堆叠多个分号。

处置：按分号拆句。设计第 15、45、50、66、78、84、86、90、94、102、106、110、114、118、119、122、126、129、130、138、146 行，规划第 9、17、22、45、51、58、60、64、72、77、83、86、96、100、104、110、127、134、135、141、145、148 行，都需要逐句处理。

## 次要问题

### 6. 单句内部名超额

设计修订稿有 5 行的内部名达到或超过 6 个，修订前是 0 行。规划修订稿有 4 行，修订前是 1 行。具体是设计第 15、17、106、110、114 行，规划第 15、32、44、104 行。设计第 106 行一句内有 13 个内部名，第 110 行有 12 个。这些行多数是字段名清单，按规范应当移入数据来源节，不放在正文句子里。

### 7. 「冻结为下表」缺少表

设计第 24 行写 fallback reason 的兼容词表已经在本版冻结为下表。fallback reason 一节是第 104 至 106 行的散文列表，不是表。文档里仅有的两张表在第 32 行和第 56 行，都与词表无关。要么把词表改成表，要么把「为下表」改成「为本节列表」。

### 8. configuredDop 与 inputDop 双名并存

修订稿设计里 `configuredDop` 出现 5 次，`inputDop` 出现 0 次。修订前两者各出现 1 次。规划 D1 第 44 行写保留已有 `inputDop`。该名字正是 `ScanParallelPlan.java` 的现有字段名。同一数量在规划里叫 `inputDop`，在设计里叫 `configuredDop`。二者应当统一，若要改名需在规划 D1 里写明是重命名而非保留。

### 9. 回退目标含义不明

设计第 98 行写在负成本、成本溢出或校验和失败时退回「完整的等量 serial/parallel-safe 计划并记录 reason」。`parallel-safe` 没有定义。若允许并行回退，判据 2 的「serial 对照结果一致」没有固定基线。若回退只能是 serial，`parallel-safe` 应当删掉。

### 10. thrift 改动条件性与判据错位

规划 D3 第 73 行把 thrift 修改写成有条件：「如 C0/D0 manifest 确认需要跨 RPC 传输」才改。设计判据 4 第 129 行、规划判据 4 第 134 行、规划 D6 验收顺序第 2 步第 125 行都是无条件的，第 125 步要在 RPC stub 上验 exchange-edge 唯一性。manifest 若判定不需要跨 RPC，这三处无法达成。条件性应当一致，要么 D3 对判据点名的字段无条件改 thrift，要么判据和 D6 第 2 步带上同一条件。

### 11. 规划头部结论节超出范围

规划第 11 行的标题是「结论与生产调用链」，节下挂了一条调用链加三段文字。规范允许文档头只有目的、摘要、一段话结论三项，未决问题集中在头部。调用链应当下移到正文，头部只留一段话结论。

### 12. 快照值对象整层缺席

规划 D5 第 96 行写 `RuntimeSnapshotView` 应当增加 actual driver count、work-unit 与 bucket 视图。两份修订稿里只出现 `RuntimeSnapshotView` 与 `RuntimeSnapshotDerivation` 两个名字。承载这些字段的值对象一个都没出现，以下六个名字在两份修订稿中的出现次数都是 0：

- `QueryRuntimeSnapshot`
- `FragmentRuntimeSnapshot`
- `DriverRuntimeSnapshot`
- `RuntimeSnapshotBuilder`
- `RuntimeSnapshotMerger`
- `RuntimeSnapshotValidity`

这六个名字在 C 两份文档里都至少出现 1 次。

值对象不增加字段，视图就没有可暴露的内容。D0 第 36 行记录新增字段时也只写了 thrift 与 `FragmentInstanceContext`，没有写快照值对象。D6 第 125 行的 RPC stub 检查因此没有可验的对象。

处置：规划 D5 应当点名要修改的快照值对象，D0 第 36 行的字段编号清单应当把快照值对象与 thrift、`FragmentInstanceContext` 并列。
