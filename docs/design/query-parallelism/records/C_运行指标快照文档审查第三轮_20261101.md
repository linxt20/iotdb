# C 运行指标快照文档审查第三轮报告

## 目的

核对 C 两份文档修订版与 `/root/iotdb` 工作区实际代码的一致性，判定 C0–C6 各阶段门能否按文档执行，并核对退出测试是否覆盖文档写明的判据。

## 摘要

本轮流转审查对象为 sc01 `/root/w5-docs/` 下的两份 C 文档修订版。审查方式为逐条比对文档陈述与工作区源码、thrift 结构和已存在测试类。核对范围包括上一轮九项必改项的落地情况、四阶段门的代码前置条件、退出测试与判据的对应关系、传输字段的完整性、验收阈值的可测性和校验和的覆盖范围。

## 结论

两份文档的表述和结构已符合技术文档规范，上一轮九项必改项全部落地。当前阻塞项是文档与代码状态脱节：文档写「本版仍是实施前设计」，而 C1 全部文件、C2 主体、C3 全部、C4 主体和 10 个测试类已在工作区，且全部未提交。其次是三个退出测试名不副实、四个 driver 字段无建值无标记、`actualDriverCount` 无传输位、CPU 阈值分母未定义、校验和不覆盖墙钟和 pipeline 身份。修复这六项之后 C2–C6 可按文档推进。

## 传输字段的缺口

`TDriverRuntimeSnapshot` 有 15 个字段，其中 5 个 optional 纳秒和字节字段。`buildDriverSnapshots` 只建值 10 个，未建值的 4 个既没有值也没有 unsupported 标记：

| 字段 | thrift 位置 | 建值 | 无值时的标记 |
| --- | --- | --- | --- |
| driverCpuNanos | 808 | 无 | 无 |
| driverReadyNanos | 811 | 无 | 无 |
| driverBlockedNanos | 812 | 无 | 无 |
| driverOutputBytes | 813 | 无 | 无 |
| driverWallNanos | 809 | 有条件 | 有 |

`driverWallNanos` 的处理方式是可参照的正确样本：值小于零时调用 `addToValidityReasons`。写入的字符串形如 `UNSUPPORTED_FIELD:driverWallNanos`。另外四个字段没有走同一分支。设计 L45 和 L99 都写缺失字段保留 validity reason，不以零值补齐。`buildDriverSnapshots` 对这四个字段的现状是读取端拿到未设置的 optional，既不是零值也没有理由。

`actualDriverCount` 没有任何传输位。thrift 的 `TFetchFragmentInstanceStatisticsResp` 31 个字段里没有 driver 计数，`TDriverRuntimeSnapshot` 也没有。规划 L60 的字段 manifest 和设计 L43 的 driver 字段穷举清单都不含它。设计 L99 把它列入 D 的静态比较必读清单，设计 L151 和规划 L243 把它列入退出判据第 5 项。D 的必读字段和退出判据引用了响应上不存在的字段。

**修订方向**：给 4 个未建值字段补与 `driverWallNanos` 相同的降级分支，或在 thrift 和 manifest 中删除并同步 D 的必读清单。`actualDriverCount` 先在 thrift 和 manifest 中定位，再决定保留还是从判据第 5 项移除。

## 验收阈值的可测性

设计 L95 和规划 L195 写 CPU 采集开销上限为「单次 processFor 采样额外耗时不超过该次切片墙钟的 1%，且单次绝对增量不超过 50 微秒」。「该次切片墙钟」在工作区有三个候选读数：

| 候选读数 | 代码位置 | 量级示例 |
| --- | --- | --- |
| 锁等待加循环 | processFor 入口到返回 | 100 ms |
| 循环体内 | start 到 while 判断 | 40 µs |
| 单次 processInternal | 一次调用 | 10 µs |

`processFor` 的锁等待上限是 100 ms，一次切片的循环体可以短到 40 µs。1% 上限按这两个读数分别是 1 ms 和 0.4 µs，相差 2500 倍。阈值本身没有指明取哪一个。

锁获取失败时还有一处采集断点。`processFor` 用 `tryWithLock(100, TimeUnit.MILLISECONDS, false, ...)` 取锁。锁等待超时后 lambda 不执行，`start` 不取值。这一次没有任何 CPU 采样，也没有对应 validity reason。被锁饿死的 driver 在快照里表现为零次采样，与采样关闭不可区分。

CPU 采代码本身不存在。`Driver` L177 的注释写「CPU is intentionally absent until ThreadMXBean is enabled」。`execution` 目录下检索不到 CPU 采样符号。`ThreadMXBean` 与 `getThreadCpuTime` 均无引用。规划 L195 的超限关闭逻辑和八驱动片段 p95 记录都还没有可执行的落点。

**修订方向**：把「该次切片墙钟」改成指名的一个读数，并给出该读数在锁等待超时时的取值规则。CPU 采集未实现期间，判据第 4 项的 CPU 分支按「无来源时断言降级」执行，阈值句移入 C5 实现后的验收条件。

## 校验和的覆盖范围

`buildStatistics` 的 checksum 输入是 instanceId、generation，以及每个 driver 的 driverTaskId、driverSampleGeneration、driverOutputRows（可选）、driverTsBlockCount（可选）。

设计 L99 把 `driverWallNanos`、`driverFirstProcessNanos`、`driverCpuNanos` 列为 D 的静态比较必读字段。这三个纳秒字段都不在 checksum 输入里。跨节点对账的核心比较量没有校验和保护。

driver 身份只覆盖了 `driverTaskId` 一项。设计 L74 规定的 driver 去重键是 FragmentInstanceId + driverPipelineId + driverTaskId + planNodeId。两个 pipeline 下 taskId 相同的 driver 贡献完全相同的 checksum 输入，pipeline 串位不会被检出。

`RuntimeSnapshotChecksum.sha256` 对每个字段先写 4 字节大端长度再写内容，不存在拼接歧义，这一点实现正确。

`snapshotGeneration` 参与 checksum。`buildStatistics` 每次调用都执行 `incrementAndGet`。同一 fragment 的两次显式抓取得到不同 generation 和不同 checksum，属预期行为。终态路径走缓存返回同一对象，generation 和 checksum 保持幂等，判据第 1 项的前半句成立。

**修订方向**：把三个纳秒字段和 driverPipelineId 加入 checksum 输入，或在设计 L74 和 L99 附近写明校验和不覆盖这些量、对账时另找一致性依据。

## 命名与位置不一致

`stableDriverOrder` 用 `Comparator.comparing(DriverRuntimeSnapshot::getDriverPipelineId)`，即字符串自然序。设计 L118 写「driver 数字排序为 fragmentId、driverPipelineId 数值、driverTaskId 字符串三层比较」。pipeline 编号为 9 和 10 时，字符串序把 10 排在 9 前，数值序把 9 排在 10 前。`RuntimeSnapshotFoldIsolationTest` 用的是 base-10 和 base-20，两种序结果相同，测试通过但设计 L118 未被满足。

driver 字段名在两份文档里有两个拼写。设计 L43 用 `driverTsBlockCount`，与 thrift L814 一致。设计 L99 和规划 L60 用 `driverTsBlocks`。

validity 枚举实际值有 15 个，名字是 `MISSING_FRAGMENT` 和 `UNEXPECTED_FRAGMENT`。设计 L76 写「多出才是 UNEXPECTED」，规划 L175 写「意外片段」，都短于实际枚举名。

设计 L83 到 L92 的字段来源表有 8 行，没有 `plannedDop` 一行。设计 L78 写 plannedDop 有结构化来源，规划 L59 把它列入 manifest。来源表覆盖不到它。

流水线字段名不一致。规划 L59 和设计 L78 用 `actualPipelineCount`、`splitMode`、`splitReason`，与 thrift L918 到 L920 一致。规划 L189 改用 `targetPipelineCount`、`mode`、`fallbackReason`。

`driverRole` 的取值只有 `input` 和 `root`。取值来自 `isInputDriver()` 的三目表达式。设计 L118 写文本 Drawer 规定「根/收集 driver 与并行子扫描 driver 的共同字段落点」，收集角色没有对应取值。

设计 L143 是一句话，含 13 个类名和两个用斜杠合并的写法（`ScanParallelPlan/Planner`、`MPPQueryContext/QueryPlanStatistics`）。规则 58 限定一句话最多两个内部量名。

有序路径的识别方式有两种互相矛盾的说法。设计 L138 和规划 L134 写「由 C2 扩展的 `isParallelSubScan` 识别」，该方法按 planNodeId 字符串后缀匹配 `-parallel-` 和 `-morsel-`。设计 L151 和规划 L125 写「结构化 planNodeId 识别」「不从后缀解析」。同一个识别点给出了字符串后缀和结构化两种互相排斥的实现方式。

thrift 行号已过期。两份文档的数据来源都写 `TQueryStatistics` 在第 798 行、`TFetchFragmentInstanceStatisticsResp` 在第 868 到 886 行，规划 L52 写「已确认」。实际 `TQueryStatistics` 在第 818 行，第 798 行是 `TOperatorStatistics` 的右花括号。实际 `TFetchFragmentInstanceStatisticsResp` 在第 888 到 920 行。文档写出的 868 到 886 落在 `TQueryStatistics` 与 `TFetchFragmentInstanceStatisticsReq` 两段上。两份文档都没有列出 `TDriverRuntimeSnapshot` 的第 800 到 816 行。

`CPN` 在规划 L272 首次出现且无定义。

**修订方向**：统一 driver 字段拼写和流水线字段拼写。枚举名补全为 `MISSING_FRAGMENT` 和 `UNEXPECTED_FRAGMENT`。字段来源表补 `plannedDop` 一行。设计 L143 拆成多句。有序路径只保留一种识别方式并与 `isParallelSubScan` 的现状对齐。thrift 行号按当前文件重写并加入 `TDriverRuntimeSnapshot`。定义或删除 `CPN`。
