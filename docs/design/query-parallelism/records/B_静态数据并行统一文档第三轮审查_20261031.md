# B 静态数据并行统一文档第三轮审查

**目的**：核对 B 的两份第二轮正文与一份处理说明能否进入代码实施，逐项判定复审报告十条意见的处理结果，给出第三轮新发现问题的文档位置、源码依据、反例与修改要求，并把已证实缺陷与待执行验证分开。

**摘要**：B 要把 IoTDB 本地查询执行里三条已有的扫描拆分路径接到同一套构建与登记流程上，同时让交换对象的内存额度、记账键与失败清理可被逐项断言。三份第二轮文档给出了文件级方案。本文按固定源码基线逐条核对十条意见的处理结果，并独立核查其中七个重点条目。审查只读源码与文档，不运行测试，也不改动仓库。

**结论**：复审十条意见中九条得到可实施处理，本文新发现一条 P1 与四条 P2。这条 P1 是设计第 185 行的轮询门限算例把两个不同片段形态的数值写成一个形态，使规划第 157 行要求拒绝的反向副本在生产形态上与正确实现给出同一结果。该条修改完成前，两份正文不进入实施，四条 P2 与它一并修改。

## 审查任务与判定标准

一条查询可以在本地把扫描工作拆成多条流水线。拆得好不好有两条判据。第一条是扫描范围：所有分支读到的设备与时间分区组合合起来必须等于输入集合，任一组合只能出现一次。例如六台设备各有三个时间分区，输入是十八个组合，重复读一个分区会多出三行，漏读一个分区会少三行，两种错误在行数上方向相反，只看输出行数分不出来。第二条是资源释放：申请失败、查询取消或驱动创建失败时，已经建立的队列、算子与驱动必须全部关闭，内存预留必须回到进入值。例如三个驱动里第二个创建失败时，第一个驱动的队列必须关闭，交换池剩余字节必须回到进入值。

本文核查支撑这两条判据的文档陈述与源码是否一致，不运行任何测试。受审文档是三份 2026-10-31 的第二轮稿，分别是静态数据并行统一设计、静态数据并行统一实现规划与复审处理说明。审查方法是读取源码，比对文档写出的方法名、字段名、算术式与数值。

分级按三条定义。P0 表示正确性或方向存在阻断，实施前必须解决。P1 表示关键行为或验证存在缺口。P2 表示文字与位置存在问题。每条意见写出文档位置、源码方法、具体反例、影响与可验证的修改要求。

本文的判定分两类。已证实问题有源码依据，本文直接给出结论。待执行验证只有测试运行才能裁定，本文列进第 6 节待执行验证清单，不预先判定。

数据来源：源码基线是 sc01 上一处仓库的 next-p0 分支，提交号为 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`，仓库根目录为 `/root/iotdb`。受审文档位于 sc01 `/root/w5-docs/`，文件名为 `B_静态数据并行统一设计_20261031_第二轮.md`、`B_静态数据并行统一实现规划_20261031_第二轮.md` 与 `B_静态数据并行统一复审处理说明_20261031.md`。被复审报告为同目录的 `B_静态数据并行统一文档复审_20261031.md`。下文仓库路径均相对于 `/root/iotdb`。

## 轮询门限算例的形态核查

本节问题是第三轮新发现，编号与复审报告的 P1 编号无关。设计第 185 行给出的算例把 3,016,881 字节与 804,501 字节写成同一形态的两个数，源码里没有一个形态同时产生这两个数。

3,016,881 字节是四通道轮询 sink 的构造门限，算法是 4,022,509 除以四再乘三。该形态的局部计数为一。它的最终句柄额度为 4,022,509 字节。804,501 字节是表模型四条扫描流水线加一个 sink 的最终句柄额度，算法是 4,022,509 除以五。该形态的 sink 使用明文策略，不构造轮询门限。两个数各自可以构造，放在一句话里作为同一形态的两个值无法构造。

轮询策略在源码里只有一个生产选中点，位于树模型的 shuffle sink 访问方法。本地扫描流水线的多条拆分只出现在表模型的算子生成器里。表模型生成器不继承树模型生成器，它单独实现计划访问接口，由本地规划器按 SQL 方言选择。表模型的 shuffle sink 与 identity sink 两个入口都用明文策略。所以一条片段里不会同时出现轮询 sink 与多条本地扫描流水线。

树模型这一侧也到不了计数五。轮询 sink 的访问方法先把局部计数器加一，随后把并行度设为一，再进入子流水线拆分助手。并行度为一时该助手走不拆分分支，不新增计数。分布规划器在每个交换节点处切断计划树，并把每个 sink 节点单独作为子计划根。因此以轮询 sink 为根的片段，其子树不含交换节点，也不含嵌套 sink。树模型生成器的局部计数器只有三个自增点，每点加一，三个都不在该子树内可达。

这一形态还带出一个验证后果。规划第 157 行要求拒绝一个用规划后句柄额度反推构造门限的副本。在轮询 sink 形态里，最终句柄额度恒等于构造时用的完整片段预算，用前者反推得到的门限与后者相同，都是 3,016,881 字节。该副本在生产形态上与正确实现给出同一结果，第 157 行的退出条件无法区分两者。要让这条反向断言生效，测试必须把一个生产不存在的句柄额度注入策略对象，再断言门限保持 3,016,881 字节。这一注入动作三份文档都没有写。

修改要求分两处。设计第 185 行与规划第 151 行把算例拆成两个可构造形态。树模型一侧写四通道轮询 sink，子树只有本地算子，局部计数为一，构造门限 3,016,881 字节，最终句柄额度 4,022,509 字节。表模型一侧写四条本地扫描流水线加一个明文 sink，局部计数为五，最终句柄额度 804,501 字节。规划第 157 行把反向副本改为手工注入句柄额度 804,501 字节，再断言门限仍为 3,016,881 字节，并写明该额度只由测试注入。处理说明第 49 行同步修改。

数据来源：下列位置均相对于 `/root/iotdb`，模块前缀 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/` 已省略。

## 本轮新发现的位置与文字问题

四条 P2 分别关于退出条件遗漏、反向算例对不上、执行顺序未列入修改清单、一致性断言缺前提。四条都不改变实施方向，与第 4 节的 P1 一并修改后进入实施。

### B0 退出条件与 32 桶形态确认

规划第 295 行把 32 桶形态的可实施性确认派给 B0，规划第 299 行要求 B0 确认该入口能构建、序列化并绑定实际节点，还要保存对象身份清单与计划 SHA。规划第 41 行的 B0 退出条件只写六类定向测试全部成功、形态与资源对象清单可重放、配置在每个测试退出时恢复，没有这一项。B0 可以满足第 41 行而未确认 32 桶形态，缺口到 B6 才暴露，而 B6 的工期估计为半日至二日。修改要求是在第 41 行退出条件加入一项：32 桶纯 sink 形态完成构建、序列化与节点绑定，并保存源纯 sink 的完整对象身份清单与计划 SHA。

### 反向核查算例的对象数

规划第 313 行写漏登记后独立对象清单包含八项而冻结计数只有七项。设计第 129 行的规范算例是七项，由四条本地流水线、一条远端输入与两个各含一条通道的远端输出组成。规划这句话把真实数写成八，且未说明是哪个形态。实施者无法从这句话还原该构造哪张对象清单，反向断言的目标值不确定。修改要求是把该例改为设计第 129 行的七对象形态，写成独立枚举得到七项、故障副本的登记表记录六项。

### 冻结与内存估计的先后顺序

设计第 205 行与规划第 163 行都要求先冻结真实交换对象，再构造完整内存估计，最后执行全局算子内存申请。源码顺序相反：本地规划器先构造内存估计，再执行全局申请，最后发布句柄额度。规划第 169 行的修改位置只列出本地规划器的两个 plan 方法与 checkMemory，没有写调用点重排。实施者按字面执行会把冻结留在估计之后。修改要求是在第 169 行写明句柄额度发布点移到内存估计构造之前，并把冻结先于估计列入该小节退出条件。

### 查询级一致性断言的读取前提

规划第 249 行说查询级总数在终态静止点用同一份账户快照求和，必须等于所有片段数之和。规划第 251 行的示例丢掉了这个前提，把关系写成快照内的恒等说法。拟新增的片段级读取入口每次只读一个片段，查询级总数是另一次读取，两次之间没有共同锁。实施者照第 251 行写断言会用两次无同步读取，该断言在并发下会偶发失败。修改要求是在第 251 行补上静止点前提，或新增一个查询级快照入口一次返回全部片段读数。
