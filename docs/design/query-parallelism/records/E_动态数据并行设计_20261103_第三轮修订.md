# E 动态数据并行设计

目的：定义扫描并行计划如何复用运行统计，并规定反馈来源、调整边界、内存准入和验收方法。

摘要：同样数量的设备可能需要不同的扫描时间。静态计划可以利用已完成扫描的记录改进下一次分配。本文给出反馈的保存和读取路径，并定义计划调整的条件。实现按配套规划逐步验证。

结论：E 是待实施设计，反馈只影响尚未构造执行资源的片段。运行中的驱动保持原计划，选定计划只执行一次内存准入。A–D 的前置验收与冻结生产版本统一由 [A–D 完整实现补全核查](A-D_完整实现补全核查_20261102.md) 维护。

## 未决问题

- CPN 是否进入论文正文，等 sxing 决定。

## 任务背景

E 调整下一片段的扫描分配，并保持结果完整。一次片段执行开始后，工作单元的归属固定。主要反馈来自相同查询形态的已完成执行，历史只在该 DataNode 本地使用。

同一查询的前序片段也可提供反馈。它必须先于后续规划完成，且端点、区域和形态都匹配。并发扇出分支没有这种先后保证。前序片段位于另一 DataNode 时，本地历史不可见。系统有可用反馈才使用，禁止跨节点拉历史或等待前序完成。无反馈时采用 D 的静态计划。

例如，三个扫描组的成本为 9000、6000、1500。相同数量的设备仍可能产生不同的完成时间。E 用已完成记录估计后续工作的成本，然后重新分组。验收同时检查完整结果、工作覆盖和实际采用的计划。

E 覆盖 D 的设备、时间分区和已证明自然顺序的扫描入口。任意连接重分区、执行中扩缩容和运行中迁移属于独立设计范围。D 的属性守卫继续决定哪些扫描允许拆分。没有扫描任务的根片段保留拓扑身份，其零扫描并行度不参与扫描调度。

数据来源：工程为 sc01 `/root/iotdb`，分支为 `feat/next-p0`。固定基线为 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520`。E 的生产代码尚未实施。

E 的前置版本使用最终冻结源码及其发行包。核心、RPC、单源三十二桶、一般资源与真实数据非法块已有同版运行证据。无序收集与受检内存估计已接入表模型，候选大输入通过仅覆盖活性。原八项反证已完成组件身份与变动生成器的适用性审核。完整模块与补充边界均已完成同版独立终态审核。前置状态统一见 [A–D 完整实现补全核查](A-D_完整实现补全核查_20261102.md#原合同与证据)，原因语义沿用 [D 原因分类](D_静态数据并行设计_20261101.md#退回原因)。本文的反馈历史、生产配对、策略和回执属于 E 待实施范围。

数据来源：[A–D 完整实现补全核查](A-D_完整实现补全核查_20261102.md#原合同与证据) 保存前置范围与权威回执。研究验收工具 r14 单独绑定版本，其源码身份与生产构建 manifest 分别记录。

## 术语与身份

工作单元是所选计划内固定归属的扫描范围。D 静态路径按目标并行度生成分组，工作单元数与桶数相等。E 在规划期另算设备组和时间组，允许多个工作单元归属同一个桶。执行开始后不再拆分或移动它们。

扫描桶是一条本地扫描流水线接收的工作集合。扫描桶与 GROUP BY 的哈希交换桶分别编号。历史语义键描述真实设备和时间范围，运行工作单元 ID 则属于该次计划。

查询形态描述可以共享反馈的扫描语义。它包含数据库、表、区域、设备集合和时间谓词。它也包含过滤表达式、字段类型、排序条件和拆分模式。改变其中任一内容，都必须得到不同的形态校验和。

运行身份用于校验一份快照的来源。历史匹配身份用于判断下一计划能否使用该反馈。运行身份保留查询 ID 和片段 ID。历史匹配身份使用稳定的扫描语义键。

例如，两次相同扫描的查询 ID 可以不同。它们可以作为两条历史记录，但禁止对它们做计数差分。设备从 d0 改成 d1 时，即使设备数量仍为一，历史匹配也必须失败。

历史源使用扫描语义位置区分同表的两个输入。该位置由规范计划遍历和别名绑定生成，运行期节点 ID 只用于配对。查询 ID 改变时，历史语义键保持稳定。

数据来源：新增 `DynamicQueryShape` 和 `DynamicWorkUnitKey`。运行键沿用 C 的 query、fragment、driver 身份。新增 `sourceSemanticKey` 保存稳定扫描位置，历史键必须包含真实设备值。

## 指标复用

E 复用 C 已冻结的驱动输出行数、TsBlock 数和墙钟时间。算子统计继续由 IoTDB 的计时与计数入口采集。E 新增计划归属、独立反馈保存和决策记录。

缺少 CPU、输出字节、就绪时间或阻塞时间时，相应派生值保持字段级不支持。全局调度器计数只能描述 DataNode。禁止把全局阻塞数推断成某个扫描桶的阻塞数。

B 的资源观察窗口服务于隔离验收，使用显式开启、有界保留的本地 JMX 接口。E 的生产策略读取 C 的冻结快照与自身历史。内存拒绝反馈读取原单次准入结果，动态运行无需保持资源观察窗口开启。观察用的完整片段 ID 含查询 ID，内存池账户把查询与短片段 ID 分开保存。转换只服务账目核对，E 的稳定扫描语义键沿用本设计的定义。

规划前取消可能只有真实取消终结证据，尚无驱动样本。B 的取消终结证据证明该生命周期已经结束，规划开始标志继续为假。

本地窗口的 `sharedQueryContextPresent` 用于检查查询终止后的共享映射。这些清理读数不提供扫描成本，也不进入 E 的驱动反馈估计。

例如，两条驱动输出 10 行和 20 行，已配对扫描桶的总行数为 30。同一行经过扫描和过滤算子时，只采用 C 的单驱动输出值。禁止再次相加各算子的行数。

数据来源：B 的本地观察入口为 `MPPDataExchangeServiceMBean`，窗口由 `ResourceAuditManager` 管理。观察输出使用 `fragmentInstanceId`，账户输出使用 `memoryFragmentInstanceId`。C 的字段来源见 [A–D 运行字段来源](A-D_运行字段来源_20261102.json)。驱动协议为 `TDriverRuntimeSnapshot`。输出行数与块数字段为 `driverOutputRows` 和 `driverTsBlockCount`。墙钟来源为 `driverWallNanos`。缺失原因沿用 `UNSUPPORTED_FIELD:<field>`。全局查询和交换来源为 `QueryMetricsManager` 与 `DataExchangeCostMetricSet`。扫描和调度来源为 `SeriesScanCostMetricSet` 与 `DriverScheduler`。

## 驱动与扫描桶配对

计划构造器在创建扫描流水线时登记归属。配对使用实际流水线 ID，禁止从桶序号推算驱动 ID。每个配对还保存源扫描 ID，避免两个源的桶零发生冲突。一条驱动可以拥有多个配对，禁止将其压成单个源字段。一个片段的多源决策按源扫描 ID 分别保存。片段级准入结果再关联到这些决策。

复合键由片段、源扫描和实际流水线组成。同一源的每个工作单元必须恰好归属一个扫描桶。只消费交换的根合并驱动和交换专用驱动没有扫描桶，配对字段保持缺失。串行驱动直接拥有扫描时，仍须登记实际配对。driverRole 仅用于展示，反馈资格根据显式配对判定。

D 的片段级桶列表按源 ID 的字典序组合，再重新编号。其容器使用 TreeMap，源字符串“10”先于“2”。这是全局唯一的展示身份。

E 的配对条目保存每个源自身的桶编号。来源与源内编号一起识别实际扫描桶，禁止拿片段级展示编号替换源内编号。

例如，源 a 和源 b 各自只有桶零，D 的组合列表可以显示零和一。E 的两条配对分别保存 a 的零桶与 b 的零桶。一个源的两个桶同时包含工作单元 d0 时，配对校验必须失败。

协议在驱动快照中增加可选配对列表。每个条目保存源扫描、扫描桶及工作单元。冻结入口按实际驱动写入列表，接收方通过同一适配器构造不可变副本。缺少配对的节点保留兼容读取，反馈资格为不支持。

串行扫描在其生成入口登记该驱动上下文及源归属。公共构建器登记并行扫描归属。根 factory 加入后执行统一校验，冻结时补入实际任务身份。一个驱动拥有两个串行源时，两条配对分别保存，驱动计数只取一次。

例如，同一驱动读取源 a 与源 b，各自桶零。它必须传输两个配对条目，不能只保留最后一个源。其一百毫秒总时间只有一份，禁止给两个源分别记一百毫秒。

数据来源：新增 `DynamicDriverBucketAssignment`。运行归属保存 fragmentInstanceId 和 sourcePlanNodeId。驱动键保存 driverPipelineId 和 driverTaskId。工作归属保存 bucketId 和 workUnitIds。修改 `DataNodeTableOperatorGenerator` 的串行入口与 `LocalScanPipelineBuilder`。根 factory 接线修改 `LocalExecutionPlanner`。`FragmentInstanceContext` 按实际流水线保存列表。`FragmentInstanceExecution.buildDriverSnapshots()` 写入 optional `scanAssignments`。协议路径为 `iotdb-protocol/thrift-datanode/src/main/thrift/datanode.thrift`。

## 反馈保存与规划期构造

每个 DataNode 持有一个可注入的有界历史存储。动态开关默认关闭，片段在创建时固定该开关值。普通查询仅在开关开启时增加终态冻结。EXPLAIN ANALYZE 保持原有终态统计。开关关闭的普通查询不增加冻结开销。

### 终态构造与独立发布

源码的终态监听只为 EXPLAIN ANALYZE 调用统计构造。E 必须在该监听中主动增加普通查询路径，不能等清理后调用统计 RPC。该 RPC 对普通终态上下文可能返回 NOT_FOUND。

终态监听取得统计写锁，先记录各驱动的完成统计。满足展示或动态采集条件时，调用一次 `buildStatistics()`。同一次构造同时供展示和反馈使用，禁止重复增加采样代次。展示缓存仍由原上下文保存。

锁内将响应和已冻结的计划元数据深拷贝为发布载荷。拷贝必须隔离 Thrift 的可变列表，发布方不得再改动它。计划元数据在资源构造前登记，包含真实设备和时间范围。它也包含工作单元、源内桶和实际流水线的映射。仅复制工作 ID 无法支持下一次重分组。

释放统计写锁后，发布器才计算存储计费并写入历史。序列化、淘汰和历史锁都在统计锁外进行。发布先于驱动关闭和上下文清理，清理由 finally 保证执行。构造、拷贝或存储失败只放弃这条反馈，并记录原因。不得跳过原有清理，也不得改变已完成查询的业务状态。

锁内构造复杂度为 O(驱动数＋算子数＋配对工作引用数)。独立深拷贝再增加 O(响应载荷＋计划元数据)。不能从这些量承诺固定毫秒上界。E 将新增拷贝限制在 32 MiB 的保守内存计费内。配对条目最多 4096 个，工作引用最多 16384 个。超界时丢弃动态发布，展示路径仍按原合同执行。

计划登记时先核对元数据预算。锁内使用有界遍历估计复制大小，达到预算即停止。禁止在锁内通过序列化计算大小。测试记录锁内构造和复制耗时，分别报告驱动数与载荷大小。它们用于评估开销，不能替代资源上界或制造固定延迟保证。

### 规划期读取与源内选择

本地规划器在构造算子树之前调用规划服务。服务提取扫描语义，读取同形态、同区域和同端点的冻结响应。按来源查询适配和合并后，生成只读反馈视图。此时只准备反馈，不预先决定扫描并行度。

各扫描入口先完成 D 的输入构造，包括可选的数据量估算。服务再依据该源的实际输入选择计划。静态加权分支还要确定最终生效分组。源在构造子扫描前登记最终计划，算子树完成后统一冻结决策映射。一个源不得覆盖另一个源的决策。整个过程不创建候选驱动或交换端点。

该路径在规划期直接执行，与 EXPLAIN ANALYZE 的执行后渲染分别调用。读取方只持历史接口，不能等待统计写锁。历史独立持有副本，IoTDB 删除片段上下文不影响记录寿命。

例如，匹配的本地片段在 10:00:07 冻结。后续在 10:00:08 规划时可以使用它，10:00:06 规划时则使用更早记录。系统禁止等待它完成来制造反馈。

### 发布范围与存储上界

每条记录保存发布方预先登记的片段身份。单片段反馈只声明该片段完整，不能声明整个分布式查询完整。预期集合来自规划登记，禁止从收到的响应键反推。

例如，双节点查询在本地只保存片段三的终态。它可以提供片段三的成本，不能证明远端片段四的统计完整。

每个历史键最多保存 1024 条样本，保留 30 分钟。整个存储最多保存 4096 条样本、256 个键和 32 MiB 计费数据。响应副本与计划元数据都计入字节上限。达到任一上限时，按接收时间淘汰最早记录。按运行身份和代次去重，禁止另建无界元数据缓存。

数据来源：新增 `DynamicSnapshotRecord` 和 `DynamicSnapshotHistoryStore`。记录独立响应和源计划覆盖。新增 `DynamicSnapshotPublisher`。终态位置为 `FragmentInstanceExecution.initialize()`，构造为 `buildStatistics()`。规划准备为 `DynamicParallelPlanningService.prepare()`，源内选择新增 `selectScanPlan()`。视图沿用 C 的接收、合并和适配入口。

## 协议与校验和

复用外层响应已有的 `schemaVersion` 字段 18。它是唯一版本判据，禁止根据配对列表是否存在推断版本。E 的写入方和 Java 片段快照必须保存相同版本。第二版发布路径对所有响应写 2，与动态开关是否开启无关。

| 外层版本 | 校验算法 | 展示与反馈 |
| --- | --- | --- |
| 1 | 原 C 算法，字节序列完全不变 | 可展示，缺扫描配对时不参与 E 成本 |
| 2 | 第二版域标记、版本及规范配对编码 | 自校验与覆盖均有效后才可反馈 |
| 缺失 | 不推断为 1 | 标记 LEGACY_UNVERSIONED，只作兼容展示 |
| 未知 | 不尝试降级算法 | 标记不支持版本，只保留可解析的展示值 |

第二版规范编码按源、桶和工作 ID 排序。缺失列表使用专门标记，不能与空列表混同。仅交换或根合并驱动没有配对，响应仍是第二版。扫描驱动缺少配对时拒绝动态反馈，不能退回第一版算法。

例如，版本 1 且无配对时仍按原算法验证。版本 2 且无配对时按第二版验证。版本 2 的工作单元从 d0 改成 d1，校验和必须改变。版本 1 携带第二版配对属于版本与载荷不一致，拒绝反馈。旧接收方无法验证第二版时，也不得使用动态成本。

数据来源：协议复用 `TFetchFragmentInstanceStatisticsResp` 字段 18。新增驱动内的可选配对列表。`FragmentRuntimeSnapshot` 新增不可变版本字段，旧构造入口显式委托到版本 1。适配器必须读取外层版本，缺失版本保持独立状态。`RuntimeSnapshotChecksum` 按该字段分支。两个统计 Drawer 读取同一值对象，不自行猜版本。

## 输入资格与差分

动态输入必须通过响应自校验、端点核对和计划归属检查。缺失片段、意外片段、过期样本和重复身份均使样本失效。历史存储使用本机接收时间检查过期。跨节点纳秒时钟只用于各响应内部记录。

计数差分只接受同一查询、片段、计划代次和驱动集合。后一个样本的代次必须更大。任一计数回退时，整个差分返回无效。运行快照校验和允许变化，计划身份必须相同。

例如，同一驱动两次输出 20 行和 35 行，增量为 15。第二次只有 10 行时，差分无效。两次属于不同查询时，即使都是 35 行，也必须拒绝差分。

差分覆盖行数、TsBlock 数、墙钟、样本代次和字段资格。墙钟缺失时，行数差分仍可独立有效。跨查询终态样本用于历史成本估计，按各自运行身份校验后匹配语义键。

数据来源：扩展 `RuntimeSnapshotDelta.between()`，新增结构化驱动键。片段资格沿用 `RuntimeSnapshotValiditySet`。必须拒绝参与调整的样本资格如下。

- `PARTIAL` 表示返回不完整。
- `STALE` 表示样本过期。
- `CHECKSUM_MISMATCH` 表示自校验失败。
- `MISSING_FRAGMENT` 表示预期片段缺失。
- `UNEXPECTED_FRAGMENT` 表示出现意外片段。

## 成本与策略

历史成本优先采用有效墙钟与已完成工作量。只有一个归属条目的驱动可以直接提供该桶时间。一个驱动有多个源归属时，先按工作量分摊驱动时间，再在各桶内分摊。所有分摊值都保存估计来源，禁止将其报告成逐设备实测。

例如，一条驱动耗时一百毫秒，两个源工作量为一和三，分别分摊二十五与七十五毫秒。两个源成本之和仍为一百毫秒。

历史记录不足时，估计器使用 D 的文件大小成本。文件大小也缺失时，估计器使用等量成本。输出行数只描述产出，过滤结果为零时仍可能有扫描成本，因此禁止直接把零输出解释成零成本。

至少两个有效桶、两条完整反馈和连续两次同向差异才能触发重分组。至少两个桶具有正成本，且最大与最小正成本之比大于 1.50。零成本桶不进入比值分母，但仍参与覆盖和重分组。正成本桶不足两个时保持静态计划。

例如，9000、6000、1500 的比值为 6，满足比值条件。6000、5500、5000 的比值为 1.2，保持静态计划。9000、1500、0 的正成本比值仍为 6，三个桶都参与重分组。9000、0、0 只有一个正成本桶，保持静态计划。首次满足条件只保存方向，第二次同向满足才调整。

历史粗分组不能直接充当新细分组的实测成本。聚合器按真实范围核对新旧覆盖，再按文件字节或等量权重分摊。不能证明精确覆盖时，改用 D 的成本估计。一个旧组包含 d0 至 d2，成本为 9000。等权细分后各估计 3000，总和仍为 9000。不能整除时按稳定单元次序分配整数余数，累计值不得溢出。这三份成本标记为 BUCKET_AVERAGE，不能标成逐设备实测。

反馈方向反转后，策略冷却连续三次规划检查。冷却检查次数使用同一历史键的单调序号。并发请求通过该键的原子更新取得唯一序号。

数据来源：新增 `DynamicCostHistoryStore` 作为历史响应存储的成本视图，容量沿用上一节的统一上限。新增 `DynamicSnapshotAggregator` 和 `DynamicParallelScheduler`。成本来源分为实测与估计。`MEASURED_BUCKET` 保存独占桶时间，`BUCKET_AVERAGE` 保存分摊值。`TSFILE_BYTES` 保存文件字节估计，`EQUAL_WORK` 保存等量估计。

## 并行度与动作

### 并行度上限的读取点

扫描入口先读取上下文并行度，记为 `contextDop`。可选的数据量估算完成后，再构造 D 的不可变输入。该输入的 dop 才记为 `inputDop`。动态选择从这个实际输入读取上限，禁止绕过估算压减。

目标公式为 `targetDop = min(inputDop, workUnitCount, policyDop)`。每次反馈最多改变一个并行度等级。覆盖减少或安全守卫可以直接压低上限。空输入与强制串行沿用 D 的计划。

例如，上下文为 8、估算为 2，策略提出 4，最终最多为 2。估算关闭且有五个工作单元时，策略提出 4，最终为 4。前次为 4 时，普通反馈只能提出 3、4 或 5。工作减少到两个时，最终压到 2。

回执保存数据量估算开关、估算状态和估算值。它同时保存上下文值、实际输入上限和目标值。不可变输入不增加 setter，也不靠覆盖 dop 字段承载重分组。

### KEEP_STATIC

反馈不足或样本不合格时，返回 D 的完整静态计划。保留其原分组和加权时间分区行为，并记录被拒样本与原因。E 关闭时跳过历史读取和额外终态冻结。

### REBALANCE_NEXT_FRAGMENT

E 负责生成不可变的设备组和时间组。新增分组对象连同目标桶数送入扫描计划器。计划器复用 D 的守卫、工作单元构造及 LPT 分配。桶数与工作单元数因此可以不同。

设备与有序模式最多生成 1024 个设备组，按原输入顺序连续切分。有序模式保留原顺序证明。时间分区模式先取时间组数，再取设备组数。两者乘积不能超过 1024，也不能超过各维实际元素数。只物化分组，禁止展开全部设备与时间分区的笛卡尔积。

分组内保存真实设备值和时间分区值。每个维度必须无重叠、无缺失，与原输入完整相等。计划器构造分组间的工作单元，再验证每个单元只归属一个桶。每个源的工作单元最多 1024 个，超过预算或验证失败时返回静态计划并保留原因。

例如，12 个设备按静态 DOP 4 生成四个粗单元。E 为下一片段生成 12 个单设备单元，再分入四个桶。四个单元成本为 9，四个为 6，四个为 3。LPT 得到四个总成本均为 18 的桶。桶数仍为四，分组已改变，因此这个动作区别于降低并行度。

LPT 保留 D 的平局规则。先按成本降序，再按运行工作单元源 ID 的字典序。每次选负载最低的桶，负载相同则选桶下标较小者。历史语义键只匹配成本，不替换该排序键。

例如，同成本工作单元的源 ID 为“10”和“2”时，“10”先分配。即使语义键按数值设备编号把 d2 排在 d10 前面，也不能改变此顺序。

### 扫描消费入口保持所选分组

设备扫描将桶内工作单元合并为完整设备集合。自然顺序扫描还要按原已证明的设备顺序重排桶内集合。不能直接按 LPT 插入顺序拼接，否则可能破坏排序证明。

时间分区扫描的动态分组分支逐个消费桶内工作单元。已有文件大小加权逻辑不得再次替换这些分组。静态保持分支继续使用原加权逻辑。元数据、配对和实际子扫描都必须来自最终生效计划。静态路径完成加权替换后才登记该源最终计划，不能提前冻结过期分组。

### REDUCE_DOP

前次同形态的内存准入拒绝可以降低下一次请求目标。前次目标减一，并受实际输入上限与串行下限限制。动态分组仍通过同一纯计划入口产生。禁止从全局阻塞数猜测拒绝。

例如，目标四因算子内存不足被拒，下一请求可以选择三。目标一仍被拒时，后续保留原因并使用串行准入。该请求本身不重试多个 DOP。

### SERIAL_FALLBACK

属性守卫要求串行时，使用 D 的串行计划。缺少自然顺序证明、全局 limit、offset 或 spill 限制继续沿用 D 判定。E 不放宽这些守卫。

数据来源：新增 `DynamicScanGrouping` 及其有界构建器。计划器新增 `planWithGrouping(Input, grouping, targetDop)`。原 `plan(Input)` 与三个输入构造入口保持静态行为。输入增加只读 getter，目标作为独立参数传递。`createStaticScanPlan()` 拆出输入构造与选择过程，估算压减发生在选择之前。三个消费入口位于 `DataNodeTableOperatorGenerator`。

## 内存准入与生命周期

一个选定计划只构造一次执行资源，只执行一次真实内存准入。静态分组和历史计算均为纯计算。禁止调用有预留副作用的接口试探多个成功候选。

通过准入后，规划器冻结决策回执并创建驱动。准入拒绝时，原有失败清理释放该次规划资源。管理器保存拒绝回执，下一请求才能据此降级。该请求按 IoTDB 的内存失败合同返回错误。

例如，准入分配 120 MiB，运行期算子再申请 30 MiB。准入计数仍为一次分配、一次释放，分别对应那笔 120 MiB。共享池还会观察到运行期操作。验收不能把共享池的总调用次数断言为一。失败准入增加零字节，禁止试探多个候选累积预留。

两个内存开关均关闭时，准入状态记录免检查原因。最高优先级在内存不足时取得零预留，也记录独立原因。这两种成功只表示允许执行，禁止将它们解释成测得的内存容量。动态并行度由上节公式决定。

选定计划沿用 B 的完整树额度发布与原子收紧协议。名义份额只用于诊断，禁止将其解释成实际预留或内存容量。运行中的队列继续由 B 的冻结和关闭协议管理。决策保存新片段的计划值，禁止重置共享队列。片段生命周期和关闭槽保持原责任。

数据来源：真实准入为 `LocalExecutionPlanner.checkMemory()`。它保持私有，只为该次选定计划调用一次。分配与释放计数只限定该准入账户。拒绝回执由 `FragmentInstanceManager.execDataQueryFragmentInstance()` 的规划失败分支提交。免检查使用 `ADMISSION_ACCEPTED` 加 `CHECK_DISABLED` 原因。最高优先级零预留使用 `HIGHEST_PRIORITY_ZERO_RESERVATION`。准入只处理已选计划。

## 决策回执与验收

每次决策保存输入身份、目标计划和准入结果。回执在准入前标记待定，通过或拒绝后原子定稿。重复读取必须得到同一份定稿。重复派发继续按 IoTDB 的重复 RPC 规则拒绝，禁止再次构造和预留。

跨侧验收比较完整业务多重集。有序查询额外比较完整行序列。不同并行度的驱动数量和逐驱动行数可以不同，因此每份快照分别检查覆盖与归属。

历史记录还保存真实分组的规范校验和。它覆盖设备、分区、成本来源和归属，接收时与响应中的工作 ID 配对核对。篡改计划覆盖而不改工作 ID 时，也必须拒绝历史输入。

运行快照校验和只检查各响应自身。两侧采样时间不同，禁止要求这两个校验和相等。计划校验和按各自输入重算。新旧分组粗细可能不同，跨侧比较真实设备和时间覆盖域。禁止要求工作单元 ID 或数量相同。

例如，候选四条拥有扫描配对的驱动各输出八行，对照一条输出三十二行。两侧扫描覆盖均为三十二行，业务结果一致。合并根输出单独保存，禁止再加进扫描覆盖。候选漏一个工作单元时，即使聚合后行数相同，覆盖检查仍必须失败。

数据来源：新增 `DynamicParallelScheduleDecision` 和 `DynamicDecisionReceipt`。动作记录为 dynamicAction。原因记录为 rawReason 和 canonicalReason。并行度记录为 contextDop、inputDop、previousDop 和 targetDop。估算记录为 dopEstimationEnabled、estimateStatus 和 estimatedDop。分组记录包含 groupingChecksum、实际工作单元数和桶数。准入记录为 admissionStatus 和 admissionReason。输入校验记录为 inputSnapshotChecksum 和 inputPlanIdentityChecksum。工程身份还必须包含 HEAD、工作区 manifest、配置 SHA、server jar SHA 和 Thrift jar SHA。
