# B 静态数据并行统一文档复审

## 目的

逐项复核 20261031 三份文档对 20261028 一轮审查给出的 2 条 P0、8 条 P1 和 5 条 P2 的处理是否明确、可实施、可验证，独立核查七个重点项在基线源码中的真实行为，给出新发现问题的文档位置、源码方法、反例、影响与可验证修改，并判定两份正文能否作为 B 阶段编码的依据。

## 摘要

三份文档对一轮 15 条意见都有落到文字的处理，P0 两条的处理方向与源码一致。关闭槽一项指向的基线缺陷成立：`FragmentInstanceContext` 的关闭计数在所有驱动创建完成后才初始化，驱动销毁却会递减它，构造中途失败会走到空指针或永久等待。多通道轮询门限的定性与源码一致，源码里该门限只作为简单轮询策略的选路条件，预留额度由通道和内存池分别执行。本轮新发现 6 条 P1 和 4 条 P2。P1 集中在 B4 的限额机制与验收断言。按真实对象数算出的分配目标在所有可构造形态下都不高于兼容下限，首版不改变任何对象的最终额度，而规划写的退出条件只断言最终额度不低于基线，一个把 32 个通道数成 1 个的实现照样通过。另有一条是同节点跨片段共享队列的内存记账键属于上游片段，规划只做 query 级归零断言，片段级残留读不到。复审全程只读，未改动被审文档、代码与配置。

## 结论

两份正文都没有 P0 级阻断项，修完 6 条 P1 后可进入 B 阶段编码。设计侧要改 5 处，实现规划侧要改 8 处，逐条列在「文档需要修改的段落」一节。修完后 B0 到 B6 的次序不变，B4 的退出条件要增加对分配目标本身的断言，B5 的关闭槽修复要覆盖 schema 查询路径。4 条 P2 不阻断实施，随下一轮文档修订一并改掉。

## 一、复审范围与判定口径

IoTDB 表模型查询把一个设备表扫描拆成多个分支并行读取，每个分支读一部分设备和一部分时间分区。所有分支读到的行合起来必须等于一次完整扫描，每一行只能出现一次。申请内存失败、查询被取消或者创建驱动中途失败时，已经建出来的队列和算子都必须释放。B 阶段要把三条已经存在的拆分路径的统一步骤写成可实施的文档。这份文档写得好的标准是：实现者按它做完，建出来的对象数量、每个对象能申请的内存上限、失败时的释放顺序都能被测试逐条验证，而且基线已经能跑通的查询不会因为文档改动而失败。

本轮复审对象是 20261031 三份文档与基线 `8d5d9c6a2c838e42f21be9ebd3278151fb75c520` 的源码。处理说明中引用的静态核查目录只证明源码与符号核对，不能作为 B 的测试已通过的证据，本轮同样只做静态核查。

下文用四个词，各按一句事实定义。分配目标指用片段配置预算除以真实对象数、向下取整得到的每对象额度，真实对象数由 B 新增的登记表在规划时数出。兼容下限指同一个对象在基线代码里最终生效的额度。遗留计数指基线执行上下文里的一个旧计数器，基线的每对象额度由它算出。记账键指内存池用来累加预留字节的三层键，依次是查询 id、片段实例 id、计划节点 id。四个词在两份正文里的名字与这里一致。

分级口径沿用一轮审查的三档。P0 是实施前必须解决的正确性或方向问题，实现按文档做完会建出错误结构或让现有查询失败。P1 是关键行为缺口或验证缺口，实现能做完但行为与文档承诺不一致，或测试无法发现实现错误。P2 是文字与位置问题，只改文档不改代码。

判定一条处理是否可验证用三个条件。第一，文档给出可观测的量或对象身份，不只用文字描述。第二，该量在现有或拟新增的测试里被读到。第三，反例存在时测试确实失败。三个条件同时满足记为可验证，缺任何一个记为有缺口。

类名与方法名按一处约定摆放。每条 P1 的源码方法一段集中写类名与方法名，其余段落只写文档行号与文档小节名，不插类名。第七节末尾的源码位置一段列出本轮核对过的全部文件与方法。

## 三、本轮新发现问题

### P1 级问题

六条。五条落在 B4 的限额机制与验收断言，一条落在 B5 的清理范围。

#### P1-1 分配目标与兼容下限的关系

文档位置：设计「分配目标与兼容下限」第 139 行与第 143 行。实现规划「冻结与兼容退出条件」第 119 行到第 130 行，「登记与基线额度快照」第 115 行。

源码方法：每对象额度由 `LocalExecutionPlanContext.getMaxBytesOneHandleCanReserve` 给出。`exchangeSumNum` 为零时它返回完整片段预算，为零以外时返回片段预算除以该数。七处 `addExchangeSumNum` 调用点决定该数的终值。两个 `plan` 方法在遍历完整算子树之后才调用额度发布方法，此时计数已是终值。

反例：逐个形态核对计数与真实对象数的关系。无序设备扫描与时间分区拆分各调用一次 `addExchangeSumNum(pipelineNum)`，同形态建立同样条数的本地共享队列。有序扫描调用一次 `addExchangeSumNum(deviceGroups.size())`，同形态建立同样数量的队列。IdentitySink 与 ShuffleSink 各加一，登记表按设计要求把多桶 sink 展开为各个 channel，对象数不小于计数。远端 Exchange 加一并建立一个 `SourceHandle`。同节点 Exchange 加零却建立一个 `LocalSourceHandle`，是唯一对象数大于计数的形态。

逐类核对七处计数调用点后，真实对象数都不小于遗留计数，目标恒不大于下限。差距最大的形态是多桶 sink，32 个通道时目标为 125,703 字节，下限为 4,022,509 字节，相差 32 倍，这个结果由设计第 143 行自己给出。

影响：设计第 139 行把按真实数量计算分配目标写成一等机制，首版它不改变任何对象的最终额度，兼容下限单独就实现了一轮 P0-2 要求的全部保护。规划第 119 行到第 130 行的退出条件只断言最终额度不低于基线最终值，一个把 32 个 channel 数成 1 个对象的实现照样通过这条断言。规划第 115 行要求测试同时给出对象数、记账键数与基线额度，但退出条件没有把这三者中的任何一个设为断言对象。

修改：设计第 139 行后补一句，说明首版下限恒不小于分配目标及其原因，并说明发布只能收紧不能放宽，因此分配目标取较大值的写法在首版各形态下不产生提升。规划第 115 行改为对登记表 `nominalShareBytes` 字段的直接断言，32 桶形态必须等于 125,703 字节。B4 增加一个分配目标可见的形态，或明确写出真实计数的收紧收益留给后续方案，首版只作记录。

#### P1-2 跨片段共享队列的记账键归属

文档位置：设计「对象身份与内存记账」第 127 行与第 129 行。实现规划「登记与基线额度快照」第 113 行，「本地资源验收观测」第 237 行。

源码方法：同节点跨片段的源句柄由 `MPPDataExchangeManager.createLocalSourceHandleForFragment` 建立。它用上游的片段实例 id 与上游的计划节点 id 构造共享队列，队列的三个记账字段因此取上游片段。`SharedTsBlockQueue.add` 用队列自身的三个 final 字段调用注册方法与预留方法。`LocalSinkChannel.send` 转交 `queue.add`，不使用自己的片段标识。注册方法用 `computeIfAbsent` 与 `putIfAbsent` 建条目。注销方法在强制参数为假且有条目非零时只返回不删除，为真时抛 `MemoryLeakException`。

反例：同节点两片段查询，下游片段的汇通道复用上游片段建立的队列。下游片段向队列写入 200,000 字节后取消。若上游片段先注销，下游的预留按上游键重建条目，上游随后以强制方式注销时抛 `MemoryLeakException`，以非强制方式注销时静默返回，条目留在映射里。`getQueryMemoryReservedBytes(queryId)` 按 queryId 汇总所有片段，两种情况下都能归零，规划第 237 行的断言读到零。

影响：设计第 127 行写跨片段队列在两侧各登记一次，第 129 行写记录必须保存内存池使用的 query、片段与 planNodeId，两句合起来是对称模型，源码按队列创建方记账。实现按对称模型写登记表，会把预留归属记到下游片段。片段级归零与 `forceDeregisterFragmentInstance` 的泄漏检测出现未申报的不对称，B6 的双节点验收读不到这一项。

修改：设计第 127 行后补一句，共享队列的预留记账键取队列创建方的片段实例 id 与 planNodeId，同节点路径下创建方是上游片段。规划第 237 行的归零断言增加按片段实例 id 的预留读数，窗口字段表补 `fragmentReservedBytes`。第 237 行的示例补一个片段级非零而 query 级为零的反例。

#### P1-3 轮询门限的基线取值

文档位置：设计「多通道轮询门限」第 167 行到第 176 行。实现规划「轮询门限冻结」第 141 行到第 150 行。

源码方法：`ShuffleSinkHandle` 的额度字段初值取完整片段预算。构造函数内调用策略工厂方法，`SimpleRoundRobinStrategy` 的门限在同一时刻求值，早于规划期的额度发布。选路判断只被简单轮询策略使用。背压判断走另一条路，两个方法都调用通道自身的满判断。`shuffle` 在没有通道满足条件时保持原下标不变。

反例：预算 4,022,509 字节、4 个通道、同片段另有 4 条本地流水线。基线门限为 4,022,509 除以 4 乘 3 等于 3,016,881 字节。该形态的遗留计数为 5，基线每句柄额度为 804,501 字节，新规则给出两者较小值 804,501 字节，相对基线收紧 3.75 倍。32 通道时基线门限为 4,022,509 除以 32 乘 3 等于 377,109 字节，设计第 173 行示例写的 1.5 MiB 在该配置下不对应任何基线读数。

影响：选路条件变严，选路判断的失败变多，`shuffle` 退化为停在原通道，通道间的发送分布改变。规划第 141 行到第 150 行的退出条件只有轮询消费后有进展这一条活性断言，没有与基线的发送分布对比，收紧造成的吞吐变化测不到。

修改：设计第 173 行的示例数改为该配置的实算值，并写明基线门限按构造时刻的字段初值计算，与遗留每句柄额度不同。设计第 171 行后补一句合同，没有通道满足条件时选路保持原下标。B4 增加与基线的通道发送计数对比，或在文档中显式论证收紧不影响吞吐并说明理由。

#### P1-4 关闭槽修复的路径覆盖范围

文档位置：实现规划「驱动与工厂的释放责任」第 179 行。设计「内存准入与失败清理」第 206 行的数据来源。

源码方法：`FragmentInstanceManager` 的两个执行入口是同一段代码模式，一个是数据查询入口，一个是 schema 查询入口。两处都先用 `forEach` 建完所有驱动，再调用 `initializeNumOfDrivers` 按驱动数初始化，然后取最后一个驱动的 sink。两个 `plan` 方法在收尾时都调用额度发布方法，规划第 159 行已正确列出两个 `plan`。

反例：schema 查询有三个工厂，第二个构造失败。此时关闭计数尚未初始化，第一个驱动的销毁路径调用递减方法会走到空指针。若关闭计数按三个工厂预初始化，而只有第一个驱动实际销毁，第二个与第三个工厂各自的关闭入口若未结算，等待方永久阻塞。

影响：这条处理只覆盖一半入口。设计第 206 行的数据来源同样只引数据侧方法名，读者按清单核对会漏掉 schema 路径。规划第 179 行的测试扩展只提 `FragmentInstanceManagerTest`，没有要求 schema 工厂失败样例。

修改：规划第 179 行与设计第 206 行的数据来源补 `execSchemaQueryFragmentInstance`。关闭槽测试增加 schema 查询的中间工厂失败样例，断言三个关闭槽归零。

#### P1-5 记账键的读取入口

文档位置：设计「对象身份与内存记账」第 129 行与第 135 行。实现规划「登记与基线额度快照」第 111 行，「本地资源验收观测」第 243 行的数据来源。

源码方法：`LocalSinkChannel` 的片段标识字段是可变的非 final 字段，两参数构造函数不赋值。`createLocalSinkChannelForPipeline` 用的正是这个构造函数，因此该通道的片段标识读取结果为空。`LocalSourceHandle` 的片段标识同样只在完整构造函数里赋值，本地扫描的源句柄经 `PipelineSourceHandle` 走三参数构造函数，读取结果也是空。`SharedTsBlockQueue` 持有真实的三个记账字段，全部为 private final，公开方法里没有对应读取入口。

反例：B 要登记四条本地扫描流水线的记账键。汇通道的片段标识为空，源句柄的片段标识为空，队列里三个字段读不到。按设计第 135 行列的枚举接口走一遍，四个对象的记账键都取不到，登记表只能存空值，规划第 111 行要求的保存实际 planNodeId 记账键无法完成。

影响：这是一处可实现性缺口，实现步骤无法按文档直接落地。实现者要么给队列加读取入口，要么把建队列时的三个参数经登记回调传出，两条路都要改生产代码，文档必须选定一条并写进修改位置。

修改：设计第 135 行后补一句，本地扫描路径的记账键由建队列时的登记回调传出，或给 `SharedTsBlockQueue` 增加三个记账字段的公开读取方法，二者选一并列入规划的修改位置。规划第 243 行的数据来源同步补该入口。

#### P1-6 查询级断言的承载测试类

文档位置：实现规划「冻结与兼容退出条件」第 125 行。处理说明「P0-2」第 41 行。

## 四、重点核对项的独立核查结果

八个重点项中，五项本轮未发现问题，三项产生上节的 P1。未产生问题的五项结论如下。

兼容下限的来源。基线每对象额度由 `LocalExecutionPlanContext.getMaxBytesOneHandleCanReserve` 给出，`exchangeSumNum` 为零时取完整片段预算，为零以外时取除以该数的商。七处计数调用点与真实对象数的配对关系见本轮 P1-1 的反例。设计第 139 行写下限由默认额度和全部原限额调用共同确定，这个描述对本地扫描路径成立，该路径的额度来自最终遍历对 `PipelineSourceHandle` 的写入，这条路径上的 setter 有实际作用。

内存池真实记账粒度。`MemoryPool` 的注释与实现一致，账目结构是 queryId 到片段实例 id 到 planNodeId 三层，第三层累加预留字节。全池另有总量约束，`tryReserve` 同时检查累计键额度与全池已用量。设计第 131 行的描写与源码一致。

多通道共享 planNodeId。`createShuffleSinkHandle` 只接受一个本地 planNodeId，`createSinkChannel` 是唯一的通道构造点，因此一个句柄的所有通道共用同一个记账键。设计第 131 行写多个 channel 可以共享同一个 planNodeId、通道额度不代表独立预留池，与源码一致。设计第 133 行给的两通道各申请 600 KiB、第二笔进入等待的例子，对应 `tryReserve` 对同一键累加后与句柄额度比较的逻辑，成立。

工厂失败关闭槽。`FragmentInstanceContext` 的关闭计数字段没有初值，初始化方法在驱动全部创建完之后才被调用，递减方法在驱动销毁时调用。构造中途失败时销毁路径会走到空指针，或按工厂数预初始化后只有部分驱动销毁而永久等待。设计第 197 行到第 199 行与规划第 175 行到第 177 行写的处理方向与源码一致，缺口只在覆盖范围，见本轮 P1-4。

轮询门限与硬预留的区分。`SimpleRoundRobinStrategy` 的门限只进选路判断。两个背压判断方法都调用通道自身的满判断，预留由 `SinkChannel.send` 与 `MemoryPool` 执行。处理说明对该门的定性与源码一致。缺口在基线门限的取值来源，见本轮 P1-3。

跨片段队列并发。`SharedTsBlockQueue` 的额度字段在基线是一个普通 long，没有 volatile 修饰。发送线程在 `add` 里读它，两个包装层在不同线程写它，两个包装层各自做读后取小。设计第 159 行到第 161 行与规划第 131 行到第 140 行要求改成同一个原子数读写并移除包装层的读后判断，方向正确。七个重点项中的这一项没有留下新的缺口，P1-2 讲的是记账键归属，与并发无关。

资源观察接口能否拒绝假归零。三个 JMX 操作与它们要复用的内存池接口在基线上都存在，窗口容量与超限判失败的约定具体。缺口有两处，一处是证据只到 query 级，见本轮 P1-2，一处是队列记账键没有读取入口，见本轮 P1-5。

B0 至 B6 的依赖与测试范围。六条依赖都写明且方向成立。B1 的不可变描述先完成并单测，B2 与 B3 才接真实算子。B2 建立登记表的清理部分，B4 再补额度冻结。B0 先冻结基线额度轨迹，B4 才做同形态比较。B5 先实现验收观测接口，B6 才跑依赖它的服务验收。B6 的完整模块不沿用 A 的结果，测试数量按 B 最终可运行清单重新核定。五个新测试类分别落在 B1 到 B5，与 B6 写的五个一致。

缺口在依赖与测试范围交界的两处。一处是 B4 的查询级断言没有承载类，见本轮 P1-6。一处是服务级开关的恢复没有纳入运行前核对，见本轮 P2-4。

## 五、B 与 C 至 E 的边界核对

运行指标归 C。设计在统计一节写统一 query 或 fragment 运行快照由 C 设计，策略比较和运行中调整分别归 D 与 E。规划在本地资源验收观测一节写本接口只提供单节点单次验收的生命周期计数与本地内存读数，C 仍负责运行指标协议、跨节点合并、CPU 与吞吐采样，并禁止把验收脚本输出称为 C 已实现。两处口径一致。

A 与 B 的接口清晰。设计写 B 使用 A 输出的扫描资格，A 负责分布式属性判定，B 负责本地执行构造。规划 B3 写分布式属性组件保持 A 的合同，没有在 B 内重写属性判定。

一处范围句与规划的关系。设计在术语与范围一节写 B 首版统一已有三条路径及直接过滤融合入口，并保留串行路径，这句话只覆盖扫描路径。规划 B4 同时要求纯扫描路径与已有通用交换路径统一登记，改的是所有查询的限额计算、登记和失败清理。设计第 27 行写明资源登记同时接入表模型、树模型与 schema 模型的通用交换构建，范围句与规划一致，本轮不分级。
