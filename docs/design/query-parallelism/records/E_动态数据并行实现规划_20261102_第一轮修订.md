## 3. E1：快照差分与 bucket 统计

### 修改位置

- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/statistics/snapshot/RuntimeSnapshotDelta.java`
- 新增 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DynamicBucketRuntime.java`
- 新增 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DynamicSnapshotAggregator.java`

### 处理

1. `RuntimeSnapshotDelta` 对相同 query shape、fragment、plan identity 的相邻 snapshot 做非负差分；generation 回退、checksum 不同或 driver 身份变化时返回 invalid。
2. `DynamicSnapshotAggregator` 按稳定 driver 顺序将 rows、TsBlocks 和 wall 聚合到 bucket；wall 缺失时只保留 rows/TsBlocks。
3. `remainingCost` 先取 `StaticCostCalibrator` 的同 key 历史 cost，再取 D 计划 cost，最后才使用 rows 等量 fallback，并记录来源。
4. 只读使用 `RuntimeSnapshotView.getWorkUnitIds()`、`getBucketIds()` 和 `getActualDriverCount()`，不直接读取 `FragmentInstanceExecution.drivers`。

### 测试与退出判据

- `RuntimeSnapshotDelta` 覆盖 generation 回退、driver 增删和 checksum mismatch；
- `DynamicSnapshotAggregatorTest` 覆盖 rows/TsBlocks/wall 缺失和 bucket 多 driver 聚合；
- 同一输入重复聚合得到相同 checksum 和相同排序；
- 历史 cost 的 endpoint、query shape、validity 过滤与 D 的 `StaticCostCalibratorTest` 对齐。

## 4. E2：纯动态策略

### 修改位置

- 新增 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DynamicParallelScheduler.java`
- 新增 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DynamicParallelPolicy.java`
- 新增 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DynamicParallelDecisionReason.java`

### 处理

1. 输入为 `DynamicParallelScheduleInput` 和 bucket runtime aggregates，输出 `DynamicParallelScheduleDecision`。
2. 样本数小于 2、validity 不完整、wall 支持状态不对等或计划身份变化时输出 `KEEP_STATIC`。
3. 最大/最小 remaining cost 比值大于 1.50 且连续两次方向一致时，输出 `REBALANCE_NEXT_WAVE`。
4. `targetDop = min(configuredDop, workUnitCount, admissionDop)`；单轮最多改变一个等级，反向变化进入冷却窗口。
5. LPT 重新分配只接受尚未开始的 work unit；已提交 exchange 的 work unit 固定不动。
6. 新 bucket 按整数升序编号，work unit canonical ID 不变；输出重新计算 plan identity checksum。
7. 输入不满足属性门时输出 `SERIAL_FALLBACK`，保留 raw/canonical reason。

### 测试与退出判据

- `DynamicParallelSchedulerTest`：keep/static、rebalance、reduce DOP、serial fallback；
- `DynamicParallelHysteresisTest`：连续两次方向和冷却窗口；
- `DynamicParallelLptDeterminismTest`：相同输入同 decision checksum；
- `DynamicParallelPropertyGateTest`：ordering、global limit、spill、single device、source uniqueness；
- 测试不能依赖 wall 的实时值，使用固定 snapshot fixture。

## 5. E3：资源准入与 planner 接线

### 修改位置

- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/LocalExecutionPlanner.java`
- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/LocalExecutionPlanContext.java`

- `iotdb-core/datanode/src/main/thrift/datanode.thrift`

### 处理

1. 在下一 fragment 计划边界创建 `DynamicParallelScheduleInput`，先生成候选 `ScanParallelPlan`，再调用已有 `freezeResourceQuota()` 和 `checkMemory()`。
2. `checkMemory()` 失败时不执行动态计划，输出 `ADMISSION_REJECTED`，回退到上一静态计划或 SERIAL。
3. 将 dynamic action、raw/canonical reason、previous/target DOP、admission status、输入 snapshot checksum 和 plan identity checksum 写入 fragment snapshot；现有 driver 指标不重复采集。
4. thrift 新增字段全部 optional，旧 DataNode 返回仍映射为 `LEGACY_UNVERSIONED`，不能被动态策略当作有效历史样本。
5. `FragmentInstanceExecution` 在 snapshot 冻结边界记录 decision receipt，写入幂等，不能在 driver close 后回写。

### 测试与退出判据

- `DynamicParallelAdmissionTest`：通过、拒绝、内存不足和 SERIAL fallback；
- `DynamicParallelTransportCompatibilityTest`：旧/新 thrift optional 字段；
- `DynamicParallelPlannerIntegrationTest`：D 的 device/time/ordered 三类 planner 入口都保持 source accounting；
- `RuntimeSnapshotSingleNodeIntegrationTest` 增加 dynamic decision 只读验证。

## 6. E4：执行边界接线

### 修改位置

- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/execution/fragment/FragmentInstanceExecution.java`
- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/PipelineDriverFactory.java`
- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/LocalExecutionResourceRegistry.java`
- `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/execution/exchange/SharedTsBlockQueue.java`

### 处理

1. 首版只允许在 driver wave 尚未提交前生成下一轮计划，不对已运行 driver 调 `close()`，不清空 queue，不迁移 exchange channel。
2. `PipelineDriverFactory` 暴露只读 wave state；`LocalExecutionResourceRegistry` 冻结每轮资源身份，动态决策只使用快照而不是可变 quota。
3. 在 wave 边界将新 bucket/work unit 映射到新的 local pipeline；source operator 仍由 `LocalScanPipelineBuilder` 构造。
4. wave 交接失败、source accounting 不闭合或 exchange edge 不唯一时立即回到 D 静态计划，并记录失败 reason。

### 测试与退出判据

- `DynamicWaveBoundaryTest`：提交前可调整、提交后保持不变；
- `DynamicQueueOwnershipTest`：不重置 queue、不重复消费、不丢失 source；
- `DynamicPipelineLifecycleTest`：driver close、memory release、sink close 与 decision receipt 顺序；
- D 的 `PipelineDriverFactoryLifecycleTest`、`DeviceTableScanParallelPipelineTest` 回归通过。

## 7. E5：单节点、双节点和全量验收

### 单节点

固定 fixture、固定 query、固定 Java/Maven/runtime 身份，至少覆盖：

- 无反馈：`KEEP_STATIC`；
- bucket 不平衡：`REBALANCE_NEXT_WAVE`；
- 内存拒绝：`REDUCE_DOP` 或 `SERIAL_FALLBACK`；
- 缺 wall：两侧都 unsupported 时继续 rows/TsBlocks；单侧支持时失败；
- source/bucket/checksum 不一致：拒绝动态计划。

### 双 DataNode

使用 D6 的隔离集群方式，candidate/control 必须使用同一重建发行包、同一 fixture 和同一 query。每轮保存：

- source HEAD、工作区 status、server jar SHA、配置 SHA；
- candidate/control runtime snapshot、decision receipt、admission status；
- 完整结果多重集和 SHA；
- 至少三轮，三轮都通过 admission 且结果 SHA 相同才通过。

### 全量 DataNode

执行 D 同一全量命令并保留 ANSI/去色日志、Surefire XML 和退出码。`AnnotationTest` 的 ArchUnit OOM 必须作为单独资源例外记录，不得将其改写为 E 策略失败，也不得只凭定向测试宣称全量通过。

## 8. E 退出判据

1. `DynamicParallelScheduleInput`、delta、aggregator、policy 和 decision 值对象具有 immutable、deterministic、validity-aware 测试。
2. 动态策略只能读取 C/D snapshot，不能新增重复 per-driver 指标采集。
3. planner、memory admission、property gate 和 exchange ownership 的生产接线通过单节点测试。
4. 双 DataNode 三轮 candidate/control 通过完整结果多重集、SHA、snapshot checksum、plan identity checksum 和 admission 对账。
5. 全量 DataNode 结果、资源例外和失败证据归档；全量未达到 clean pass 时明确标记 `BASELINE_RESOURCE_BLOCKED`。
6. E 的任何性能数字都来自独立 receipt，不从 CLI elapsed time 推导倍率。

## 第一轮审查修订

### E0：输入合同和生产构造

修改位置增加：
- RuntimeSnapshotAdapters.java：构造 driver bucket assignment。
- RuntimeSnapshotFetchResult.java：保留逐 fragment errors、response checksum 和 assignment。
- RuntimeSnapshotView.java：提供按 driver key 查询 bucket/work units 的只读方法。
- 新增 DynamicDriverBucketAssignment.java 和 DynamicParallelScheduleInput.java。
- datanode.thrift：给 TDriverRuntimeSnapshot 增加 optional bucketId、workUnitIds。

E0 由 coordinator/ExplainAnalyze 的 fetch→merge 链构造 RuntimeSnapshotView。E0 不直接访问 FragmentInstanceExecution.drivers。输入构造拒绝重复 driver key、重复 bucket、重复 work unit、重复 exchange edge 和空 plan checksum。

### E1：有界历史样本和完整差分

新增 DynamicCostHistoryStore.java，实现每个 key 最多 1024 条、30 分钟过期、validity 过滤、按 generation 单调写入。写入者是 fragment snapshot merge 完成后的 coordinator。store 为空时明确返回 NOT_FOUND，策略退回 D cost 或 rows fallback。

RuntimeSnapshotDelta.java 修改为结构化 driver key。差分字段包括 rows、TsBlocks、wall、sample generation、driver validity 和 plan generation。driver 增删、generation 回退、checksum/endpoint/query shape 改变全部返回 invalid。新增 DynamicBucketRuntime.java 和 DynamicSnapshotAggregator.java，保留 cost 来源枚举。

### E2：纯策略、DOP 和冷却

DynamicParallelScheduler.java 接收唯一名称 inputDop。该值来自 LocalExecutionContext.getDegreeOfParallelism()，由下一 fragment 的新 setter 写入候选 plan input。

admissionDop 由 E3 的候选 DOP 试探返回。E2 不猜测 admission 上界。候选 DOP 从 1 到 inputDop，按升序调用 admission provider，最后一个成功值才可用于 min(inputDop, workUnitCount, admissionDop)。

阈值固定为最大/最小 remaining cost 大于 1.50、至少两个完整 bucket、连续两次同方向。冷却窗口为连续 3 次决策检查。blocked 只在同一 bucket 连续 3 次 blocked>0 且 ready=0 时成立；没有 bucket 级计数时保持 KEEP_STATIC。

### E3：准入、协议和命令

生产接线在下一 fragment 计划边界执行。先构候选 ScanParallelPlan，再冻结 resource snapshot 并调用现有 checkMemory。失败写 ADMISSION_REJECTED 和资源原因，并回退 D 静态或 SERIAL。

协议实际路径是：iotdb-protocol/thrift-datanode/src/main/thrift/datanode.thrift。

所有定向命令使用 reactor 依赖构建，不能只构建 datanode：

    cd /root/iotdb
    FLAGS="-Dspotless.check.skip=true -Drat.skip=true -Dlicense.skip=true -Dmaven.javadoc.skip=true -Dcheckstyle.skip=true -Denforcer.skip=true -DfailIfNoTests=false"
    mvn -B -pl iotdb-core/datanode -am test-compile surefire:test -Dtest=<TestClass> $FLAGS

协议修改后先保留生成 thrift JAR SHA。全量命令也加 -am，并保存 ANSI、去色日志、Surefire XML、退出码和生成 JAR SHA。

### E4：下一 fragment 边界，不实现 wave

E4 删除执行侧 wave 作为实施对象。PipelineDriverFactory、SharedTsBlockQueue 和现有 driver close 生命周期不改。动态决策生成 receipt，并在下一 fragment 创建前重新调用 D planner。

E4 测试改为：
- DynamicFragmentBoundaryTest：已提交 fragment 不变，下一 fragment 可以采用新 decision；
- DynamicQueueOwnershipTest：不重置 queue、不重复消费；
- DynamicDecisionReceiptTest：decision 输入、输出、admission 和 checksum 可重放；
- DynamicPipelineLifecycleTest：旧 fragment 的 close/release 顺序不被新 decision 改写。

### E5：验收

单节点固定 fixture 覆盖 KEEP_STATIC、REBALANCE_NEXT_FRAGMENT、REDUCE_DOP、SERIAL_FALLBACK、缺 wall、checksum mismatch 和 endpoint mismatch。

双节点 candidate/control 使用同一当前源码重建发行包。同一 fixture 至少三轮。每轮保存 source HEAD、workspace status、server jar SHA、配置 SHA、snapshot/decision receipt、admission status、结果多重集和 SHA。三轮都通过 admission 且结果 SHA 一致才通过。

全量命令使用 -pl iotdb-core/datanode -am test-compile surefire:test，保留 ANSI 和去色日志。资源不足时单独记录资源原因，不能把未完成套件写成策略通过。
