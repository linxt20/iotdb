# E：动态数据并行设计（第一轮审查修订版）

目的：定义 E 的动态数据并行边界、输入合同、决策对象和验收方式。本文只描述待实施方案，不把设计对象写成已落地代码。

摘要：E 复用 C 的运行快照和 D 的静态计划。首版只在下一 fragment 计划边界调整，不在运行中迁移 driver、morsel 或 exchange queue。动态输入必须有可回放的 work unit、bucket、driver 配对关系，并且通过 generation、endpoint、checksum 和 admission 校验。

结论：E 代码尚未开始。E0 至 E5 只有在本修订版列出的载体、生产构造者和测试退出证据全部完成后才能关闭。

- CPN 是否进入论文正文。
- 性能口径采用 3.33 倍还是 2.95 倍。

## 1. 目标与边界

E 在 D 的静态扫描计划之上增加运行反馈驱动的下一轮并行决策。它复用 C 已定义的 fragment runtime snapshot 和 D 已接入的 `StaticParallelPlanIdentity`，根据已经完成的 driver 工作量、输出行数、TsBlock 数和 wall time 判断下一轮是否需要调整并行度或重新分配工作单元。

首版 E 只做“下一轮计划调整”：一个 fragment instance 已经开始执行后不迁移正在运行的 morsel，不重排已经写入 exchange queue 的数据，不改变查询结果顺序。调整发生在下一次 fragment/查询计划生成边界；无法证明安全时继续使用 D 的静态计划或 SERIAL fallback。

E 不把 CPU、output bytes、ready time、blocked time 当作必需输入。这四个字段在 C/D 中没有统一生产来源，继续使用字段级 `UNSUPPORTED_FIELD:<field>`。wall time 只有 candidate/control 两侧支持状态一致且 checksum、generation、plan identity 都通过时才参与比较。

hash join 是否进入生产规划路径仍由 sxing 决定。E 第一版只覆盖已经由 D 接入的扫描 source/bucket 计划，不改变 hash join 的生产 guard。CPN 形式化和性能倍率口径也不作为 E 的实现前置条件。

## 2. 复用的 C/D 输入

动态决策的唯一跨节点输入是 `RuntimeSnapshotView`。它通过 `RuntimeSnapshotFetchResult` 将 RPC 的 `TFetchFragmentInstanceStatisticsResp` 转换为 Java snapshot，再由 `RuntimeSnapshotMerger` 做 fragment 完整性、endpoint、checksum 和重复身份校验。

每个动态样本必须同时满足：

- query shape、fragment instance、source endpoint 与计划记录一致；
- runtime `snapshotGeneration` 单调且没有 `STALE`、`MISSING_FRAGMENT`、`UNEXPECTED_FRAGMENT` 或 `CHECKSUM_MISMATCH`；
- fragment 具有 D 的 `StaticParallelPlanIdentity`，其 plan checksum、work unit IDs、bucket IDs 和 exchange edge IDs 可回放；
- `driverOutputRows` 与 `driverTsBlockCount` 已设置；两者是第一版强制比较字段；
- wall 有值时 candidate/control 的支持状态相同；两侧都不支持时保留 unsupported reason 并降级到 rows/TsBlocks；
- `checkMemory()` 对新计划返回 `ADMISSION_ACCEPTED`。

动态策略继续复用现有的 per-driver thrift 字段：`driverPipelineId`、`driverTaskId`、`driverOutputRows`、`driverTsBlockCount`、`driverWallNanos` 和 `validityReasons`。不为已有字段再造一套全局监控指标。`QueryMetricsManager`、`DataExchangeCostMetricSet` 和 `SeriesScanCostMetricSet` 只作背景 sanity check，不直接驱动一次动态决策。

## 3. 决策对象

新增的 `DynamicParallelScheduleInput` 保存一次决策的只读输入：

- `queryShape`、`fragmentInstanceId`、`sourceEndpoint`；
- `planIdentityChecksum`、`planGeneration`、`inputDop`；
- 每个 work unit/bucket 的已完成 rows、TsBlocks、wall、样本 generation；
- `RuntimeSnapshotValiditySet` 与字段级 validity reason；
- 当前 resource snapshot、fragment memory budget 和 `checkMemory()` admission 状态。

新增的 `DynamicParallelScheduleDecision` 保存纯策略输出：

- `action`：`KEEP_STATIC`、`REBALANCE_NEXT_WAVE`、`REDUCE_DOP`、`SERIAL_FALLBACK`；
- `targetDop`；
- bucket 到 work unit 的新归属；
- raw reason、canonical reason；
- 输入 snapshot checksum 和 plan identity checksum；
- `ADMISSION_ACCEPTED` 或明确拒绝原因。

决策对象不持有 driver、operator 或 queue 的可变引用。所有列表在构造时复制并冻结，方便单元测试和审计重放。

## 4. 反馈计算

对每个 bucket，按稳定的 `fragmentInstanceId`、`driverPipelineId` 字符串序和 `driverTaskId` 字符串序聚合：

- `rows`：driver output rows 之和；
- `tsBlocks`：driver TsBlock 数之和；
- `wallNanos`：wall 有值时取该 bucket 的最大 wall；
- `throughput`：`rows / wallNanos`，wall 不支持时不生成；
- `remainingCost`：优先使用 D 的历史/计划 cost，缺失时用 rows 作为等量 fallback。

不把缺失字段当成 0。一个 bucket 的 rows、TsBlocks 或 generation 缺失时，该 bucket 被标记为 `PARTIAL`，本轮只能 `KEEP_STATIC` 或 `SERIAL_FALLBACK`，不能触发 rebalancing。

默认不平衡判据为同时满足以下条件：至少两个有效 bucket、有效样本数达到 2、最大/最小 remaining cost 比值大于 `1.50`，并且两次连续 snapshot 的方向一致。首次样本只记录趋势，不立即调度，避免启动阶段噪声导致抖动。

调整幅度受限于 `targetDop = min(configuredDop, workUnitCount, admissionDop)`，单轮最多增加或减少一个并行度等级；连续两轮方向相反时进入冷却窗口。任何 rebalancing 都保持 source 唯一覆盖、bucket 唯一归属和 exchange edge 唯一性。

## 5. 调整模型

### 5.1 KEEP_STATIC

当样本不足、validity 不完整、plan identity 不一致、wall 支持状态不对等或不平衡比值低于阈值时，沿用 D 的 `ScanParallelPlan`。记录 `DYNAMIC_INSUFFICIENT_EVIDENCE` 或对应 canonical reason，不修改查询执行。

### 5.2 REBALANCE_NEXT_WAVE

当多个 bucket 的 remaining cost 明显不平衡且 admission 通过时，使用确定性的 LPT 重新分配尚未开始的 work unit。已完成或已提交到 exchange 的 work unit 固定不动；新 bucket ID 按升序重新编号，work unit canonical ID 不改变。新计划生成新的 `planGeneration` 和 plan identity checksum，并在下一 fragment snapshot 中回传。

### 5.3 REDUCE_DOP

当资源 snapshot 显示 admission budget 下降、bucket queue 长时间 blocked，或新 DOP 的 `checkMemory()` 失败时，将 target DOP 降到最大的可准入值。不能准入任何并行计划时走 SERIAL fallback；不能用历史 wall 或全局 CPU 指标绕过内存准入。

### 5.4 SERIAL_FALLBACK

输入缺失、重复 source/bucket、checksum mismatch、endpoint mismatch、overflow、ordering 未证明、global limit/offset 或 spill 条件出现时，生成 D 的完整 SERIAL 计划并保留 raw/canonical reason。动态策略不得把安全拒绝改写成“低收益”。

## 6. 时序与一致性

```text
LocalExecutionPlanner.plan()
  -> D ScanParallelPlan + checkMemory()
  -> FragmentInstanceExecution freezes TDriverRuntimeSnapshot
  -> RuntimeSnapshotFetchResult.fromResponse()
  -> RuntimeSnapshotMerger + RuntimeSnapshotView
  -> DynamicParallelScheduleInput
  -> DynamicParallelScheduler.decide()
  -> next-wave plan or KEEP_STATIC
```

快照冻结边界继续由 `FragmentInstanceExecution` 持有。driver 先执行 `recordMorselCompletionStatistics()`，再复制 operator 指标并生成 thrift/Java snapshot；动态策略只能读取冻结值，不回读可变 `OperatorContext`。

candidate/control 对账使用生产 snapshot checksum 和 plan identity checksum。Java `RuntimeSnapshotChecksum` 含 capturedAtNanos，只用于单侧 self-check，不用于两侧相等判断。wall 两侧都 unsupported 时继续 rows/TsBlocks 降级；只有一侧支持 wall 时判定为不一致。

## 7. 安全约束

动态调整必须再次通过 D 的属性门：

- 计划 source、work unit、bucket、exchange edge 互斥且可回放；
- `Filter`/`Project` 透明夹层仍要求递归 `isHashRepartitionSource` 和现有 ordering/limit/spill guard；
- global limit/offset、自然顺序未证明、spill device entries 和 single-device 输入不能被动态策略强行拆分；
- `checkMemory()` 失败不改写成 cost 估计失败，记录 `ADMISSION_REJECTED` 和具体资源 reason；
- 不在运行中调用 `close()`、重置 `SharedTsBlockQueue` 或迁移已经发布的 exchange 数据；
- 旧 snapshot、不同 endpoint 或不同 query shape 的历史样本不可用于校准。

## 8. 可观测性

首版仅增加 decision metadata，不新增重复的监控值：`dynamicAction`、`dynamicReasonRaw`、`dynamicReasonCanonical`、`inputSnapshotChecksum`、`inputPlanIdentityChecksum`、`admissionStatus`、`previousDop`、`targetDop`。这些字段放在 fragment/query snapshot 的扩展对象中，现有 CLI 展示可以继续只显示计划和 driver 细节。

每次决策保存一条结构化 receipt，至少包含 source HEAD、工作区 identity、snapshot/plan checksum、配置 SHA、runtime jar SHA、decision 输入和输出。receipt 不覆盖旧实验结果。

## 9. 当前未决项

- hash join 是否进入生产规划路径：E 第一版保持关闭；
- CPN 形式化是否进入论文正文：不影响实现；
- 性能倍率采用 3.33 还是 2.95：E 只记录真实 receipt，不在实现中硬编码倍率；
- history calibration 的时间窗和样本数：默认两次连续完整 snapshot，最终阈值在 E2 评审后冻结。


## 第一轮审查修订覆盖

本节覆盖正文中同名条目的具体定义。E0/E1 不再依赖计划对象在接收端常驻。

### 配对关系与快照生产者

E0 新增 DynamicDriverBucketAssignment，保存 fragmentInstanceId、driverPipelineId、driverTaskId、bucketId 和该 bucket 的 work unit ID 列表。列表按稳定 driver key 排序并冻结。

配对关系在 D 计划生成时形成。ScanParallelPlan.Bucket.getDriverPipelineId() 是计划侧来源。fragment snapshot 通过新增 optional bucketId 和 workUnitIds 字段传输 driver 配对关系。旧节点没有这些字段时，输入标为 LEGACY_UNVERSIONED，不能参加重平衡。

RuntimeSnapshotAdapters.fromResponse() 是 response 到 Java snapshot 的生产适配器。QueryStatisticsFetcher.fetchAllStatisticsBestEffort() 负责逐 fragment 获取 response。coordinator/ExplainAnalyze 负责把 fetch result 的 response、errors 和 returnable fragment 集合交给 RuntimeSnapshotFetchResult.merge()，再构造 RuntimeSnapshotView。E0 不自行从 FragmentInstanceExecution.drivers 读取可变对象。

### 历史成本样本

E1 新增 DynamicCostHistoryStore。它是 DataNode 内存中的有界环形存储，键为 queryShape、sourceId、mode、endpoint，值为 cost、rows、TsBlocks、generation、capturedAt 和 validity。默认每个键最多 1024 条，样本保留 30 分钟；过期或 validity 不完整的样本先淘汰。

fragment snapshot 冻结后由 coordinator 写入该存储。首轮进程重启后存储为空，策略必须退回 D 的计划 cost 或 rows fallback。E1 通过接口注入该 store，测试不依赖静态全局状态。

### DOP 与准入来源

inputDop 是唯一名称。它来自下一 fragment 的 LocalExecutionPlanContext.getDegreeOfParallelism()，动态决策通过新建的 plan input setter 写入，不再使用 configuredDop 别名。

admissionDop 不是监控字段。E3 对候选 DOP 从 1 到 inputDop 做确定性上界试探，每次候选都调用已有 freezeResourceQuota() 和 checkMemory()；最后一个成功值才是 admissionDop。试探失败保留 ADMISSION_REJECTED 和资源原因，不能把失败转换为 cost 不足。

### 调整边界

E 第一版不引入执行侧 wave。调整边界统一为下一 fragment instance 创建前。E4 不修改 PipelineDriverFactory 的单 driver 生命周期，不清空或重置 SharedTsBlockQueue，也不迁移已经提交的 exchange channel。

正文中 next wave、尚未提交的 wave 和 wave state 均解释为下一 fragment 计划边界的 receipt 状态。若将来要做真正的 wave，必须另开设计变更并增加调度器的分批提交能力。

### 差分范围

RuntimeSnapshotDelta 在 E1 扩展为结构化键：queryId + fragmentInstanceId + planGeneration + driverPipelineId + driverTaskId。

差分同时覆盖 rows、TsBlocks、wall、sample generation 和 driver validity。driver 消失、新 driver 出现、generation 回退、plan checksum 变化或 endpoint 变化都返回 invalid。wall 缺失只影响 wall 派生值，不能把 rows/TsBlocks 置零。

### 阈值与算例

冷却窗口固定为连续 3 次决策检查。方向相反时清除待调整状态，窗口结束前只输出 KEEP_STATIC。blocked 判据为同一 bucket 连续 3 次 snapshot 的 blocked 计数大于 0 且 ready 计数为 0；调度器只提供总计数时不得按 bucket 推断。

remaining cost 比值使用大于 1.50。例一：9000、6000、1500 的最大/最小比值为 6.0，满足重平衡条件。例二：6000、5500、5000 的比值为 1.2，不触发重平衡。首次完整 snapshot 只记录趋势。
