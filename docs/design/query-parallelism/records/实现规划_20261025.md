# IoTDB 查询执行并行化实现规划

目的：记录毕业设计的 A → B → C → D → E 顺序、原工作项编号和后续实施范围。

摘要：一条查询并行执行需要先确定分组与顺序要求，再构建执行资源。运行统计必须与真实计划绑定，才能支持策略选择。A–D 分别承担属性、构建、统计和静态计划。E 使用已冻结反馈调整下一片段。

结论：工作顺序保持 A → B → C → D → E。A–D 已进入最终生产源码，完整模块、双节点与资源故障均有同版证据。候选大输入活性与性能采用各自范围。E 处于设计与实现规划阶段，W1–W9 使用自己的退出条件。统一状态见 [A–D 完整核查](A-D_完整实现补全核查_20261102.md)。

## 查询执行背景

查询拆成多个分支后，相同键仍须汇入正确分组，每行仍须恰好读取一次。需要有序输出时，各分支及根合并都必须满足顺序要求。完成标准包含真实结果、计划覆盖和资源清理。

例如，两个来源分别读到键 a 的两行与三行，最终计数必须为五。两个局部计数直接返回会改变查询语义，因此计划正确性先于并行度调整。

数据来源：[整体设计](修改位置与整体设计_20261025.md) 说明各层责任，[A–D 核查](A-D_完整实现补全核查_20261102.md) 保存最终源码、测试和真实运行状态。

## A 属性判定框架

A 提供独立的属性计算、强制处理、原因与不可变决策。通用逻辑分区使用保守收集，受限 GROUP BY 走专用拓扑。未知提供者需要有序输出时补排序，禁止从父要求推断子输出。

数据来源：[A 设计](属性驱动并行判定框架设计_20261027.md)、[A 实现规划](属性驱动并行判定框架实现规划_20261027.md) 和 [A 实施记录](属性驱动并行判定框架实施记录_20261028.md)。

## B 静态数据并行统一

B 统一设备、时间分区和有序扫描构建，并管理实际资源、额度冻结与所有权移交。多源哈希路径按实际依赖启动消费者和生产者，按待发送桶处理背压。成功、取消和部分失败共用明确关闭责任。规划前取消保留真实终态，禁止晚建归属队列。查询终止另清理共享上下文映射，资源归零与生命周期终结分别取证。

例如，第二个工厂失败时，第一个已建驱动与其余未消费工厂分别关闭，片段的全部关闭槽最终必须归零。

数据来源：[B 设计](B_静态数据并行统一设计_20261031_实施版_复审修订.md)、[B 实现规划](B_静态数据并行统一实现规划_20261031_实施版_复审修订.md) 和 [B 实施记录](B_静态数据并行统一实施记录_20261031.md)。

## C 运行指标快照

C 复用 IoTDB 的算子计时、输出计数和统计 RPC，增加不可变身份、冻结代次、校验和及缺失原因。驱动输出来自根输出边界，扫描与合并根分别保存。全局调度计数只描述节点。

例如，扫描读十行、过滤输出四行时，驱动计数为四。CPU 没有可靠来源时，墙钟仍只表示经过时间。

数据来源：[C 设计](C_运行指标快照设计_20261101.md)、[C 实现规划](C_运行指标快照实现规划_20261101.md)、[C 实施记录](C_运行指标快照实施记录_20261101.md) 和 [运行字段来源](A-D_运行字段来源_20261102.json)。

## D 静态计划

D 在执行前选择扫描并行度并确定工作归属。稳定排序与分桶保证相同输入产生相同计划，缺少成本使用等量分配。内存准入在构建后处理，只为已选计划执行一次。

例如，配置上界四而只有三个工作单元时，扫描并行度至多为三。没有管理扫描的根片段保留零扫描并行度和真实交换边。

数据来源：[D 设计](D_静态数据并行设计_20261101.md) 和 [D 实现规划](D_静态数据并行实现规划_20261101.md)。设备、时间分区及有序模式的真实证据由 A–D 核查索引。

## E 动态并行控制

E 在下一片段构造前读取独立冻结历史。新增工作包括真实驱动与桶的配对、有界历史、策略滞回、协议版本和决策回执。运行中驱动保持原计划。

例如，前一个片段已经提交四个桶，下一片段可以依据反馈选择三个桶。前一个片段的队列及工作归属保持原值。

E 必须先完成文档审核，再按 E0 至 E5 实施。每步同时具备生产调用、单元正反测试和真实运行身份。最终退出包含完整模块回归与双节点结果。

数据来源：[E 设计](E_动态数据并行设计_20261102_第二轮修订.md) 和 [E 实现规划](E_动态数据并行实现规划_20261102_第二轮修订.md)。

W1 至 W9 对应阶段零至八，W5 对应阶段四。下表仅用于编号查找。

| 工作项 | 阶段 | 主题 |
| --- | ---: | --- |
| W1 | 0 | 基线门禁 |
| W2 | 1 | 语义准入 |
| W3 | 2 | 哈希属性 |
| W4 | 3 | 交换拓扑 |
| W5 | 4 | 多源双节点 |
| W6 | 5 | 哈希连接 |
| W7 | 6 | 扫描背压 |
| W8 | 7 | 性能矩阵 |

W1–W4 保留各自已关闭判据。W5 的受限多源能力在 A–D 中继续扩展验证。W6 的生产范围仍待决定，W8 的正式性能矩阵与 W9 的动态实施分别验收。A–E 不能直接替代 W1–W9 的状态。

例如，完成三十二桶正确性验收可以支持多源拓扑结论，但不能同时证明 W8 的性能倍率。

## 执行与排期

开发、编译、测试和服务全部在 sc01。每次执行保存工作区 manifest、入口、配置和产物 SHA，启动后继续核对实际类与依赖。完整 DataNode 套件应当预留约一小时机器时间，编译和双节点验收另计。

例如，两次修改各需一次完整回归，应当预留约两小时。E 的策略、协议及故障测试工期由其文件级规划决定，文档审核等待单独计算。

代码提交与推送按用户明确指令执行。文档同步前保留原件，三端逐文件核对 MD5。
