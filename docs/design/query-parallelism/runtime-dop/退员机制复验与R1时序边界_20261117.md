# 退员机制复验与 R1 时序边界

**目的**：解释原 R1 未触发退员的证据，并记录同一 v3 发行包上的补充功能验收。

**摘要**：两个原短查询都完成增员，没有观察到 SHRINK 决策。在保持引擎、策略、布局上限及真值不变的前提下，新增较长 CPU 扫描窗口。预先规定的三轮候选和固定一人对照全部通过，形成十八份片段资源回执。

**结论**：新发行包的实际增员与退员机制已得到重复服务验证。原短场景仍存在时序敏感的验收覆盖缺口，保留原失败；新运行不提供性能收益结论。

## 诊断依据

原短查询约一秒多完成，两次尝试中候选都从一人增至两人或三人。控制诊断没有 SHRINK 决策，不能解释为已经发出退员但执行器拒绝。相同策略每百毫秒采样，增员受连续窗口和冷却约束；工作在两个采样点之间自然结束时，并不保证出现可观察的缩容窗口。

旧 v2 成功轨迹在接近结束时记录 UNFINISHED_LANE_CONTRACTION；新 v3 两次原短尝试没有捕获这一决策。它们说明该用例对运行时序敏感，不能据此认定所有退员路径失效，也不能凭旧版成功把新尝试判为通过。

## 补充用例与事先判据

补充 SQL 保持原输入、列类型、输出列和 0–63 时间窗口，在残余 CASE 中增加有数据依赖的三角函数深度。有限整数输入的正弦平方与余弦平方之和仍远高于 0.5。分支改变计算负担，预期真值仍为原独立 fullScanWindowFiltered 真值。

SQL 中 d063 分支深度为 96，另一分支为四；本实验不以该表达式认定原生算子恰好花费某个预测 CPU 时间。标准原生执行器、优化器与控制器均未修改。输出完整比较与唯一真实扫描计数承担正确性判定，表达式恒等推导不能替代运行核对。

运行前固定三轮，每轮候选和固定一人对照。候选仍要求同一真实 SQL/FI/group 的初始一人、实际增员、随后实际退员。对照固定一人，两个实际 DataNode、八条逻辑 lane、原截止时间、冻结统计及真实资源终态检查全部保留。每轮完整结果必须与独立真值匹配，每次唯一原生源计数必须为 9,404,416 行。

## 实际结果

三轮的六次普通 SQL 均通过既有审计客户端，三组候选/对照/真值比较均通过。每次输出完整 4,096 行，唯一原生扫描实例为十六个，合计全部 9,404,416 输入行。十八个实际 FI 都有冻结终态和资源责任回执。

每次候选都记录到实际增员之后的退员。第一轮的两个来源组均记录 1→2→3→4→5→4→3→2→1。三次固定一人运行的各来源组始终一人。原两次短用例保持失败记录，补充用例使用独立名称和输出目录。

## 结算观测的限制

第三轮一个组的最后事件为请求一人、观察零人、APPLIED。现有实现等待退休与资源结算完成后，记录当时仍存活的成员数；自然完成可能与这次结算并发。因此不能将该事件写成配置了零个执行 worker，也不能把整个组描述为稳定停在一人。

该次完整结果、全部扫描计数、真实 FINISHED 和资源结算另有证明，但当前事件缺少足以还原精确交错的时间戳。补充验收使用之前清楚记录的 5→4→3→2 等实际收缩建立退员结论，不把末次零观测当作独立的成功目标匹配。

## 写作与复现范围

本实验使用普通 SQL 审计，包含 JMX 轮询，且没有五次预热和十五轮配对的性能协议。不得计算或引用这些运行的加速比。它只验证当前机制能在较长工作窗口内完成真实增员、退员、完整结果与资源结算。

原始材料位于 sc01 `/root/rivermind-data/iotdb-paper-experiments-20261117/runtime-output-schema-v3/tail-contraction-acceptance-r1/`。SQL、plan、驱动与运行身份、六套原始服务记录、三组完整比较及写作摘要已冻结在本稿 `evidence/tail-contraction/sc01/`。源码引擎仍为此前冻结 v3，生产代码没有变化，因此本轮没有重复原已通过的全量回归。

下一步需要把短查询的结果正确性与能稳定覆盖退员窗口的动作验收分别固定为标准用例，并保存二者的原始范围。完整布局、性能因果消融、强基线和独立联合选择器仍待补。
