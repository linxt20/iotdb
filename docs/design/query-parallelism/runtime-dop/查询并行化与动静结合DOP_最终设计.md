# 查询并行化与动静结合 DOP 最终设计

**目的**：在不依赖代码细节的层次，说明 A–E、同查询运行期扩展、正确性条件及研究边界。

**摘要**：方案先判断查询语义允许的并行形态，再固定数据归属，以原生统计支撑静态估计和历史反馈，最后在固定布局内调整实际扫描 worker。分布路由、有序要求、资源上界和原始截止时间共同约束调整。

**结论**：本文给出完整设计脉络，最终版本 v6 已完成组件、完整回归、双语编译、双节点 SQL 和标准 CLI 验收。它不把历史反馈等同于同查询弹性，也不将既有 property enforcement 方法或未经测量的性能数字列为新贡献。

## 背景与问题

同一条时序查询可能跨越多个设备、时间分区和 DataNode。分布式执行决定工作位于哪些节点，查询内数据并行决定一个节点上的独立扫描工作由多少执行者推进，两者需要共同保持 SQL 语义。

固定并发度难以同时适应短查询、长扫描、倾斜数据和竞争资源。并发度过低会延长可并行工作的关键路径，过高则增加队列、交换和内存成本。查询开始前的估计也看不到全部运行变化，因此需要把规划选择、可信反馈和执行中的调整连接起来。

这并不意味着每个算子都可以任意扩缩容。分组状态、排序归并、窗口函数和全局 LIMIT 各有约束；没有合法的执行形态时，系统必须保持原计划或串行回退。

数据来源：[A–E 阶段设计入口](../README.md)、[本轮运行期设计](运行期动态DOP设计草案.md)。

## A：以属性约束决定并行是否合法

计划为输入和输出保留分布与顺序要求。分布属性回答哪些行位于同一执行位置，顺序属性回答流按哪些键排列。一个父算子只有在输入满足自己的要求时，才可使用对应执行方式。

Filter 和适当的 Project 可在保持语义的条件下传播资格，但表达式改变键、顺序或状态依赖时必须重新判断。需要按分组键聚合时，系统建立一致的哈希重分布；只需无序结果时，可以使用就绪输入收集；需要全局顺序时，必须有合法有序流与归并。

构造算例：两个来源都含有分组键 g=7 的行，分别做完局部处理后直接拼接，不能代替按 g 汇总。系统必须保证这些局部结果最终到达同一个合法分组归属。

属性强制是既有数据库优化方法。本阶段的价值在于把它接入 IoTDB 表模型、扫描资格、透明包装和分布执行边界，并保留既有优化。不能为了获得并行资格而关闭谓词下推、删除全局限制或忽略顺序敏感函数。

数据来源：[属性框架设计](../records/属性驱动并行判定框架设计_20261027.md)、[本轮设计的计划资格](运行期动态DOP设计草案.md#计划资格与原优化器)。

## B：先固定归属，再提供执行者

逻辑 lane 表示稳定的工作划分，worker 表示推进这些工作的执行者。二者分开后，一个组可以固定八个 lane，却先由一个 worker 轮转推进，再由三个 worker 共同推进。

每个工作单元具有唯一身份，全部工作单元覆盖扫描输入，单元之间的归属不能重叠。worker 领取执行权，在协作边界归还执行权；改变 worker 数不重新定义数据属于哪个 lane。

设备、时间分区和有序扫描使用各自可证明的划分方式。小输入、无法证明的外部来源或不满足语义条件的形态可保持串行。初始并发度受实际可划分工作和资源限制，不能凭配置上限制造空工作者。

分组聚合的 bucket 另有固定路由。若两个来源连接三个 bucket，系统需要六条真实来源到 bucket 的边，并为每个 bucket 确认唯一拥有者。bucket 数来自计划，不能把两个 DataNode 直接解释成两个 bucket。

运行中增减扫描 worker 不改变 bucket 数、哈希规则或有状态结果的归属。通用 hash join 是否进入生产规划属于独立范围，本文不把扫描组弹性扩展为所有 join 或聚合算子的动态迁移。

数据来源：[B 设计](../records/B_静态数据并行统一设计_20261031_实施版_复审修订.md)、[固定布局](运行期动态DOP设计草案.md#固定布局与初始并发度)、[R7 验收范围](运行期动态DOP实现规划草案.md#双节点多源分组聚合与透明包装)。

## C：尽可能复用原生指标

静态和动态决策共同读取 IoTDB 既有驱动、算子、片段统计及传输流程。可复用的数据先复用，新增信息只补原统计没有表达的归属、计划身份、有效范围、资源责任和扫描进度。

一个时间值必须说明属于哪个查询、FI、计划版本和驱动；一个源行数必须说明是否完整、是否只是累计别名。缺少这些条件时，统计可以保留用于诊断，却不能直接用于控制。

构造算例：两个包装端点共用同一物理队列，资源统计按一个账户计费，端点各自仍有关闭责任。把两份包装记录相加会重复计算物理内存，把它们合成一个责任又会遗漏关闭工作。

统计还需区分零值和不支持。未采集 CPU 时间、spill 或外部扫描覆盖时，系统保存缺失与覆盖原因，不能填零后解释为没有成本。固定单 worker 对照未保留冻结统计时，也应记录未执行检查，而不是补造完整快照。

原生指标可以同时支撑静态校准、历史反馈和运行期控制，但三者使用时间不同。计划前读取已完成的可信记录，运行期读取本查询的有限实时采样，终态快照负责固化结果和资源结算。

数据来源：[C 指标快照设计](../records/C_运行指标快照设计_20261101.md)、[运行控制与进度](运行期动态DOP设计草案.md#控制策略与扫描进度)、[观测边界](REPRODUCING_RUNTIME_SQL.md#对照统计的可观测边界)。

## D：静态估计提供可解释的初值

静态选择先依据实际可见输入建立工作估计，再受可划分单元、并行上限、CPU 配额及内存约束限制。它决定初始 worker，并保存计划身份和估计依据。

估计需要区分物理扫描输入、文件字节、输出行数和表达式计算量。一个最终只输出少量行的查询，仍可能读遍多个时间分区；输出小不能直接推出扫描成本小。压缩文件字节也不能被混同为解压后的内存需求。

初值和布局分别受约束。在一个固定八 lane 的构造算例中，估计可以选择一个初始 worker，并允许在资源许可时增长。只有一个合法工作单元时，则不能通过增加 worker 获得数据并行。

静态策略提供保守起点，不声称一次估计就是全局最优。证据不足或输入不受支持时，策略使用明确回退原因；后续反馈只在可比范围内修正该选择。

数据来源：[D 静态设计](../records/D_静态数据并行设计_20261101.md)、[本轮初值与布局](运行期动态DOP设计草案.md#固定布局与初始并发度)。

## E：历史反馈与同查询控制的职责

历史反馈只接收身份、覆盖和终态可信的记录，用于后续相同或可比形态。它可以影响新的初值或在开始前重新均衡一份新布局；已经运行的查询继续使用自己的冻结布局。

本轮扩展在原生执行过程中采样本查询的活动、剩余工作与资源情况，再选择保持、请求增长或协作缩减。调整须有收益条件、抖动限制和资源门槛；观测缺失、工作结束或清理开始时，不继续制造新的工作者。

增长先准备并准入新增成员，再将它们纳入原生调度。CPU、内存或截止时间条件不成立时，保留拒绝结果。缩减停止成员继续领取新工作，让已执行量子协作退出，再确认任务、配额和临时资源的归还。

~~~mermaid
flowchart LR
  S["可信实时采样"] --> P["保持／增长／缩减"]
  P --> G["语义、CPU、内存、截止时间门槛"]
  G --> M["原生成员准备或退休"]
  M --> A["实际结算事件"]
  A --> S
  T["查询终态"] --> X["封闭调整并等待责任结算"]
  X --> F["冻结统计与清理回执"]
~~~

请求和实际执行分别记录。构造算例中，请求从一变二但配额拒绝时，只能说发生增长请求；同一查询、FI、组实际先一、二、三，再二，才证明真实扩容后缩容。终态清理变为零属于停止，不属于运行中缩容。

数据来源：[E 历史反馈设计](../records/E_动态数据并行设计_20261103_第五轮修订.md)、[运行期原生调度](运行期动态DOP设计草案.md#原生调度与成员调整)、[控制证据](运行期动态DOP设计草案.md#查询身份与运行证据)。

## 有序执行和合法回退

有序扫描需要在每条逻辑流中保留对应顺序，再通过归并建立所需全局顺序。多个有序 lane 由一个 worker 推进时，不能在等待一条流时永久阻塞其他流；每条流还需有可推进的前沿容量。

按 device_id、time 排序与只按 time 排序具有不同合同。前者在键唯一时比较完整序列；后者允许相同时间内设备顺序不同，但必须保持时间单调并逐时间组保留完整多重集。

构造算例：time=0 有来自六十四个设备的行，组内交换两个设备顺序合法；把 time=1 的行插入 time=0 组则违反顺序，即使全体行的多重集仍相同。

全局 LIMIT、OFFSET、TopK、窗口、FILL 和 DIFF 等按各自语义保留资格否决或原路径。合法串行回退仍可通过结果兼容性，但不能登记为运行期能力覆盖。系统不为触发实验而绕过这些条件。

数据来源：[有序设计](运行期动态DOP设计草案.md#有序归并与前沿预留)、[标准 SQL 与完整比较](REPRODUCING_RUNTIME_SQL.md#普通-sql-与完整结果比较)。

## 正确性与资源不变量

设计以五类不变量约束每个阶段，并用单元测试和实际 SQL 检查对应执行路径。形式化论证必须明确前提与支持范围，有限夹具本身不能证明所有 SQL。

| 不变量 | 约束 | 违反时的结果 |
| --- | --- | --- |
| 完整且唯一的工作归属 | 所有单元覆盖输入，同一数据归属不重复执行 | 缺行、重复行或状态重复更新 |
| 分布与路由一致 | 相同分组键按同一规则进入唯一 bucket 归属 | 分组结果分裂或错误合并 |
| 顺序保持 | 各流与全局归并满足查询要求 | 结果行序或顺序敏感函数错误 |
| 有界资源与单一责任 | 实际物理预留不重复计费，每个责任结算一次 | 超额、泄漏、重复释放或提前释放 |
| 原始截止时间与终态封闭 | 新成员沿用所属 FI 原绝对截止时间，终态不再加入成员 | 延长查询时限或清理后重新活动 |

无序结果按完整有类型多重集判断等价，保留每行的全部出现次数；有序结果另满足排序键条件。聚合保留原算子的类型和合并语义，不宣称超出 SQL 既有数值保证的浮点逐位恒等。

取消、deadline 和真实失败分别保持自己的原因。一个查询的超时触发后，同次 FI 和任务保留原始超时原因，不能被普通级联取消改写。截止触发器已经被替换时，旧触发器不能停止新登记的任务。各 FI 保留各自原值；真实分布执行的初始值可有毫秒级差异，不能把它们表述成同一个毫秒数。

收尾先封闭新增工作，等待正在执行的成员和控制结算，再关闭实际资源并冻结可验证证据。关闭失败继续保留尚未证实释放的责任。全部字段为零却没有正向创建记录，不构成释放证明。

数据来源：[生命周期与统计](运行期动态DOP设计草案.md#终止与统计冻结)、[查询级超时接线](运行期动态DOP实现规划草案.md#查询级超时原因与哨兵代际)、[资源验收](运行期动态DOP设计草案.md#结果与资源验收)。

## 从计划类型到有界输出切块

计划中的结果类型与原生物理列表示可能不同。例如，一个计划为八字节整数的常量，经原生折叠后可暂用四字节表示；严格跨片段交换仍必须遵守计划端点的类型合同。

系统在独立输出副本中进行明确、无损的表示归一化。相同物理表示的逻辑别名、小整数到长整数的扩宽，以及目标类型的全空列可按合同处理；缩窄、无关转换或错误列数继续拒绝。

切块必须先按目标表示预算，再选择可输出行数，最后复制和编码。仅在发送端复制时扩宽不够：若切块仍按四字节值选择过多行，扩成八字节数组后就会超出已准入额度。

构造算例：4096 个四字节值的值数组为 16 KiB，扩宽后为 32 KiB；还需时间、空值和对象空间。一个只适合较小副本的额度必须提前缩小行块，不能先分配完整大数组再检查。空列也按目标表示参与同一预算。

这一规则由 v6 贯穿计划端点、输出切块和独立复制。严格编解码器保持原拒绝条件。同 v6 产物的常量 SQL 已完整返回 257 次 INT64 [1]，既有测试另覆盖多列常量和全空列跨块时的完整性与资源上界。

数据来源：[外部输出的实现规划](运行期动态DOP实现规划草案.md#外部输出的计划类型与有界副本)、[最终版本状态](实现进度与验证记录_20261115.md)。

## 验收如何建立结论

正常场景保存精确 SQL、查询和 FI 身份、实际主机与交换边、完整类型结果及资源回执。独立比较器核全部行和重复次数，SHA 用于身份和摘要补充，不替代完整比较。

| 能力 | 必须出现的额外证据 |
| --- | --- |
| 同查询扩缩容 | 同 query/FI/group 的正值实际增长、随后实际缩减，布局不变 |
| 单 worker 多有序 lane | 实际 ORDERED、多 lane、初始和最大 worker 都为一 |
| 多源 GROUP BY | 实际 DataNode、源、bucket、FI 及逐边互认，完整聚合结果 |
| 原生 LIMIT 提前结束 | 完整常量多重集、真实运行组及大于零且少于全输入的源计数 |
| 定向取消 | 活动后对实际查询发出取消，真实取消终态和清理 |
| deadline | 原正截止时间实际到达、精确超时原因、真实活动与清理 |
| 执行异常 | 数据依赖表达式实际执行失败，原生运行组、FAILED FI 与清理 |

无序 LIMIT 的新夹具投影常量后取完整 257 行，全部结果均为同类型的 [1]。它避免给无序选行强加不合法顺序，仍需验证 257 次出现而非去重集合。实际源未读完整体输入，才构成提前结束证据。

v6 的最终矩阵与八组完整结果比较已通过：运行期 LIMIT 的源输出为 160000 行，小于全输入 9404416 行；R1 同一组实际形成 1→2→3→2→1；19 个接受运行的 65 个 FI 均有完整资源回执。历史版本的通过、合法串行回退和失败原件分别保留，不相互替代。

## 研究贡献与论文边界

研究叙述可以从“在语义与资源约束下让单查询使用适当执行宽度”展开。背景解释时序输入的多设备、多分区与倾斜，动机展示固定宽度的局限，方案再逐步给出资格、布局、可信观测和动静结合的控制。

| 条目 | 可组织的贡献 | 必须补齐的边界 |
| --- | --- | --- |
| 技术贡献一 | 面向 IoTDB 表模型的并行资格、固定数据归属与顺序/哈希语义组合，以及正确性论证 | property enforcement 本身不是新方法；需与已有执行模型比较 |
| 技术贡献二 | 静态初值、可信历史反馈和同查询原生 worker 调整的结合 | 三层作用时间要分清；收益、稳定性和适用范围需独立实验 |
| 系统贡献 | 在真实 IoTDB 规划、原生执行、指标与资源生命周期中形成可复现实现 | 扫描能力不外推到全部算子；测试范围不能省略 |
| 效果贡献 | 在代表性负载和资源约束下展示收益与成本 | 这是待实验验证的条目，不能先填加速倍率 |

理论部分应定义工作归属、属性满足、路由、执行宽度与资源责任，再说明哪些条件保证结果和顺序不变、调整不重复执行工作，以及终态能够完成责任结算。已有方法的应用、工程不变量和完整形式化证明分别表述。

性能实验需要区分串行、静态、历史反馈和真正运行期控制，报告查询延迟、吞吐、CPU 成本、峰值资源、控制开销、不同选择率和倾斜，以及无收益或回退的情形。重复、暖机、误差和实际执行身份不可省略。

本轮没有冻结的性能结论，不选择 3.33 或 2.95 倍作为统一倍率。通用 hash join 的生产范围、CPN 是否进入正文和投稿拆分继续遵守用户确定的口径。论文是否有足够独立创新，需要相关工作对比和实验来支撑，不能由两个功能模块直接推出两篇系统论文。
