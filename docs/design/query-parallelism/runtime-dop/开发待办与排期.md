## 并发与冻结规则

主源码在编译、测试和打包期间冻结。独立全量使用同输入的独立 checkout；审查和文档只写各自 staging。不能让另一个 Maven clean 删除正在使用的产物或报告。

服务验收可用独立候选、对照和运行目录并行准备；共享池基线、JMX 资源审计和定向取消仍必须绑定唯一 SQL，不能交叉归因。重跑用新路径，不覆盖旧部署、结果或失败。

research、SQL、参数和夹具绑定已经冻结时，文档人员不直接修改它们。最终绑定由主流程在实际发行身份确定后生成。例子：v5 的参数指向 v4 JAR 时，应修正绑定并新建运行，不能沿用“参数文件名相同”推断正确。

数据来源：[源码身份](README.md#源码与冻结版本)、[证据规则](REPRODUCING_RUNTIME_SQL.md)。

## 每项服务的通过条件

正常 SQL 同时具备完整排空回执、实际执行身份、候选/对照/oracle 全部出现次数与类型比较，以及所有 FI 的资源结算。有序查询另核排序键单调，唯一键比较全序列，同键组比较完整组内多重集。

原生 LIMIT 使用完整 257 次常量结果，另证真实运行组及部分源扫描；有序主场景合法 SERIAL 只登记兼容。R1 必须出现同 query/FI/group 的实际正值 GROW 后 SHRINK，终态零成员不是缩容。

取消、deadline 和执行异常分别保留精确代码与真实终态。R5 使用原始绝对截止时间和 720；R6 使用原生 CAST 的权威非零 701，加实际运行组与 FAILED FI。旧包装识别不扩展任意文本或错误码。

数据来源：[场景实现规划](运行期动态DOP实现规划草案.md#普通-sql-服务验收)、[概念层正确性条件](查询并行化与动静结合DOP_最终设计.md#正确性与资源不变量)。

## 独立于工程收尾的研究欠缺

性能评估需要固定数据规模、查询选择率、数据倾斜、CPU/内存额度、暖机与重复统计；分别比较串行、静态、仅历史反馈及同查询运行期控制。延迟、吞吐、CPU 时间、峰值资源、调整开销与受限场景都需原始数据。

论文还需完成相关工作对比、创新边界和理论论证的完整表达。property enforcement 不作为新算法贡献；hash join 生产规划范围与 CPN 正文位置保留用户口径。这些事项不由正确性用例的 PASS 自动完成。
