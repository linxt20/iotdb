# IoTDB 运行期动态 DOP 开发排期

**目的**：明确新实例迁移核查后的开发范围、依赖、验收条件和预计完成时间。

**摘要**：现有执行平台在构建后固定驱动数量与工作归属，历史反馈作用于后续规划。新增能力需要让同一次查询在执行中改变并行度。本文先安排迁移和基线核查，再安排运行状态、驱动生命周期及控制策略，最后执行兼容、异常和真实服务验收。

**结论**：生产开发以新实例迁移核查通过为前提，完整工程验收按十五至二十五个有效工作日估计。设计和独立组件可以并发，核心执行集成依次通过验证。登录等待、材料补迁和投稿级多机实验单独计时。

当前状态：新实例认证与密钥恢复已完成。冻结源码与清单覆盖的 326 项历史材料摘要一致，旧临时工作树没有迁移；最终源码已在数据盘恢复。完整英文编译与全量基线单测通过。运行组件的 59 项专项、7580 项完整单测与中英文编译通过，真实服务接线与验收尚未完成。

## 开发背景与完成标准

该功能允许一条正在执行的查询增加或减少实际工作的扫描驱动，并把尚未领取的工作交给合适的驱动。调整过程中，输入必须保持完整且唯一，结果及要求的顺序必须正确，资源与终止过程必须有效。

整体 goal 已建立，范围包含迁移核查、设计、实现和工程验收。源码、编译和运行工作继续在 sc01 进行，本地只整理设计、排期与核查材料。服务器为 `sc01-ssh.gpuhome.cc:30920`，已恢复密钥登录。开发分支为 `feat/runtime-dop`，源码目录为 `/root/rivermind-data/iotdb-runtime-dop-20261115/repo`；冻结基线在相邻的 `baseline` 目录运行，旧开发目录保持原状。

实际 DOP 表示同时获准处理扫描工作的驱动数量。已创建驱动数、Hash 桶数和片段实例数分别记录。例如一个片段创建四个驱动而只允许两个处理工作时，活动 DOP 为二。工程交付还必须验证新增驱动的准入和退休驱动的资源释放，资源行为以实际回执为准。

执行权在驱动量子结束后归还，游标、算子树和队列始终保存在原逻辑驱动中。另一工作者可以继续调用同一个逻辑驱动；同一逻辑驱动不能被同时领取。该设计不复制或序列化读取游标，逻辑布局与工作粒度由静态阶段选择，运行阶段调整实际工作者数量。

扫描侧调整需要兼容无序扫描、Filter、Project、有序路径和既有受限 GROUP BY。Hash 桶与聚合状态的所有者保持稳定，扫描驱动变化通过明确的生产者与结束协议传递。运行期改变 Hash 桶数、迁移 Join 或聚合状态属于独立扩展，论文和验收报告必须准确说明这些边界。

数据来源：冻结参考提交为 `da2f455c3a2216f1f676844f91b32e724d7d5709`，参考分支为 `feat/query-parallelism-six-parts`。直接相关工作包括 Xukang Zhang、Huanchen Zhang 和 Xiaofeng Meng 的 *Intra-Query Runtime Elasticity for Cloud-Native Data Analysis*（PACMMOD 2025，DOI 10.1145/3725315）。其 Accordion 系统采用遵循 Presto 模型的独立 C++ 实现，已讨论初始并行度、预测和运行调整，不能把“静态加动态”本身作为新贡献。

运行状态与资源协议见[运行期动态 DOP 设计草案](运行期动态DOP设计草案.md)，文件职责与验证安排见[运行期动态 DOP 实现规划草案](运行期动态DOP实现规划草案.md)。两份草案已绑定恢复后的远端冻结源码。执行权状态机、工作者和驱动静止接口已开始实现，组件测试与真实执行验收分别报告。

## 迁移与基线核查

迁移核查必须同时检查仓库内容和原始数据盘材料。固定提交、工作区变化、远端地址、设计原件、验收摘要及历史运行原件分别核对。每个检查项保存存在状态、解析路径和适用的摘要。

数据盘核查优先检查历史持久根与 `/tmp/Dev_1/` 的实际链接和挂载。证据清单没有覆盖整个旧磁盘，因此报告只能对清单覆盖的材料给出结论。可恢复依赖与不可恢复原件分别登记，缺失内容在影响判断完成前必须保留为未关闭项。

认证成功后记录新机器的 CPU、内存、磁盘与运行环境，再使用仓库复现指南运行标准验证。执行前核查入口、直接 driver、配置与发行包身份，启动后检查实际加载类和运行端点。现有 Java 与 Python 验证作为新功能开发前的参考。

数据来源：迁移锚点与配置变更回执保存在 [新实例迁移与基线核查](迁移与基线核查_20261115.md)。标准验证入口为仓库 `docs/design/query-parallelism/REPRODUCING.md`，依赖锁定与验证选择由同目录的 manifest 提供。

## 开发顺序与并发边界

设计必须先确定运行状态、工作领取、驱动注册和终止条件，再并发实现组件。一个负责人统一集成规划器、调度器和终态路径，避免多个实现各自修改相同生命周期。

接口固定后，可以并发推进工作归属、观测与策略、测试输入与事件校验三条工作线。单片段真实升降宽通过后，再集成有序与多源路径。标准回归通过后运行隔离双节点验收和性能测量。

静态身份继续使用冻结的工作描述，运行期另行记录工作代次、领取状态与驱动成员。控制器必须在可检查的边界提交变化，过期请求和终态后的请求分别拒绝并记录原因。

### 运行中观测

观测复用原生算子计数和驱动执行入口，新增数据只覆盖运行期必要的进度、在途工作与调整代次。样本必须携带时间边界和来源，未支持字段保持缺失原因。驱动墙钟包含等待，控制器需要结合实际工作进度解释它。

### 工作领取与归属

工作单元必须有稳定身份以及待领取、执行、完成和取消状态。领取与完成必须可核对，退休驱动只交还尚未开始的工作。重复请求、过期完成回调与并发领取进入既有单测体系，完整结果检查与工作身份检查同时执行。

### 驱动与资源生命周期

升宽必须先通过新增资源准入，再创建与发布驱动，部分失败按同一次变更回滚。降宽先停止领取新工作，再排空在途工作，最后释放已无引用的资源。取消与终态必须阻止新成员提交。

结束判断必须同时覆盖待领取工作、在途工作、成员变更和输出排空。固定收集器和固定驱动关闭计数需要匹配新的成员生命周期，新增协议必须防止提前完成和永不结束。

### 静态与运行控制

静态阶段给出初始 DOP、工作粒度、合法调整范围及成本来源。运行阶段结合真实剩余工作、资源状态与调整代价选择保持、升宽或降宽。策略需要记录目标宽度、实际宽度、触发依据和调整结果。

控制器必须与静态单独使用、动态单独使用和直接组合分别比较。已有 Accordion 已考虑预测与调整成本，新研究需要检验静态结构怎样影响运行期动作及总体效果。

## 单元与真实运行验收

新增功能测试直接进入 IoTDB 既有 Java 与 Python 测试体系，并按仓库标准命令验证。测试需要随功能实现，表中完整回归阶段用于跨组件集成，测试目的与未覆盖范围随结果报告。

同次查询必须真实完成一、二、四、二、一的 DOP 变化。每次变化之后仍需有实际工作执行，工作身份覆盖与业务结果同时正确。新查询或下一次片段才改变宽度，只能计入历史反馈验收。

有序查询比较完整输出顺序，无序查询比较完整结果多重集。GROUP BY 检查跨源同键、空源、空桶、倾斜和空值。Filter、Project、LIMIT、窗口、FILL 和 TopK 保留原生优化的计划与结果回归，运行调整资格由明确条件控制。

异常测试覆盖部分创建失败、预算拒绝、调度提交失败、读取异常、下游失败和调整期间取消。使用 latch 或 barrier 控制关键交错，并检查实际账户、队列、句柄和驱动终态。终态快照必须保留退休驱动已经贡献的工作和计数。

双节点验收核对实际 DataNode、片段、源、桶和交换边的身份，保存完整结果与规范摘要。同主机多进程结果用于对应拓扑的功能结论，跨物理机效果在投稿扩展实验中单独验证。

数据来源：标准入口由[冻结版本复现指南](https://github.com/linxt20/iotdb/blob/da2f455c3a2216f1f676844f91b32e724d7d5709/docs/design/query-parallelism/REPRODUCING.md)提供，新增选择并入相同验证体系。已有测试数量与历史验收事实见[冻结版本证据索引](https://github.com/linxt20/iotdb/blob/da2f455c3a2216f1f676844f91b32e724d7d5709/docs/design/query-parallelism/README.md)。
