# 真实数据查询的输出列映射与交换 schema 修复

**目的**：记录 Beijing 真实数据首次执行暴露的输出列映射错误、修复范围和验证要求。

**摘要**：两侧各 420,768 行完整类型导入校验通过后，过滤投影查询在运行期紧凑输出处失败。原生 OutputNode 只保存结果映射，执行器透传子节点的数据块；新增交换合同错误使用逻辑输出符号的列顺序。修复应从物理子节点推导 schema，保留原生客户端映射。

**结论**：修复前，三项新增回归断言全部失败，所选三类测试共 68 项、失败三项、错误零项。生产修复只调整端点 schema 的推导来源。本文冻结时，新发行包和真实 SQL 复验仍待完成；后续结果写入独立验收记录，不修改旧 v2 清单。

## 失败条件与证据

查询在表模型中返回 station_id、time、pm25、pm10、wind_direction，并按 pm25、wind_speed 和名义时间轴过滤。源数据为 UCI Beijing 的十二站点。完整导入校验逐列比较各站点全部行，保留 DOUBLE、STRING、BOOLEAN、INT64、TIMESTAMP 和 SQL NULL。

失败的运行有三个实际 FI、两个实际来源 DataNode。错误来自根 FI 的 RuntimeCompactOutputOperator，信息为 Native output type differs from planned runtime schema。该次未进入性能计时。

首次审计编排还遗漏既有 Java 17 的 --add-opens 参数，续跑已经恢复该参数；两次失败分别保留。Java 启动错误与后续生产 schema 错误不是同一问题。

数据来源：实验根目录 fixed-worker-controls-v2/beijing-real-controls-01/。完整导入在 import-validation.json，SQL 失败在 resume-audits-01/audit/beijing-filtered/candidate/，原编排失败在 audit/ 下。

## 原生语义与根因

TableOperatorGenerator.visitOutput 直接返回子节点算子。OutputNode 的输出符号可以重排、重复或只声明部分物理列，客户端按原生结果映射取得逻辑输出。因此，OutputNode.getOutputSymbols 不必等于实际 TsBlock 的物理顺序和列数。

LocalExecutionPlanner.runtimeEndpointBounds 原来只解开 IdentitySinkNode 或 ShuffleSinkNode，随后从直接子节点推导 schema。根部直接子节点为 OutputNode 时，逻辑输出顺序被错误用作物理交换 schema。严格类型检查正确拒绝了不匹配的数据块。

例如，物理顺序为 TIMESTAMP、STRING、INT32，逻辑输出为 STRING、TIMESTAMP、INT32。原合同声明后者，而算子实际仍输出前者。三个测试还分别覆盖重复 STRING 的子集，以及嵌套的 metadata-only 输出节点。

## 修复范围与处理

在 LocalExecutionPlanner.runtimeEndpointBounds 解开 sink 后，继续循环解开 OutputNode，从第一个实际生成数据块的节点读取输出符号及类型。继续使用原有 TypeProvider、块字节上限、列数、内存预付和严格 codec。缺失类型仍在物理资源建立前拒绝。

本修复不增加物理投影算子。它保留原生谓词下推、扫描、聚合、TopK 和结果列映射。其他真实算子仍按各自输出符号确定交换合同；不把 ProjectNode、FilterNode 或任意单子节点视作可以跳过的元数据节点。

生产位置为 iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/LocalExecutionPlanner.java。测试加入既有 RuntimePlannerAdmissionTest，沿用真实计划节点、TypeProvider 和预算入口。

## 验证顺序与退出条件

先在生产代码未改动时运行三类现有测试，确认新增三项断言失败，其他测试不引入失败。该反向记录为 runtime-output-schema-v3/reverse-before-fix/summary.json，原生产文件字节单独保留。

修复后，执行标准专项、英文与中文编译、干净打包，再对独立源码快照执行完整 DataNode 依赖 reactor。发行包与实际回归生产 class 逐字节核对。后台线程断言继续按其实际来源单独检查，不以 JUnit 零失败代替。

以新的 v3 发行目录和隔离服务复验原始 SQL，并增加 SQL 重排和重复别名的完整有类型结果比较。Beijing 每侧重新导入并核全部 420,768 行。普通 SQL 审计检查实际 FI、来源、冻结统计、资源终态和固定 worker 合同。原生回退单列，不能把没有 runtime group 当作 worker 收益。

全部功能验证通过且没有 Maven 消耗测量主机后，再执行四查询各侧五次预热和十五轮配对。保留全部样本、失败及独立原始 CSV 真值。真实 UTC、完整跨运行设备/时间/bucket 内容及跨物理机扩展仍需独立证据。
