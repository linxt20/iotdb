# 新 sc01 迁移与基线核查

**目的**：为开发与验收人员说明可用的迁移材料、执行身份及 v1 实物证据范围。

**摘要**：迁移核查覆盖冻结源码、文档、快照和依赖材料。本文核对 SSH 密钥、开发目录与发行包之间的身份关系。本文同时登记 v1 双节点加载后的文件布局和完整回归产物对照。服务修复版继续使用独立构建和独立验收记录。

**结论**：密钥登录和已登记材料可用于继续开发，v1 两侧加载及生产 class 字节对照已有冻结证据。运行期服务修复已经集成，修复版专项已通过。修复版完整回归、发行包和普通 SQL 服务验收按[专项与全量验证](运行期动态DOP实现规划草案.md#专项与全量验证)及其服务回执完成后确认。

本文保留迁移及 v1 阶段的核查口径，其中“登记提交”“未提交修改”和后续验收安排均指当时快照。当前最终代码为 `38fc937fe3b3cc1d34827fb76a3ce96380b9b58c`；v6 的完整回归、发行包及普通 SQL 服务矩阵已完成，当前结论见[最终验收摘要](audit/final-runtime-v6-validation.json)和[实现进度](实现进度与验证记录_20261115.md)。

## 迁移核查背景

迁移核查需要证明开发者能访问正确实例，并能找到对应源码、依赖和原始结果。成功的定义是每份已登记材料具有可定位路径与内容摘要，每次构建和服务运行具有单独的执行身份。

文件迁移、CPU 测试和普通 SQL 服务分别提供各自范围的证据。验收必须将结果绑定到实际使用的源码和发行包。不同发行包必须分别保留运行记录。

## 运行数据与产物对照

v1 的候选和对照各有两个真实 DataNode，加载器各记录写入 9,404,416 行、2296 个成功批次和四个时间分区刷盘。两侧加载执行均正常结束，收据状态均为已加载并刷盘。加载收据的 SQL 行数独立核查字段仍为 false，写入计数按加载器回执解释。

每侧数据库分布在两个 DataRegion，每个区域包含四个时间分区和四个已闭合 TsFile。区域 1 的文件总量为 1,971,034 字节，区域 2 为 2,435,219 字节。两个值分别约为 1.880 MiB 和 2.322 MiB，都小于 128 MiB 的估计门限，因此满足一个初始工作者的字节条件。

估计门限按单区域的顺序和乱序 TsFile 总量计算。例如，总量为 64 MiB 的区域按 128 MiB 每工作者向上取整，得到一个工作者。实际激活人数仍必须由同一次查询的运行组记录确认。

采集时两侧共六个服务 JVM。16 个 TsFile 在计算摘要期间保持稳定，具有闭合尾标记和资源侧文件。按区域与时间分区对应的八对跨侧 TsFile，其大小和 SHA256 全部一致。

v1 独立完整回归的全部 4503 个 DataNode 生产 class，与 v1 server JAR 对应项逐 SHA256 一致。比较包括嵌套类、匿名类及其他编译器产物，缺失和差异均为零。该结果证明被测 CPU 产物和 v1 发行 class 一致，服务通过范围由普通 SQL 回执另外确定。

数据来源：现场证据位于 `fixture-layout-evidence-v1/delivery.json`，SHA256 为 `c05abba5104ab63f559dd7b9a99d4cdd618d7f113116baf89481e115e2c89a00`。文件清单为 `tsfile-roster.json`，布局为 `fixture-layout.json`，进程为 `process-snapshot.json`。完整 class 对照为 `full-release-class-equivalence.json`，SHA256 为 `8f9c1357a6b223d29ce449bba76ac5a0deca719eca5d6053385f3f39fb435976`。加载回执位于 `runtime-sql-acceptance-v1/load-candidate-001` 和 `load-control-001`，上述路径均相对于[源码与执行目录](#源码与执行目录)的执行记录根目录。
