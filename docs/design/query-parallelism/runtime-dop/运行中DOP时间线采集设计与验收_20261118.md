# 运行中 DOP 时间线采集设计与验收

**目的**：补齐长查询跨越背景负载变化时所需的控制输入、实际成员调整与时间关联证据。

**摘要**：扩展复用已有控制器事件、策略输入、成员结算和资源审计窗口。新增读取接口只复制现有记录，客户端持续写出原件、去重事件和缺段判定。终态冻结接口仍按原生命周期执行。

**结论**：隔离工作树中的八类专项共 99 项通过，中英文全工程编译通过；客户端经修复返回类型后独立编译通过。全量回归、发行包对应、实际服务连续采集、丢段负例和观测开销仍待验收。本扩展没有增加 CPU 利用率输入，也尚未证明外部 CPU 竞争下的策略收益。

## 场景与版本

动态主实验要求长查询覆盖背景负载的增加和回落。最终快照只保留有界事件尾段，不能单独重建查询中段。调用 `freezeControlEvidence` 还会封闭成员结算，并要求控制器已停止，因此运行中采集必须使用独立读取方法。

工程根为 sc01 `/root/rivermind-data/iotdb-paper-experiments-20261117/`。本扩展工作树为 `runtime-live-observation-v6/source`，分支为 `feat/runtime-live-observation-20261118`，基提交为 `1959820d4eec2c5f4154ee3c7652b1a9f85caa32`。它继承 v5 实验变更，来源记录保存在 `runtime-live-observation-v6/worktree-identity.json`。已测 v5 源码、服务、发行包与 r11 文稿保持冻结。

本目录名中的 v6 指本次运行中观测扩展，必须通过路径和发行摘要与较早论文中的原生动态 DOP v6 区分。分支基提交不包含本次未提交修改，不能单独识别执行版本。

## 指标复用与新增关联

控制器原先已经取得完成工作、总工作、就绪 lane、背压 lane、活动租约、当前 worker、资源容量及调整中状态。本扩展将实际传入策略的不可变输入随原事件保留，不重复读取 CPU、扫描器或资源池。一次采样中前组已经请求调整时，后组输入包含调整中标记；采集保留该实际求值输入。

控制器的事件环仍为 128 条，另保留累计事件总数。一个采样 tick 可以记录多个组，因此累计数不能用采样序号替代。例如，两个组各记录两百次，共四百条事件，尾段的一百二十八条对应本地事件序号 273–400。

成员结算沿用 INITIAL_ACTIVATED、APPLIED、拒绝和停止结果。真实记录增加 `System.nanoTime` 时间戳；旧构造器和夹具没有时间戳时保留缺失。终态 JSON 的既有字段继续由原序列化路径生成，新增运行中接口使用自己的外层结构。关闭到零及 STOPPED 不作为查询中的有效缩容收益。

## 服务端读取路径

| 文件 | 增加的处理 |
| --- | --- |
| `RuntimeDopController.java` | 在原事件中保留实际 Input；提供不可变 TraceSnapshot，含时钟原点、事件总数和停止确认 |
| `RuntimeDopExecutionSnapshot.java` | 实际成员事件可携带结算时间；旧构造器明确保留缺失 |
| `RuntimeFragmentLifecycle.java` | `snapshotLiveControlEvidence` 复制组记录和控制器尾段；终态保留纯值 TraceSnapshot，释放物理拥有者后仍可读 |
| `FragmentInstanceManager.java` | 按完整查询与 FI 身份读取已发布上下文，不初始化服务单例 |
| `ResourceAuditManager.java` | 复用显式、有期限的资源审计窗口，要求查询与 FI 已登记 |
| `MPPDataExchangeService.java` 与 MBean | 暴露 `readRuntimeControl(windowId, queryId, fragmentInstanceId)` |

上表生产文件位于 DataNode 的 `src/main/java/org/apache/iotdb/db/queryengine/` 下。控制器和成员事件不保留 driver、future、队列或资源拥有者。读取不采样、不调用 resize、不封闭结算、不冻结状态，也不修改截止时间。

组记录与控制器采用分别加锁复制，读取窗口由开始和结束的单调时钟界定，不宣称跨组原子快照。读取时不在持有 evidenceLock 的情况下再取控制器锁。终态字段和采样停止确认分别表达其含义。上下文缺失、没有运行组、没有控制器和控制器尚无样本有不同状态，禁止补成全零资源观测。

## 客户端采集

现有 `OrdinarySqlAcceptanceDriver.java` 增加可选 RuntimeTimeline。参数 `captureRuntimeTimeline=true` 开启采集；`runtimeTimelineOnly=true` 关闭重复的运行中完整 Thrift 统计轮询，保留 JMX 时间线、完整结果和终态审计。默认关闭，两项都写入执行参数及结果回执。

客户端先取得实际普通 SQL roster，再按每个 FI 的实际 DataNode 调用接口。每份原始响应记录查询、FI、节点、窗口与客户端读取时间范围。原件写入 `runtime-live-timeline.jsonl`，去重后的控制与成员事件写入 `runtime-live-event-stream.jsonl`。

控制事件以累计数和尾段长度恢复事件序号；成员事件以各结果类别累计数恢复组内事件序号。同一序号重复出现时摘要必须一致。当前总数减去先前总数大于可用尾段时，缺段永久登记。初次观察已经丢掉开头同样失败，不能只证明后半段连续。

资源结算后再次读取尾段，核对所有已观察组的冻结状态、控制器停止状态、事件累计数和已收事件数。`minimumRuntimeTimelineGroups` 默认一，实验必须按预期真实组数设置。完整结果、原有资源结算与时间线分别验收，时间线失败不跳过其他证据的清理和采集。

## 边界与正式实验前置条件

现有资源审计窗口上限为六百秒。校准必须确认各参测配置的整次采集都在窗口期限内，并给启动及结算留出余量；不能只用最快配置的九十秒估计最窄配置。更长运行需要另行设计窗口合同，禁止静默续期并假定旧登记仍然存在。

时钟证据保留 Java 进程的单调原点、事件相对时间和读取范围。跨进程对齐先核目标平台与时钟关联，跨物理主机另测偏差。不得将读取范围的差值解释为纯网络时间。成员结算时间、策略请求时间与负载实际进入时间分别呈现。

连续采集必须有独立开销对照。它可能增加 JMX 请求、不可变快照和客户端写盘成本。正式计时不与编译、导入和完整数据回读重叠。负例可显式停止采集客户端，检验事件环覆盖后是否拒绝完整性；负例时间不参与性能倍率。

运行策略的资源容量仍来自逻辑 lane 数，并不直接跟踪外部 CPU 利用率。本扩展只让实际输入与动作可观察。首先验证竞争是否传入输入，再决定是否需要独立的策略修改；慢消费不能替代外部 CPU 竞争验证。

## 验证记录与后续顺序

标准测试沿用本目录 README 的 Maven reactor 命令，保留 RAT 跳过、锁定依赖、关闭测试缓存和独立输出目录。专项选择 RuntimeDopControllerTest、RuntimeFragmentLifecycleTest、RuntimeDopExecutionSnapshotTest、ResourceAuditManagerTest、FragmentRuntimeSnapshotProductionTest、FragmentInstanceContextTest、MPPDataExchangeManagerTest 和 RuntimeDopPolicyTest。

新增四个专项方法覆盖无副作用读取、多组滚动计数、未完成成员结算和窗口及身份门槛；既有方法增加冻结后可读、并发采样期间读取和 JSON 输入及时间戳检查。`focused-02/targeted-summary.json` 记录 99 项、零失败、零错误、零跳过；`focused-02/exit.json` 记录中英文全工程编译结果。首个客户端编译失败保留在 `timeline-client-01`，修复后的编译及 class 摘要在 `timeline-client-02`，编译成功仍不代表 JMX 服务验收。

后续顺序为完整模块回归与发行对应、隔离服务正反例、采集开销、长查询及背景独立校准、十八次最小试跑，最后才进入正式矩阵。所有运行记录按实际路径与摘要绑定；本扩展仍未 commit 或 push。
