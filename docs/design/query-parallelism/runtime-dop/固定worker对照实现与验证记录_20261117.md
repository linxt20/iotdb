# 固定 worker 对照的实现与验证记录

**目的**：记录固定扫描 worker 对照的实现、验证和正式实验尚缺的证据。

**摘要**：新增配置保留 runtime 扫描管线和交换路径，固定实际 worker 初值并关闭扩缩容。服务检查发现最终计划登记曾丢失固定标记，现已修复，并由反向测试和实际回执覆盖。

**结论**：v2 专项测试、普通查询和三类异常结束验收已通过。v2 全量回归已通过；四组配置共 640 次完整结果校验通过，包含 160 次预热与 480 次测量。跨部署的完整设备与时间分配等价性仍待证明。

## 最终计划登记的修复

`runtime_scan_parallelism_fixed_workers` 默认零，保留自适应行为。正值采用 `min(请求值, 实际管线数)`，必须从执行回执核对实际人数。

根执行上下文捕获配置，子上下文共享该值。规划先生成布局，再选择固定模式；生命周期沿用原生准入、关闭和统计冻结。固定组不进入控制器，也不接受内部 resize。

初版在 `selectRuntimeLayout` 设置模式，但 `registerFinal` 为最终加权计划重新创建布局，其默认构造方式启用了扩缩容。仅检查配置和初始规划无法发现该问题。修复增加 `RuntimeScanLayout.withLanePlan`，更换工作分配时保留调整策略，并按最终管线数限制初值。

## 验证结果与范围

修复前，最终登记断言在既有 JUnit 体系中复现失败：312 项专项测试出现 1 项失败。修复后同组 312 项全部通过，并检查了重建工作分配后的模式。记录为 `fixed-worker-controls-v2/validation-20261117T061255Z/test-summary.json`。英文、中文编译和干净发行包构建均通过。

v1 全量曾得到 8,044 项 JUnit 测试零失败，但早于最终登记修复，不作为 v2 的全量结论。日志中两条压缩模块后台断言与上游 `522c080` 的独立复现一致，不能省略这一限制。

v2 普通查询覆盖多源聚合、Filter/Project 聚合、有序输出、LIMIT 和全扫描过滤。固定侧 runtime 组保持 1 人，没有已应用扩缩容事件，也没有控制器采样；候选侧仍执行自适应行为。

全局 ORDER BY 和 LIMIT 的原生 TopK 查询没有 runtime 扫描组。该项只验证结果、排序、原生回退和资源关闭，不能标为固定 worker 测量点。原实验门槛曾将没有组一律拒绝，现只对这一指定形态作明确分类，其他缺失组仍拒绝。原拒绝报告保留；修正只重新核查已有输出，没有重跑 SQL 或改写结果。

取消、原始 deadline 和晚发生 CAST 错误分别在两侧通过，检查了预期终态、片段身份、统计冻结和资源结算。功能验收不代表性能目标通过。

## 布局等价性缺口

结构检查保留 FI、算子、子节点、交换边、lane、原始 pipeline、bucket 和工作索引。两侧 region 编号与片段角色的对应关系存在差异。按算子和有序子节点位置匹配，排除查询、region 及计划节点编号后，四组配置的算子图、交换图和工作索引分配一致。固定 2 人场景另有计划节点编号差异，原始敏感检查与后续角色匹配报告均保留。

索引相同不足以证明其设备列表和时间分区相同，也不能证明物理文件与估计成本相同。后续需要实际内容身份，才能形成完整同布局因果比较。原 region 敏感差异报告保留，不覆盖为全部等价。
