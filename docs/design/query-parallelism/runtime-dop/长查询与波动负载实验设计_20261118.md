# 长查询与波动负载实验设计

**目的**：为动静结合调度论文规定长查询实验的负载、对照、观测与验收方法。

**摘要**：一个长查询可能经历其他查询进入和退出，其可用资源随之变化。规划阶段选定的并发度可能因此失去优势。本文以查询执行中的背景负载升降为主实验，分别检验控制输入、实际动作和整体收益。稳定负载、短查询和下游背压提供独立对照。

**结论**：主实验采用完整消费的长查询与预先冻结的背景请求轨迹。正式计时前必须证明查询覆盖压力变化、控制器能够观测相关变化、完整结果一致。2026-11-18 核查表明生产策略使用就绪与输出背压，资源容量输入为逻辑 lane 数，外部 CPU 竞争下的主动收缩能力仍需验证。

## 实验目标

实验检验同一个查询在运行环境变化时，调整并发度能否改善整体执行代价。并发度指一个扫描执行组实际运行的 worker 数，以下简称 DOP。论文主场景是长查询执行期间，背景请求先增加、再减少。评估同时观察长查询耗时、短查询响应和 CPU 消耗。

长查询提供调整后的剩余执行时间，背景负载变化提供重新选择的机会。估计误差和数据倾斜也可能产生调整收益，作为扩展因素单列。负载升高既可能要求释放 worker，也可能需要维持宽度。实验必须根据完成时间和资源竞争解释动作方向。

## 场景机会与开销边界

主场景必须同时覆盖足够长的前台执行和查询中途的背景资源变化。二者提供动态调整的机会，收益仍取决于信号、动作、剩余工作与目标。禁止把任何长查询或任何 CPU 波动直接判为自适应优势场景。

| 查询与环境 | 主要用途 | 必须保留的解释 |
| --- | --- | --- |
| 短查询、稳定低压 | 固定开销对照 | 可能来不及调整 |
| 长查询、稳定低压 | 强固定宽度对照 | 固定八可能持续优于渐增策略 |
| 短查询、负载变化 | 响应窗口边界 | 动作可能晚于查询完成 |
| 长查询、负载升降 | 动态主实验 | 需证明信号可见且动作来得及产生价值 |

独立校准先测各固定宽度在低压和高压下的前台耗时、CPU 成本与背景尾延迟。若最优宽度没有变化，仍保留该输入作为稳健性对照。若目标强调背景请求的服务质量，则必须在运行前声明约束或权重，禁止事后用不同目标解释胜负。

适应窗口从负载实际影响资源开始，到动作实际生效后仍有足够工作可执行为止。分别记录观测等待、决策、准入、激活或退休结算、以及剩余工作时长。只有收益可能超过这些成本，才有必要进入昂贵的正式矩阵。该判断使用独立校准，不能用评估结果挑选最有利轨迹。

## 生产策略与场景适配

生产控制器通过扫描组内的就绪工作、输出背压和设备完成增量作出决策。采样输入还包含未完成 lane 数和实际 worker 数。资源容量输入采用逻辑 lane 数。新增 worker 的共享用户 CPU 额度与内存由实际准入过程检查。

例如，一个组拥有八条 lane、四个 worker，外部 CPU 任务开始运行后，容量输入仍可能是八。CPU 竞争可以降低处理速率，却没有直接提供“容量变成二”的输入。额度拒绝解释一次增员未获准，主动退员还需要对应的策略分支证据。

下游背压具有明确的生产输入路径。若输出信用耗尽、就绪 lane 为零、背压 lane 数达到 worker 数，连续压力窗口可以触发退员。CPU 竞争、存储竞争和慢消费必须分开试跑。禁止用慢消费实验替代外部 CPU 竞争的适配证据。

数据来源：源码分支 `feat/paper-experiments-20261117`，HEAD `1959820d4eec2c5f4154ee3c7652b1a9f85caa32`，工作区存在未提交修改。直接依据为 `RuntimeFragmentLifecycle.sampleControlInputs`、`RuntimeDopPolicy.evaluate`、`RuntimeScanGroup.snapshotWithObservedOutputs` 和 `RuntimeFragmentLifecycle.resize`。文件摘要见同目录 `scenario-plan.json`。

## 查询长度与独立校准

主查询应当在最快的参测配置下覆盖完整的压力升降阶段。试跑目标为无背景负载时持续九十至一百八十秒。这个范围用于选择输入规模和自然计算量，正式报告同时给出实际持续时间。禁止通过客户端睡眠、重复提交短查询或隐藏人为计算来标记自然长查询。

校准集与评估集必须分开。校准阶段可以扩大时间范围、设备数和真实数据规模。计算压力表达式只作为明确标注的机制实验，业务查询另行提供。配置选定后必须冻结 SQL、输入、输出真值和背景轨迹。

例如，校准得到最快配置需要一百二十秒，可以安排第十五秒增加背景请求，第四十五秒停止新增背景请求。高负载阶段持续三十秒，主查询还留有恢复观察时间。评估中提前完成的样本必须保留，记录其实际覆盖时长。

Electricity 首轮完整数据实验中的自适应计算压力查询中位耗时为 4206.54744 毫秒。普通全局与分组聚合中位耗时约为 54 至 141 毫秒。因此，这些已测形态提供正确性和短期行为证据，主场景需要独立的长查询输入。

数据来源：`electricity-experiments-v1/measurement-01/summary.json` 的客户端完整消费时间。CPU 表达式属于显式计算压力查询。

## 背景负载轨迹

主矩阵包含稳定低负载、稳定高负载、低高低负载和高低负载四种轨迹。稳定轨迹测量常态开销，变化轨迹检验适应过程。另设短脉冲和慢消费作为压力持续时间及背压机制对照。

背景负载优先采用同一部署内的独立查询客户端。请求到达时间由冻结轨迹决定，客户端执行速度只影响实际排队和完成时间。低负载可以不增加背景请求，高负载强度由独立校准选择。校准必须记录请求速率、并发上限和溢出处理。

例如，校准可以选择每秒四个短查询和最多十六个在途请求。若在途请求达到上限，生成器必须记录延迟发送或拒绝，保留原定到达时刻。主比较使用相同的原定请求轨迹，并分别报告各策略实际完成的请求数。

主查询确认进入 RUNNING 后，生成器按固定时间表改变到达率。所有策略使用相同时间表，禁止依据候选的 DOP 或进度改变压力。背景停止发送后，在途请求的排空时间必须保留。实际压力起止由请求、排队和节点资源观测解释。

独立 CPU 压力进程用于诊断调度器可见范围。存储竞争另用可归属的读请求。每类压力保留进程、主机、CPU 绑定及资源范围，确认其与主查询竞争同一资源。不同压力类型必须采用独立的输出目录。

## 策略与执行结构

第一组机制比较采用固定一、二、四、八个 worker 和自适应 worker。五个配置必须共享同一合法逻辑布局、源归属和交换结构。初始 worker 数与后续调整分别记录。对实际不可达到的宽度，报告准入限制及原因。

布局比较使用设备、时间分区、源语义、顺序要求和投影内容。执行专属的 query ID 只用于绑定各次记录。跨运行比较必须使用经过验证的语义身份。完整布局尚未核对时，配置间时延仅能解释为整个部署方案的差异。

第二组方法比较加入仅静态、仅运行和直接组合。仅运行的初值必须通过独立校准选择，直接组合采用同一静态方法与同一控制器。独立联合选择器的实现与消融属于另一个前置条件。禁止把同一实现重复命名为两个算法。

最佳固定参照通过校准集选择。使用评估轨迹搜索得到的事后最佳固定值可以单列为离线参照，必须报告搜索成本。原生上游保留为部署层对照，其执行结构与候选逐项记录。

## 时间线与指标

每个样本必须关联主查询、背景请求、各 FI 和执行组。记录查询开始、原定压力变化、实际请求进入、策略请求、准入结果和实际 worker 生效时间。单机记录使用统一单调时钟，跨机记录还必须给出时钟偏差范围。

实际 worker 增减必须以成员生效或退休回执判断。例如，请求从四减为三发生在第二十秒，退休确认在第二十点二秒，则生效时间为第二十点二秒。查询结束时关闭到零属于清理。近结束时未完成 lane 减少引发的退员，单列为剩余工作收缩。

控制器的内存事件队列最多保留一百二十八条事件。若两个执行组每隔一百毫秒各记录一次，队列约覆盖最后六点四秒。长查询的最终快照因此只能提供有界尾段证据。完整时间线采集入口必须先验证可用性，再通过独立观测开销实验确定采集频率。

观测优先复用原生查询状态、驱动统计、扫描统计和已有资源快照。缺少完整运行中策略输入或成员变更流时，先列出采集缺口及最小补充接口。禁止仅用最终事件尾段推断查询中段动作。

端到端延迟从提交到完整消费结束。CPU 核秒由可归属的进程 CPU 时间积分得到。后台短查询同时报告吞吐、成功率和尾延迟，节点读取字节及内存按实际采集范围标注。

例如，固定配置使用一百二十秒，自适应使用一百秒，该配对样本的加速比为一点二。若自适应的 CPU 时间从六百核秒增加到九百核秒，报告必须同时给出增加的三百核秒。背景短查询第九十五百分位延迟若从二百毫秒增至四百毫秒，也必须与主查询收益一起展示。

TableScan 输出行数用于解释扫描输出，物理读取量使用对应的存储指标。例如，过滤前输出一万行只能证明该算子输出了一万行，读取磁盘字节还需要独立计数。

数据来源：`RuntimeDopController` 的有界事件队列与生产采样调用，`RuntimeDopExecutionSnapshot` 的终态证据，Thrift `TOperatorStatistics.outputRows`。运行中完整事件采集能力在本计划中标记为待验证。

## 结果判定与统计

正式收益结论必须同时具备完整结果一致、实际压力覆盖和实际策略生效证据。无序结果比较完整有类型多重集，确定全序结果比较完整序列。只规定部分顺序的查询按同键组比较完整多重集。浮点聚合采用运行前冻结的独立误差合同。

没有触发调整的执行仍计入相应配置的全部样本。未覆盖完整压力阶段、超时、拒绝和失败分别标注，报告各类数量。预先规定的有效覆盖子集可以单独分析，全部计划样本的结果必须同时保留。

每个固定实验单元预热五次，再测量十五个随机配对块。每个块重新播放同一背景轨迹，并等待在途请求排空。主查询和背景查询共同构成一个统计单位，bootstrap 区间按块计算。

例如，十五块中有两块主查询在恢复阶段前完成，则全样本报告十五块，完整阶段子集报告十三块。禁止用两次新增运行静默替换这两个样本。配对置信区间覆盖一时，报告区间及样本数，并保留可能的收益与退化范围。

## 执行次序与时间预算

先完成正在运行的发行与服务验收，再执行场景试跑。编译、导入和正确性回读必须在正式性能采样前结束。独立负载产生器与时间线采集的实现另计开发工时，前置代码核查已经确认 CPU 容量输入的边界。

最小试跑采用一个长查询、两种变化轨迹、三个配置和三次重复，共十八次执行。按每次九十至一百八十秒估计，纯前台执行需要二十七至五十四分钟。校准、背景排空和失败诊断另计，试跑阶段预计需要一至三小时。

首个正式矩阵采用两个查询、四种主轨迹和五个配置。每个单元执行五次预热及十五次测量，共八百次执行。按每次一百二十秒估计，纯前台时间约二十六点七小时。真实排期必须由试跑时长和背景排空时间计算，不能用短查询时长估计。

如果 CPU 竞争试跑表明控制输入没有对应变化，应当先形成策略能力缺口及独立修改设计。正式结果按已实现方法呈现。机制试验、策略新增和独立联合方法分别验收，避免将场景调整解释为算法收益。
