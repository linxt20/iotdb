## 固定到达的负载预检

前台使用六十四项有界三角恒等式计算构造。它是在真实 Electricity 数据上的显式 CPU 压力查询，不能当作代表性业务 SQL。原 ZIP 导出的短窗结果是独立真值，每次仍完整比较全部类型和 DOUBLE 原始位，不能仅凭恒等式跳过结果核对。

背景生成器使用普通 JDBC SQL。看到两个真实源 FI 都处于 RUNNING、具有活动租约和未完成 lane 后，才设置时间原点。预先冻结的到达时刻为第 15 至 44 秒、每秒一次，共三十次；最多四个请求在途，满载时拒绝并记录原定与实际到达时间。轨迹不随候选 DOP 改变。第 45 秒后不再新增请求，实际排空时刻单独记录。

| 观测 | 空载预检 | 低—高—低预检 |
| --- | ---: | ---: |
| 前台完整消费时间，秒 | 82.957 | 82.276 |
| 背景预定／准入／拒绝／完成 | 0／0／0／0 | 30／8／22／8 |
| 背景实际排空，原点后秒 | 不适用 | 44.447 |

两次前台和八次准入背景请求的完整多重集均通过。前台时间线分别含 1,623、1,644 个唯一事件，独立复核均无缺段。全部 689 个归档文件经过长度和 SHA256 复核。背景上限的占位包含执行和客户端核对；正式时延统计要区分结果排空与核对完成。

CPU 核数来自两个 DataNode 的进程计数窗口，包含前后台查询和服务工作，不能归因到单条请求，也不能相加重叠的逐请求窗口。主机配额为四十核，两个 DataNode 查询线程各八；16.386 核不能解释为主机 CPU 已饱和。一次预检不足以比较两种条件的时延优劣。

## 实现判断

共享查询确实改变了前台的 ready lane、短暂输出背压、完成进度与扩容轨迹。当前策略在高到达阶段每源两次 GROW，原因是 READY_BACKLOG；没有出现 SUSTAINED_BACKPRESSURE 或 RESOURCE_CAP_CONTRACTION 缩容。其后的缩容原因均为 UNFINISHED_LANE_CONTRACTION，不能算成压力触发的退员。

`maxResourceWorkers` 仍由逻辑 lane 数填入。共享额度与内存检查处于增长准入路径；当前实验用户为 root，不能将用户额度拒绝机制解释为本次已发生的共享 CPU 反馈。已有安全调整机制与外部压力目标选择是两件需要分别验收的事。

负载增加时扩容本身不构成正确性错误。较多前台 worker 可能补偿调度等待，也可能挤占背景查询。方向要由预先规定的目标、合理固定宽度的分阶段表现、背景尾延迟和 CPU 成本共同判断。本轮确立的是研究缺口，尚未证明“负载增加就应缩容”，也不能据这两个耗时报告收益。

## 后续开发与退出判据

| 顺序 | 处理与范围 | 完成判据 |
| --- | --- | --- |
| 1 | 明确目标：同时报告前台耗时、背景尾延迟、成功及拒绝数、CPU 核秒 | 冻结评价目标和统一到达合同，不针对候选修改负载 |
| 2 | 复用 DriverScheduler 已有 active、ready、blocked 和完成计数，补充本查询与其他查询的来源区分 | 单位、覆盖、时效与身份明确；不能把队列长度当成可用 CPU 核数 |
| 3 | 在独立反馈层计算共享执行容量建议，保留 lane、内存和额度上界 | 缺失观测不补零；请求与已持有授予分离；明确滞回、冷却与恢复规则 |
| 4 | 用现有 JUnit 体系覆盖竞争进入／退出、无进度、采样过期、并发收尾和退员结算 | 专项、标准完整回归、发行 class 对应及服务结果验收通过 |
| 5 | 独立校准合理固定 1／2／4／8 和自适应配置 | 最快参测配置仍为 90–180 秒，最慢配置及结算不超过审计期限 |
| 6 | 冻结 SQL、真值、布局、到达轨迹并执行固定／仅静态／仅运行／直接组合对照 | 完整结果、实际布局和完整控制时间线逐样本对应 |
| 7 | 定义并实现独立联合选择器，再做消融与跨主机验证 | 能给出区别于直接组合的规则、信息来源及可重复效果 |

第二、三项目前属于待实现设计，尚未修改生产策略。优先使用既有监控与调度计数；只有来源或语义不足时才增加观测。不能把所有 ready driver 都当成外部竞争，也不能在各 FI 独立观察同一资源后重复分配整个线程池容量。

六十四项预检约八十三秒，尚未达到最快配置九十至一百八十秒的校准要求。正式实验前还要确认各压力阶段的合理固定宽度有可辨别变化。当前审计窗口上限六百秒；运行时间超出时须显式设计期限合同，不能静默续窗。
