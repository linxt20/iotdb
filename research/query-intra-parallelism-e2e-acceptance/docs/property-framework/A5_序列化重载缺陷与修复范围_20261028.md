# A5 序列化重载缺陷与修复范围

目的：说明两个序列化重载的限定修复和单元测试证据，供 sxing 复核 A 的类型契约。

摘要：查询片段必须保留规划阶段解析的 SQL 类型，接收端才能按相同规则构建算子。代码同时提供缓冲区和流式序列化入口，解码器按流式布局读取。本文对两个重载逐字段核查，并在独立源码副本上验证共享编码实现。

结论：TypeProvider 的缓冲区重载会报空指针或丢失表模型类型，PlanFragment 的缓冲区重载与解码顺序不同。限定修复稿使两个重载复用流式编码，十个单元测试全部通过。两个生产重载及十项合同测试均已写入仓库，并通过最终回归。

## 问题背景

查询片段必须把键的 SQL 类型完整送到接收端，验收必须逐符号核对类型，并检查解码是否消费全部字节。

例如，一个键在规划端为 INT64，解码后仍必须读到 INT64，剩余字节数必须为零。类型缺失或剩余十八字节都表示往返失败。仅比较类型提供者对象相等会漏检，因为其相等方法只比较树模型映射。

发送入口在源码中调用流式重载。独立核查证明该重载保留了测试键的类型。真实双 DataNode 查询与最终构建结果见[验收报告](A_属性框架验收结果_20261028.md)。

数据来源：sc01 的仓库为 /root/iotdb，分支为 feat/next-p0，基线提交为 0ec0e02287565d9395ec676bd9fcfc6d1f644386。发送入口为 iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/plan/FragmentInstance.java 的 serializeToByteBuffer()，该方法使用 DataOutputStream 调用片段编码。

## 已复现的字段不一致

表模型专用的类型提供者把树模型映射设为空，缓冲区重载仍直接读取该映射大小，因此抛出空指针。流式重载对该映射按零条处理。

同时包含树模型与表模型类型时，缓冲区重载直接写表模型映射大小，缺少解码器要求的存在标记。解码后表模型键缺失，并留有未消费的字节。

片段的缓冲区重载先写计划节点，再写类型提供者。流式重载和解码器采用类型提供者在前、计划节点在后的顺序，因此两份输出布局不同。

两个文件的源码哈希与基线提交逐字一致。独立探针和单元测试分别编译这些原文，再核对实际加载路径和类字节哈希。

数据来源：类型文件为 iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/analyze/TypeProvider.java，片段文件为 iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/plan/PlanFragment.java。探针为 /root/property-a-artifacts/A5-20261028T072200+0000/serialization-probe-03/probe-results.json，原文与拟修改源码的绑定为 /root/property-a-artifacts/A5-20261028T072200+0000/proposal-01/sources.json。

## 限定修复

两个缓冲区重载必须复用已有流式编码，然后把产生的字节填入目标缓冲区。字段定义、解码器和现有发送入口继续使用同一布局。

修改范围为两个现有方法，以及一个新增的序列化合同测试类。修复稿采用内存字节流处理编码，消除两份字段顺序维护。编码内容为六十四 KiB 时，临时内容约为六十四 KiB，直接缓冲区调用因此增加一次暂存。

限定补丁、仓库测试、格式化和 A 的最终验收均已完成。

数据来源：待审补丁为 /root/property-a-artifacts/A5-20261028T072200+0000/proposal-01/serialization-overloads.patch。修改方法为 TypeProvider.serialize(ByteBuffer) 与 PlanFragment.serialize(ByteBuffer)。新增测试源码为 /root/property-a-artifacts/A5-20261028T072200+0000/proposal-01/TypeProviderSerializationContractTest.java，目标归属为 DataNode 测试目录的 org.apache.iotdb.db.queryengine.plan.analyze 包。

## 单元测试证据

每个往返用例必须保留相应符号的 SQL 类型，且解码后的剩余字节数为零。编码一致用例还必须逐字节相等，随后才进入片段解码。

下表按相同断言比较基线原文与独立修复稿，成功表示全部断言满足。

| 用例 | 基线原文 | 修复副本 |
| --- | --- | --- |
| 表模型缓冲区往返 | 失败 | 通过 |
| 混合类型缓冲区往返 | 失败 | 通过 |
| 表模型流式往返 | 通过 | 通过 |
| 混合类型流式往返 | 通过 | 通过 |
| 空表类型缓冲区往返 | 失败 | 通过 |
| 树类型缓冲区往返 | 通过 | 通过 |
| 混合类型编码一致 | 失败 | 通过 |
| 带类型片段流式往返 | 通过 | 通过 |
| 带类型片段缓冲区往返 | 失败 | 通过 |
| 无类型片段缓冲区往返 | 失败 | 通过 |

单测直接检查键的解析类型，避免类型映射丢失时被对象相等判断放过。两组运行都核对实际加载的类型提供者、片段和测试类身份。

数据来源：基线结果为 /root/property-a-artifacts/A5-20261028T072200+0000/proposal-01/current/results.json，修复副本结果为 /root/property-a-artifacts/A5-20261028T072200+0000/proposal-01/proposed/results.json，验证结论为 /root/property-a-artifacts/A5-20261028T072200+0000/proposal-01/proposal-verdict.json。以上结果是独立 Java 单元验证，服务端验收由 A6 执行。
