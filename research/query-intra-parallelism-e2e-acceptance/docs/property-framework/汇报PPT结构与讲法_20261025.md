# 汇报 PPT 结构与讲法

目的：为毕业设计中期汇报组织实现、测试和后续工作的讲法，供 sxing 更新演示文稿。

摘要：汇报先解释一条查询为什么需要并行，再说明如何保持分组与顺序正确。实现部分以 A 的属性组件和既有受限哈希路径为主。测试部分分别展示局部断言、规划覆盖及真实服务结果。性能和后续调度各自保留明确的证据范围。

结论：正文可以围绕十四页组织，重点是属性判断与可核查的正确性证据。A 的组件与接入已实现，A0 至 A6 的验收均已完成。双节点结果支持所测 GROUP BY 的正确性，性能口径继续由 sxing 统一。

未决问题：3.33 倍与 2.95 倍两组历史性能口径、生产哈希连接的范围、CPN 的论文正文安排，均等待 sxing 决定。序列化重载修复见[限定修复材料](A5_序列化重载缺陷与修复范围_20261028.md)。

## 汇报背景与证据

这项工作让一条长查询使用多个执行单元，同时保持结果和排序要求。听众需要知道三件事：哪些操作已经接入 IoTDB、正确性如何验证、还有哪些验收未完成。例如，两个来源对同一键分别读到两行和三行，最终必须得到计数五。

汇报应当把已实现代码、已通过验证和后续规划分别说清。完整模块测试的状态从执行记录读取，性能数字从测量档案读取。演示文稿里的进度百分比应当由已关闭退出条件推导。

数据来源：工程位于 sc01 的 `/root/iotdb`，分支为 `feat/next-p0`，HEAD 为 `0ec0e02287565d9395ec676bd9fcfc6d1f644386`，A 的修改保留在工作区。代码范围见[整体设计](修改位置与整体设计_20261025.md)，验证入口见[测试核查](属性驱动并行判定框架测试核查_20261028.md)。

## 正文页面

### 第一页 课题与目标

展示题目《IoTDB 查询执行并行化的设计与实现》、作者和导师。开场说明目标是让同一条查询使用更多执行资源，并保持结果一致。

### 第二页 查询执行的问题

用一条按设备或字段分组的 SQL 说明扫描、局部聚合、交换和最终聚合。图中标出哪些步骤可以拆分，以及相同键为什么需要在最终阶段汇合。

讲法可以从两个来源各有同一个键开始。并行后若直接输出两个局部计数，用户会收到两个分组，因此最终聚合的位置必须明确。

### 第三页 研究定位

说明计划阶段负责构建满足分布与顺序条件的结构，执行阶段负责消费数据，调度负责分配执行资源。与自适应执行比较时，只说明职责和依赖关系。

静态与动态调度仍属于后续任务。现有 DOP 配置和扫描资格标记可以作为入口，完整策略及其效果由后续验收证明。

### 第四页 研究内容

介绍属性判断、受限按键交换和扫描工作单元三个主题。每个主题配一个正确性要求：顺序可证明、相同键同桶、每行恰好读取一次。

例如，输入有十二行时，把扫描拆成四份后仍必须只读到十二行。工作单元数量本身无法证明这一条件。

### 第五页 工程结构

用流程图连接逻辑计划、分布式生成器、属性提供者、强制器、片段切分和执行器。专用分组哈希入口单独画出，避免把通用强制器描述成完整的任意重分区实现。

讲法应当沿一次合并说明：先读取实际输出属性，再比较父节点要求，最后记录插入的节点与原因。专用节点的构建规则继续保留。

数据来源：组件及接入文件见[整体设计的属性判断与计划构建](修改位置与整体设计_20261025.md#属性判断与计划构建)。

### 第六页 正确性约束与验证方法

展示三层证据：单元测试断言、规划图与片段所有权、真实查询的完整结果。每层各放一个具体例子，说明它验证什么条件。

例如，双源双桶有四条交换边。每一列的两条边必须进入同一个最终桶片段，不同列由不同桶片段拥有。CPN 的建模图可以准备为备用材料，正文安排等待 sxing 决定。

### 第七页 属性组件

介绍分布和顺序分别比较，要求属性与实际提供属性分别保存。两个无序输入需要整体有序输出时，强制器先分别排序，再合并。

通用逻辑分区要求采用保守收集，受限 GROUP BY 哈希优化走专用准入。讲法必须与已经实现的边界一致。

### 第八页 按键交换与所有权

画两个来源、两个桶和四条交换边。来源标出哈希通道，桶标出最终聚合，边标出对应的实际交换 ID。

图中的 ID 必须来自同一次运行。解释查询的计划 ID 与分析执行查询的运行 ID 各自归档，运行时所有权图使用后者。

数据来源：真实查询的规划和运行拓扑见 sc01 的 `/root/property-a-artifacts/A6-20261028T080437+0000/two-datanode-05/acceptance.json`。

### 第九页 扫描执行与统计

说明计划中的扫描资格如何交给已有执行器处理，morsel 如何表示可领取的数据工作单元。区分已存在的执行路径与 B 计划开展的扫描构建、资源准入统一。

介绍完成统计在片段快照冻结前写入，并保持重复写入幂等。统一运行快照及调度复用仍属于后续 C 至 E。

### 第十页 A 的实现与验收状态

展示已实现的提供者、强制器、不可变决策和生成器接入。验收状态按 A0 至 A6 分项标明，完整模块测试、限定修复和双节点查询分别展示自己的通过证据。

测试数量直接从核查文档读取，并注明顶层调用与内部重复运行的区别。五项按参数化条件跳过的调用应当单列。

### 第十一页 正确性实测与性能材料

先展示普通分组、空值、倾斜和空输入四组正确性查询。倾斜输入的两个结果计数为八十和四，候选、对照与确定性预期一致。

性能材料另列计时边界、DOP、样本数、冷热状态和资源字段。3.33 倍与 2.95 倍继续作为待统一的历史转述口径，正式结论等待原始测量档案核对。

图表可以左侧画两源两桶的运行拓扑，右侧列四组结果检查。性能图单独列页或备用页，数据来源和条件必须完整。

数据来源：[测试核查的双 DataNode 查询](属性驱动并行判定框架测试核查_20261028.md#双-datanode-查询)给出完整结果、SHA 和运行身份。历史性能倍数的待定范围见[总体实现规划](实现规划_20261025.md)头部的未决问题。

### 第十二页 缺陷与测试边界

用一个会被测试识别的故障说明单元断言的价值，例如删掉第二条输入分支。再说明元数据测试独立启动与配置恢复的检查，以及架构测试吞掉 OOM 时为什么要核查日志。

A5 的两个 ByteBuffer 重载复用流式编码，十项仓库测试均通过。实际服务发送路径的类型传播另有逐符号传播和双节点证据。

### 第十三页 后续工作顺序

按 A、B、C、D、E 展示依赖顺序。A 是属性判定框架，B 是静态数据并行统一，C 是运行快照，D 是静态调度策略，E 是动态并行控制。

A 的代码工作完成后，只编写 B 的设计和实现规划。各块必须先具备经审核的设计和退出条件，再安排实现，生产哈希连接范围继续等待决定。

数据来源：大块任务定义见[总体实现规划的 A 至 E 路线](实现规划_20261025.md#81-ae-大块任务路线)，A 的文件级安排见[框架实现规划](属性驱动并行判定框架实现规划_20261027.md)。

### 第十四页 研究进展与待验收项

收尾说明已经接入的属性组件、已有执行路径和已获得的正确性证据。列出 B 的文档审核及性能口径统一两项后续工作，并说明性能与后续调度按独立协议推进。

## 提问准备

被问到多节点是否执行时，展示实际 DataNode、fragment instance、通道和桶的对应关系。被问到结果正确性时，展示候选、对照和预期的完整多重集及 SHA。被问到加速时，说明历史数字与正式性能矩阵的状态。

被问到测试是否覆盖代码时，展示功能对应的断言、故障副本和覆盖记录。被问到单元测试是否等于完整验收时，展示完整模块和真实服务的独立结果。

数据来源：所有测试数量、条件跳过与边界集中见[框架测试核查](属性驱动并行判定框架测试核查_20261028.md)，实现状态见[框架实施记录](属性驱动并行判定框架实施记录_20261028.md)。
