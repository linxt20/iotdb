# 属性驱动并行判定框架设计

目的：为毕业设计的 A 阶段规定属性计算、节点插入和诊断的边界，供 sxing 二次审核及实现者按文件落地。

摘要：IoTDB 的分布式查询需要在合并输入时保留分组和排序要求。基线代码把这些判断与计划遍历写在一起，独立测试和覆盖检查因此较难。本文逐一列出实际调用面、保留专用构建的位置和组件接口。实现步骤与验证命令由配套规划规定。

结论：本稿把 A 限定为保持既有执行形状的框架整理。通用强制器处理收集、排序和合并排序，分组哈希重分区保留专用构建入口。源码核查基线为 sc01 的 `0ec0e02`，实施状态集中见[实施记录](属性驱动并行判定框架实施记录_20261028.md)。

## 任务背景

这项工作让同一种输入要求只在一个地方判断，同时保留已运行查询的执行方式。查询计划有时要求所有输入汇到一个分支，有时要求相同键的行落到同一分支，有时要求输入有序。实现者必须先确定子计划实际提供的条件，再决定是否插入节点。

例如，两个无序输入要交给一个要求全局有序的父节点，必须先分别排序，再合并。只给两个输入增加合并排序节点，无法保证结果有序。A 的验收同时检查计划结构、输入分支是否完整保留，以及扫描并行资格是否符合基线。

源码核查与实现都在 sc01 完成，阶段进度统一记录在实施记录中。本文的组件接口规定 A2 至 A6 的目标合同。

数据来源：服务器为 `root@sc01-ssh.gpuhome.cc:31158`，仓库为 `/root/iotdb`，分支为 `feat/next-p0`，版本为 `0ec0e02`。审查依据为[文档审查报告](属性驱动并行判定框架文档审查_20261027.md)。实施步骤见[框架实现规划](属性驱动并行判定框架实现规划_20261027.md)。

## 术语与文件定位

属性描述分支之间的分布和顺序，扫描并行资格描述一个片段内部能否拆成多个扫描驱动，两者分开维护。

- 要求属性是父节点对输入的条件，下文使用代码术语 required。
- 提供属性是子计划实际满足的条件，下文使用代码术语 provided。
- 提供者计算 provided，下文使用代码名 PlanPropertyProvider。
- 强制器插入满足 required 的节点，下文使用代码名 PropertyEnforcer。
- 决策记录保存一次判断的输入、结果和原因，下文使用代码名 PropertyEnforcementDecision。
- 退回表示保留安全执行方案，并记录目标优化未采用的原因。
- 片段所有权表示源、桶和交换节点分别属于哪个执行片段。
- DOP 表示查询内并行度，A 只保留它已有的执行入口。

本稿的代码路径、接口和标识符是实现定位信息，因此集中放在各节的数据来源或代码块中。源码行号均针对上述基线，实施时必须同时核对方法名。表内保留完整标识符以便检索，这是本稿对技术文档路径排版规则的限定用法。

数据来源：主代码目录为 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/`。下文简称“分布包”。测试的同包目录位于 `iotdb-core/datanode/src/test/java/`。

## 基线中的属性与执行边界

基线已有可执行的属性比较和节点插入，也有独立的分组哈希路径。A 的新增工作是提取组件、补齐覆盖和保存结构化决策。

属性值对象保存分布与可空排序方案。提供属性方法按返回分支数量给出单分支或任意分布，再核对每个分支的排序记录。强制插入方法只有一个调用入口，入口位于合并子分支方法中。

扫描资格标记会穿过单子节点的过滤和投影。过滤会删行，投影会改写输出，两者在该规则里的共同条件是保留单一扫描来源。A 必须保持这项资格标记规则。

诊断记录方法属于生成器。计划器读取诊断并追加到文本解释输出。连接守卫已返回嵌套枚举，生成器已把该枚举写入诊断。

执行侧的通用汇访问方法读取冻结的哈希描述子，并从执行上下文取得键类型。片段切分后，计划器检查分组哈希所有权，校验失败时终止规划。

数据来源：分布包的 `PlanProperties.java:38`、`DistributionProperty.java`、`TableDistributedPlanGenerator.java:3256`、`:3354`、`:3434`、`:3466`、`:3485`、`:809`、`TableDistributedPlanner.java:210`、`:311`。执行侧为 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DataNodeTableOperatorGenerator.java:400` 的 `visitShuffleSink(ShuffleSinkNode, LocalExecutionPlanContext)`。

## 属性模型

### 分布的满足关系

分布属性保留基线的三种取值，满足关系保留单向判定。下面按提供值查找可满足的要求。

| 提供值 | 要求 Single | 要求 Arbitrary | 要求 Partitioned |
| --- | --- | --- | --- |
| Single | 满足 | 满足 | 满足 |
| Arbitrary | 不满足 | 满足 | 不满足 |
| Partitioned(K) | 不满足 | 满足 | K 为要求键子集 |

单分支天然把同键行放在一起。分区键更少时，共定位保证更强。例如，按设备分区会把同一设备的全部时间放在一起，因此也满足“同设备、同时间”的共定位要求。按设备和时间共同分区，则可能把同一设备的两个时间分开，无法满足只按设备分组的要求。

键集合使用逻辑集合语义。物理路由另外保存键顺序、空值策略、哈希版本和桶数。键类型由规划端与执行端的类型提供者分别读取。例如，两份描述子的桶数分别为 2 和 4，即使逻辑键相同，也必须经过物理描述子兼容检查。

数据来源：分布包的 `DistributionProperty.java` 与 `HashPartitioningDescriptor.java`。补充方法为 `isPartitioned()`、`isArbitrary()`，以及 `isCompatiblePartitioning(other)`。最后一个方法仅表示双方均为逻辑分区且键集合相等，方向性满足判断继续使用 `satisfies(required)`。

### 排序的满足关系

属性满足性采用基线的完整排序方案相等判断。排序消除路径已有的前缀判断继续属于其专用规则。

当一个分支缺少所需顺序时，强制器必须先排序。当两个分支都已有相同顺序时，强制器只合并排序。当两个分支中只有一个已有顺序时，A 沿用基线“全部输入各包一个排序”的构建方式，以保持快照一致。

例如，两个分支都按时间升序，父节点也要求时间升序，合并排序足以保序。父节点改为降序后，完整排序方案不同，强制器必须生成排序节点。

数据来源：分布包的 `PlanProperties.java:82`、`TableDistributedPlanGenerator.java:3375`、`:623`。值对象增加 `requirementFor(distribution, ordering)`、`satisfiesDistribution(required)`、`satisfiesOrdering(required)`、`withDistribution(distribution)`、`withOrdering(ordering)`，保持不可变。

## 提供者的输入与覆盖

### 分支集合与节点属性

提供者分别描述一个物理节点的输出，以及一组并列分支的整体保证。强制器使用后一种结果，避免把“每个输入各是一条流”当成“全部输入已汇成一条流”。

例如，两个扫描各自输出一条流，但并列分支仍有两条，所以整体分布为任意分布。一个联合节点可以对外只返回一个节点，但它内部仍保留多个输入，扫描资格必须继续按专用规则判断。

A 的通用分支集合推导沿用基线的单分支与任意分布。专用哈希事件依据已构建的拓扑记录逻辑分区保证，片段所有权由后置检查确认。聚合键本身只能说明分组需求。

提供者只读取子计划和已记录的顺序。父节点要求不作为 provided 的证据。排序参数与物理记录冲突时，提供者必须给出缺少顺序的结果。

未知节点单独记录覆盖状态。它的属性值为任意分布，覆盖状态为未知，原因码为未知提供者。强制器必须保留全部分支。只有明确插入收集节点后，输出才可获得单分支保证。

数据来源：新增分布包文件 `PlanPropertyProvider.java`，提议接口如下。两个结果类型作为该类的静态内部类型，A 不新增独立文件。

```java
ProvidedProperties providedBy(
    PlanNode node,
    Map<PlanNodeId, OrderingScheme> recordedOrderings);
ProvidedProperties providedByBranches(
    List<PlanNode> branches,
    @Nullable OrderingScheme observedOrdering,
    Map<PlanNodeId, OrderingScheme> recordedOrderings);
// ProvidedProperties: properties, coverage(KNOWN/UNKNOWN), optional fallbackReason.
```

## 强制器的输出与退回

### 返回结果与实际节点

通用强制器返回完整分支列表、插入节点及前后属性。它支持保持原样、收集、排序、合并排序和退回五种行为，退回状态与实际插入节点分别记录。

例如，两个分支收到逻辑分区要求时，可以安全收集为一条流。结果的实际节点为收集，状态为退回，原因是通用分区优化未启用。这样，诊断仍能解释保守执行，测试也能检查真正生成的节点。

满足任意分布要求时，两个分支必须全部保留。返回第一个分支的做法仅适用于已证明只有一个分支的情况。保留单节点兼容入口时，实现者必须检查结果恰有一个输出节点。

数据来源：新增分布包文件 `PropertyEnforcer.java`，结果类型与实际节点种类作为其内部类型。提议接口为：

```java
PropertyEnforcementResult enforce(
    PlanProperties required,
    List<PlanNode> branches,
    PlanPropertyProvider.ProvidedProperties provided,
    QueryId queryId,
    Map<PlanNodeId, OrderingScheme> recordedOrderings);
// Result: branches, providedBefore, providedAfter, insertedNodeIds,
// actualEnforcer(NONE/COLLECT/SORT/MERGE_SORT),
// outcome(SATISFIED/ENFORCED/FALLBACK), optional fallbackReason.
```

### 通用规则

通用强制器只处理输入收敛与排序，分组聚合的拆分生命周期仍由聚合构建代码处理。

- 当整体 provided 满足 required 时，强制器保留全部输入并记录满足状态。
- 当父节点要求单分支且输入有多个无序分支时，强制器插入收集。
- 当父节点要求排序且整体顺序缺失时，强制器按基线分别排序输入。
- 当父节点要求排序且输入有多个有序分支时，强制器插入合并排序。
- 当父节点要求逻辑分区且已有单分支时，强制器记录满足状态。
- 当父节点要求逻辑分区且缺少通用分区消费者时，强制器使用满足条件的收集或排序方案，并记录退回。
- 当未知节点可经收集满足要求时，强制器记录未知提供者，并保持扫描资格原值。
- 当输出符号或结构无法证明安全时，强制器必须返回明确规划错误。

扫描资格的具体递归保留在生成器。强制器返回后，生成器只在基线已有的无排序、已覆盖路径调用资格标记。任意分布的多分支保持原样分支由合成测试覆盖，A 的生产合并调用仍要求单分支。

数据来源：基线兼容入口为分布包的 `TableDistributedPlanGenerator.enforce()` 和 `mergeChildrenViaCollectOrMergeSort()`。保守分区测试为 `PropertyDrivenDistributionTest.partitionedRequirementConservativelyCollectsUntilHashExchangeExists()`，保留收集节点与文本诊断断言。

### Top-K、联合与分组的专用形状

## 决策、片段与执行侧

### 决策的冻结与输出

决策只保存规划期值快照，计划器在解释输出和测试读取它。A 的决策存于协调端内存，片段序列化保持既有字段。

记录必须包含消费节点或规则来源、全部输入 ID、全部输出 ID、要求属性、输入提供属性、输出提供属性、实际节点种类、结果状态和可空退回原因。聚合准入决策另外保存内部拒绝原因，并按显式映射填充通用退回字段。专用哈希事件额外保存源、桶和交换 ID，使用同一规划实例的 ID。

例如，一次两输入收集必须记录两个输入 ID 和一个输出 ID。决策冻结后修改原列表，已保存的三个 ID 必须保持原值。

数据来源：两种可空原因字段分别为 `fallbackReason: FallbackReason` 和 `groupByRejectionReason: GroupByHashRepartitionAdmission.RejectionReason`。聚合诊断优先渲染准入原因域，其他退回渲染通用原因域。

生成器收集记录，计划器在分布计划构建后复制成不可变列表。文本解释渲染已冻结记录，并保留现有测试依赖的 required、provided 和节点名内容。JSON 解释输出保持既有计划格式，A 的测试通过内存访问器读取结构化决策。

数据来源：新增分布包文件 `PropertyEnforcementDecision.java`。生成器修改点为 `recordRuleHit()`、`recordHashRepartition()`、连接退回记录方法及 `getRuleTrace()`。计划器修改点为 `generateDistributedPlanWithOptimize()`、`appendRuleTrace()`，新增只读决策访问器。

### 片段所有权

片段交换规则继续处理切分结构，所有权检查继续在根实例汇设置之后执行。A 只补充边界测试与诊断接入。

当两个来源向两个桶发送数据时，同一来源只能属于一个源片段，每桶的两条交换输入必须属于同一个最终片段。不同桶必须由不同最终片段拥有。缺一条边、重复来源或桶归属冲突都必须使校验失败。

数据来源：分布包的 `AddExchangeNodes.java:199` 保留哈希交换特殊边，`TableDistributedPlanner.setSinkForRootInstance()` 之后调用 `validateGroupedHashExchangeOwnership()`，位置为 `:311`。现有测试为 `GroupedHashExchangeOwnershipGateTest.java`。

### 执行侧核查与类型来源

执行侧工作以核查为主，沿用已经消费描述子的通用汇访问方法。A 必须检查节点类型、单一输入、通道路由能力、桶数与通道数，以及键在输入中的列位置。

规划守卫通过符号分配器的类型提供者读取键类型。执行侧通过片段上下文的类型提供者读取键类型。这是同一已解析 SQL 类型在两个阶段的读取，A 保留两个读取入口，并用一致性测试核对相同符号的类型。

例如，描述子有两个桶而汇句柄只有一个通道，执行构建必须拒绝。正常用例中的一个 INT64 键在规划端与执行端都必须解析为 INT64，测试才可报告类型契约成立。

若核查发现类型传播缺陷，实现者必须单列问题与修复范围，再交 sxing 审核。A 的既定实现保持执行器与调度器结构。

类型传播已有明确路径：计划器先把符号分配器的类型复制到查询上下文，再由片段提取器生成片段类型。A 的核查必须沿这条路径比对，发现差异时报告具体传播位置。

数据来源：执行侧准确方法为 `DataNodeTableOperatorGenerator.visitShuffleSink(ShuffleSinkNode, LocalExecutionPlanContext)`，位于 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/DataNodeTableOperatorGenerator.java:400`。键类型读取位于 `:454`，规划读取位于生成器 `:818` 与守卫 `getFallbackReason(node, typeProvider)`。类型复制位于分布包的 `TableDistributedPlanner.java:193`，片段提取位于 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/planner/plan/PlanFragment.java:103` 的 `generateTableModelTypeProvider()`。序列化回归测试为 `PropertyDrivenDistributionTest.parallelScanPermissionSurvivesFragmentSerialization()`、`org.apache.iotdb.db.queryengine.plan.relational.planner.TableHashPartitioningShuffleSinkNodeSerdeTest`。

## 属性合同与验收边界

### 合同字段与断言极性

基线合同是字段完整性、测试方法存在及断言标记子串的检查索引。它会放过真假断言使用相同表达式的情况，A 必须先修合同与校验器，再把它计作验收证据。

投影条目必须采用基线的允许资格，退回说明置空。分组条目也必须写明递归过滤和投影来源已支持，实际准入条件见聚合准入结果。全部合同链接必须按真实方法声明核对，避免把相近的方法名当成同一个用例。

合同沿用已有要求、提供、执行节点和测试链接四个字段。新增退回原因码与执行标记两个字段。合同原因使用带原因域的稳定码，或以空值表示没有退回。聚合内部拒绝原因也必须完整保存。原因码允许为空，执行标记必须区别扫描资格、计划节点与运行时取证。收集、合并排序、输出增加三条合同，合计 13 条，校验器的预期集合同步更新。

测试链接使用显式真假标记。校验器把规范化后的断言与合同期望比对，直接断言支持带消息与不带消息两种形式。帮助方法必须登记并解析到自己的断言，其他形式必须返回未支持错误。

例如，合同声明允许扫描而测试只有 assertFalse，校验必须失败。把投影条目的取值单独改为禁止，也必须失败。静态检查通过仍只证明合同链接一致，运行 JUnit 才能证明计划行为。

数据来源：合同为 `research/query-intra-parallelism-e2e-acceptance/manifests/property-enforcement-matrix.json`，校验器为同目录上一级 `scripts/verify_property_enforcement_matrix.py`。沿用字段为 `required`、`provided`、`enforcer`、`plan_test`，新增字段为 `fallback_reason`、`execution_marker`。原因字段取值为 `null`、`FALLBACK:<name>` 或 `GROUP_BY_ADMISSION:<name>`，按决策实际原因域匹配。断言标记提议格式为 `true:scans.get(0).isAllowParallelScan()`、`false:scan.isAllowParallelScan()`，帮助方法标记为 `helper:false:assertAllScansForbidParallelism`，三者必须与对应方法体核对。

### A 的完成范围

A 完成的证据是覆盖清单、决策记录、同配置前后快照、合同一致性和验证报告。它向 B 提供统一的规划判断入口，B 的执行构建与资源准入继续由 B 实现。

全部既有合并调用点必须有明确的输入属性与结果记录，专用保留路径必须有提供属性或专用决策。未知节点负例必须保留全部输入并给出未知原因。任何单节点返回都必须能证明输出确实只有一个。

覆盖报告按消费方法和调用分支标识源码位置，汇总整个测试集。每个触发位置必须关联测试、配置和对应决策。一次查询只记录实际经过的位置，实际执行次数另列统计。

例如，调用清单有 21 个表达式而覆盖报告只列 20 个，即使所有已列测试通过，A 仍未完成。一条查询只经过两个合并位置时，可以只有两条普通合并决策。若 128 份基本快照中有一份同配置计划变化，实现者必须先解释并修复或另行提交范围审批。
