# 属性驱动并行判定框架测试核查

目的：说明 A 阶段的功能由哪些断言验证，并列出完成验收还需要的证据，供 sxing 审核代码正确性。

摘要：属性整理涉及输入保留、排序要求、片段归属和类型传播。只检查编译或查询结果，无法分别证明这些条件。本文对应源码职责核对单元测试、故障副本、规划覆盖和真实查询。各类证据按自己的适用范围解释。

结论：A 已具备组件单元测试、规划负例、配置恢复检查和真实双节点结果证据。独立启动、完整模块测试和真实双节点查询均通过，A 的全部验收条件已经满足。

## 验证目标与范围

这项工作检查查询在补充收集或排序节点后，是否保留全部输入并满足父节点的要求。测试必须同时检查成功路径和会破坏结果的输入。例如，两个无序来源需要整体有序输出时，计划必须保留两个来源，并分别排序后再合并。

A 只整理已有属性判断、节点插入和诊断。扫描驱动统一、运行指标快照、静态策略和动态控制分别留在 B 至 E。定向单元测试、完整模块测试和真实服务查询分别保存原始证据。

数据来源：代码位于 sc01 的 `/root/iotdb`，分支为 `feat/next-p0`，HEAD 为 `0ec0e02287565d9395ec676bd9fcfc6d1f644386`，本轮修改保留在工作区。测试归档根目录为 `/root/property-a-artifacts/A6-20261028T080437+0000/`，下文的相对证据路径均以此为起点。

## 属性推导与节点插入

提供者和强制器的测试直接检查分布、排序、输入 ID 和插入的节点形状。提供者把未知节点视为缺少证明，收集节点清除局部顺序，投影只保留仍出现在输出中的排序键。强制器分别覆盖无需处理、收集、排序、合并排序及保守退回。

下表用于查找组件测试的调用数，全部调用的失败数均为零。

| --- | ---: | ---: |
| DistributionPropertyTest | 13 | 0 |
| PlanPropertyProviderTest | 13 | 0 |
| PropertyEnforcerTest | 20 | 0 |
| PropertyEnforcementDecisionTest | 7 | 0 |
| PropertyEnforcementIntegrationTest | 7 | 0 |
| PropertyEnforcementTraceTest | 4 | 0 |

多输入测试检查每条输入都出现在结果中，也检查返回列表无法被调用者修改。缺失分区键、缺失排序键和输出符号不一致都有拒绝断言。例如，一个两输入的收集结果必须包含两个原输入，删除第二条分支会导致断言失败。

四个独立故障副本分别引入未知节点被误判为单分布、要求顺序被误当为实际顺序、遗漏第二输入和退回原因映射错误。对应测试均报告预期失败。这证明相关测试可以识别这些特定错误。

数据来源：测试源位于 `iotdb-core/datanode/src/test/java/org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/`。正向结果为 `attempt-06/junit/junit-results.json`。故障副本为 `/root/property-a-artifacts/A2-20261028T142500+0800/reverse-02/`，每个子目录保留 `negative-verdict.json` 与实际类来源。

例如，三个来源与两个桶需要六个不同交换 ID。规划测试逐个检查源、桶和矩阵，所有权测试还要求每一列交换输入属于同一个桶片段。

## 类型传播与执行契约

类型传播测试逐符号比较分配器、查询上下文、最终片段和实际发送序列化后的 SQL 类型。单来源与三来源分别覆盖属性开关的两个取值，每次检查两个最终桶，并要求类型载荷完全消费。比较直接读取表模型符号类型。

例如，同一键在规划端解析为 INT64，片段和解码后的提供者也必须返回 INT64。若任一处返回 INT32，断言必须失败并显示键名。只有对象相等而未比较符号类型，无法证明这一条件。

执行访问器的节点类型、单子节点、路由句柄、通道数和键列位置已逐项核查源码。下层测试覆盖哈希描述子往返、不完整通道集合拒绝、空块、空值、跨块等键和逐行保留。真实服务查询另外验证了有效两通道路由。

实际片段发送使用 DataOutputStream 路径，传播验证通过。两个 ByteBuffer 重载也复用该编码，仓库新增的十项合同测试分别检查完整类型和字节消费。

数据来源：类型测试为 `SingleSourceGroupByHashRepartitionPlanningTest` 的八个用例，独立核对为 `/root/property-a-artifacts/A5-20261028T072200+0000/types-test-01/type-propagation-verdict.json`。执行访问器为 `DataNodeTableOperatorGenerator.visitShuffleSink()`。相关测试为 `TableHashPartitioningShuffleSinkNodeSerdeTest`、`TsBlockHashPartitionerTest`、`HashPartitioningSinkOperatorTest`，限定修复证据为 A5 归档的 `proposal-01/proposal-verdict.json`。

## 文本解释与合同校验

决策冻结测试检查不可变列表、原计划 ID 改动和生成器继续追加事件时的重复渲染。文本断言区分已满足、收集、排序、合并排序和退回，同时检查准入原因及哈希矩阵。

合同覆盖 13 个节点家族。23 项校验器自测检查真假断言极性、消息参数、注释与字符串干扰、嵌套表达式、帮助方法和断言名称遮蔽。合同标记与 JUnit 测试各自必须通过。

例如，投影合同声明允许扫描并行时，将测试标记改成禁止，校验器必须拒绝。把同一断言写进注释也无法提供有效证据。

数据来源：文本测试为 `PropertyEnforcementTraceTest`。合同报告为 `verifier-03/report.json`，执行身份和退出记录位于同目录。脚本为 `research/query-intra-parallelism-e2e-acceptance/scripts/verify_property_enforcement_matrix.py`。

## 双 DataNode 查询

重新构建的发行包通过四组候选与对照查询。每个部署各含一个 ConfigNode 和两个 DataNode。普通重复键、空值键和倾斜输入分别检查实际来源、唯一片段、每条交换边和桶所有权，空输入按预期空结果验收。

普通输入有十二行并产生三个分组。空值输入有十六行并产生四个分组。倾斜输入有八十四行，其中一个键出现八十次，另一个键出现四次。候选、对照和确定性预期的完整多重集均一致。

结果通过 JDBC 保留 SQL 空值及列类型，按逐行 JSON 排序规范化，再计算 SHA-256。解释查询的 JDBC 句柄、分析查询的 JDBC 句柄和运行时查询 ID 分别归档。实际交换边的所有权只使用对应分析查询中的 ID。

例如，两个来源分别含同一键的两行与三行，最终必须只出现该键的一个分组，计数为五。每个来源的一条通道分别对应唯一桶，重复边和缺边都会导致校验失败。21 项解析器自测覆盖这些拒绝条件。每类运行状态最多采集三次独立分析查询，只接受全部片段完成的快照，并保留拒绝的快照。

数据来源：结果与预期为 `two-datanode-05/acceptance.json`、`expected-results.json` 及每个用例的规范化 JSONL。发行包与源码绑定为 `isolated-distribution-06/distribution-binding.json`，运行时类来源与动态库为 `two-datanode-05/runtime-after.json`，冻结类加载日志为同目录的 `frozen-loaded-runtime.json`。六个节点全部停止且端口释放的核查为同目录的 `stop-verification.json`。解析器自测为 `runtime-ownership-01/exit.json`，各分析观测的接受与拒绝记录为 `two-datanode-05/runtime-observations.json`。这批证据支持所列查询的正确性，性能测量另行验收。
