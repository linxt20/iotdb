## 实施背景与顺序

A 先统一规划判断，后续工作再统一执行构建、实时统计和调度。这样，每一块都能用自己的测试判断是否完成。

例如，两个无序输入先各自排序再合并，属于 A 的规划职责。生成几个扫描驱动属于 B 的执行构建职责。读取运行中队列和内存属于 C，静态分配策略属于 D，运行中调整属于 E。

总体规划的依赖顺序为 A、B、C、D、E。本轮只实施 A。文档二次审核通过只表示方案具备实施依据，A 的完成状态由全部步骤的证据确定。

A2 先确定原因类型，再实现四个新增文件，估计需要 2 至 3 个工作日。该步骤依赖 A0 的调用面和 A1 的值对象。

## A4 决策输出与片段边界

## A6 合同、回归与双节点验证

A6 先完成合同极性检查，再做 Java 回归和真实查询验证，估计需要 2 至 3 个工作日。

合同沿用四个已有字段，增加退回原因和执行标记。收集、合并排序、输出增加三个合同条目，脚本预期集合随之更新。合同族索引与提供者逐方法覆盖分开验收。

极性解析只支持明确登记的 JUnit 断言和帮助方法。实现者必须处理注释、字符串和嵌套括号，支持直接真假断言的消息参数。未识别的标记必须失败。脚本增加自检模式，故意翻转投影资格、替换真假断言、删除测试方法及把断言放入注释，都必须返回失败。

测试必须保存配置初值并在退出时恢复，禁止用固定关闭代替恢复。隔离范围包括三个开关，以及用例实际改动的桶数、DOP、DataNode ID 和其他配置。配置用例必须串行运行，每个计划使用独立查询上下文。
