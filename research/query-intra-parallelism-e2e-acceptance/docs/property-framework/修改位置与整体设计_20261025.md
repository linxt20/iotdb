# 修改位置与整体设计

目的：说明毕业设计在 sc01 上的实现边界、主要文件职责与验证入口，供 sxing 核查工程状态。

摘要：一条查询的并行执行需要先确定分组和顺序要求，再构建数据交换和扫描驱动。A 将已有属性判断提取为可测试组件，并保留专用哈希构建。本文按规划、交换、执行和调度区分已实现代码与后续任务。验证数量与原始证据由配套核查文档维护。

结论：A0 至 A4 已通过退出检查，属性组件、生成器接入及冻结解释已实现。A5 的限定序列化修复已完成，A6 的完整模块回归已通过。受限 GROUP BY 有重新构建发行包的双节点正确性证据，B 至 E 保留为后续工作。

未决问题：性能采用 3.33 倍还是 2.95 倍、哈希连接是否进入生产规划、CPN 是否进入论文正文，均等待 sxing 决定。A5 的两个序列化重载修复见[限定修复材料](A5_序列化重载缺陷与修复范围_20261028.md)。

## 查询正确性的要求

父算子需要整体有序输入时，每条无序分支必须先排序再合并。分组聚合按键交换数据时，相同键必须送到同一个最终桶。扫描拆成多个驱动后，输入必须恰好读取一次。

例如，两个来源各有键 a 的两行与三行，最终分组必须返回五。仅增加线程或看到两个来源，无法分别证明排序、路由和输入保留这三项条件。各层通过独立断言和真实查询共同验收。

数据来源：实现与测试均在 sc01 的 `/root/iotdb`，分支为 `feat/next-p0`，HEAD 为 `0ec0e02287565d9395ec676bd9fcfc6d1f644386`。工作区改动与实际加载身份保存在 `/root/property-a-artifacts/`，逐项完成状态见[框架实施记录](属性驱动并行判定框架实施记录_20261028.md)。

## 属性判断与计划构建

属性判断已拆分为独立的提供者和强制器。提供者根据实际物理输出计算分布与顺序，未知节点采用保守结果。强制器在需要时插入收集、排序或合并排序节点，保留全部输入分支。

逻辑分区属性比较键集合，物理哈希描述子保存有序键、桶数、版本和空值策略。通用的逻辑分区要求仍采用保守收集，受限分组哈希优化使用聚合专用准入和构建。投影、过滤与扫描资格的递归判断保留在生成器中。

例如，某父节点要求按 k 排序，子节点没有实际顺序证明时，提供者仍返回无序。父节点的要求本身无法成为子节点已排序的依据。

数据来源：生产目录为 `iotdb-core/datanode/src/main/java/org/apache/iotdb/db/queryengine/plan/relational/planner/distribute/`。值对象为 `PlanProperties.java` 与 `DistributionProperty.java`，独立组件为 `PlanPropertyProvider.java`、`PropertyEnforcer.java`、`PropertyEnforcementDecision.java` 和 `FallbackReason.java`，接入点为 `TableDistributedPlanGenerator.java`。完整接口与保留位置见[框架设计](属性驱动并行判定框架设计_20261027.md)。

## 决策记录与解释输出

生成器记录实际输入、输出、插入节点与退回原因。计划器复制并冻结这些值，文本解释从冻结记录渲染。专用哈希事件同时记录同次构建中的源、桶和交换矩阵。

例如，冻结后给原计划替换节点 ID，重复解释仍显示捕获时的 ID。解释查询与分析执行查询各有自己的 ID，运行时所有权必须使用对应执行查询的记录。

数据来源：主要文件为分布包的 `TableDistributedPlanner.java` 和 `PropertyEnforcementDecision.java`。测试入口为 `PropertyEnforcementTraceTest`，详细断言与证据见[测试核查的文本解释与合同校验](属性驱动并行判定框架测试核查_20261028.md#文本解释与合同校验)。

## 分组哈希交换与片段归属

受限分组哈希路径由专用开关控制，默认关闭。每个来源按哈希桶写入对应通道，每个桶拥有来自全部来源的交换输入。片段切分后，规划器检查源、桶及交换节点的所有权。

例如，两个来源与两个桶构成四条交换边。同一桶的两条交换输入必须属于同一个片段，不同桶分别拥有自己的片段。缺失归属或重复归属都会使所有权检查失败。

键编码由共享规范化逻辑提供。哈希连接仍保留既有安全规划路径，生产接入范围等待 sxing 决定。分组路径的实测覆盖普通重复键、空值键、倾斜和空输入，完整结果与确定性预期一致。

数据来源：主要文件为 `TableGroupByHashRepartitionTopology.java`、`TableHashPartitioningShuffleSinkNode.java`、`TsBlockHashPartitioner.java`、`HashPartitioningSinkOperator.java` 和 `DataNodeTableOperatorGenerator.java`。切分后的检查位于 `TableDistributedPlanner.validateGroupedHashExchangeOwnership()`。共享编码位于 calc-commons 的 `HashKeyCanonicalizer.java`，查询证据见[测试核查的双 DataNode 查询](属性驱动并行判定框架测试核查_20261028.md#双-datanode-查询)。

## 扫描执行与统计

已有执行器根据计划中的扫描资格及自身条件建立扫描驱动，并使用 morsel 表示可领取的数据工作单元。A 保留这一执行入口，扫描构建和资源准入的统一属于 B。已有单元测试继续检查时间分片、驱动构建和完成统计。

片段统计冻结前主动让驱动记录 morsel 完成信息，重复写入保持幂等。运行指标采集点可以作为 C 的核查基础，查询级快照、统一静态策略及动态并行控制分别由 C、D、E 后续设计和验收。

数据来源：相关测试为 `DeviceTableScanParallelPipelineTest`、`DeviceTimePartitionMorselTest` 和 `DriverMorselCompletionStatisticsTest`。后续任务边界见[总体实现规划的 A 至 E 路线](实现规划_20261025.md#81-ae-大块任务路线)，本轮只实施 A。
